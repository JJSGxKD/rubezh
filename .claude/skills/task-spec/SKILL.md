# Спецификация задачи

Задачу берёт исполнитель, который не видел наших обсуждений. Всё, что он должен
знать, — в файле задачи и в документах, на которые файл ссылается. Если
исполнителю придётся что-то решить самому, спецификация не готова.

Порядок работы с реестром — `tasks/README.md`, шаблон — `tasks/_template.md`.

## Шаг 1. Опрос до спецификации

Сначала — вопросы пользователю, а не текст. Решения по продукту, экономике,
тексту для игрока и визуалу принимает пользователь, а не модель.

- **Каждый вопрос — с вариантами** (инструмент вопросов с кнопками), первым идёт
  рекомендованный с пометкой «(Рекомендуется)». Вопросы собираются в один
  заход, а не по одному.
- **Не спрашивать** то, что отвечает код, документ или устоявшееся правило
  репозитория. Это проверяется самим.
- **Ответы записываются** в раздел «Решения» спецификации, с датой и ссылкой на
  решение, если оно меняет документ.
- **Если ответ меняет решение из плана** (Р…), сначала правится документ, потом
  пишется задача.

## Шаг 2. Разведка кода

Найти и прочитать всё, что задача меняет. Исполнитель должен получить пути и
строки, а не «где-то в модуле магазина».

- **Где лежит:** файлы, функции, строки — для раздела «Как сейчас».
- **Что сломается рядом:** тесты, которые придётся поправить; словари; тексты
  гайдбука; документы.
- **Провайдер Nest для других модулей** — сразу с `exports` в шагах. Особенно
  если его подключают через `@Optional()`: без экспорта он молча отключается
  везде, кроме своего модуля, и тесты этого не заметят (приёмка #249).
- **Общие файлы-реестры:** что задача в них допишет, по разделу «Общие файлы»
  из `tasks/README.md`.

## Шаг 3. Нарезка

- **Размер — S или M.** Больше — значит, задачу надо дробить.
- **Рефакторинг — отдельной задачей** от изменения поведения.
- **Зоны.** Задачи, которые можно делать одновременно, не пересекаются по
  `zones`. Если пересекаются — между ними `depends_on`.
- **Зоны узкие.** Каталог `**` — только если задача правда меняет его целиком.
- **`runner` честный:** если без живой базы или устройства не проверить —
  `local`; если нужен человек — `human`.
- **`executor` и `effort`** — по таблицам раздела «Исполнители и effort» в
  `tasks/README.md`. Деньги, конкурентность и миграции — `extra`, а не «на
  всякий случай» выше.
- **Haiku там, где хватит Haiku.** Задача, расписанная до строки и с малой
  ценой ошибки (тексты, словари, данные контента, документы, тесты по
  списку, экран по макету в одном файле), — `haiku-5.5`: так потоки Sonnet
  остаются для тонкого. Деньги, миграции, конкурентность, доступ и
  антифрод, детерминизм движка — только `sonnet-5.5`. У заведённых раньше
  задач `executor` не меняется.

## Шаг 4. Текст спецификации

По шаблону, все разделы. Особое внимание:

- **«Шаги по порядку»** — конкретно: файл, что поменять, сигнатуры, типы,
  тексты для игрока дословно.
- **«Чего не трогаем»** — то, что легко задеть «заодно».
- **«Тесты»** — конкретные кейсы с ожиданием. Их исполнитель пишет первым
  коммитом. Для экранов — снимки на 320, 390, 768 и 1440 px и все состояния.
- **«Критерии приёмки»** — проверяемые утверждения. Они же — чек-лист ревью.
- **Готовый раздел «PR»:**
  - заголовок по формату `CLAUDE.md`;
  - метка;
  - строки «Для игроков»;
  - сводка для команды.
- **Уязвимости и антифрод — нейтрально.** Репозиторий публичный: «лимит частоты
  на маршруты X», а не «как обойти проверку». Подробности держатся в локальном
  аудите `docs/audit/`.

## Шаг 5. Регистрация

1. Номер — следующий свободный `T-NNNN` в `origin/dev` **и** в открытых PR со
   спецификациями: два тимлида могут завести задачи параллельно. Файл —
   `tasks/T-NNNN-<slug>.md`, в `author` — твоё кодовое имя (`claude-lead-1`,
   `claude-lead2-2`), в `batch` — номер пачки очереди, с которой задача уйдёт
   в `main` (`docs/38-release-plan.md`, раздел 5; зависимость не может быть в
   более поздней пачке или без пачки — это проверит `pnpm task check`).
2. `status: ready`, только если спецификация полная. Иначе — `draft`.
3. Запустить `pnpm task fix`: он поставит строку значков и ячейку эпика; затем `pnpm task check`.
4. Спецификации вливаются в `dev` PR-ом тимлидов. Исполнитель берёт задачу
   только из `dev`.

## Тимлид второго уровня

Если ты `claude-lead2-N` (`tasks/README.md`, «Роли и кодовые имена»):

- задача — только по решению, которое **уже записано** в `docs/` или в
  задаче. Шаг 1 для тебя — найти это решение и сослаться на него. Решения
  нет — вопрос пользователю или основному тимлиду, а не своё решение;
- без прода, `main`, секретов и локального аудита (`docs/audit/` у тебя
  нет): задачи по безопасности и антифроду не пишешь;
- приёмка и мердж в `dev` — как у основного тимлида, но не своих PR.

## Ответы на вопросы исполнителя

Черновик PR с `## Вопросы` ждёт ответа тимлида:

1. Ответ — комментарием в PR, первой строкой кодовое имя
   (`**claude-lead-1:** …`), по каждому вопросу. Если ответ меняет
   спецификацию — сначала правка задачи в `dev`, в комментарии — ссылка на неё.
2. Поставить PR метку «доработка» (`gh pr edit <номер> --add-label доработка`):
   закончит его любой поток той же модели и уровня, не обязательно тот, что
   спрашивал (`tasks/README.md`, «Доработка»).

## Приёмка PR исполнителя

Чек-лист — `tasks/README.md`, «Приёмка». Сверх него:

- прочитать дифф целиком, а не только описание;
- сверить с «Шагами» и «Чего не трогаем»;
- убедиться, что тесты из спецификации проверяют то, что заявлено, а не
  подогнаны под код.

Нужны правки — ревью «Request changes» со списком и метка «доработка»: правит
поток исполнителя, а не тимлид. Подробный порядок ревью — скилл `review-pr`.

Вливать строго по одному, merge-коммитом. После мерджа отдать в чат сводку для
команды (`CLAUDE.md`, «Версии и заголовки PR»).
