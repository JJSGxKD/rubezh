# Ревью PR исполнителя

Чек-лист приёмки — `tasks/README.md`, «Приёмка (ревьюер и тимлиды)». Роли и
кодовые имена — там же, «Роли и кодовые имена». Здесь — порядок работы.

## Кто ты

Кодовое имя — из промта сессии: `claude-review-N`, `claude-lead-N` или
`claude-lead2-N`. Нет его — спроси человека. Свой PR не ревьюишь: проверяет
не та сессия, что писала. Единственное исключение — режим «Самопроверка» ниже.

## Самопроверка (поток, задача с `merge: self`)

Решение Р176, порядок — `tasks/README.md`, «Самостоятельный мердж». Если в
`origin/dev` у твоей задачи `merge: self`, свой PR ты проверяешь сам, этим же
скиллом, и вливаешь командой `pnpm task merge T-NNNN`. Проверяй как чужой:
по шагам «Порядок одного PR» ниже и чек-листу «Приёмки» построчно, дифф —
`gh pr diff`, а не память о том, что писал. Всё, что не сходится, — не галочка,
а правка в PR.

Итог — комментарий в PR, формат которого читает команда мерджа:

```
**claude-3:** самопроверка по review-pr
head: <полный SHA головы PR, 40 знаков>

- [x] <пункт «Приёмки»>
- [x] …
```

Подпись — аккаунт из `owner` файла задачи (`claude-3` у потока
`claude-3 / sonnet-5.5 / medium`), все пункты «Приёмки» отмечены, ни одной
`- [ ]`. Комментарий пишет автор PR и после последнего коммита (отредактированный
старый не годится). В проверку входит и белый список путей: каждый файл диффа
(`gh pr diff --name-only`) — в `SELF_MERGE_ALLOWED` и не в `SELF_MERGE_FORBIDDEN`
(`tasks/README.md`), иначе это не `self`-задача, а вопрос тимлиду. Новый коммит в PR делает `head:` старым: самопроверка пишется заново.
Ревью «Approve» поток себе не ставит, метку «доработка» не снимает и не ставит:
итог — только этот комментарий и мердж. Нужен владелец или ответ тимлида —
это не самомердж, а метка «ждёт владельца» или черновик с `## Вопросы`.

## Что брать

```bash
pnpm task board
```

Колонка «На ревью» — PR с меткой «на ревью» (и «ждёт владельца»), в том числе
черновики с вопросами, сначала старший приоритет. PR с метками «в работе» и
«доработка» не трогай: они ждут исполнителя.

## Порядок одного PR

1. **CI.** `gh pr checks <номер>`. Красный — дальше не смотреть: «Request
   changes» с названием упавшего шага и перевод в «доработка». Красные
   `diff-check` или `claim-check` — возврат без обсуждения.
2. **Спецификация.** Первая строка PR — путь к задаче; прочитай её в `dev`
   целиком: «Шаги», «Чего не трогаем», «Тесты», «Критерии приёмки», «PR».
3. **Дифф целиком**, а не описание: `gh pr diff <номер>`.
   - тесты из спецификации есть и проверяют заявленное, а не подогнаны под код;
   - каждый шаг сделан, «Чего не трогаем» не тронуто;
   - ничего лишнего: попутных рефакторингов, переименований, «улучшений»;
   - решения исполнителя по Р176 (`tasks/README.md`, «Что исполнитель решает
     сам») — не замечание, если записаны в «Отступлениях» и не вышли за рамки:
     вынужденная правка вне зон — одна-две строки и путь в `shared`; продукт,
     числа, новые события, настройки, зависимости и миграции — замечание;
   - правила `CLAUDE.md`: `any`, `@ts-ignore`, `process.env` вне конфигурации,
     `catch {}`, история в комментариях, слои;
   - документы из раздела «Документы» обновлены, схемы не отстали.
4. **Интерфейс** — если PR меняет экраны: снимки на шести размерах и блок
   «Интерфейс» из «Приёмки» в `tasks/README.md` — ширины и ландшафт, тексты
   и числа, состояния и контраст, подача. Недостающее додумываешь сам, а не
   пропускаешь. Владельцу — страница-галерея со снимками, ссылкой в чат.
5. **Описание PR.** Заголовок и метка — из спецификации, чек-лист критериев
   отмечен, сводка для команды — с номером PR, строка `Поток: …`.

## Исход

- **Принято.** Ревью «Approve», первой строкой кодовое имя, ниже — чек-лист
  приёмки с отметками:

  ```bash
  gh pr review <номер> --approve --body-file review.md
  ```

  Ревьюер на этом заканчивает: вливает тимлид или тимлид второго уровня.
- **Мелочь в интерфейсе — правит тимлид.** Дефект в зонах задачи примерно
  до 20 строк (обрезанный текст, перенос, отступ, подпись) тимлид исправляет
  сам коммитом в ветку PR и вливает. Ревьюер такой дефект описывает в
  «Approve» строкой «поправит тимлид». Крупнее — «Request changes» ниже.
- **Нужен владелец.** Нужно решение или действие владельца — метка «ждёт
  владельца» вместо «на ревью» (`gh pr edit <номер> --remove-label "на ревью"
  --add-label "ждёт владельца"`); после ответа переведи PR в «на ревью» или
  «доработка».
- **Нужны правки.** Ревью «Request changes»: каждое замечание — файл и
  строка, что не так и со ссылкой на шаг спецификации или правило. Затем
  статус — «доработка» вместо «на ревью» (старый статус не оставляй: иначе у
  PR две метки и `pr-check` красный); PR закончит любой поток той же модели и
  уровня:

  ```bash
  gh pr review <номер> --request-changes --body-file review.md
  gh pr edit <номер> --add-label доработка --remove-label "на ревью"
  ```

  Бот на «Request changes» делает это сам (`pr-status-label.yml`), но проверь:
  страховка не заменяет правило (`tasks/README.md`, «Метки статуса»).

- **Спецификация неверна или неполна** — это не вина исполнителя: ревью
  «Comment» с разбором и вопрос тимлиду, метку не ставь, пока задача не
  исправлена в `dev`.

## Мердж (только тимлиды и потоки по `merge: self`)

Тимлид или тимлид второго уровня вливает одобренный PR. Поток — только свою
задачу с `merge: self` в `origin/dev` и только командой `pnpm task merge`
(режим «Самопроверка»); `gh pr merge` руками потоку нельзя. Тимлид каждый
заход выборочно читает влитое потоками (по комментарию самопроверки) и при
дефекте откатывает revert-PR или заводит задачу. Правила тимлида:

- строго по одному, merge-коммитом: `gh pr merge <номер> --merge`;
- не свой PR;
- отстал от `dev` или конфликт — не вливать: комментарий «влить dev» и метка
  «доработка» (вместо «на ревью»);
- после мерджа — сводка для команды в чат (`CLAUDE.md`, «Версии и заголовки
  PR»).
