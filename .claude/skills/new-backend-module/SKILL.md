# Новый модуль бэкенда

Один модуль = один домен. Раскладка фиксированная, зависимости строго вниз.

```
modules/<domain>/
  <domain>.controller.ts     HTTP: разбор запроса, вызов сервиса, форма ответа
  <domain>.service.ts        доменная логика, транзакции, инварианты
  <domain>.repository.ts     доступ к данным (Prisma), без логики
  dto/                       Zod-схемы + выведенные из них типы
  types/                     доменные типы и enum'ы
  <domain>.module.ts
```

Правила слоёв (`docs/15-engineering-standards.md` §2.3):

- **контроллер не содержит логики** — `if` по бизнес-условию означает, что
  код должен быть в сервисе;
- **сервис не знает об HTTP** — никаких `FastifyRequest` и `HttpException`,
  только доменные ошибки, которые фильтр переводит в коды;
- **Prisma — только в репозитории.** Это то, что позволит добавить кеш или
  read-реплику в одном месте, а не в тридцати;
- сервис длиннее 300 строк — декомпозировать; длиннее 500 — блокирующее
  замечание на ревью.

## Контракт API

- Путь версионированный: `/api/v1/<domain>`.
- Форма ответа единая: `{ data }` при успехе, `{ error: { code, message } }`
  при ошибке. `code` — стабильный машиночитаемый идентификатор, клиент
  ветвится по нему, а не по тексту.
- Изменения аддитивные. Удалить поле, переименовать, сузить тип, сделать
  необязательное обязательным — ломающее изменение, требует `v2`. Причина —
  ревью-лаг площадок: старые клиенты живут днями (`docs/09-ci-cd.md` §4).
- Тексты сообщений — на русском, локализуются; коды — на английском.

## DTO и валидация

Только **Zod**, не `class-validator`. Схема является источником типа
(`z.infer`), поэтому рассинхронизация типа и валидации невозможна.

Парсится **всё, что приходит с границы системы**: тело запроса, query,
заголовки, ответы внешних провайдеров, JSON из БД. Приведение через `as` —
это обещание, а не проверка.

Общие схемы, которые нужны и клиенту, и серверу, живут в `shared-types`.

## Обязательные свойства изменяющих эндпоинтов

- **Идемпотентность по явному ключу**: `runId` от клиента, id транзакции
  провайдера, id рекламной сессии. **Не** по хэшу тела — два честных забега с
  одинаковым счётом дадут одинаковый хэш.
- Ключ хранится в БД с уникальным индексом, а не только в Redis: Redis можно
  очистить, а двойное начисление — нет.
- Инвариант, затрагивающий несколько таблиц, — в одной транзакции. Внутри
  транзакции нет сетевых вызовов наружу.
- Счётчики и лимиты — атомарными операциями Redis, никогда
  read-modify-write из кода.
- Тяжёлое — в BullMQ, ответ игроку не ждёт БД. Синхронно только то, без чего
  нельзя ответить.

## Что добавляется вместе с модулем, а не «потом»

- **Метрики**: счётчик запросов, гистограмма длительности, счётчик ошибок по
  `code`. Для новой очереди — длина, время ожидания, число неудач.
- **Структурные логи** с полями `requestId`, `userId`, `platform`, `module`.
  В Telegram-алерты уходят только `warn` и `error`, с дедупликацией.
- **Таймауты** на все внешние вызовы.
- **Лимит частоты** на эндпоинт.
- **Тесты**: юнит на доменную логику, интеграционные на транзакции и
  атомарность (настоящие Postgres и Redis — сервисы CI и адрес в окружении, не моки), HTTP-тесты на коды и авторизацию —
  включая тест «эндпоинт без гварда и без `@Public()` падает»
  (`docs/17-testing-strategy.md` §4).

## Модель данных

- `Decimal` для всего, что имеет денежный или наградной смысл. Никогда
  `Float`.
- Составные индексы под реальные запросы, в порядке селективности.
- Миграция — по схеме expand → migrate → contract.
- **ER-диаграмма в `docs/21-diagrams.md` обновляется в том же PR**, что и
  схема. Диаграмма, отставшая от схемы, хуже отсутствующей.
