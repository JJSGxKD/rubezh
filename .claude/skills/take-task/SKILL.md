# Взять задачу и сделать её

Порядок работы целиком — `tasks/README.md`. **Прочитай его до начала работы**,
особенно разделы «Автопоток» и «Доработка». Здесь — короткий маршрут и то,
что исполнители нарушают чаще всего.

## Кто ты

Поток — `аккаунт / модель / уровень`, например `claude-3 / sonnet-5.5 / medium`.
Его называет промт сессии. Нет в промте — спроси человека, не угадывай: от
потока зависит, какие задачи тебе можно.

Сверь, что ты та модель, что в потоке. Не та — не начинай и скажи человеку.

## Цикл автопотока

Повторяй, пока есть задачи:

1. **Выбор.** `pnpm task next --executor <модель> --effort <уровень>`. Команда
   читает реестр из `origin/dev`, ветки `task/*` и PR и показывает:
   - сначала PR на доработке твоей модели и уровня;
   - затем свободные задачи, лучшая — первой.

   `runner: human` не показывается; `runner: local` — только если на машине
   можно запустить приложение: dev-сервер, браузер, Docker (`--runner local`, Р177).
   Живая база для этого не нужна: интеграционные тесты прогонит CI, миграцию
   собери без базы (`tasks/README.md`, «Общие файлы», строка миграций); `runner: owner` — только
   поток на машине владельца (`--runner owner`). Значок на доске
   может отставать на 5–10 минут — верь команде.
2. **Доработка — первой.** `pnpm task resume T-NNNN --owner "<поток>"`, дальше —
   раздел «Доработка» в `tasks/README.md`:
   - прочитать PR целиком: вопросы, ответы, ревью;
   - перечитать спецификацию в `dev`;
   - `dev` ушёл вперёд — `git merge origin/dev`, не rebase;
   - сделать ответ, гейт, комментарий «Доработано: …» с подписью потока,
     `gh pr ready`;
   - `resume` поставил «в работе» вместо «доработка»; закончив, **сними «в работе»
     и поставь «на ревью»** (`gh pr edit <номер> --remove-label "в работе"
     --add-label "на ревью"`) — без этого задача висит «в работе» и держит зоны.

   Отказ «уже продолжает другой поток» — бери следующую.
3. **Иначе — свободная задача.** `pnpm task claim T-NNNN --owner "<поток>"`:
   ветка `task/T-NNNN` от `origin/dev`, коммит со `status: in-progress` и
   `owner`, push без `--force`. Отказ push — «задачу уже взяли», бери следующую
   из списка. Нет команды — ручной захват из `tasks/README.md`, шаг 3.
4. **Работа** — маршрут ниже.
5. **PR открыт** (или черновик с вопросами запушен) — **сначала метка «на
   ревью»** (`gh pr create --label "на ревью"`, на уже открытом — `gh pr edit`),
   потом `git switch --detach origin/dev` и снова шаг 1. **Ответа не жди:** закончит PR тот поток, что
   первым возьмёт его на доработку.
6. **Задач нет** — отчёт человеку и стоп: открытые PR, PR с вопросами без
   ответа, почему остальное недоступно (зависимости, зоны, другая модель или
   уровень).

## Маршрут одной задачи

1. **Чтение.** Спецификация целиком, документы и код, на которые она ссылается.
   Скилл `pre-pr` пригодится в конце.
2. **Тесты до кода.** Первый коммит — кейсы из раздела «Тесты», они красные.
   Тест — договор: подгонять его под код нельзя.
3. **Код по «Шагам по порядку».** Коммиты дробные, формат — `CLAUDE.md`.
4. **Гейт.** `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm build`,
   `pnpm budget`, `pnpm docs:check`. Для экранов — снимки на 320, 390, 768 и
   1440 px и в ландшафте 667×375 и 640×360 против макета и блока
   «Интерфейс» из `tasks/README.md`, «Приёмка».
5. **Закрытие.** `status: done` в файле задачи — файл остаётся в `tasks/`, в
   архив его перенесёт уборка тимлида; `pnpm task fix` не нужен. Всё в этом же
   PR. PR в `dev`:
   - заголовок и метка — из спецификации;
   - описание — по скиллу `pre-pr`;
   - первая строка — `Задача: tasks/T-NNNN-<slug>.md`;
   - чек-лист критериев приёмки с отметками;
   - сводка для команды — блок из спецификации как есть. Номера PR до
     `gh pr create` нет, поэтому сразу после создания впиши его в заголовок
     сводки вместо `#<номер>` (`gh pr edit <номер> --body-file …`);
   - трейлеры коммита (`Co-Authored-By`, `Claude-Session`) — после пустой
     строки, иначе git склеит их с заголовком; `pr-check` это ловит;
   - предпоследняя и последняя строки перед подписью агента — `Поток: <поток>` и
     `Запустил: владелец` (или `Запустил: помощник <ник>`);
   - **метка статуса «на ревью»** — всегда, и на готовом PR, и на черновике с
     вопросами. Без неё поток блокируется: задача висит «в работе», а не «на
     ревью», и держит зоны. Ровно одна метка статуса, иначе `pr-check` красный
     (`tasks/README.md`, «Метки статуса»).

6. **Самомердж — только если в `origin/dev` у задачи `merge: self`** (пометка
   из `dev`, не из твоей ветки; `git show origin/dev:tasks/T-NNNN-<slug>.md`;
   поля нет — это `lead`, PR вливает тимлид, и ты просто берёшь следующую
   задачу). Порядок (`tasks/README.md`, «Самостоятельный мердж», Р176):
   - дождись зелёных `check` и `gate` (красный `board` не помеха);
   - проверь свой PR по скиллу `review-pr` как чужой, по чек-листу «Приёмки»;
   - напиши комментарий в PR: первая строка
     `**<аккаунт из owner, например claude-3>:** самопроверка по review-pr`,
     вторая — `head: <полный SHA головы PR>` (`git rev-parse HEAD`), дальше
     чек-лист «Приёмки», каждый пункт `- [x]`, ни одной `- [ ]`;
   - комментарий пиши тем же аккаунтом GitHub, что открыл PR, и после
     последнего коммита (`committedDate` головы): старый отредактированный не
     годится; ветка не должна отставать от `dev` — влей свежий и дождись CI;
   - `pnpm task merge T-NNNN` из рабочей копии, где `scripts/tasks` как в
     `origin/dev`. Команда сверяет и реальный дифф PR с белым списком путей, и
     предел правок вне зон (5 строк на файл, 20 всего). Отказ — список причин:
     исправь их, после нового коммита самопроверку напиши заново (старый
     `head:` не годится);
   - влито — отдай раздел «Сводка для команды», который напечатала команда, в
     чат; затем следующая задача.

## Чего не делать

- **Не додумывать.** Неясно, два прочтения, нужен файл вне зон сверх
  вынужденных следствий, спецификация спорит с кодом — черновик PR с разделом `## Вопросы`
  (`tasks/README.md`, «Если что-то неясно»). Перед вопросом перечитай
  спецификацию целиком и процитируй в вопросе строку с номером. Независимые
  шаги доделай, потом следующая задача.
- **Не ставить метку «доработка» самому.** Её ставят тимлиды и ревьюер, когда
  ответили. А вот «в работе» и «на ревью» — твои: отправил на проверку (в том
  числе черновик с вопросами) — «на ревью», продолжаешь писать код — «в работе».
- **Не выходить за зоны.** Можно трогать только `zones`, свои строки в `shared` и
  файл задачи. Попутный рефакторинг, переименование и «улучшение рядом» — причины
  вернуть PR.
- **Решай сам четыре вещи** (`tasks/README.md`, «Что исполнитель решает сам»,
  Р176): технические детали внутри зон; вынужденные следствия вне зон — одна-две
  строки, файл не держит задача «в работе», путь дописан в `shared`; текст игроку
  под правила текстов; следствия в эталонах и документах. Каждое — в
  «Отступления» PR с причиной. Продукт, числа, новые события, настройки,
  зависимости, миграции, деньги, права и антифрод — всегда вопрос.
- **Не вливать PR и не пушить в `dev` и `main`.** Вливают тимлиды. Единственное
  исключение — задача, у которой в `origin/dev` стоит `merge: self`: её влей по
  шагу «Самомердж» ниже. `gh pr merge` руками нельзя никогда.
- **Не трогать чужие ветки `task/*`** — кроме PR, взятого `pnpm task resume`.
  Не пушить с `--force` и не перебазировать ветку с чужими коммитами.
- **Не работать в общей рабочей копии с другим потоком.** У каждого потока —
  свой клон или worktree.
- **Опасного не делать.** Нельзя `prisma migrate reset`, `docker compose down -v`,
  копировать корневой `.env` с настоящими ключами, запускать бота с боевым
  токеном, менять настройки репозитория, секреты и переменные Actions.
- **Не менять пороги** `scripts/bundle-budget.mjs`: они стоят с запасом, и
  двигает их тимлид отдельным PR. Задача вышла за порог — это вопрос тимлиду
  с замером, а не правка числа.

## Если задачу пришлось бросить

`pnpm task release T-NNNN --yes` (удаляет ветку на origin) и закрыть PR, если
он был, с причиной в комментарии. Задача снова свободна.
