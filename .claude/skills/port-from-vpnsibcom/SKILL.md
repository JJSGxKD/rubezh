# Перенос блока из vpnsibcom

Перенос в этом проекте — **адаптация с рефакторингом, а не копирование**.
Полная политика — `docs/13-reuse-from-vpnsibcom.md` §1, разбор конкретных
дефектов источника — там же §2. Этот скилл ведёт по процедуре и не даёт
пропустить шаги.

## Шаг 0. Определить вердикт блока

Открыть `docs/13-reuse-from-vpnsibcom.md`, найти раздел про нужный блок и
прочитать его вердикт. От вердикта зависит объём работы:

- **Опора** — решение по существу верное, берём как основу и переписываем под
  нашу модель;
- **Переработка** — задача поставлена верно, реализация слабая: пишем свою,
  источник читаем только ради краевых случаев;
- **Только идея** — берём подход, к коду не обращаемся;
- **Не берём** — остановиться и уточнить задачу у человека.

Вердикта «копируем как есть» не существует. Если блока нет в документе —
сначала добавить его туда с вердиктом и обоснованием, потом писать код.

## Шаг 1. Выписать краевые случаи

Прочитать оригинал целиком и выписать **список ситуаций, которые он
обрабатывает**. Это главная извлекаемая ценность: она добыта в продакшене и
стоит дороже самого кода.

Типичные примеры из источника: клиент отключился до ответа; повторный запрос;
повторное получение рекламной награды; вход с второго устройства; старый
аккаунт по чужой реферальной ссылке; истёкший токен; недоступный провайдер.

Список фиксируется — он станет тестами на шаге 4.

## Шаг 2. Спроектировать свою реализацию

Под нашу раскладку слоёв (`docs/15-engineering-standards.md` §2) и наш стек
(`docs/16-tech-stack-decisions.md`). Обязательные отличия от источника:

- **Zod** вместо `class-validator` для DTO и данных с границы системы;
- **композиция** вместо наследования от клиентов библиотек (`RedisService
  extends Redis` в источнике — так не делаем);
- **никаких `any` и `@ts-ignore`**;
- **идентичность** — `{ sub, platform, platformUserId, role, jti }`, а не
  `telegramId`: аккаунты не связываются между платформами;
- **`Decimal`** для всего, что имеет денежный или наградной смысл;
- **сервис до 300 строк** — god-сервисы источника декомпозируются;
- **никаких комментариев-чейнджлогов** (`// ИСПРАВЛЕНО:`, `// [БАГ #4]`).

Если реализация получилась проще исходной — это нормальный результат, а не
повод искать пропущенное: часть сложности источника наносная.

## Шаг 3. Прогнать чек-листы

Построчно, оба целиком:

- безопасность — `docs/15-engineering-standards.md` §7;
- устойчивость к нагрузке — `docs/15-engineering-standards.md` §8.

Отдельно свериться со списком дефектов источника
(`docs/13-reuse-from-vpnsibcom.md` §2) — воспроизводить их нельзя. Самые
частые ловушки при переносе:

| Ловушка в источнике | Как правильно |
|---|---|
| IP берётся из сырого `X-Forwarded-For` | Только `req.ip` при настроенном `trustProxy` |
| Счётчики и лимиты через read-modify-write | Атомарная операция Redis или Lua |
| Секрет с дефолтным значением (`\|\| 'default-secret'`) | Валидация конфигурации при старте, дефолтов у секретов нет |
| Идемпотентность по хэшу тела запроса | Явный клиентский ключ (`runId`, id транзакции) |
| Блэклист по полному JWT в ключе Redis | По `jti` |
| `initData` без явного окна свежести | Явный короткий `expiresIn` |
| Логирование каждого события в Telegram | Только `warn`/`error`, с дедупликацией |
| Ошибка хранилища схлопнута в `null` | Различать «нет данных» и «хранилище недоступно» |

## Шаг 4. Написать тесты

На каждый краевой случай из шага 1, до мержа. Перенос без тестов не считается
переносом. Что именно и чем — `docs/17-testing-strategy.md`; для логики с
транзакциями и атомарностью — интеграционные тесты на настоящих Postgres и
Redis — сервисы CI и адрес в окружении (`docs/17-testing-strategy.md` §4.2), не на моках.

## Шаг 5. Оформить PR

В описании — раздел **«Перенос»**:

- что взято за основу и из какого файла источника;
- что переделано и **почему** (со ссылкой на пункт §2, если закрывался
  конкретный дефект);
- какие краевые случаи покрыты тестами;
- отметки по чек-листам §7 и §8.

## Напоминание про приватность

Антифрод-детали — окно привязки реферала, правила верификации рекламной
сессии, пороги проверки забегов — не должны оказаться в публичном
репозитории: опубликованные, они теряют смысл. Если переносимый блок содержит
такую логику, а `backend/api` ещё публичный — остановиться и поднять вопрос
выноса в приватный репозиторий (`docs/12-ip-and-licensing.md` §4).
