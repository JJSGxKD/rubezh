# Аналитика: события, витрины, дашборды

## 0. Требование

**Аналитика — не отдельная фича «на потом», а сквозное требование ко всем
модулям.** Любой модуль, который что-то делает с игроком, деньгами или
трафиком, обязан порождать события. Всё это должно удобно читаться **в
своей админ-панели в режиме, близком к реальному времени**: платежи,
регистрации, посещаемость, забеги, реклама, реферальная и партнёрская
программы (`29-admin-panel.md` §5).

**Grafana — только техническая аналитика**: задержки, ошибки, очереди,
состояние БД и хоста, алерты. Решение пересмотрено на этапе 2: продуктовые
дашборды для геймдизайнера, маркетинга и партнёров переехали в админ-панель
— там права по ролям, семантический слой метрик и учёт денег рядом
(`29-admin-panel.md` §1). До появления панели, на закрытом тесте этапа 2, —
выгрузка данных и разбор ИИ-агентом (`26-stage2-plan.md`, WP8).

Практическое следствие для разработки: раздел «Аналитика» появляется в
описании каждой задачи, а не в отдельной задаче «прикрутить аналитику»
через полгода. Данные, не записанные сегодня, задним числом не
восстанавливаются — это уже отмечено про сессии в
`13-reuse-from-vpnsibcom.md` §6 и верно для всего остального.

Смежное: `14-scalability.md` §6 (технические метрики),
`23-referral-and-partner-program.md` (что именно считаем по программам),
`24-attribution-and-sharing.md` (откуда берутся данные атрибуции),
`19-content-admin.md` §9 (дашборд баланса рядом с редактором).

## 1. Два источника данных, и их нельзя путать

| Источник | Что в нём | Чем хорош | Чем опасен |
|---|---|---|---|
| **Prometheus** | Технические и агрегатные счётчики: RPS, задержки, ошибки, длина очередей, живые счётчики регистраций и платежей | Секундная свежесть, дешёвые графики | **Кардинальность.** Метка с `user_id`, `run_id` или `partner_id` порождает миллионы временных рядов и кладёт Prometheus |
| **PostgreSQL** | Факты: события, забеги, платежи, клики, атрибуция | Любые разрезы, когорты, соединения | Тяжёлые запросы; нельзя пускать на горячие таблицы |

Правило, нарушение которого стоит дороже всего:

- **В Prometheus — только низкая кардинальность.** Метки: платформа,
  страна, тип события, код ошибки, сеть рекламы. Никаких идентификаторов
  пользователей, забегов, партнёров.
- **Аналитика админ-панели ходит в Postgres только через read-реплику и/или
  витрины**, но не в горячие таблицы напрямую. Иначе открытый на стене дашборд с
  автообновлением раз в 10 секунд становится постоянной паразитной
  нагрузкой ровно на ту БД, которая принимает забеги
  (`14-scalability.md` §4.1).

## 2. Как достигается «лайв»

Честное разделение по свежести, чтобы «в реальном времени» не превратилось
в обещание, которое архитектура не выдержит.

| Слой | Задержка | Механизм | Что показывает |
|---|---|---|---|
| Живые счётчики | 5-15 секунд | Инкремент в Redis при событии → чтение админ-панелью через API; технические — экспорт в Prometheus | Онлайн, регистрации/мин, платежи/мин, ошибки, показы рекламы |
| Оперативные витрины | ~1 минута | Материализация rollup-таблиц по расписанию | Воронки за сегодня, разрезы по источникам, партнёрам, платформам |
| Глубокая аналитика | 5-60 минут | Агрегаты по часам и суткам | Retention, LTV, когорты, кривые удержания |
| Разбор инцидента | по запросу | Сырые события на реплике | «Что именно случилось с этим игроком» |

Панель на дашборде обязана подписывать свою свежесть. Цифра без указания,
за какой период и с какой задержкой она посчитана, порождает неверные
решения быстрее, чем отсутствие цифры.

## 3. Событийная модель

### 3.1 Общий конверт

Каждое событие — строка в append-only таблице. Единый конверт, разный
`payload`:

| Поле | Назначение |
|---|---|
| `event_id` | uuid, генерируется источником — ключ идемпотентности |
| `event_type` | из словаря §3.3, только оттуда |
| `schema_version` | версия структуры `payload` |
| `occurred_at` | когда произошло у клиента |
| `received_at` | когда получено сервером (расхождение — сигнал проблем со связью или подкрутки часов) |
| `user_id` | nullable: у клика по ссылке пользователя ещё нет |
| `install_id` | uuid установки на устройстве. Появился на этапе 2, когда авторизации ещё нет: без него события закрытого теста нельзя разложить по устройствам |
| `platform_user_id` | nullable: ID на площадке, **только при проверенной подписи** `initData`. На этапе 3 по нему история до авторизации привязывается к аккаунту (`28-diagnostics.md` §5.2) |
| `session_id` | связь событий одного захода |
| `platform` | telegram / max / vk / web |
| `app_version` | из-за модерации площадок одновременно живут несколько версий |
| `attribution` | **снимок** источника на момент события: source, campaign, ref_id, partner_id, click_id |
| `payload` | JSONB, разбирается Zod-схемой по `event_type` |

Два решения, которые стоит объяснить:

- **Атрибуция денормализована в событие.** Не ссылка на текущее состояние
  пользователя, а снимок. Иначе последующая перепривязка или ручное
  исправление меняют историю, и отчёт за прошлый месяц перестаёт
  воспроизводиться.
- **`occurred_at` и `received_at` раздельны.** Клиент может отправить
  событие с задержкой (не было сети) или с искажённым временем. Считать
  по `received_at`, а расхождение использовать как антифрод-сигнал.

### 3.2 Как события попадают в БД

```
Модуль → эмиттер события → BullMQ → воркер → батч-INSERT в Postgres
                         ↘ инкремент счётчика в Redis (для живых панелей)
```

- **Запись события никогда не блокирует ответ игроку.** Тяжёлое — в
  очередь (`15-engineering-standards.md` §4).
- **Батч-вставка**, а не по одной строке: на порядок меньше транзакций
  (`14-scalability.md` §4.1).
- **Идемпотентность по `event_id`** — уникальный индекс. Ретрай очереди не
  должен удваивать регистрацию.
- Потеря события допустима как деградация, **удвоение — нет**: на удвоенных
  платежах и регистрациях строятся денежные решения.

**Как это устроено на этапе 2** (`backend/api/src/modules/events`, схема
потока — `21-diagrams.md` §4.13). Клиент шлёт пачку до 100 событий на
`POST /api/v1/events`, ответ `202` со счётчиками принятых и отброшенных:
битое событие не выбрасывает пачку. Каждое событие проверяется по словарю —
имя, версия, схема `payload`; незнакомые поля нового клиента пропускаются.
Telegram ID берётся только из проверенной подписи `initData` в заголовке, а не
из тела. Пачка уходит в очередь BullMQ, воркер пишет её одной вставкой; Redis
недоступен — пачка пишется в базу напрямую, недоступно и то и другое — `503`,
и клиент оставляет её у себя. Живых счётчиков в Redis на этапе 2 нет — они
приходят с панелями этапа 4 (§8).

На клиенте события копит эмиттер (`app-shell/src/state/telemetry.ts`): пачка
уходит раз в 15 секунд или по 25 событиям, при сворачивании — запросом с
`keepalive` до 60 КБ, при появлении сети — сразу. Неотправленное лежит в
хранилище устройства (до 500 событий, старые вытесняются) и уходит со
следующим запуском с теми же `eventId`. Эмиттер — отдельный чанк после
главной; события до него, вроде `load_time` и `app_first_open`, ждут в
буфере со временем, когда они случились. `client_error` ловит необработанные
исключения и отклонённые промисы, ошибки экранов и движка; одна ошибка — не
чаще раза в минуту и не больше 30 за запуск.

### 3.3 Словарь событий

Единый словарь — обязателен. Без него через три месяца в базе живут
`run_end`, `runFinished` и `end_run`, и ни один отчёт не сходится.

**Правило:** новое событие добавляется сначала сюда и в Zod-схему, потом в
код. Переименование существующего — смена `schema_version`, а не правка на
месте.

Zod-схемы `payload` — в словаре сервера
`backend/api/src/modules/events/event-dictionary.ts`, список имён клиента — в
`app-shell/src/state/analytics.ts`. Не в `shared-types`: собранный бэкенд не
может импортировать TypeScript-исходники пакетов монорепо. Что все три места —
сервер, клиент и эта таблица — говорят об одних событиях, проверяет
`scripts/test/event-dictionary.test.ts`.

| Группа | События |
|---|---|
| Привлечение | `link_clicked`, `redirect_served`, `hub_platform_chosen`, `app_first_open` |
| Аккаунт | `user_registered`, `user_authenticated`, `session_started`, `promo_code_applied` |
| Забеги | `run_started`, `run_resumed`, `run_finished`, `run_abandoned`, `run_paused`, `upgrade_offered`, `upgrade_chosen`, `wave_reached`, `continue_used` |
| Интерфейс | `screen_viewed`, `settings_changed` |
| Монетизация | `purchase_initiated`, `purchase_completed`, `purchase_failed`, `purchase_refunded` |
| Реклама | `ad_requested`, `ad_shown`, `ad_reward_claimed`, `ad_failed` |
| Рефералы | `referral_link_created`, `referral_bound`, `referral_activated`, `referral_reward_granted` |
| Партнёры | `partner_click`, `partner_registration`, `partner_ftd`, `partner_revenue_accrued`, `partner_payout` |
| Шеринг | `share_offered`, `share_completed`, `shared_link_opened` |
| Прогрессия | `level_up`, `item_obtained`, `character_unlocked` |
| Удержание | `daily_reward_claimed`, `wheel_spun`, `task_completed`, `achievement_unlocked` — вместе с механиками этапа 4 (`05-game-design.md` §3, `07-monetization-and-ads.md` §7) |
| Техника | `client_error`, `fps_sample`, `load_time`, `diagnostics_mode_changed`, `bench_finished` |
| Плейтест | `playtest_run_synced` — временное, на время закрытого теста (`26-stage2-plan.md`, WP13) |

Добавлено на этапе 2 (`26-stage2-plan.md`):

| Событие | Зачем | Ключевые поля `payload` |
|---|---|---|
| `upgrade_offered` | Выбор улучшения при наборе уровня. Без предложений частота выбора не считается: «выбрали 5 раз» ничего не значит, пока неизвестно, сколько раз предлагали. Отдельного события набора уровня нет — оно следует из этого | `level`, `count` — сколько вариантов, `queued` — сколько выборов ждут в очереди. Состав вариантов в плоский `payload` не помещается и придёт отдельной версией схемы |
| `upgrade_chosen` | Какой вариант выбран — пара к `upgrade_offered` | `option`, `level` |
| `run_paused` | Как часто забег прерывается — вход для решения о длине забега | `reason`: `manual` / `app_inactive`, `elapsedSec` |
| `run_resumed` | Сколько прерванных забегов игроки продолжают — окупилось ли сохранение и как часто приложение закрывают посреди забега | `seed`, `elapsedSec`, `level` |
| `screen_viewed` | Путь по интерфейсу; заходы в заглушки — замер интереса к будущим разделам | `screen`, `stub` |
| `settings_changed` | Какие настройки меняют — режим экрана, вибрацию, громкость | `setting`, `value`; у смены режима экрана клиентом Telegram — `source: platform` |
| `diagnostics_mode_changed` | Сколько тестеров включают диагностику | `setting`, `value` |
| `app_first_open` | Первый запуск на устройстве — знаменатель воронок закрытого теста | без полей: установка и так в конверте |
| `client_error` | Ошибки клиента на тестера по версии и устройству (`26-stage2-plan.md` §7) | `scope` — где случилась, `message` — текст без стека, до 512 знаков |
| `share_offered`, `share_completed` | Приглашение друга на плейтест: сколько нажимают и чем кончается — выбор чата, копия ссылки или неудача | `context` (`friends_invite`), у завершения — `result` |
| `bench_finished` | Сводка теста производительности — стресс-теста из «Играть» (`28-diagnostics.md` §2.3); полный отчёт уходит на сервер плейтеста, не в события | `mode`, `stopReason`, `peakObjects`, `verdict`, `reportId` |
| `playtest_run_synced` | Дошёл ли итог забега до лидерборда плейтеста: сколько забегов ждут сети, сколько сервер отверг. Растущая доля `queued` с `unauthorized` — устаревшая подпись запуска, а не сеть | `result`: `sent` / `queued` / `dropped`; `trigger`: `finish` / `launch` / `screen`; у неудачи — `failure`; у отправленного — `rank`, `isNewBest`, `recorded` (`false` — забег с читами сервер не записал) |

Уточнения существующих событий на этапе 2:

- `run_started` — стартовое оружие, карта, сложность, ориентация экрана и режим экрана
  (полноэкранный или обычный), `devMode` — забег разработчика (`26-stage2-plan.md`, WP14);
- `run_finished`, `run_abandoned` — `cheats`: в забеге включали читы режима
  разработчика. Такие забеги из воронок и распределений длины исключаются;
- `load_time` — `phase` и `ms`. Фазы: `shell_ready` — от старта оболочки до
  интерактивной главной, с признаком `fontsLoaded` (успели ли свои шрифты
  к главной); `run_first_frame` — от «В бой» до первого снимка HUD, то есть
  до первого кадра забега. При «Ещё раз» не пишется: сцена уже загружена, и
  такое время смешало бы распределение;
- `run_finished` — время выживания как главный показатель, уровень, урон по
  оружиям, оружие и пассивки с уровнями, причина смерти, сводка
  производительности (`28-diagnostics.md` §3.2), хэш контента. `fps_sample`
  при этом **не** шлётся поминутно: сводки на забег достаточно, а детальный
  таймлайн живёт в отчётах диагностики;
- `wave_reached` — «волна» означает **отрезок таймлайна спавна** (по
  умолчанию минута): волн с паузами в игре нет, спавн непрерывный
  (`26-stage2-plan.md`, WP4.4). Смысл уточнён, имя сохранено — событие ещё
  не записывалось, смены `schema_version` не требуется. Payload: `index` —
  номер отрезка с нуля в поле `wave`, `elapsedSec` — секунда забега, на которой он начался.
  Движок отдаёт это обратным вызовом, отправляет — оболочка.

`run_finished` и `run_abandoned` несут сложность (`difficulty`) — время на разных сложностях несравнимо, и распределение без этого разреза смешивает их, — и ещё два поля, без которых распределения
по волнам нечем разрезать: `mapId` (карта забега — на старте она одна, но
разрез нужен сразу) и `contentHash` — отпечаток игрового контента. Хэш
считается по всем таблицам контента разом и меняется от любой правки чисел:
без него эффект вчерашней правки скорости роя не отделить от сезонности.

## 4. Витрины

Сырые события неудобны для дашбордов и слишком дороги при частом опросе.
Поверх них — предпосчитанные таблицы, и именно их читает аналитика
админ-панели.

| Витрина | Гранулярность | Разрезы |
|---|---|---|
| `mart_dau` | сутки | платформа, страна, источник, партнёр |
| `mart_funnel_hourly` | час | клик → запуск → регистрация → первый забег → первая покупка |
| `mart_runs_daily` | сутки | распределение по волнам, счёту, длительности, персонажу |
| `mart_revenue_daily` | сутки | SKU, платформа, источник, партнёр, тип (IAP / реклама) |
| `mart_retention` | когорта × день | D1, D3, D7, D14, D30 |
| `mart_referral_daily` | сутки | приглашения, привязки, активации, награды, K-фактор |
| `mart_partner_daily` | сутки × партнёр | клики, регистрации, FTD, доход, начисления |
| `mart_ads_daily` | сутки | сеть, место показа, fill rate, подтверждённые награды |

Правила:

- Витрина **пересчитывается идемпотентно** за период — повторный запуск не
  удваивает.
- Пересчёт — крон под распределённым локом
  (`15-engineering-standards.md` §4.3).
- Пересчёт задним числом за N суток: события могут прийти с опозданием.
- Витрины **не источник истины**, а производная. При расхождении правы
  сырые события; должна быть процедура полного перестроения витрины.

## 5. Что считаем

Список задаёт объём событий, который нужно порождать. Метрика без события,
из которого она считается, — пожелание, а не метрика.

### 5.1 Привлечение и атрибуция

Клики по ссылкам, показы редирект-страницы, выборы платформы на хабе,
первые запуски, регистрации. Конверсии между шагами. Время от клика до
запуска. Разрезы: источник, кампания, UTM, реферер, партнёр, платформа,
страна, устройство, ОС, язык.

Отдельно: доля кликов без последующего запуска — базовый индикатор
накрутки (`24-attribution-and-sharing.md` §5).

### 5.2 Активация и удержание

Доля дошедших до первого забега; до N-й волны; время до первого забега.
DAU / WAU / MAU и sticky (DAU/MAU). Сессии в сутки, длительность,
забегов на сессию. Retention D1/D3/D7/D14/D30 по когортам регистрации, с
разбивкой по источнику и платформе. Reactivation — вернувшиеся после
паузы.

### 5.3 Забеги и баланс — данные для геймдизайнера

Это тот раздел, который напрямую питает работу с балансом
(`19-content-admin.md`):

- забегов в сутки, распределение по достигнутой волне, счёту, длительности;
- **на какой волне игроки умирают чаще всего** — где кривая сложности
  режет;
- доля дошедших до каждой волны — та же кривая с другой стороны;
- **какие апгрейды выбирают, а какие игнорируют** — прямой сигнал, что
  апгрейд слабый или непонятный;
- выбор персонажей и их винрейт;
- использование континью: сколько, на какой волне, за деньги или за
  рекламу;
- доля брошенных забегов и момент выхода.

Разрез по версии конфигурации обязателен — иначе после публикации нового
баланса нельзя отделить эффект правки от эффекта сезонности.

### 5.4 Монетизация

Платежи: количество, сумма, средний чек, ARPU, ARPPU, конверсия в
платящего, доля первых платежей (FTD) и повторных, время до первого
платежа. Распределение по SKU и платформе. Возвраты и их причины. LTV по
когортам и по источникам — именно это отвечает на вопрос, окупается ли
канал.

Разрез по платформе обязателен: экономика считается раздельно
(`03-notes-and-risks.md`), и складывать Stars с рублями в один график —
способ принять неверное решение.

### 5.5 Реклама

Запросы, показы, fill rate по сетям, доля подтверждённых наград,
подсчитанный eCPM, доход по сетям и местам показа, отказы и таймауты
сетей. Fallback-цепочка: как часто доходим до второй и третьей сети —
прямой сигнал качества основной.

### 5.6 Реферальная программа

Созданные ссылки, переходы, привязки, **активации** (реферал дошёл до
целевой волны), выданные награды. Конверсия на каждом шаге. Глубина: сколько
игроков привёл один игрок — распределение, не только среднее.

**K-фактор** (среднее число приведённых активных игроков на одного
игрока) — главная метрика виральности: при K ≥ 1 аудитория растёт сама.
Виральность в жанре не встроена по умолчанию (`03-notes-and-risks.md`),
поэтому её нужно измерять, а не предполагать.

### 5.7 Партнёрская программа

Клики, регистрации, FTD, доход приведённых игроков, начисления партнёру,
выплаты, задолженность. Конверсии клик→рег→FTD по каждому партнёру. ROI
партнёра: выплачено против дохода. Качество трафика: retention и LTV
приведённых игроков в сравнении с органикой — партнёр, дающий регистрации
без удержания, стоит дороже, чем кажется.

### 5.8 Шеринг

Сколько раз предложено и сколько принято (отдельно результат забега и
карточка профиля), по каналам и платформам. Переходы по расшаренным
ссылкам, конверсия в регистрацию. Какой вариант карточки и какой
маркетинговый текст конвертит лучше — под A/B
(`24-attribution-and-sharing.md` §7).

### 5.9 Техническое здоровье

Крэши по версии, платформе, устройству, ОС. Перцентили FPS по устройству —
главный технический риск проекта (`01-tech-stack.md` §8) измеряется
именно так. Время загрузки и размер бандла у реальных игроков. Ошибки API
по кодам. Задержки ответов. Длина очередей.

### 5.10 Антифрод

Отдельный набор, потому что смотрят на него иначе — ищут аномалии, а не
тренды: регистрации с одного IP и устройства, скорость регистраций по
источнику, доля рефералов, не дошедших до активации, совпадения отпечатков,
забеги с невозможными показателями, аномально быстрые FTD после клика,
клики без запусков.

## 6. Дашборды

Дашборды — по аудитории, а не по таблицам. Дашборд, который читают все и
никто, бесполезен.

**Продуктовые — в админ-панели** (`29-admin-panel.md` §5), с доступом по
ролям:

| Дашборд | Для кого | Ключевые панели |
|---|---|---|
| **Live** | все по правам | Онлайн, регистрации/мин, платежи/мин, забеги/мин |
| **Привлечение** | маркетинг | Воронка клик→рег→забег→покупка, по источникам и кампаниям, стоимость и качество трафика |
| **Рефералы и партнёры** | маркетинг, владелец | K-фактор, активации, топ партнёров, ROI, задолженность по выплатам |
| **Монетизация** | по правам на выручку | Выручка по платформам и SKU, ARPU, ARPPU, конверсия, LTV когорт |
| **Геймплей и баланс** | геймдизайнер | Кривая смертности по минутам, темп уровней, частота выбора улучшений, выживание по стартовому оружию, урон по оружиям, разрез по версии конфигурации |
| **Реклама** | напарник | Fill rate, eCPM, доход по сетям, глубина fallback-цепочки |
| **Антифрод** | владелец, модератор | Аномалии §5.10, всплески по источникам, очередь разбора |

**Технические — в Grafana:**

| Дашборд | Для кого | Ключевые панели |
|---|---|---|
| **Техническое здоровье** | участник 1 | Задержки, ошибки, крэши, очереди, Postgres, Redis, хост |
| **Приём данных** | участник 1 | Принятые и отброшенные события и отчёты, лимиты частоты, задержка записи |

Правила оформления — общие для обеих сред:

- у каждой панели подписаны период и задержка (§2);
- деньги — всегда с разбивкой по платформе, никогда одной суммой;
- сравнение с предыдущим периодом там, где абсолютное число ничего не
  говорит;
- алерты Grafana — в тот же Telegram-тред, что и ошибки приложения, с
  дедупликацией (`15-engineering-standards.md` §6.2);
- дашборды Grafana **экспортируются в репозиторий** как JSON, готовые
  дашборды админ-панели и определения метрик — код; и те и другие ревьюятся
  как код.

## 7. Приватность и хранение

- **Минимизация.** Собираем то, что нужно для конкретного решения. «Пусть
  полежит, вдруг пригодится» — не основание.
- IP и User-Agent — персональные данные. Хранить в сыром виде ограниченный
  срок (порядка 30-90 суток), дальше — усечённый IP и хэш. Юридическая
  сторона отмечена как требующая проверки юристом
  (`03-notes-and-risks.md`).
- В логи и в аналитические payload'ы **не попадают** токены, `initData`,
  тела платёжных вебхуков.
- **Партнёр не видит персональных данных приведённых игроков** — только
  агрегаты (`23-referral-and-partner-program.md` §4.4).
- Retention данных: сырые события партиционируются по месяцам и
  отцепляются в холодное хранилище (`14-scalability.md` §3, этап 4);
  агрегаты живут долго — они маленькие и не содержат персональных данных.
