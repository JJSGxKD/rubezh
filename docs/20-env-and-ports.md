# Окружения, переменные и порты

Справочник, к которому обращаются, когда нужно поднять проект, добавить
переменную или понять, кто занял порт. Шаблон со всеми переменными —
`.env.example` в корне; здесь — смысл, правила и различия между режимами.

Смежное: `09-ci-cd.md` §3 (секреты в CI) и §9 (окружения),
`15-engineering-standards.md` §9 (правила конфигурации),
`19-content-admin.md` (переменные админки).

---

## 1. Правила

1. **Один `.env` на весь монорепо, в корне.** Vite-приложения читают его
   через `envDir`, бэкенд — напрямую. Отдельные `.env` в пакетах не заводим:
   рассинхронизация между ними — источник багов, которые ищут часами.
2. **`.env` не коммитится.** В git только `.env.example` с пустыми
   значениями. Проверяется `gitleaks` в CI.
3. **Конфигурация валидируется при старте**, единой Zod-схемой. Невалидная
   конфигурация = процесс не поднимается. Это осознанное поведение: ошибка
   при старте дешевле неверного поведения в рантайме.
4. **У секретов не бывает значений по умолчанию.** Конструкция вида
   `process.env.SECRET || 'default'` запрещена — именно так в источнике
   переноса приложение могло стартовать с публично известным секретом
   (`13-reuse-from-vpnsibcom.md` §2.1 C).
5. **`process.env` в коде за пределами модуля конфигурации запрещён.**
   Доступ — через типизированный конфиг.
6. **Всё с префиксом `VITE_` попадает в клиентский бандл и является
   публичным** — независимо от названия. Секрет, оказавшийся там, считается
   скомпрометированным.
7. **У staging и production — отдельные наборы значений и отдельный бот.**
   Общий бот означает, что тестовая рассылка уходит реальным игрокам.

## 2. Карта портов

Порт **не выбирается на месте** — берётся отсюда. Все значения задаются
переменными, дефолты в коде совпадают с этой таблицей.

| Сервис | Переменная | dev | staging | production |
|---|---|---|---|---|
| Бэкенд API | `API_PORT` | `4000` | `127.0.0.1:4100` | **не публикуется**: Caddy в Docker обращается по имени сервиса через общую внешнюю сеть (`26-stage2-plan.md`, Р16) |
| Origin статики клиента | — | — | не публикуется | не публикуется, за Caddy и Bunny.net (`26-stage2-plan.md`, WP10) |
| Dev-сервер Telegram | `WEB_TELEGRAM_PORT` | `5173` | — | — |
| Dev-сервер MAX | `WEB_MAX_PORT` | `5174` | — | — |
| Dev-сервер VK | `WEB_VK_PORT` | `5175` | — | — |
| Админка геймдизайнера | `ADMIN_PORT` | `5176` | через Caddy | через Caddy, отдельный поддомен |
| Кабинет партнёра | `PARTNER_CABINET_PORT` | `5177` | через Caddy | через Caddy, отдельный поддомен |
| PostgreSQL | `POSTGRES_PORT` | `127.0.0.1:5432` | `127.0.0.1:5532` | **не публикуется** |
| Redis | `REDIS_PORT` | `127.0.0.1:6379` | `127.0.0.1:6479` | **не публикуется** |
| Prometheus | `PROMETHEUS_PORT` | `9090` | `9190` | не публикуется |
| Grafana | `GRAFANA_PORT` | `3001` | `3101` | через Caddy, поддомен |
| Caddy | `HTTP_PORT` / `HTTPS_PORT` | — | `80` / `443` | `80` / `443` |

Три правила, которые из таблицы не видны:

- **Смещение staging = dev + 100** для инфраструктурных сервисов. Оба
  окружения живут на одном VPS (`09-ci-cd.md` §9), и без смещения они
  подрались бы за порты.
- **Caddy на сервере — общий и работает в Docker.** На VPS уже есть инстанс
  Caddy с другими сайтами; наш проект своего Caddy не поднимает, подключает
  сервисы к его внешней Docker-сети и конфиг — отдельным файлом
  (`26-stage2-plan.md`, WP10). Порты `80`/`443` в таблице — его, а не наши.
- **В production наружу смотрит только Caddy.** Порты БД, Redis и Prometheus
  не публикуются вовсе — это пункт чек-листа безопасности
  (`15-engineering-standards.md` §7). В источнике переноса прод-compose
  публиковал `5432` и `6379` на хост; мы так не делаем.
- **В dev БД и Redis публикуются на `127.0.0.1`, а не на `0.0.0.0`.** Иначе
  Postgres с паролем `postgres` доступен всей локальной сети — включая
  публичный Wi-Fi в кафе.

**Dev-серверы Vite запускаются со `strictPort: true`.** Занятый порт должен
падать с явной ошибкой, а не молча уезжать на соседний: иначе Telegram-сборка
внезапно оказывается на `5174`, а вы полчаса отлаживаете «неправильный
адаптер».

Фронтенда как сервиса в staging и production не существует — там статика,
собранная Vite и разложенная на CDN с хэшами в именах файлов
(`09-ci-cd.md` §5).

| 10. Наблюдаемость | `LOG_LEVEL`, треды Telegram, Sentry, Grafana | id тредов — из супергруппы алертов |

| 13. Публичные для клиента | `VITE_*` | только не-секреты |
| 14. Диагностика и телеметрия | `EVENTS_INGEST_ENABLED`, `DIAGNOSTICS_INGEST_ENABLED`, `INGEST_INIT_DATA_MAX_AGE_SEC` | приёмники событий и отчётов (`28-diagnostics.md` §5): выключены по умолчанию, включённый без `DATABASE_URL` не стартует. `ALLOWED_ORIGINS` у приёмников — ещё и проверка `Origin`: пустой список на машине разработчика её выключает, в проде домен клиента обязан в нём быть. `TRUST_PROXY_HOPS` (группа 6) — за Caddy `1` |
| 15. CDN | ключ API Bunny.net для сброса кеша после деплоя | **только секреты CI**, на сервере не нужен (`26-stage2-plan.md`, WP10) |
| 16. Плейтест | `PLAYTEST_ENABLED`, `PLAYTEST_INIT_DATA_MAX_AGE_SEC`, `PLAYTEST_DATA_TTL_DAYS`, `PLAYTEST_DEV_AUTH`, `VITE_PLAYTEST_DEV_USER`, `PLAYTEST_STATS_ENABLED`, `PLAYTEST_STATS_DAILY_AT`, `PLAYTEST_STATS_UTC_OFFSET_MIN` | временная группа закрытого теста (`26-stage2-plan.md`, WP13 и WP14). Игрок проверяется подписью initData токеном `TELEGRAM_BOT_TOKEN` из группы 7; вход без подписи — только `NODE_ENV=development`, иначе бэкенд не стартует. `PLAYTEST_STATS_*` — сводка статистики картинкой в чат администраторов: включённая без чата администраторов или чтения обновлений бота не стартует |

`VITE_API_URL` пустой по умолчанию: собранный клиент ходит в API на свой же
домен, маршрут `/api` держит Caddy. Отдельный адрес задаётся, только если API
живёт на другом домене, — тогда этот домен добавляется и в `ALLOWED_ORIGINS`.
Dev-сервер переменную не читает вовсе: запросы `/api/v1/playtest` он всегда
проксирует на локальный бэкенд (§4). Иначе старое значение
`http://localhost:4000` из `.env` отправляло бы телефон через туннель в его
собственный localhost.

## 4. Работа в dev

**Вся команда работает на Windows в PowerShell** — команды даны под него. Три
особенности, о которые спотыкаются чаще всего:

- в Windows PowerShell 5.1 **нет оператора `&&`**: команды разделяются `;`,
  а «выполнить вторую только при успехе первой» — это `A; if ($?) { B }`;
- `nvm-windows` **не читает `.nvmrc`** — версию Node называем явно:
  `nvm install 22.22.3`, затем `nvm use 22.22.3`. Сам `.nvmrc` остаётся
  источником истины и используется в CI;
- Unix-команд (`cp`, `rm -rf`, `touch`) в PowerShell нет — эквиваленты ниже.

Один раз на машину:

```powershell
corepack enable pnpm
```

В корне репозитория:

```powershell
Copy-Item .env.example .env
pnpm install
docker compose up -d
```

Проверить, что инфраструктура поднялась:

```powershell
docker compose ps
```

Сгенерировать секреты (`openssl` идёт с Git for Windows; для access и refresh
значения обязаны быть разными):

```powershell
openssl rand -hex 32
```

Запуск одной командой:

```powershell
pnpm dev        # бэкенд + Telegram-клиент
pnpm dev:all    # бэкенд + все три клиента
```

Или по отдельности, каждая команда — своё окно терминала (порты не
конфликтуют):

```powershell
pnpm dev:backend     # API на http://localhost:4000
pnpm dev:telegram    # http://localhost:5173
pnpm dev:max         # http://localhost:5174
pnpm dev:vk          # http://localhost:5175
```

Туннель для проверки в Telegram с телефона — `pnpm tunnel` отдельным окном
(§4). Производительность на устройстве меряет стресс-тест в самом приложении
(`28-diagnostics.md` §2.3).

Миграции и Prisma:

```powershell
pnpm --filter backend-api prisma:migrate    # создать миграцию в dev
pnpm --filter backend-api prisma:generate   # перегенерировать клиент
```

Схема — `backend/api/prisma/schema.prisma`, строка подключения `DATABASE_URL`
читается из корневого `.env` в `backend/api/prisma.config.ts`: Prisma 7 сама
окружение не загружает. Клиент генерируется в `backend/api/src/generated/prisma`
при `pnpm install` и в git не хранится. Применить миграции без создания
новых — `pnpm --filter backend-api prisma:deploy`, как в CI и в проде.

Остановить инфраструктуру: `docker compose down` (данные останутся в томах),
`docker compose down -v` — вместе с данными.

**Если порт остался занят после Ctrl+C.** На Windows прерывание убивает
процесс, который держит консоль, но не всегда его потомков: бэкенд под
наблюдателем файлов переживает родителя и держит порт до перезагрузки.
Следующий запуск падает с `EADDRINUSE`.

```powershell
pnpm stop           # освободить порты разработки
pnpm stop 4001      # или конкретный
```

Что сделано, чтобы это случалось реже: из команд запуска убран флаг
`--respawn` (он воскрешал убитый процесс), бэкенд закрывает соединения по
`SIGINT`/`SIGTERM`/`SIGBREAK`, а в разработке ещё и сам замечает, что остался
без родителя — по закрытому stdin — и освобождает порт. `pnpm stop` остаётся
на случай жёсткого закрытия окна терминала, когда до процесса не доходит
вообще ничего.

Переустановить зависимости, если после `git pull` что-то ведёт себя странно:

```powershell
Remove-Item -Recurse -Force node_modules; pnpm install
```

**Переводы строк.** В репозитории лежит `.gitattributes`, который хранит всё
с LF. Это не косметика: shell-скрипты с CRLF внутри Linux-контейнера падают с
невнятным `bad interpreter`. Ничего настраивать вручную не нужно — файл
работает сам, но и переопределять `core.autocrlf` под проект не стоит.

**Тестирование Mini App локально.** Telegram не откроет `http://localhost` как
Mini App — нужен публичный HTTPS-адрес. В проекте для этого поднят `frp`:
шаблон конфигурации — `infra/frpc/frpc.example.toml`, рабочая копия
`frpc.local.toml` не коммитится, потому что содержит токен.

```powershell
Copy-Item infra/frpc/frpc.example.toml infra/frpc/frpc.local.toml
# вписать токен, затем:
frpc -c infra/frpc/frpc.local.toml
```

Домены закреплены за dev-серверами: `rubezh-tg` → `5173`, `rubezh-max` →
`5174`, `rubezh-vk` → `5175` (все на `*.frps.gonet.fun`). Тот же адрес
прописывается в `DEV_TUNNEL_*_HOST` — без него Vite отклонит запрос с чужим
заголовком `Host`, а HMR уйдёт на `localhost` телефона и обновления молча
перестанут доходить. Адрес туннеля добавляется и в `ALLOWED_ORIGINS`, иначе
CORS отклонит запросы к API.

**Обрыв связи с dev-сервером страницу не перезагружает.** Штатно клиент Vite,
потеряв websocket, перезагружает страницу, как только сервер снова ответит, —
а через туннель связь рвётся от блокировки экрана телефона, сворачивания
Telegram или простоя туннеля. Плагин `scripts/vite/stable-dev-session.ts`
заменяет перезагрузку плашкой «dev: связь восстановлена · обновить» в левом
нижнем углу: забег продолжается, обновить можно, когда удобно. До обновления
горячие правки не приходят. Правка кода, которую Vite применяет полной
перезагрузкой, по-прежнему перезагружает страницу. Если после обновления Vite
шаблон в клиенте поменяется, упадёт `scripts/test/stable-dev-session.test.ts`,
а dev-сервер напишет предупреждение.

**Dev-сервер при этом продолжает слушать только петлю** — наружу его выводит
`frpc`. `vite --host` не используется намеренно: он отдал бы несобранную
dev-сборку всей локальной сети, включая публичный Wi-Fi.

**Сохранения и лидерборд плейтеста в dev** идут через dev-сервер Vite: он
проксирует `/api/v1/playtest` на `http://127.0.0.1:${API_PORT}`, поэтому
телефон через туннель `rubezh-tg` достаёт до бэкенда без отдельного прокси и
без CORS. Проксируется только этот префикс: каждый его запрос проверяется
подписью initData, а остальные эндпоинты dev-бэкенда наружу так не выходят.
Порядок на машине разработчика:

```powershell
docker compose up -d redis
# в .env: PLAYTEST_ENABLED="true", TELEGRAM_BOT_TOKEN — токен тестового бота
pnpm dev
pnpm tunnel
```

Проверить в обычном браузере без Telegram: `PLAYTEST_DEV_AUTH="true"` и
`VITE_PLAYTEST_DEV_USER="dev-1:Разработчик"` — клиент подставит заголовок
вместо подписи. Обе переменные только для dev: бэкенд с `PLAYTEST_DEV_AUTH`
вне `NODE_ENV=development` не стартует, а сборка клиента заголовок не шлёт.

Сводка статистики в чат администраторов (`21-diagrams.md` §4.12) включается
на **одной** машине: `PLAYTEST_STATS_ENABLED="true"`, `ADMIN_CHAT_ID` — id
группы, куда добавлен бот, и `TELEGRAM_BOT_UPDATES="polling"`. Бот читает
команды long polling'ом, и два бэкенда на одном токене без общего Redis
мешают друг другу: Telegram отвечает второму `409`, тот ждёт и пишет об этом
в лог. У бота с вебхуком `getUpdates` не работает вовсе. Картинка рисуется системными
шрифтами (Segoe UI на Windows); в Linux-контейнере без шрифтов с кириллицей
текст на ней не появится — туда ставится `fonts-dejavu-core`, а главное
всё равно продублировано подписью к фото.

**Отдельного прокси на API в туннеле нет.** Телефон ходит в бэкенд через
dev-сервер Vite, который пропускает только префиксы с проверкой подписи
запуска (`apps/web-telegram/vite.config.ts`). Прокси `rubezh-api` существовал
ради приёмника отчётов стенда этапа 1 и удалён вместе с ним
(`26-stage2-plan.md`, WP6).

**Замер производительности делается на прод-сборке**, а не на dev-сервере:
dev-сборка Phaser, sourcemap и клиент HMR занижают FPS и дают ложный «no-go».
Порядок и протокол — `25-week1-fps-trials.md`.

**Заполнять `.env` реальными ключами не обязательно, чтобы начать.** Игровой
цикл (недели 1-2 роадмапа) работает без бэкенда вообще. Ключи нужны с недели 3.

## 5. Работа в production

Схема — Docker Compose на **Ubuntu Server LTS** (`01-tech-stack.md` §10),
развёртывание из образа, собранного в CI (`09-ci-cd.md` §10). Прод-compose
лежит **не в этом файле**: `docker-compose.yml` в корне — только dev.

### 5.1 Разработка на Windows, прод на Ubuntu — что расходится

Команда пишет код на Windows, а исполняется он в Linux-контейнере. Пять мест,
где это по-настоящему кусается, и что с каждым сделано.

**1. Регистр в путях — самая частая и самая обидная ошибка.**
Windows не различает `Enemy.png` и `enemy.png`, Linux различает. Импорты
TypeScript прикрыты флагом `forceConsistentCasingInFileNames` в
`tsconfig.base.json`, но **строковые пути к ассетам он не проверяет**:
`this.load.image('enemy', 'assets/Enemy.png')` соберётся, запустится локально
и отдаст 404 в проде. Для игры с сотнями спрайтов это вопрос «когда», а не
«если».

Меры: имена файлов ассетов — всегда строчными; сборка в CI идёт на Linux и
ловит расхождение до деплоя; ручная проверка билда перед релизом
(`17-testing-strategy.md` §8).

**2. Бит исполняемости.** Git на Windows не выставляет `+x`. Скрипт,
добавленный из PowerShell, попадёт в образ без права на запуск, и контейнер
упадёт при старте. Для каждого нового `.sh`:

```powershell
git update-index --chmod=+x путь/к/script.sh
```

Либо `chmod +x` внутри Dockerfile — надёжнее, потому что не зависит от того,
кто и откуда добавил файл.

**3. Переводы строк.** Закрыто `.gitattributes` (§4): в репозитории всё
хранится с LF. Без этого shell-скрипт с CRLF падает внутри контейнера с
невнятным `bad interpreter`.

**4. Разделители путей.** В коде — только `node:path` и прямые слэши.
Захардкоженный `\` работает на Windows и ломается в контейнере.

**5. Время.** Сервер и контейнеры живут в **UTC**, машины разработчиков — в
местном времени. Правило: в БД и логах всё в UTC, преобразование в локальное
время — только на отображении. Это не педантизм: у нас крон-задачи, витрины
по суткам, `occurred_at` / `received_at` в событиях
(`22-analytics-and-metrics.md` §3.1) и hold-период партнёрских выплат
(`23-referral-and-partner-program.md` §4.3) — при расхождении часовых поясов
сутки в отчётах «поедут», и расхождение заметят не сразу.

### 5.2 Подготовка сервера

Разово, до первого деплоя:

- Ubuntu Server LTS, обновления безопасности включены
  (`unattended-upgrades`);
- отдельный **непривилегированный пользователь** для деплоя, вход по ключу,
  парольная аутентификация SSH отключена;
- Docker Engine + плагин Compose (не Docker Desktop — это десктопный продукт);
- firewall: наружу открыты только `22`, `80`, `443`. Порты БД, Redis и
  Prometheus не публикуются вовсе (§2);
- часовой пояс UTC: `timedatectl set-timezone UTC`;
- swap на небольшом VPS — Postgres и сборка образов иначе упираются в память;
- ротация docker-логов (`max-size`, `max-file`), иначе логи съедают диск
  тихо и полностью.

### 5.3 Отличия прода от dev

Все существенные:

| Аспект | dev | production |
|---|---|---|
| Источник образа | локальная сборка | образ из GHCR по тегу, собранный CI |
| Порты БД/Redis | `127.0.0.1` | не публикуются вовсе |
| Вход снаружи | напрямую в Vite/API | только Caddy на `80`/`443`, автоматический TLS |
| Секреты | `.env` в корне | секреты окружения на хосте, права `600`, владелец — сервисный пользователь |
| Фронтенд | dev-сервер Vite | статика на CDN с хэшами в именах |
| Миграции | `prisma migrate dev` вручную | `prisma migrate deploy` в `entrypoint` до старта приложения |
| `NODE_ENV` | `development` | `production` |
| `LOG_LEVEL` | `debug` | `info` |
| `COOKIE_SECURE` | `false` | `true` |
| CORS | localhost-адреса | только реальные домены мини-приложений |

Порядок выката (подробно — `09-ci-cd.md` §10):

1. CI собирает образ, тегирует и пушит в GHCR.
2. На VPS: `docker compose pull && docker compose up -d` для нужного
   compose-проекта.
3. `entrypoint` применяет `prisma migrate deploy` **до** старта приложения.
4. Healthcheck подтверждает готовность; при провале — откат к предыдущему
   тегу образа.

**Перед миграцией в проде — свежий бэкап и проверка, что он читается.**
Бэкап, из которого ни разу не восстанавливались, бэкапом не является.

**Схема миграций expand → migrate → contract** обязательна: из-за модерации
площадок старые клиенты живут днями и продолжают дёргать API
(`09-ci-cd.md` §4). Удаление колонки в том же релизе, где прекратилась
запись, запрещено.

## 6. Staging

Отдельный compose-проект на том же VPS: свои тома, своя БД, свой бот, свои
тестовые ключи провайдеров, порты со смещением +100 (§2).

Компромисс осознанный: отдельный сервер удваивает расходы, а изоляции на
уровне compose-проекта достаточно. Ограничение честное — нагрузочные прогоны
на staging искажают картину прода, их делаем в окно низкой нагрузки или на
временном хосте (`17-testing-strategy.md` §7).

## 7. Как добавить новую переменную

1. Добавить в `.env.example` — в нужную группу, с комментарием «зачем» и с
   пустым значением, если это секрет.
2. Добавить в Zod-схему конфигурации: тип, обязательность, значение по
   умолчанию (для не-секретов).
3. Добавить в секреты CI для тех пар `platform × env`, где она нужна
   (`09-ci-cd.md` §3).
4. Задать значение на staging и production **до** выката кода, который её
   читает. Иначе приложение не поднимется — и это правильное поведение, но
   узнать о нём лучше не в момент релиза.
5. Если это порт — внести в таблицу §2, включая staging-смещение.
6. Предупредить команду: у остальных `.env` не обновится сам.

## 8. Диагностика

| Симптом | Причина и что делать |
|---|---|
| Приложение падает при старте с текстом про переменную | Так и задумано: не задана обязательная переменная. Сверить с `.env.example` |
| `EADDRINUSE` на dev-сервере | Порт занят — из-за `strictPort` он падает явно. Освободить: `pnpm stop` |
| `EADDRINUSE` после Ctrl+C, хотя всё закрыто | Осиротевший процесс от прошлого запуска, см. ниже про Windows. `pnpm stop` |
| Vite не видит переменные | Читаются только `VITE_*`; остальное в бандл не попадает намеренно |
| CORS-ошибка в браузере | Адрес не в `ALLOWED_ORIGINS`. При работе через туннель добавить адрес туннеля |
| Prisma не подключается | `DATABASE_URL` указывает на `localhost`, а приложение в контейнере: там нужен host = имя сервиса compose |
| Telegram не открывает Mini App | `http://localhost` не подходит, нужен публичный HTTPS — см. §4 |
| Через туннель отдаётся `Blocked request. This host is not allowed` | Домен не задан в `DEV_TUNNEL_*_HOST`, Vite режет чужой `Host` |
| Через туннель страница работает, но правки не подхватываются | Клиент HMR стучится не на тот адрес: проверить `DEV_TUNNEL_*_HOST` и что `frpc` поднят на нужный порт |
| В Telegram открывается вчерашняя сборка | Кеш WebView: открывать ссылку с `?v=<хеш сборки>` |
| Всё поднялось, но API отвечает 401 | Не заданы `JWT_*` или `TELEGRAM_BOT_TOKEN`, либо истекло окно `INIT_DATA_EXPIRES_IN` |
