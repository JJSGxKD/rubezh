# Технологические решения: библиотеки, инструменты, версии

`01-tech-stack.md` отвечает на вопрос «какая архитектура». Этот документ —
«какими конкретно инструментами» и, главное, **почему именно ими**, чтобы через
полгода не переспорить решение заново и чтобы ИИ-агент не притащил в проект
четвёртую библиотеку для той же задачи.

Состояние на **сентябрь 2026**. Мажорные версии проверять перед стартом
соответствующей недели роадмапа — экосистема движется, а документ статичен.

---

## 0. Критерии выбора

Библиотека принимается, если проходит все пять:

1. **Живая.** Релизы за последние 6 месяцев, реакция на security-issue.
2. **Заменяемая.** Понятно, чем и какой ценой заменить. Библиотека, вокруг
   которой придётся строить архитектуру, требует отдельного обсуждения.
3. **Соразмерная.** Не тянет за собой десятки транзитивных зависимостей ради
   одной функции. Для клиента дополнительно — вес в бандле.
4. **Одна на задачу.** В источнике переноса одновременно живут `redis`,
   `ioredis`, `keyv` и `cache-manager` (`13-reuse-from-vpnsibcom.md` §2.3 S).
   У нас так не будет: вторая библиотека для решённой задачи — повод для
   отказа в PR, а не для обсуждения вкусов.
5. **Типизированная.** Нативный TypeScript или качественные типы.

## 2. Рантайм и пакетный менеджер: Bun рассмотрен, выбран Node + pnpm

Решение принималось отдельно по двум вопросам, которые часто путают: **чем
исполнять код** и **чем ставить зависимости**. Bun претендует на оба, и
ответы получились разными по причинам, но одинаковыми по итогу.

### 2.1 Рантайм бэкенда: Node LTS, не Bun

Bun как рантайм технически подходит: поддержка `emitDecoratorMetadata` есть с
версии 1.0.3, то есть NestJS с его рефлексией декораторов запускается. Вопрос
не в этом, а в трёх зависимостях, на которых держится наш бэкенд.

**Prisma — блокирующий фактор.** Официального Bun-адаптера у Prisma нет:
запрос на него открыт (`prisma/prisma#28110`), доступны только
community-адаптеры (`@abcx3/prisma-bun-adapter`, `@onreza/prisma-adapter-bun`).
Альтернатива — гнать `pg` через node-совместимость Bun. Оба варианта означают,
что **самая критичная подсистема проекта — деньги, транзакции, балансы
`Decimal` — стоит на неофициальном пути**. Команда из трёх человек не может
позволить себе отлаживать баг уровня драйвера БД на неделе лонча, а
воспроизвести такой баг локально обычно не получается — он проявляется под
нагрузкой и в конкурентности.

**BullMQ — второй фактор.** В BullMQ 6 появилась абстракция бэкендов, включая
нативный клиент Bun с обёрткой `createBunRedisClient`; ioredis из пакета
вынесен в опциональные peer-зависимости, и под Bun у него есть свои оговорки
(например, несовместимость опции `keyPrefix`). Путь рабочий, но новый — а через
эту очередь у нас идут платёжные вебхуки и начисление наград. Быть ранним
пользователем именно здесь — плохой размен.

**Выгода при этом мала.** Наш профиль нагрузки (`14-scalability.md` §1) — один
запрос на забег, и время в нём уходит на round-trip к Postgres и Redis и на
проверку подписи, а не на пропускную способность JS-рантайма. Bun выигрывает
там, где узкое место — сам рантайм; у нас оно не там. Мы бы приняли реальный
риск ради ускорения того, что и так не тормозит.

**Дополнительные соображения:** переносимый код и продакшен-опыт команды —
на Node (`13-reuse-from-vpnsibcom.md`); разработка идёт на Windows, а прод —
Linux в Docker, и Bun добавил бы вторую ось расхождения сред на менее
обкатанной комбинации.

**Что делаем, чтобы не закрыть себе дверь.** Пишем бэкенд без нужды в
Node-специфичных API там, где есть стандартная альтернатива (нативный `fetch`
вместо `axios` — уже §5, стандартные веб-API вместо узких `node:`-модулей).
Это ничего не стоит сейчас и оставляет переход возможным позже.

**Когда пересматриваем** — при выполнении всех трёх условий, не раньше:

1. Prisma выпустила **официальный** Bun-адаптер (закрыт `prisma/prisma#28110`);
2. Bun-бэкенд BullMQ отработал стабильно минимум два минорных релиза на
   нагрузке, сопоставимой с нашей;
3. Прошёл публичный лонч в Telegram (после этапа 6 роадмапа). Менять рантайм
   на этапах 3–5 нельзя ни при каких условиях — это недели, когда всё должно
   быть предсказуемым.

### 2.2 Пакетный менеджер: pnpm

Здесь нужно честно скорректировать более раннюю формулировку этого документа.
Аргумент «строгая раскладка `node_modules` есть только у pnpm» **больше не
верен**: у Bun есть isolated installs — центральное хранилище в
`node_modules/.bun/` с симлинками и запретом фантомных зависимостей, и для
новых монорепо это поведение по умолчанию. То есть требование
`15-engineering-standards.md` §2.2 (границы слоёв защищены файловой системой,
а не договорённостью) Bun закрывает не хуже.

Выбор в пользу pnpm поэтому опирается на другое:

- **Единство инструментария.** Раз рантайм — Node (§2.1), то `bun install`
  означает два тулчейна: установка по правилам Bun, исполнение по правилам
  Node. Это работает, но добавляет класс проблем «у меня ставится, в CI
  падает» без соразмерной выгоды.
- **Зрелость обвязки.** Renovate, аудит уязвимостей, кеширование в GitHub
  Actions, интеграция с Turborepo — под pnpm всё это отлажено и предсказуемо.
- **Расстановка сил в экосистеме 2026.** pnpm + Turborepo — де-факто стандарт
  для монорепо; ценность Bun максимальна, когда на Bun и рантайм, и скрипты, а
  у нас это не так.

Скорость установки в решении не участвует: на шести пакетах разница между
менеджерами не влияет ни на что.

**Статус: выполнено.** Репозиторий переведён на pnpm 10. Что сделано:

- `pnpm-workspace.yaml` — состав монорепо (`packages/*`, `apps/*`, `backend/api`);
- внутренние зависимости переведены на протокол **`workspace:*`** вместо `"*"`
  (в pnpm 10 связывание workspace-пакетов по обычной семверной строке больше
  не подразумевается по умолчанию — протокол делает намерение явным);
- версия менеджера зафиксирована полем `packageManager`, ставится через
  `corepack enable pnpm` — одинаковая у всех и в CI;
- `engines.node` + `engine-strict=true` в `.npmrc` — версия Node проверяется
  при установке, а не обнаруживается по странному поведению;
- `"type": "module"` в корне — ESM-конфиги без предупреждений (§1).

**Изоляция проверена фактически**: `packages/core-game/node_modules` содержит
только `@bh/*` и `phaser`, то есть ровно объявленные зависимости; `ioredis` из
`backend/api` оттуда недоступен. Это и есть механизм, на котором держатся
границы слоёв (`15-engineering-standards.md` §2.2) — теперь не договорённость,
а свойство файловой системы.

**Побочный эффект, который стоит знать.** pnpm 10 по умолчанию **не
выполняет** postinstall-скрипты зависимостей — это защита от вредоносного
кода в цепочке поставки. Пакеты, которым скрипт нужен по делу (`esbuild`,
`prisma`, `@prisma/*`, `msgpackr-extract`), перечислены в
`onlyBuiltDependencies` в `pnpm-workspace.yaml`. Добавление нового пакета в
этот список — отдельное решение на ревью: по сути это разрешение выполнить
чужой код на машине разработчика и на раннере CI.

**`npm install` в этом репозитории больше не работает** — он не понимает
`workspace:*`. Это не недостаток, а полезное свойство: разойтись менеджерами
внутри команды теперь невозможно.

### 3.1 Движок и сборка

| Решение | Значение | Обоснование |

Аргумент против React — конкуренция за главный поток с игровым циклом — верен для React **внутри кадра забега**, и эта часть сохраняется: HUD обновляется не чаще 10 Гц, оверлеи показываются над остановленной симуляцией, Phaser грузится отдельным чанком. Разбор, выбор между React/Preact/Solid/Svelte и правила производительности — `27-design-system-and-app-shell.md` §1, §3.3 |
| Стили интерфейса | **Tailwind CSS 4**, токены дизайн-системы в `@theme` | Опыт команды (`vpnsibcom_web`); токены сразу и CSS-переменные, и утилиты. Копия палитры для Phaser сверяется тестом (`27-design-system-and-app-shell.md` §4.2) |
| Шрифты интерфейса | **`@fontsource-variable/rubik` и `@fontsource-variable/inter` 5.3.0**, файлы в бандле | Google Fonts без сети: файлы из npm точной версией, как у `next/font`. Вариативные — одна пара файлов на все начертания; подключаются только кириллица и латиница, 115 КБ `woff2` при бюджете 120 (`27-design-system-and-app-shell.md` §3.4, §4.3). Лицензия SIL OFL 1.1, у пакетов нет зависимостей и postinstall |
| Навигация интерфейса | **Свой стек экранов**, без роутера | Адресной строки в Mini App нет, «назад» — платформенная кнопка (`27-design-system-and-app-shell.md` §7) |
| HTTP-клиент | **нативный `fetch`** + тонкая обёртка (таймаут, ретрай с джиттером, ре-авторизация) | Источник использует axios; в 2026 это лишняя зависимость — `fetch` есть везде, где мы работаем. Обёртка пишется своя, поведение берём из `authApiClient.ts` (`13-reuse-from-vpnsibcom.md` §11) |
| Состояние вне игры | **Zustand** — только для мета-UI (профиль, баланс, токен) | Игровое состояние живёт в Phaser, in-memory. Синк на бэкенд — по окончании забега (`01-tech-stack.md` §2) |
| Локализация | Собственный словарь JSON (ru/en) | `next-intl` из источника завязан на Next.js. Для двух локалей и статичных строк полноценная i18n-библиотека избыточна (`01-tech-stack.md` §7) |
| Отчёты об ошибках | **Sentry (или GlitchTip self-hosted)** | В источнике клиентского трекинга крэшей нет вообще — это пробел, который мы не наследуем. Игра падает в WebView конкретных устройств, и без стектрейсов с версией клиента и моделью телефона такие падения не диагностируются. Обязательно к этапу 5 (софт-лонч) |

### 3.2 Требования к производительности (следствие §3.1)

Не библиотеки, но решения того же уровня — они определяют, влезем ли мы в
бюджет кадра на бюджетном Android (`02-roadmap.md`, критерий этапа 1):

- **Пулинг объектов** для врагов и снарядов. Создание/уничтожение сотен
  объектов за кадр — главный источник пауз сборщика мусора.
- **Текстурные атласы**, а не отдельные файлы спрайтов: меньше запросов и
  меньше переключений текстуры на кадр. Атласы делятся на паки, и забег
  стартует с одним обязательным — остальные приходят по требованию
  (`27-design-system-and-app-shell.md` §3.5).
- **Фиксированный шаг симуляции**, отвязанный от частоты кадров — требование
  детерминизма (`15-engineering-standards.md` §2.4) и одновременно защита от
  разного поведения игры на 30 и 120 Гц.
- **Бюджет бандла**: целевой размер первой загрузки объявляется на этапе 1 и
  проверяется в CI (`09-ci-cd.md`). Игра, которая грузится десять секунд, теряет
  игрока до начала геймплея.

## 4. Платформенные адаптеры

| Платформа | SDK | Комментарий |
|---|---|---|
| Telegram | **`@tma.js/sdk`** | Источник использует `@tma.js/sdk-react` — React-обёртка, нам не нужна. Берём ядро без React. Про выбор между `@tma.js/*` и `@telegram-apps/*` — примечание ниже |
| Telegram, серверная валидация | **Своя проверка на `node:crypto`**, без библиотеки (`backend/api/src/modules/telegram/telegram-init-data.ts`) | План брал `@tma.js/init-data-node` из источника, но проверка вышла короче обвязки вокруг библиотеки: два HMAC-SHA256 и сравнение за постоянное время. Лишняя зависимость на участке, который выдаёт вход, стоила бы дороже. Окно свежести — явное и короткое, из конфигурации (`13-reuse-from-vpnsibcom.md` §2.1 F). Каждая ветка закреплена тестом: подмена поля, чужой токен бота, устаревшие данные, дата из будущего. Понадобится проверять без токена бота — у Telegram есть подпись Ed25519 публичным ключом (`33-telegram-mini-app-pitfalls.md` §1.1) |

**Примечание про имя пакета.** У этой библиотеки две линейки имён:
`@tma.js/*` и `@telegram-apps/*`. Раньше актуальной считалась вторая, сейчас
поддерживается первая: на момент выбора (сентябрь 2026) `@tma.js/sdk` имеет
свежие публикации, а `@telegram-apps/sdk` не обновлялся с декабря 2025. Перед
обновлением зависимости стоит перепроверить обе линейки по реестру, а не по
памяти: имя пакета здесь уже мигрировало дважды.
| MAX | MAX Bridge (по документации dev.max.ru) | Схема валидации — открытый вопрос, сверка на этапе 5 (`03-notes-and-risks.md`) |
| VK | VK Bridge | Фаза после MAX |

Адаптер обязан быть тонким: получить контекст пользователя, провести оплату,
показать рекламу, отправить шеринг, вибрация. Всё остальное — в `core-game`
или на бэкенде. Тест на «правильную толщину» простой: если в адаптере
появилась игровая логика — она там лишняя.

## 5. Бэкенд

| Слой | Решение | Обоснование и отличие от источника |
|---|---|---|
| Фреймворк | **NestJS 12**, бэкенд — ESM-пакет | Модульность и DI совпадают с нашей моделью слоёв. С 12-й версии Nest выходит только в ESM: `"type": "module"`, `NodeNext`, относительные импорты с `.js`. Запуск в разработке — `node --watch` с загрузчиком `@swc-node/register` (он понимает метаданные декораторов, без которых нет DI), сборка — `tsc` |
| HTTP-платформа | **Fastify** (`@nestjs/platform-fastify`) | Express убран при переезде на NestJS 12 (WP8). Fastify быстрее и уже обкатан в источнике. **Важно**: держать только одну платформу — в источнике установлены обе, плюс дублирующиеся `express-session`/`@fastify/session`. Сборка приложения — одна на прод и HTTP-тесты: `backend/api/src/http-app.ts` |
| ORM | **Prisma 7** + `@prisma/adapter-pg` | Как в источнике. Генератор `prisma-client` пишет клиент TypeScript-модулями в `backend/api/src/generated/prisma` — **не** в git, собирается `prisma generate`. Строка подключения — в `backend/api/prisma.config.ts`, а не в схеме |
| БД | PostgreSQL 17 | Точная версия и digest образа — в `docker-compose.yml` и в сервисах CI, одни и те же (§9.4) |
| Кеш / локи / лидерборды | **ioredis** | Один клиент Redis на проект. BullMQ всё равно требует ioredis — вторая библиотека была бы дублированием |
| Очереди | **BullMQ 6** | Как в источнике: ретраи, backoff, отложенные задачи |

## 6. Валидация и конфигурация: почему Zod, а не class-validator

Решение с последствиями, поэтому обосновано отдельно.

`class-validator` + `class-transformer` (стек источника) даёт **два источника
истины**: TypeScript-тип и набор декораторов, которые про этот тип ничего не
знают. Рассинхронизация не ловится компилятором — поле можно добавить в
интерфейс и забыть декоратор, и оно молча пройдёт валидацию. Плюс декораторы
требуют `experimentalDecorators` и `reflect-metadata` и плохо работают с
композицией схем.

Zod: схема **является** источником типа (`z.infer`). Невозможно добавить поле в
тип, не добавив в валидацию, — они одно и то же. Отсюда:

- **DTO** — Zod-схемы, типы выводятся из них;
- **конфигурация окружения** — одна Zod-схема, парсинг при старте, процесс не
  поднимается при невалидной конфигурации (`15-engineering-standards.md` §9);
  это закрывает класс проблем вида «секрет не задан, взяли дефолт»
  (`13-reuse-from-vpnsibcom.md` §2.1 C);
- **данные с границы** — ответы платёжных и рекламных провайдеров, JSON из
  БД, `initData` — парсятся теми же схемами. Внешний API поменял формат — мы
  узнаем об этом из ошибки валидации, а не из странного поведения через неделю;
- **общие схемы** живут в `shared-types` и используются и клиентом, и
  сервером — контракт перестаёт быть договорённостью и становится кодом.

Стоимость: `nestjs-zod` менее «нативен» для Nest, чем `ValidationPipe`, и
интеграция с генерацией OpenAPI требует настройки. Считаем это приемлемым.

## 9. Политика версий и обновлений

- **Все версии зафиксированы точно** (без `^` и `~`), lock-файл в git.
  Диапазоны означают, что у разработчика и в проде разный код. У
  Docker-образов роль lock-файла играет digest (§9.4).
- **Renovate** с группировкой: патчи — автомерж при зелёном CI; минорные —
  раз в неделю одним PR; мажорные — вручную, с заметкой о ломающих изменениях.
- **Только LTS** для Node. Не бегать за нечётными версиями.
- **Обновление security-патчей — вне очереди**, в течение суток после
  появления.
- **Новая зависимость** добавляется через PR с обоснованием по критериям §0.
  Для клиентской части дополнительно указывается прирост размера бандла.
- Раз в квартал — ревизия: что не используется, что дублируется, что можно
  выкинуть. Список отставших смотреть `pnpm outdated -r`.

### 9.3 Phaser 4: проверен и отложен

**Зачем пробовали.** Последний выпуск тройки — 3.90.0 в мае 2025 года, дальше
по реестру npm выходит только четвёрка (4.0.0 — апрель 2026, 4.2.1 — июль).
Переходить дешевле всего, пока мир забега рисуется примитивами: после эффектов
и шейдеров переход стоил бы их переписывания.

**Что показала миграция.** Кода она почти не требует — по официальному гайду
нас коснулись две правки (режим заливки тинтом и `Graphics.fillPoints`).
Обычная точка входа четвёрки тяжелее на 38 КБ gzip, почти всё — Matter.js;
сборка без него возвращает чанк движка к весу тройки. Код перехода лежит в
ветке `feat/phaser-4` (PR #12, закрыт без мержа).

**Почему отложен.** Замер по протоколу `25-week1-fps-trials.md` §7 с порогом,
записанным до прогонов, — «предел четвёрки не ниже 90% тройки»:

| TECNO CH7n, 61–62 Гц, DPR 3 | Phaser 3.90.0 | Phaser 4.2.1 |
|---|---|---|
| Предел в `stress` | 3473 врага | **867 врагов** — 25% тройки |
| p95 кадра при ~970 врагах | 16.5 мс, ровно | 20.2 мс и растёт |

Разница не в разовом рывке: у четвёрки время кадра ползёт вверх с ростом
нагрузки, у тройки на тех же отметках стоит ровно. Режим заливки тинтом к ней
не причастен — в четвёрке он передаётся атрибутом вершины и батчи не рвёт.
Узкое место и в этапе 1 было в работе на объект (`25-week1-fps-trials.md`
§6.2), и именно её четвёрка сделала дороже.

**На рабочей нагрузке разницы в кадрах нет.** Потолок живых врагов в
бесконечном режиме — 240 (`content/waves.ts` → `ENDLESS_CURVE`), а до 570
врагов обе сборки держат 60 кадров с одинаковым p95 16.5 мс. По ощущениям на
тесте четвёрка казалась даже живее и плавнее. Главное видимое отличие той
сборки — вспышки попаданий: в тройке белый множитель цвет не менял, и их почти
не было видно. Вспышки перенесены на тройку через `setTintFill`; если после
этого разница на глаз останется, её стоит разобрать отдельным сравнением —
в метриках кадра её нет. Запас по нагрузке у четвёрки вчетверо меньше, а
настоящие спрайты и эффекты стоимость объекта только добавят.

**Когда возвращаться** — при любом из условий:

- в четвёрке появится исправление производительности рендера спрайтов —
  проверяется повтором того же замера на той же сборке ветки;
- понадобится то, чего в тройке нет: фильтры на любом объекте, свет,
  `SpriteGPULayer`. Последний рисует тысячи однотипных объектов на GPU и мог бы
  перевернуть результат, но требует переписать рендер врагов под себя — это
  отдельная задача, а не обновление версии.

### 9.4 Docker-образы: точная версия и digest

Одного точного тега мало. Официальные образы пересобирают под тем же тегом,
когда выходит патч базовой системы, поэтому `17.11-alpine3.24` через месяц —
уже другой набор байтов. Ссылка на образ — тег с полной
версией и digest:

```yaml
image: postgres:17.11-alpine3.24@sha256:b0f9560a2de083e2cc7382e75f808c7381a32852a7ec49117deedb300e552b24
```

Docker берёт образ по digest и тег не читает. Тег нужен ревьюеру: по 64
знакам версию не узнать. Так закреплены Postgres и Redis в
`docker-compose.yml` и в сервисах джоба `gate` в `.github/workflows/ci.yml`,
а также база `backend/api/Dockerfile`. Postgres и Redis в этих двух файлах
одни и те же, поэтому интеграционные тесты в CI идут на той базе, на которой
идёт разработка. Прод-compose (`26-stage2-plan.md`, WP10) берёт те же образы.

Проверяет `scripts/image-pins.mjs`, тестом в `pnpm test`. Она обходит
workflow, все `compose*.yml` и `docker-compose*.yml` и все Dockerfile
репозитория и считает ошибкой:

- образ без digest или с digest без тега;
- плавающий тег: `17-alpine`, `latest`, `alpine`. Тег начинается с полной
  версии, у alpine-варианта указана версия Alpine;
- образ из переменной: по файлу не видно, что запустится;
- разные версии или digest одного образа в разных файлах;
- строку с `image:` или `FROM`, которую проверка не разобрала.

Полноту версии проверка не видит: `7.4-alpine3.21` она пропустит, хотя у
Redis полная версия — `7.4.11`. Это остаётся на ревью.

**Сверки с реестром по сети нет, и это намеренно.** Digest тега законно
меняется при каждой пересборке образа. Проверка на равенство падала бы в
случайный день без единой правки в репозитории. Подставить под именем
`postgres` чужой образ digest не позволит: Docker ищет его только в
репозитории самого образа.

**Как обновить образ.**

1. Выбрать тег с полной версией, например `postgres:17.12-alpine3.24`, а не
   `17-alpine`. Теги перечислены на странице образа в Docker Hub.
2. Взять digest индекса:

   ```bash
   docker buildx imagetools inspect postgres:17.12-alpine3.24
   ```

   Нужен `Digest` верхнего уровня, над списком `Manifests`: это индекс сразу
   всех платформ. Digest из списка — образ одной платформы. С ним CI на amd64
   работает, а Mac на arm64 запускает образ под эмуляцией или не запускает
   вовсе.
3. Поменять ссылку во всех местах сразу. Разные версии одного образа тест не
   пропустит. Быстрая проверка без всего `pnpm test` —
   `node scripts/image-pins.mjs`.
4. Локально `docker compose up -d` пересоздаст контейнеры на новом образе.
   Данные остаются в томах.

**Патч и мажор.** Патч Postgres (17.11 → 17.12) совместим с данными в томе.
Мажор (17 → 18) несовместим: том с данными 17 на 18 не запустится, нужен
дамп и восстановление. К тому же в образах с 18-й версии каталог данных
включает номер версии, так что меняется и путь тома. Поэтому мажор делается
отдельным PR с процедурой переезда для dev и прода, как у любой зависимости
(§9). Redis 7 → 8 — тоже отдельное решение.

**Когда обновлять.** Сами по себе образы теперь не обновляются. Это плата
за то, что они не меняются без нашего ведома. Исправления безопасности
Postgres, Redis и Alpine ставятся вне очереди, как любые security-патчи (§9).
Остальное пересматривается на квартальной ревизии: минорные выпуски Postgres
выходят раз в квартал. Renovate из §9 ещё не подключён. Когда его подключат,
он будет обновлять тег и digest одним PR.

## 9.1 Решение: частота отрисовки — 60 FPS

**Принято на старте этапа 2** (`26-stage2-plan.md` §2, Р4): отрисовка
фиксируется на 60 кадрах для всех устройств. Ниже — обоснование, на котором
решение принималось.

**Вопрос**: фиксировать ли отрисовку на 60 кадров для всех устройств.

**Что показали замеры** (`25-week1-fps-trials.md` §6.2): браузер рисует со
скоростью экрана, и на 120-герцовом телефоне тот же аппарат в том же
разрешении выдерживает на 27% меньшую нагрузку — вдвое больше кадров в секунду
уходит в отрисовку. На десктопе видели 144 и 200 FPS по той же причине.

**Рекомендация**: зафиксировать 60 на MVP. Симуляция и так идёт фиксированными
шагами по 60 Гц, поэтому лок не трогает геймплей — только отрисовку;
освободившийся запас уходит контенту, а замеры между устройствами становятся
сравнимыми без оговорок. Переключатель «120» — после софт-лонча, если появятся
жалобы на плавность.

**Цена решения**: одна строка в конфигурации Phaser (`fps.target` +
`forceSetTimeOut`), в стенде испытаний механизм уже есть (`?fps=60`).

## 10. Реестр отклонённых решений

Фиксируем, чтобы не обсуждать повторно.

| Что | Почему отклонено |
|---|---|
| React **внутри забега** (перерисовка в кадре, React-рендер игрового мира) | Конкуренция за главный поток при главном риске «производительность WebView». React-оболочка вокруг забега при этом **принята** на этапе 2 (§3.1) |
| Интерфейс меню на канве Phaser | Отклонено на этапе 2: переизобретение вёрстки, прокрутки, шрифтов и отступов безопасной зоны на двенадцати разделах (`27-design-system-and-app-shell.md` §1.2) |
| Preact, SolidJS, Svelte для оболочки | Выигрыш в весе или скорости не попадает в узкое место; у команды и агентов нет сопоставимого опыта (`27-design-system-and-app-shell.md` §1.3) |
| git-cliff, semantic-release, Changesets, release-please | Первые два выводят масштаб релиза из типа коммита, а объявлять его должен автор PR; Changesets заточен под публикацию npm-пакетов и коммитит версии обратно; release-please назначает номер не при каждом мердже (`09-ci-cd.md` §8.1) |
| Продуктовые дашборды в Grafana | Аналитика для геймдизайнера, маркетинга и партнёров — в своей админ-панели с правами по ролям; Grafana — только техническая (`29-admin-panel.md` §1) |
| axios | Нативный `fetch` покрывает потребность; лишняя зависимость |
| class-validator / class-transformer | Два источника истины вместо одного (§6) |
| Несколько библиотек кеша (`keyv`, `cache-manager`) | Хватает ioredis; дублирование — критерий §0.4 |
| Kubernetes | Docker Compose достаточен на этом масштабе (`09-ci-cd.md` §6, `14-scalability.md` §3, этап 5) |
| Микросервисы | Один домен, три человека. Модульный монолит с чистыми границами даёт то же разделение без сетевых вызовов между своими же частями |
| GraphQL | Клиент один и известен заранее; REST + `bootstrap`-эндпоинт проще и быстрее |
| Своя система авторизации по e-mail/паролю | Идентичность даёт платформа; хранение паролей — риск без пользы (`08-web-and-identity.md`) |
| Мультивалютный слой с курсами | Экономика по платформам считается раздельно (`03-notes-and-risks.md`) |
| MongoDB / «что-нибудь быстрое» вместо Postgres | Наши данные транзакционные и реляционные: балансы, платежи, рефералы |
| Монорепо-инструменты (Nx) | Тяжелее, чем нужно шести пакетам; Turborepo при необходимости (§2) |
| **Bun как рантайм бэкенда** | Нет официального Bun-адаптера Prisma, Bun-бэкенд BullMQ новый — риск на подсистемах, отвечающих за деньги. Выигрыш мал: наше узкое место не в JS-рантайме. Условия пересмотра — §2.1 |
| **`bun install` как пакетный менеджер** | Isolated installs закрывают требование границ не хуже pnpm, но при Node-рантайме это второй тулчейн без соразмерной выгоды; обвязка (Renovate, аудит, кеш CI) зрелее под pnpm. §2.2 |
| **`bun test` как тест-раннер** | Второй раннер к Vitest — нарушение критерия §0.4; на Node-рантайме выигрыша нет |
