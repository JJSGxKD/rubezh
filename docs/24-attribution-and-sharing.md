# Атрибуция, редирект-страница и виральный шеринг

Документ описывает путь от клика по ссылке до атрибутированного игрока и
обратный виток: как игрок сам порождает новые ссылки.

Смежное: `23-referral-and-partner-program.md` (кому и за что платим),
`22-analytics-and-metrics.md` (что считаем), `08-web-and-identity.md`
(веб-версия и идентичность), `10-progression-and-ladder.md` (что показываем
в карточке профиля).

---

## 1. Общая схема

```
Ссылка (реф / партнёрская / из шеринга)
        │
        ▼
Редирект-страница на нашем домене  ──►  запись клика в БД, короткий click_id
        │
        ├── прямой переход на платформу (deep link с click_id)
        └── хаб-страница с кнопками платформ (каждая кнопка несёт тот же click_id)
        │
        ▼
Первый запуск Mini App: startParam = click_id
        │
        ▼
Сервер связывает клик с пользователем → атрибуция → награды
```

---

## 2. Почему своя редирект-страница, а не прямая ссылка на платформу

Соблазн — давать сразу `t.me/bot/app?startapp=...`. Так делать нельзя, и
причин четыре.

1. **Параметр запуска слишком мал.** У Telegram `startapp` ограничен по
   длине и алфавиту; упаковать в него UTM-метки, кампанию, идентификатор
   партнёра и тип креатива невозможно. Короткий `click_id` — единственная
   схема, которая масштабируется: сам параметр остаётся коротким, а данные
   лежат в строке БД.
2. **Данные видны только до перехода.** `Referer`, User-Agent, IP, язык,
   часовой пояс доступны на нашей странице. После перехода в мессенджер их
   уже нет. Это же — исходные данные для антифрода (§5).
3. **Без страницы неизвестен знаменатель.** Сколько было кликов — база всех
   конверсий. Без неё «100 регистраций» ничего не значит: из тысячи кликов
   это провал, из ста двадцати — отличный результат.
4. **Цель можно менять без смены ссылки.** Партнёр разместил ссылку в
   закреплённом посте полгода назад; мы добавили VK — ссылка продолжает
   работать и ведёт куда нужно.

## 3. Устройство редирект-страницы

### 3.1 Адрес

```
https://<домен>/r/<code>
```

`code` — короткий (8-10 символов) **непредсказуемый** идентификатор. Два
требования, оба существенные:

- **не инкрементальный** — иначе перебором можно просканировать чужие
  ссылки и накрутить чужие клики;
- **сам по себе не содержит данных** — это ключ к строке в БД, а не
  упаковка. Идентификатор партнёра, зашитый в код ссылки, читается любым
  желающим и провоцирует подмену.

**Владелец ссылки** (`35-stage4-plan.md` Р96, T-0067). У ссылки может быть
владелец-партнёр (`link.partner_id`): кто он, знает только строка в базе, а
не код. Владелец задаётся при создании и не меняется — в `PATCH` поля нет,
лишнее поле в теле даёт 400: клики и привязки уже записаны за ним. Партнёра,
которого нет, ссылка не принимает (404). Список ссылок в панели
фильтруется по владельцу (`?partner=<id>`), вид ссылки несёт
`partner: { partnerId, name }` или `null`. Что владелец меняет для игрока —
в §5 (шаг 3) и в `23-referral-and-partner-program.md` §4.1.

### 3.2 Что собираем при клике

| Данные | Источник | Зачем |
|---|---|---|
| `code` | путь | какая ссылка сработала |
| UTM: source, medium, campaign, content, term | query | разрезы в аналитике |
| `Referer` | заголовок | откуда пришли, если браузер отдал |
| User-Agent | заголовок | устройство, ОС, платформа |
| IP | соединение | гео, антифрод (хранение — §6) |
| `Accept-Language` | заголовок | язык интерфейса при первом запуске |
| Часовой пояс, разрешение экрана | JS, если исполнился | точность гео и антифрод-отпечаток |
| Метка времени | сервер | скорость конверсии клик → запуск |
| Макросы сети | query, только у ссылки сети (§3.5) | отдать сети её конверсию |

Всё это пишется одной строкой `click` с уникальным `click_id`. Запись —
асинхронная, редирект не ждёт её завершения: страница должна отдаваться
мгновенно, иначе часть переходов теряется на медленной сети.

### 3.3 Превью ссылки — отдельная задача

Мессенджер, получив ссылку, сам запрашивает страницу, чтобы построить
превью. Отсюда два требования:

- страница отдаёт корректные OG-теги: заголовок, описание, картинку.
  Ссылка без превью в чате конвертит заметно хуже — а для шеринга (§7) это
  основной канал;
- **запросы краулеров не считаются кликами.** Иначе одна отправка ссылки в
  чат порождает фантомный клик, и конверсия оказывается заниженной, а
  метрика «клики без запусков» ложно сигналит о накрутке;
- **запросы сервисов проверки доступности тоже не клики** (T-0073).
  Признак — `Referer` или User-Agent из явного списка
  `links/availability-checkers.ts` (`check-host.net`, UptimeRobot, Pingdom,
  Site24x7, HostTracker); подделать его может кто угодно, цена ошибки — один
  неучтённый клик. Проверка получает страницу 200 без кеша (`no-store`):
  общий кеш не должен отдать заглушку человеку; если приложение недоступно —
  503, как человеку, чтобы монитор видел настоящую недоступность. Отсечённый
  запрос — строка лога `availability_check_skipped` с именем сервиса. Клики с
  такими `Referer`, записанные до T-0073, остаются в базе, но в цифры ссылки
  не идут. Класс устройства на клике известен только у телефонов (данных
  клиента Telegram у клика нет), поэтому в карточке ссылки остальное стоит
  строкой «Устройство не определено».

### 3.4 Куда ведём

Цель — свойство самой ссылки, поле `target` (`35-stage4-plan.md` Р95,
T-0057); площадка — по-прежнему поле `platform`: когда игра появится на
другой площадке, целью станет её Mini App или бот.

| `target` | Через переходник `/r/<код>`, после клика | Прямая ссылка, без переходника |
|---|---|---|
| `app` (умолчание) | Mini App: `launch(platform, c-<клик>)` | `launch(platform, l-<код>)` |
| `bot` | чат с ботом, `/start c-<клик>` | чат с ботом, `/start l-<код>` |
| `landing` | `https://<домен>/?c=<клик>` | `https://<домен>/?l=<код>` |

`<домен>` — тот же, на котором живёт переходник (`20-env-and-ports.md`
§2.1). Цель меняется после создания, с записью в журнал аудита
(`links.retarget`, «было → стало»): прошлые клики остаются, новые идут
по-новому. Сеть и код не меняются никогда.

**Диплинк вместо 302** (`35-stage4-plan.md` Р94, T-0058). Цели `app` и `bot`
переходник отдаёт не 302 на `https://t.me/…` (на ПК и в части мобильных
браузеров это ещё одна страница с кнопкой «Открыть в Telegram»), а страницей:

1. скрипт сразу переходит по диплинку `tg://resolve?domain=<бот>&…` с тем же
   `c-<клик>` (`launchDeep` или `chatDeep` порта ссылок);
2. через 2,5 с, если страница всё ещё видна и окно не теряло фокус,
   `location.replace` на прежний `https://t.me/…`: открылось приложение —
   браузер теряет фокус или скрывается, и запасной переход не нужен;
3. на странице две кнопки — «Открыть в Telegram» (диплинк) и «Открыть в
   браузере» (`https://`): они работают и без скрипта, и когда автопереход не
   сработал.

`landing`, площадка без диплинков, превью для краулеров и проверки
доступности — как раньше: 302 или страница с OG-тегами. Ответ с диплинком —
`cache-control: no-store`, как у 302: клик одноразовый.

**Политика источников без `'unsafe-inline'`.** У страницы своя политика:
`default-src 'none'; script-src 'sha256-…'; frame-ancestors 'none'`. Скрипт
один и постоянный, его хэш считается от текста при загрузке модуля
(`OPEN_SCRIPT_HASH`), а адреса скрипт читает из
`<script type="application/json">` — это данные, и политика их не исполняет;
`<` в них заменён на `\u003c`, чтобы адрес с `</script>` не закрыл тег. Хэш, а
не `'unsafe-inline'`, потому что разрешение на любой встроенный скрипт
отменило бы смысл политики: один пропущенный `escapeHtml` — и страница
исполняет чужой код. У остальных ответов API политика прежняя —
`default-src 'none'`.

**Прямая ссылка** — сразу в бота или Mini App: короче и без лишней страницы,
годится для поста, описания канала, партнёра. Клика у неё нет, считаются
только запуски: параметр `l-<код ссылки>` даёт касание вида `link`, `ref` —
код ссылки, и оно такое же первое и последнее касание, как у клика (§5).
**У ссылки с сетью (§3.5) прямой ссылки нет:** сетям нужны макросы на клике
(`{click_id}` и другие), а их пишет только переходник.

В панели запуски ссылки — раздельно: «через переходник» (по её кликам) и
«прямых». Доля «клик → запуск» считается только по первым: у прямых кликов
нет.

**Через хаб** (§4) — когда площадка размещения не совпадает с целевой
платформой или неизвестна: сайт, видео, подкаст, офлайн.

### 3.5 Ссылка закупки в сети: макросы и конверсии

Реклама, купленная в сети, сама учится приводить тех, кто нам нужен, —
если сеть узнаёт, кто из пришедших зарегистрировался и заплатил
(`35-stage4-plan.md` Р86, WP43). Поэтому ссылка кампании знает сеть, где
куплена реклама. Сейчас это AdsGram; другую сеть добавляет профиль в
`backend/api/src/modules/links/link-networks.ts` и отправитель в
`modules/ad-conversions`.

**Адрес для кабинета.** Панель отдаёт адрес с макросами сети:

```
https://<домен>/r/<code>?campaign={campaign_id}&banner={banner_id}&pub={publisher_id}&clickid={click_id}&record={record_data}
```

Его вставляют в поле ссылки кампании как есть, скобки подставит сеть. Наша
ссылка — веб, через переходник, поэтому в ней есть обязательный для веба
`{record_data}`. В кампаниях Telegram Ads сеть макросы не передаёт — там
обычная ссылка.

**Клик.** Переходник берёт из запроса только параметры профиля сети:
печатные знаки, до 256 на значение. Неподставленный макрос — превью
кабинета или проверка руками — отбрасывается. Подставленное ложится на
клик (`link_click.network_params`) и обнуляется через 31 сутки: это окно
покупок с запасом на повторы отправки.

**Что уходит сети** — три цели AdsGram (`goaltype`):

| Цель | Когда | Окно от клика |
|---|---|---|
| 1 — регистрация | первый засчитанный забег: от 30 секунд, без читов, не отклонён. У ссылки можно выбрать «при первом запуске» | 7 суток |
| 2 — первая покупка | первая настоящая оплата: не тестовая, без запроса возврата, отлежалась 10 минут | 30 суток |
| 3 — повторная покупка | каждая следующая такая же | 30 суток |

Конверсия — только у **новичка**: аккаунт создан после клика, а первое
касание аккаунта — этот клик (`acquisition`, §5). Старый игрок, открывший
игру по рекламе, сети не отдаётся: его привела не она. Аккаунты команды
пишутся в журнал пропущенными — их отправляют руками, чтобы проверить
связку с кабинетом.

**Отправка** — `confirm_conversion` с токеном нашего кабинета (ключ
интеграции `adsgram.conversion-token`, `30-configuration-map.md`):

- основной вариант — `record`;
- если сеть подставила только `{campaign_id}` — вариант Telegram-ссылок:
  `tgid` и `campaignid`;
- ни того, ни другого — конверсия пропускается с причиной «нет меток».

Нет токена — конверсии ждут и уходят, когда его зададут. Сбой сети —
повтор с паузой от минуты до суток; отказ по сути — «не ушла» в журнале,
повторить можно из панели. Каждая конверсия видна в журнале ссылки
(`29-admin-panel.md`, «Ссылки»).

### 3.6 Ссылки с метками (Р116)

Ссылку в бота или Mini App с метками не нужно сначала заводить в панели:
`https://t.me/<бот>?startapp=src-tgads_cmp-oct` разбирает сервер, и первый же
игрок по ней заводит источник с пометкой «авто». Запуски считаются с первого
игрока, а не теряются в «неизвестно», пока ссылку не занесли руками
(`35-stage4-plan.md` Р116, T-0179). В панели «Ссылки» такой источник виден
с пометкой «авто», его можно переименовать и скрыть, а незнакомые ключи видны
сводкой (T-0180, ниже — «Что видно в панели»).

**Формат** — `ключ-значение_ключ-значение`:

- пары разделены `_`, ключ от значения — `-`; порядок пар и регистр не важны,
  значение хранится в нижнем регистре;
- значение — латиница и цифры, 1–24 знака, без `-` и `_` (это разделители);
  ключ — `[A-Za-z][A-Za-z0-9]{1,15}`, не короче двух знаков: однобуквенные
  приставки заняты — `c-` (клик), `l-` (прямая ссылка), `f-` (дружба),
  `n-` (уведомление);
- не больше шести пар, ключ не повторяется;
- `panel` и `role` зарезервированы — это вход в панель и подтверждение
  роли в боте (`PANEL_LOGIN_PREFIX`, `ROLE_CONFIRM_PREFIX`); строка с таким
  ключом не пары, а прежний «неизвестный» параметр;
- границы Telegram те же: до 64 знаков из `A-Za-z0-9_-`
  (`33-telegram-mini-app-pitfalls.md` §5.1), поэтому в реальной ссылке пар
  три-четыре, а не шесть.

**Ключи** — закрытый список (`attribution/start-param-pairs.ts`, `AUTO_KEYS`):

| Ключ | Что | Куда ложится у источника |
|---|---|---|
| `src` | источник | `link.source` |
| `cmp` | кампания | `link.campaign` (нет `cmp` — `auto`) |
| `plc` | место размещения | `link.medium` |
| `prt` | партнёр | `link.partner_tag` — **только метка**: ни привязки к карточке партнёра, ни начислений |

Новый ключ — это код, а не настройка: строка в `AUTO_KEYS`, поле в
`PairsResult.known`, раскладка в `links/auto-sources.service.ts` и строка в
таблице выше.

**Источник привязан к набору известных пар**, а не к одной паре:
`src-a_cmp-b` и `src-a_cmp-c` — два источника, а `cmp-b_src-a` и
`SRC-A_CMP-B` — тот же, что первый. Ключ набора — известные пары в порядке
`AUTO_KEYS` (`link.auto_key`, уникален; он же `start_ref` сессии вида
`tagged`). Незнакомые ключи в набор не входят.

**Что делает сервер.** Путь один и для Mini App (`initData.start_param`), и
для бота (`/start`): оба приходят в `announce` → `SessionRecorder`, и после
настоящей записи сессии (`recorded`, не `duplicate` от повтора задания
очереди) вызывается `AutoSourcesService.onSession`:

1. известные пары → `ensure`: источник с таким `auto_key` уже есть (в том числе
   скрытый) — ничего не меняется; иначе заводится новый, если за скользящие
   24 часа автоисточников создано меньше потолка. Создание идёт под
   `pg_advisory_xact_lock`: без него параллельные первые игроки разных ссылок
   пробили бы потолок. Заведённый ключ замка не берёт;
2. незнакомые ключи → сводка `start_param_key`: ключ, сколько раз, когда
   первый и последний раз. **Значения не хранятся.** Новые ключи добавляются,
   пока в сводке меньше 200 (`UNKNOWN_KEYS_MAX`), известные считаются всегда;
3. сбой не пробрасывается: сессия уже записана, а источник заведёт следующий
   игрок. В лог идёт исход (`auto_source`: `created`, `existing`, `capped`) и
   вид ошибки, но не значения пар — их вписывает кто угодно.

**Потолок** — настройка `links.auto-daily-cap` (панель → «Настройки» →
«Автоисточники», 0–500, по умолчанию 20; `30-configuration-map.md`). Нуль —
автосоздание выключено, и база такой сессии не видит. Сессии при потолке всё
равно записываются, а когда источник появится, запуски подхватятся: связь
с источником идёт по ключу, а не по времени.

**Чем отличается от `l-<код>`.** Прямая ссылка (§3.4) — строка `link`, которую
сначала заводят в панели и которая знает сеть, цель и владельца-партнёра.
`src-…_cmp-…` — для рекламы и постов, которые уходят в мир быстрее, чем их
заводят: сервер заводит источник сам, а команда потом даёт ему название или
скрывает. Автоисточник без сети и без владельца-партнёра: цель — Mini App,
`created_by` пуст. Ссылку закупки в сети (§3.5) и ссылку партнёра по-прежнему
заводят руками.

**Что видно в панели** (T-0180). В списке «Ссылок» автоисточник помечен «авто».
Название — `link.title`, поле для людей: в списке и карточке показывается оно, а
нет его — кампания; `campaign` и `source` не меняются, по ним идут разрезы
аналитики. Скрытие — `link.hidden_at`: скрытый источник уходит из списка
(возвращается переключателем «Показывать скрытые»), но запуски по нему
считаются как раньше, а повторный запуск по той же метке не заводит новый
источник и не снимает скрытие. Переименовать и скрыть можно только автоисточник
(`PATCH /admin/links/:code/display`, у ручной ссылки — 400), оба действия — под
`links.manage` и в аудит (`links.rename`, `links.hide`, `links.unhide`).
Сводка незнакомых ключей (`start_param_key`) — блок «Незнакомые метки» под
списком (`GET /admin/links/unknown-keys`, по убыванию последнего раза, не больше
200): только чтение, ключ добавляется правкой списка в коде.

## 4. Хаб-страница

Страница на сайте с кнопками «Играть в Telegram», «в MAX», «в VK» и
«в браузере».

**Главное свойство: атрибуция не теряется при выборе платформы.** Каждая
кнопка уже несёт тот же самый `click_id`, полученный на редиректе. Игрок
может открыть VK вместо Telegram — источник, кампания и партнёр останутся
теми же.

Дополнительно:

- порядок и подсветка кнопок подстраиваются под устройство: на iOS сначала
  то, что там реально работает;
- выбор платформы пишется событием `hub_platform_chosen` — это данные о
  том, какая площадка нужна аудитории конкретного канала, и они влияют на
  приоритет портирования;
- хаб — часть веб-версии (`08-web-and-identity.md`), не отдельный продукт;
- ссылка может вести и **в бота**, а не в игру: `t.me/<бот>?start=<параметр>`;
  домен ссылок, которые собирает сервер, задаёт настройка `telegram.link-host`
  (`t.me`, `telegram.me` или `telegram.dog`, `Р100`), ссылка кампании строится при
  клике — переключение действует сразу, а разосланные ссылки не меняются.
  `/start` заводит аккаунт сразу, и параметр становится касанием так же, как
  `startapp` у приложения (`35-stage4-plan.md`, Р29) — кампанию, которая
  прогревает людей в боте, воронка посчитает от первого сообщения;
- кнопка «в браузере» ведёт в гостевую игру без входа
  (`08-web-and-identity.md` §7): код клика приходит туда параметром адреса,
  и атрибуция не теряется даже у того, кто не стал ставить мини-приложение.

## 5. Связывание клика с игроком

1. Клиент при первом запуске читает параметр запуска платформы и передаёт
   его на бэкенд вместе с данными авторизации. В Telegram параметр уже
   лежит в подписанном `initData` (`start_param`), и сервер берёт его
   оттуда, а не из тела запроса. Клик в параметре — `c-<код>`, код из 6–32
   латинских букв и цифр: формат занят заранее, чтобы запуски по будущим
   редирект-ссылкам узнавались с первого дня
   (`backend/api/src/modules/attribution/start-param.ts`). Прямая ссылка
   (§3.4) — `l-<код ссылки>`, код проверяется тем же правилом, что `/r/<код>`
   (`links/link-code.ts`); вид `link`, в `ref` — код ссылки, а не клика,
   поэтому шаг 2 для неё не нужен.
   Ссылка с метками (§3.6) — `src-…_cmp-…`, вид `tagged`: в `ref` канонический
   набор известных пар (`link.auto_key`), в `start_param` — строка как пришла;
   клика и шага 2 у неё нет.
2. Сервер находит строку клика по `click_id`, проверяет срок жизни
   (гипотеза — 30 суток: дольше связь между кликом и запуском
   недостоверна).
3. Применяет правила приоритета атрибуции
   (`23-referral-and-partner-program.md` §5). Если у ссылки клика или
   прямой ссылки есть владелец-партнёр, здесь же игрок записывается за ним
   — по первому входу, при активном партнёре, аккаунте в окне привязки и
   свободном слоте источника; запись помнит код ссылки
   (`partner_binding.link_code`) и идёт сразу после записи сессии, а её
   сбой сессию не откатывает.
4. Пишет `Session` и `Acquisition` — модели уже описаны в
   `13-reuse-from-vpnsibcom.md` §6, здесь они получают ещё и `click_id`.
5. Порождает события `app_first_open` и `user_registered` с приложенным
   снимком атрибуции (`22-analytics-and-metrics.md` §3.1).

**Устойчивость.** Параметр запуска теряется чаще, чем кажется: игрок открыл
ссылку, отвлёкся, вернулся в приложение из истории. Поэтому: клик живёт 30
суток, а промокод (`23-...` §3) — способ восстановить атрибуцию вручную,
когда параметр не дошёл.

## 6. Антифрод и приватность

**Сигналы, ради которых всё и собирается:**

- клики без последующих запусков — доля и её всплески;
- много кликов с одного IP или подсети за короткое время;
- одинаковый отпечаток устройства у «разных» игроков;
- аномально быстрая цепочка клик → регистрация → платёж;
- `Referer` с ферм и агрегаторов;
- расхождение между заявленным клиентом временем и серверным.

Сырые данные хранятся ограниченный срок, затем усечённый IP и хэш
(`22-analytics-and-metrics.md` §7).

**Приватность.** IP и User-Agent — персональные данные; юридическая сторона
отмечена как требующая проверки юристом (`03-notes-and-risks.md`). Правила:
собираем только то, что используется в конкретных проверках и отчётах;
партнёрам и игрокам сырые данные не показываем; данные клика не связываем с
профилем глубже, чем нужно для атрибуции.

Сети уходит только то, что она сама дала: `record` с клика и номер её же
кампании. Telegram ID — лишь в варианте Telegram-ссылок, где сеть сама
показала рекламу этому пользователю в Telegram. Макросы на клике
обнуляются через 31 сутки (§3.5).

## 7. Виральный шеринг

Обратный виток: игрок сам порождает ссылки. Это дешевле любого закупленного
трафика и единственный масштабируемый источник роста при K ≥ 1
(`22-analytics-and-metrics.md` §5.6).

### 7.1 Чем делятся

**Результат забега.** Карточка со счётом, достигнутой волной, персонажем,
временем. Уместна сразу после забега.

**Карточка профиля («престиж»).** Уровень аккаунта, персонаж, снаряжение,
ключевая статистика, титулы и достижения — то, что описано в
`10-progression-and-ladder.md`. Это объект хвастовства, а не отчёт: игрок
делится им, потому что им приятно обладать.

**Оформление карточки зависит от статистики.** Рамка, фон, эффекты
меняются с уровнем, лигой, редкими достижениями. Смысл двойной: во-первых,
это награда, которую видно другим; во-вторых, разные карточки дают
естественный A/B — видно, какое оформление приводит больше переходов.

Варианты оформления — данные, а не код: набор, условия получения и тексты
настраиваются в админке (`19-content-admin.md`).

### 7.2 Куда делятся

Набор каналов определяется платформой и здравым смыслом — не все варианты
уместны везде.

| Платформа | Каналы |
|---|---|
| Telegram | Пересылка в чат, история (stories), inline-шеринг |
| MAX | По возможностям площадки — уточнить при портировании |
| VK | Стена, история, личное сообщение |
| Веб | Системное меню «Поделиться», копирование ссылки, скачивание картинки |

Правило: если площадка даёт нативный формат историй — используем его.
История видна широкому кругу без адресного выбора получателя, а это
единственный по-настоящему массовый канал из перечисленных.

### 7.3 Как устроена расшаренная ссылка

**Каждый шеринг порождает собственную ссылку** со своим `code` — не общую
реферальную ссылку игрока. Это даёт:

- измеримость: видно, что конвертит лучше — результат забега или карточка
  профиля, какой канал, какое оформление;
- защиту: скомпрометированную или накрученную ссылку можно погасить, не
  трогая остальные;
- контекст: по ссылке из результата забега приглашённого можно встретить
  соответствующим экраном.

При этом реферальная привязка остаётся привязкой к игроку: в строке ссылки
хранится и `ref_id`, и тип шеринга.

### 7.4 Картинка

Генерируем **на сервере**, кешируем по хэшу параметров, отдаём с CDN.

Причины: истории требуют конкретных пропорций и предсказуемого рендера;
OG-превью в мессенджерах в любом случае требует серверной картинки; на
слабых Android генерация на клиенте отнимает кадры у игрового цикла — а
производительность WebView и есть главный технический риск
(`01-tech-stack.md` §8).

Кеш обязателен: одна и та же карточка профиля запрашивается многократно, а
рендер — самая дорогая операция во всём потоке.

### 7.5 Текст

Маркетинговый текст — **данные, а не строка в коде**: варианты лежат в
конфигурации, локализуются, участвуют в A/B (`19-content-admin.md`).
Тексты пишутся под канал: то, что уместно в личном сообщении другу, плохо
работает в истории.

### 7.6 Когда предлагать

Момент важнее оформления.

- После **личного рекорда** — не после каждого забега.
- После получения редкого предмета или уровня, то есть в момент, когда есть
  чем хвастаться.
- Никогда не блокируя путь игрока: предложение поделиться, которое надо
  закрыть, чтобы продолжить, воспринимается как реклама.

Навязчивый шеринг стоит не только раздражения: площадки рассматривают
агрессивные механики распространения как повод для санкций при модерации
(`09-ci-cd.md` §4).

### 7.7 Что работает сейчас

Пока карточки результата нет, «Поделиться» на экране итогов забега идёт
путём приглашения друга (`35-stage4-plan.md` Р63): выбор чата со ссылкой и
строкой о забеге — «Мой рубеж — 7:42. Сможешь продержаться дольше?», у
рекорда — «Новый рекорд на рубеже…». С входом ссылка — дружбы
(`POST /api/v1/friends/link`), и позванный по итогу засчитывается так же, как
позванный из «Друзей»; без входа — просто ссылка на игру. В браузере — системный
лист или копия ссылки, под кнопками строка о том, что вышло. Без бота площадки
(сборки VK и MAX) кнопка честно говорит, что делиться можно в сборке для
Telegram, а не молчит. События — `share_offered` и `share_completed` с
`context: run_result` (`22-analytics-and-metrics.md`).

Код — `packages/app-shell/src/state/run-share.ts`, грузится по нажатию: чанк
забега на пределе бюджета. От §7.1–7.6 пока нет картинки, своей ссылки на
каждый шеринг, текста-данных и выбора момента — это остаётся работой этапа 4;
метод адаптера `share()` для неё зарезервирован и пока пуст.

## 8. Что попадает в аналитику

События `link_clicked`, `redirect_served`, `hub_platform_chosen`,
`app_first_open`, `share_offered`, `share_completed`, `shared_link_opened`
(`22-analytics-and-metrics.md` §3.3).

Конверсии, отданные сети (§3.5), — таблицей `ad_conversion`, а не
событием: это журнал и очередь отправки сразу, как `ad_session` у показов
рекламы.

Запуск по прямой ссылке (§3.4) — та же сессия и то же касание, только вида
`link`: новых имён событий нет. В ежедневный отчёт в чат команды источник
`link` пока не входит в разбивку и попадает в «неизвестно»
(`tasks/inbox.md`).

Запуск по ссылке с метками (§3.6) — тоже та же сессия и то же касание, вида
`tagged`, с каноническим набором пар в `start_ref`: новых имён событий нет.
Автоисточник — строка `link` с `auto = true`, незнакомые ключи — таблица
`start_param_key`. В ежедневный отчёт в чат команды вид `tagged` попадает в
«неизвестно», как `link`.

Считаем: клики и их источники, конверсию клик → запуск → регистрация,
долю кликов без запусков, время до запуска, распределение по платформам с
хаба, принятие предложения поделиться, обратные переходы и их конверсию,
эффективность вариантов карточки и текста.
