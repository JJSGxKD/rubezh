# Редактор контента и баланса для геймдизайнера

> **С этапа 2 редактор — модуль единой админ-панели** (`29-admin-panel.md`):
> вход, роли, аудит и аналитика общие для всех модулей. Правила этого
> документа — рантайм-изменения, рельсы публикации, цены, откат — остаются в
> силе; «отдельное приложение» в §8 означает приложение админ-панели, а не
> отдельный редактор.

## 1. Зачем это нужно и почему это не «приятно иметь»

В роадмапе этап 5 (софт-лонч) содержит пункт **«быстрые итерации по балансу
на основе реальных данных»**. Как проект устроен сейчас, этот пункт
невыполним: баланс лежит в файлах `content/*`, попадает в бандл при сборке, и
любая правка означает новый билд клиента. А новый билд на MAX и VK проходит
модерацию площадки — до нескольких дней (`09-ci-cd.md` §4). «Быстрая итерация»
превращается в цикл длиной в неделю.

Отсюда решение: **балансные и экономические параметры должны меняться в
рантайме, без пересборки клиента и без модерации.** Это не удобство для
геймдизайнера — это условие, при котором софт-лонч вообще имеет смысл.

Второй мотив — разделение ролей. `06-team-and-workflow.md` отводит контент
геймдизайнеру, но сейчас его правка обязательно проходит через git, PR и
ревью программиста. Для опечатки в числе это неоправданно дорого с обеих
сторон.

## 2. Что можно менять в рантайме, а что нельзя

Ключевое разделение, из которого следует всё остальное.

| Категория | Примеры | Меняется в рантайме |
|---|---|---|
| **Числа и таблицы** | hp/скорость/урон врагов, состав и тайминг волн, значения апгрейдов, цены SKU, награды за рекламу, кулдауны, проценты рефералки, пороги прогрессии | **да**, через админку |
| **Композиция из существующих кирпичей** | новый враг на существующем паттерне, новая волна, новый уровень из имеющихся ассетов и механик, новый набор апгрейдов | **да**, через админку |
| **Ассеты** | спрайт нового врага, тайлсет уровня | **да**, если загружены на CDN и конфиг ссылается по URL |
| **Параметры программ роста** | порог активации реферала, размеры наград и вехи, проценты RevShare, hold-период, окна промокодов, пороги антифрода, тексты и оформление приглашений | **да** (`23-referral-and-partner-program.md` §7, `24-attribution-and-sharing.md` §7.5) |
| **Новое поведение** | принципиально новый паттерн движения, новый тип эффекта апгрейда, новая механика уровня | **нет** — это код, задача владельца |
| **Структура данных** | новое поле у врага, новая сущность | **нет** — миграция схемы + релиз клиента |

Правило формулируется просто: **админка меняет значения и композицию, но не
вводит новых понятий.** Как только нужно новое понятие — это код, релиз и
модерация.

Важное следствие для дизайна игры: чем больше механик выражено параметрами, а
не ветвлениями в коде, тем больше можно менять без релиза. Это прямое
продолжение принципа «контент как данные» (`01-tech-stack.md` §9) — просто
доведённое до рантайма.

## 3. Архитектура

```
Админка (браузер)
   │  черновик, валидация, прогон симуляции
   ▼
Бэкенд: модуль content
   │  версии конфигурации в Postgres (источник истины)
   │  публикация → неизменяемый снапшот
   ▼
Снапшот по хэшу /content/v/<хэш>.json  ──►  CDN (адрес по хэшу, кеш вечный)
   │
   ▼
Клиент: GET /content/current?schema=<n> отдаёт номер, хэш и URL версии
```

Решения и их причины:

- **Источник истины — Postgres.** Каждая правка — строка с автором, временем
  и содержимым. История и аудит бесплатны (`15-engineering-standards.md` §9).
- **Публикация создаёт неизменяемый снапшот с номером версии.** Не «правим
  живой конфиг», а «выпускаем версию N+1». Это то, что делает откат
  мгновенным: откат — это указание на предыдущую версию, а не обратная правка.
- **Клиент забирает конфиг со статики, а не из API.** Конфиг одинаков для
  всех, и незачем на каждый заход ходить в приложение
  (`14-scalability.md` §5). `GET /content/current` отдаёт только номер версии,
  хэш и URL — это один запрос по индексу, а сам снимок кешируется навсегда.
- **Ассеты по URL из конфига.** Тогда новый уровень с новым спрайтом
  выкатывается без пересборки клиента: спрайт кладётся на CDN, конфиг на него
  ссылается. Это заметно расширяет объём того, что можно делать без модерации.

### Снимок контента `ContentSnapshot`

Основа песочницы редактора (фаза 1, шаг 1; `35-stage4-plan.md`, Р16, T-0301):
весь контент, который влияет на забег, — одним объектом, а не импортом из
`content/*`.

| Что | Где |
|---|---|
| Тип и снимок по умолчанию `CONTENT_SNAPSHOT` (собран из `content/*`, они остаются источником и эталоном golden-тестов) | `packages/core-game/src/content/snapshot.ts` |
| Хэш снимка `hashSnapshot`; для умолчания равен `CONTENT_HASH`, считается по полям забега в порядке типа, версия схемы и коридоры в него не входят | там же, `content/hash.ts` |
| Схема Zod `contentSnapshotSchema` и JSON-схема `contentSnapshotJsonSchema()`: форма, обязательные поля, знак и целость чисел; опечатка в имени поля — ошибка | `content/snapshot-schema.ts` |
| Проверки контента `findContentProblems(snapshot)` → `[{ path, message }]`; `path` — имя раздела снимка (`enemies`, `timeline`, …), сообщение по-русски; не бросает на неполном снимке | `game/content-problems.ts` (в `game/`: проверки знают код движка, а `content/` о нём знать не должен). Из `index.ts` пакета не экспортируется: статический экспорт утащил бы код симуляции в первую загрузку оболочки (+15 КБ при бюджете 185); оболочка получит проверки вместе с движком, отдельным чанком |
| Движок: `RunOptions.content?`; хэш чужого снимка уходит в итог забега вместо `CONTENT_HASH` | `run-api.ts`, `game/run-world.ts` |
| Бот калибровки: `BalanceRunOptions.content?` | `game/balance/simulate.ts` |

Без поля `content` забег побитно прежний. Хэш считается по порядку ключей
`JSON.stringify`: копия через `JSON.parse` порядок сохраняет, а разбор схемой
и хранилище с сортировкой ключей (jsonb) — нет, поэтому хэш считают по
снимку до такого пути и хранят рядом с ним.

**Выгрузка:** `pnpm content:export [--out <каталог>]` кладёт в `dist/` (вне git)
четыре файла: `content-snapshot.json` (из него сервер заводит версию 0),
`content-snapshot.schema.json` (ею сервер проверяет форму правки, не
импортируя пакеты игры), `content-names.json` (тексты `nameKey`,
`descriptionKey` и имён врагов из словаря оболочки — панель показывает имена,
а не id; ключи без текста скрипт перечисляет в предупреждении) и
`content-hash.json` (`hashSnapshot` снимка: тот же `content_hash`, что игра
пишет в итог забега; сервер сам его не посчитает — в хэш входят рубеж и пролог,
которых в снимке нет).

### Версии и черновики на сервере (песочница, шаг 1)

Реализовано в `T-0303`; публикация и выдача версии клиенту — `T-0306` (ниже,
«Публикация и выдача версии»), загрузка версии клиентом — `T-0307`. Таблицы —
`content_version`, `content_draft`, `content_check`, `content_current`
(`21-diagrams.md`), модуль — `backend/api/src/modules/content`, маршруты —
`/api/v1/admin/content` (`29-admin-panel.md` §5.8).

- **Версия 0 — из репозитория.** `pnpm --filter backend-api content:import
  <каталог выгрузки или content-snapshot.json>` (в контейнере —
  `node dist/cli/content-import.js <путь>`) читает четыре файла выгрузки,
  проверяет снимок его же схемой и заводит версию с источником `repo`. Тот же
  `content_hash` — ничего не меняется, номер версии не тратится: выкат можно
  повторять. Код-PR, меняющий `content/*`, после выката заводит новую версию той
  же командой (шаг деплоя `deploy.yml`, см. «Публикация и выдача версии»).
- **Черновик — копия снимка версии.** Основа — последняя версия или названная
  в запросе; название до 80 знаков; открытых черновиков не больше 100 (архив
  освобождает место). Версию-основу черновик не меняет.
- **Правка — по пути.** `PATCH /drafts/:id` с телом `{ path, value }`:
  `enemies[id=swarm_rat].hp`, `timeline[3].spawns[0].perSec`, `levelCurve.growth`.
  Звено — ключ, `[3]` (индекс) или `[id=…]` (элемент списка по значению поля);
  заменить можно число, объект целиком или элемент списка, добавить — поле
  объекта, добавить или убрать элемент списка нельзя. Значение до 32 КБ. Снимок
  после правки целиком проверяется JSON Schema версии-основы (серверный
  проверяющий знает только слова, которые строит Zod, и на незнакомом падает,
  а не пропускает); не та форма или путь в никуда — `422` с путём до поля
  (`enemies[id=swarm_rat].hp: должно быть больше 0`), черновик не меняется.
  Ссылочная целостность и бюджеты — не здесь, а в проверке воркера.
  Правки под блокировкой строки: два редактора не затирают друг друга.
- **Проверка.** `POST /drafts/:id/check` ставит задание `content-check` с
  черновиком и базой (`sim-worker`, `4.3`); ответ — `{ check, reused }`.
  Итог — `GET /checks/:id` (`queued` → `done` | `timeout` | `failed`; `report` —
  итог воркера: `schemaProblems`, `contentProblems`, медианы, дельты и коридоры
  по сценариям). Повтор с тем же снимком (`snapshot_hash` — sha256
  канонического JSON, порядок ключей jsonb его не меняет) отдаёт прошлую
  проверку без нового прогона; упавшая проверка не считается. Не чаще 10
  проверок за 10 минут на человека (`ADMIN_LIMITS.contentCheck`); очередь —
  не больше 5 ждущих, снимок до 2 МБ (пределы воркера). Проверка, которую
  воркер не взял за 15 минут или итог которой пропал из Redis (он хранится
  час), становится `failed` — повторить её можно.
- **Разница.** `GET /drafts/:id/diff` → `[{ path, from, to }]` против версии-
  основы: только изменённые пути, список объектов с `id` сравнивается по `id`
  (добавленный и убранный враг — отдельные строки); `null` в `from` — поля не
  было, в `to` — в черновике его нет. Путь из разницы принимается правкой.
- **Права и аудит.** Читать (версии, черновики, разница, итог проверки) —
  `content.view`, создавать, править, архивировать и проверять — `content.edit`;
  цены и награды — `sku.price.edit` (`T-0309`). В аудит идут создание черновика,
  правка (путь, было → стало), запуск проверки, архив и импорт версии.

### Публикация и выдача версии (шаг 2)

Реализовано в `T-0306`. Черновик становится версией игры: сначала её получают
аккаунты команды, потом все. Загрузку версии клиентом делает `T-0307`.

- **Указатель «что в игре»** — таблица `content_current`: не больше одной
  строки на аудиторию, `team` или `all`, с номером версии, автором и временем.
  Нет строки `team` — команда играет версией «всем»; нет строки `all` — ничего
  не публиковалось, и клиент играет встроенным контентом. Публикация «Всем»
  ставит оба указателя. Версия, на которую указывает строка, из базы не
  удаляется.
- **Условия публикации** — право `content.publish` и свежая зелёная проверка
  **того же снимка** (`snapshot_hash`): проверка готова (`done`), нет проблем
  схемы и контента, симуляция уложилась во время и все посчитанные метрики в
  коридорах (хотя бы одна метрика посчитана). Иначе — `409
  content_check_required` с причиной: «проверки не было», «черновик менялся
  после проверки», «метрика вне коридора: …». Те же шаги, что у рельсов панели
  (§4.3), только на сервере. Форму снимка (`schemaVersion`) панель не меняет: её
  меняет код.
- **Обход проверки** — только ключом панели `content.publish-require-check =
  false` (умолчание — включён; группа «Баланс игры», `docs/30`). Он нужен на
  случай, когда проверку не запустить, а баланс нужно поправить срочно; каждая
  публикация в обход помечается в аудите (`checkBypassed`).
- **Публикация** публикует тот снимок, что прочитан из базы один раз: по его
  отпечатку ищется проверка и из него же заводится версия (`source: panel`,
  `published_at`, хэш — sha256 канонического JSON: хэш движка сервер посчитать
  не может). Версия и указатель — одна транзакция. Идемпотентность — от
  отпечатка: тот же снимок второй раз версию не заводит («Команде», потом
  «Всем» — одна версия), две публикации разом дают одну версию — её держит
  уникальный хэш в базе, а Redis-замок (`content:publish:lock`, 30 с, ожидание
  до 5 с, иначе `409 content_publish_busy`) упорядочивает публикации и откаты
  между репликами.
- **Откат** — «Откатить на v{N}»: указатель аудитории на версию, что уже
  бывала в игре (`published_at` задан). Новой версии не заводит, записывается в
  аудит. Откат «Всем» команду не трогает, и наоборот. Откатывать «Всем» нечего,
  пока ничего не публиковалось.
- **Версия для клиента** — `GET /api/v1/content/current?schema=<n>` под
  токеном игрока: `{ versionNo, hash, url }` или `null` (играть встроенным).
  Аудиторию сервер берёт из сессии: аккаунт с ролью — команда; параметра в
  запросе нет, иначе любой игрок получил бы версию, которую смотрит только
  команда. Версия — та, что в игре у аудитории; если её форма новее клиента
  (`schema_version > n`) — последняя из бывших в игре, не новее неё, с формой не
  выше клиентской (§5).
- **Снимок по адресу** — `GET /api/v1/content/v/<хэш>.json`: тело — сам снимок
  без конверта, `Cache-Control: public, max-age=31536000, immutable`, `ETag`
  по хэшу (повторный вопрос — `304`). Отдаются только версии, что бывали в игре;
  черновики и ждущие версии «из кода» — нет. Сжатие и раздачу CDN даёт край:
  Caddy сжимает ответы API (`encode zstd gzip`), а ответ с вечным кешем CDN
  снимает с сервера, как картинки из панели.
- **Версии из репозитория при выкате.** Шаг `deploy.yml` после выката
  выгружает контент релиза (`pnpm content:export`) и заводит версию командой
  `content:import` в контейнере API (`docs/09` §10). Версия `repo` становится
  текущей у аудитории, только если текущая версия у неё тоже `repo` (или её нет —
  до первой публикации из панели). Иначе она ставится рядом и показывается в
  «Истории» как «из кода — новое понятие»; её поля сливает в черновик «Взять из
  кода»: новые `id` и поля добавляются, значения существующих не меняются, а
  основа черновика переезжает на версию из кода — дальше правки проверяются её
  схемой.
- **Права и аудит.** `content.publish` — публикация и откат (геймдизайнер и
  владелец), `content.view` — указатели и предпросмотр, `content.edit` — «Взять
  из кода». В аудит идут `content.publish` (аудитория, версия, хэш, прежняя
  версия), `content.rollback`, `content.draft.merge-code`, а от системы —
  `content.version.adopt` (подхват версии из кода выкатом).

## 4. Защитные механизмы

Редактирование баланса в проде без рельсов — способ уронить игру одним
неверным нулём. Рельсы обязательны, и их пять.

### 4.1 Валидация схемой

Черновик проверяется теми же Zod-схемами, что и данные в коде
(`16-tech-stack-decisions.md` §6). Невалидное значение нельзя сохранить —
не «сохраним и предупредим», а именно нельзя.

### 4.2 Ссылочная целостность

Те же проверки, что в тестах контента (`17-testing-strategy.md` §3.1): враг из
волны существует, `pattern` реализован в коде **этой версии клиента**, нет
дублирующихся `id`, `second` в волнах монотонен. Ссылка на несуществующий
паттерн — самая вероятная ошибка при работе через UI, и она обязана
отлавливаться до публикации.

### 4.3 Прогон симуляции перед публикацией — главный рельс

Здесь окупается требование детерминизма игрового цикла
(`15-engineering-standards.md` §2.4). Перед публикацией сервер прогоняет
**golden-сценарии** (`17-testing-strategy.md` §3.2) на черновике конфигурации и
показывает дельту:

```
Черновик vs версия 47
  пассивный игрок:      волна 8  → волна 6   (-2)
  агрессивный:          волна 14 → волна 13  (-1)
  билд на урон:         волна 19 → волна 19  ( 0)
  время до 1-й смерти:  2:10     → 1:40      (в коридоре)
```

Геймдизайнер видит последствие правки **до** того, как её увидят игроки. Это
то же самое, что golden-тесты дают в CI, только доступное человеку, который не
открывает git.

**Как это видно в панели** (`tasks/T-0305`). В «Балансе» справа — панель
«Симуляция: черновик против v{N}»: проверки схемы и контента галочками (✗ ведёт
к записи в таблице), метрики ботов полосами с коридором баланса и двумя метками
— версия в игре и черновик — и справа «1:12 → 1:18 ✓», «· у края» (в пределах
10 % от границы коридора) или «✗ вне коридора». В шапке — рельсы «Схема →
Проверки → Симуляция». Правка после прогона помечает его «устарела»: «Проверить
снова». Кнопки «Команде» и «Всем» (`T-0306`) оживают, только когда все шаги
зелёные и прогон свежий; сервер проверяет то же самое ещё раз (§3, «Публикация
и выдача версии»).

Проверка обязательна: ключ панели `content.publish-require-check` по умолчанию
включён. Выключение — осознанное временное действие; каждая публикация в
обход проверки попадает в аудит с пометкой.

Дополнительно проверяются свойства баланса (`17-testing-strategy.md` §3.3):
кривая сложности не убывает, пассивный игрок гарантированно умирает, ни один
апгрейд не даёт бесконечного роста параметра.

### 4.4 Staging перед production — «Команде», потом «Всем»

Публикация идёт в два шага: сначала версию получают только аккаунты команды —
посмотреть глазами в настоящем клиенте, — потом все. Один и тот же черновик,
две публикации; вторая версии не заводит, а только переставляет указатель.

Отдельной базы staging нет: версия лежит в той же базе, что и прод, а «команда»
— это аккаунты с ролью (`account_role`). Так проверяется то, что важнее всего:
как версия играется в живом клиенте, на живом профиле. Устройство — §3,
«Публикация и выдача версии». «Всем» в панели открывает окно со списком правок
против версии, которая сейчас в игре, и предупреждает, если команда эту версию
ещё не смотрела.

### 4.5 Откат и постепенный выкат

- **Откат** — переключение на предыдущую версию, секунды. Отдельная кнопка
  «Откатить» в «Истории», а не «поправьте обратно руками»: указатель аудитории
  возвращается на версию, что уже бывала в игре, новой версии откат не заводит
  и пишется в аудит. Игроки получат версию при следующем входе в игру.
- **Постепенный выкат** (фаза 2): новая версия конфигурации отдаётся доле игроков
  (10% → 50% → 100%). Метрики сравниваются между группами. Это же механизм
  A/B-тестов баланса после лонча. Первая ступень уже есть — «Команде».
- Постепенный выкат — частный случай feature flag, а флаг для всего рискового
  обязателен, потому что версию в сторе площадки быстро не откатить
  (`09-ci-cd.md` §11).

## 5. Совместимость со старыми клиентами

Из-за модерации площадок одновременно живут несколько версий клиента. Конфиг
это учитывает, иначе публикация сломает тех, кто ещё не обновился.

- У конфигурации есть **версия схемы**, у клиента — диапазон схем, которые он
  понимает.
- Сервер отдаёт клиенту (`GET /api/v1/content/current?schema=<n>`) **последнюю
  версию конфигурации, совместимую с его схемой**, а не просто последнюю: версию,
  что в игре у его аудитории, если её схема не выше `n`, иначе — последнюю из
  бывших в игре, не новее неё, с `schema_version ≤ n`. Нет такой — `null`, и
  клиент играет встроенным контентом.
- Изменения конфигурации **аддитивны** по умолчанию; удаление поля или
  сущности — это смена версии схемы, а не обычная правка.
- Правило то же, что для БД и API: **expand → migrate → contract**
  (`15-engineering-standards.md` §3, §10).

Практический вывод для геймдизайнера: удалить врага из данных нельзя, пока
живут клиенты, которые его знают, — сначала он убирается из волн, и только
потом, через релиз, из справочника.

## 6. Цены и деньги — отдельный режим

Цены меняются через ту же админку, но с дополнительными правилами:

- **Цена — серверная величина.** Клиент её только показывает; при покупке
  сервер берёт цену из конфигурации сам. Клиент, заявляющий цену, —
  заявление, а не факт (`15-engineering-standards.md` §7.1).
- **Экономика по платформам раздельна.** Stars и рубли — два независимых
  набора значений, не конвертация по курсу (`03-notes-and-risks.md`).
- **Правка цены требует подтверждения второго участника.** Не потому что
  геймдизайнеру не доверяют, а потому что ошибка в цене — прямой финансовый
  эффект без права на «сейчас поправлю». Как это устроено — ниже, «Как
  подтверждается правка».
- **Только фиксированные цены.** Никакого рандома в монетизации — лутбоксы и
  гача исключены сознательно и по регуляторным причинам
  (`03-notes-and-risks.md`, `07-monetization-and-ads.md`).
- Если площадка требует предварительной регистрации SKU на своей стороне,
  админка не может создать новый SKU одна — этот шаг остаётся ручным и
  описывается в чек-листе релиза.

### Как подтверждается правка (`T-0309`)

Каталог товаров остаётся в коде (`shop/shop-catalog.ts`), а правку команды
панель кладёт **поверх него** (`shop_sku_override`) — и только заявкой:

1. **Заявка.** Человек с правом `sku.price.edit` предлагает «было → стало» с
   причиной (обязательна, до 200 знаков). «Было» берёт сервер из товара с уже
   действующей правкой; то, что не меняется, из заявки убирается. Правятся цена
   в звёздах и в рублях, самоцветы состава, значок «Хит» и порядок; `id`, вид и
   «один на аккаунт» — нет: новый товар — код. Итог проверяется той же
   `shopSkuSchema`, что и каталог, поэтому цена 0 не пройдёт.
2. **Подтверждение.** Подтверждает **другой** человек с тем же правом — владелец
   или геймдизайнер; автор свою заявку не решает (даже владелец), а может её
   отозвать. Подтверждение и применение — одна транзакция под блокировкой цели:
   правка кладётся, только если цель всё ещё равна «было». Изменилась (выкат с
   новой ценой, правка руками) — 409, заявка `superseded`, цена не тронута.
3. **Срок и очередь.** Заявка живёт 72 часа, потом `expired`. Живая заявка на
   цель одна: новая гасит прежнюю (`superseded`).
4. **Счёт игрока.** Цена серверная и в счёте записана: покупка, начатая до
   правки, оплачивается по цене счёта, новые счета и витрина берут новую (кэш
   реплики — до 10 секунд). Изменили состав набора — тексты в окне оплаты
   пересобираются по новому числу самоцветов.
5. **Уведомление и аудит.** Участники с правом получают строку ленты, общий чат
   админов — сообщение; в аудит идут заявка, подтверждение, отклонение, отзыв и
   применение.

Механизм общий: числа наград (T-0310) идут теми же заявками, отличается только
вид правки. Экран и маршруты — `29-admin-panel.md` §5.8.

### Награды числами (`T-0310`)

Награда — та же валюта, что продаётся за звёзды, поэтому правило то же, что у
цен. Награды за забег, за уровень аккаунта и награда дня — **ключи каталога
настроек с пометкой «деньги»** (`money: true` в `settings/setting-catalog.ts`,
группа «Награды»); умолчание ключа — прежнее постоянное в коде:

| Ключ | Что | Умолчание |
|---|---|---|
| `rewards.run-max-coins` | потолок монет за забег | `MAX_COINS_PER_RUN` (600) |
| `rewards.run-max-xp` | потолок опыта за забег | `MAX_XP_PER_RUN` (1 500) |
| `rewards.run-min-sec` | забег короче — без награды | `MIN_REWARDED_SEC` (30) |
| `rewards.level-ladder` | награды за уровень списком ступеней «с уровня:монет за уровень:самоцветов:раз в сколько уровней», через «;» | `1:50:10:5` — прежняя формула |
| `rewards.daily-ladder` | основа награды дня: семь дней «монеты/осколки» через запятую | `60/0, 80/0, 100/0, 120/0, 150/0, 180/0, 300/10` |

- **Правка ключа «деньги» — только заявкой** вида `reward_setting`: подаёт и
  подтверждает человек с `sku.price.edit`, подтверждает другой. Обычная правка
  настроек (`POST /admin/settings/:key`) и сброс к умолчанию для такого ключа
  отвечают `409 change_request_required`. Значение проверяется схемой ключа до
  заявки (пределы чисел, формат лестниц), лестницы хранятся в каноническом виде.
- **Действует со следующей награды.** Подтверждённое значение ложится в
  `app_setting` одной транзакцией с подтверждением; сервер читает ключ на каждом
  начислении, начисленное не пересчитывается. Забег, поставленный в очередь до
  правки, считается по числам на момент начисления.
- **Потолки кошелька остаются в коде** (`wallet/wallet-limits.ts`): это защита от
  ошибки, а не настройка. Награда выше суточного потолка заводится, но в заявке
  предупреждение «Выше суточного потолка — часть не начислится»: его видят и
  автор, и подтверждающий.
- **Не ключи:** множители сложности `DIFFICULTY_REWARD_MUL` (сложность одна, Р126),
  множитель победы над стражем, множитель недели и уровня награды дня — они
  по-прежнему в `progress-rules.ts` и `daily-rules.ts`.

## 7. Git против БД: где источник истины

После подключения админки источник истины для **значений** — БД. Но история и
восстановление должны оставаться в git, иначе потеря БД означает потерю всего
баланса.

Решение: **каждая публикация автоматически экспортирует снапшот в
репозиторий** отдельным коммитом. Что это даёт:

- история баланса читается через `git log` и `git diff`, как всё остальное;
- восстановление после потери БД — из репозитория;
- golden-эталоны и снапшоты лежат рядом и не расходятся.

Рассматривали обратную схему — правка в админке создаёт PR, и источником
истины остаётся git. Отклонена: она возвращает нас к циклу «ревью + CI +
деплой» и убивает главную цель (§1). Ревью баланса заменяется прогоном
симуляции (§4.3) и постепенным выкатом (§4.5) — для чисел это работает лучше,
чем чтение диффа человеком.

## 8. Доступ и безопасность

- **Вход через Telegram**, не через логин и пароль: идентичность даёт
  платформа, хранить пароли — риск без пользы (`08-web-and-identity.md`).
- **Два рубежа**: `ADMIN_TELEGRAM_IDS` в конфигурации окружения **и** роль в
  БД. Ни один из них не единственный.
- Админка — **отдельное приложение** на отдельном поддомене за Caddy, не
  раздел игрового клиента. Игровой бандл не должен содержать ни строчки
  админского кода.
- **Полный аудит**: кто, когда, что изменил, какая версия опубликована, кто
  откатил. Аудит не редактируется из интерфейса.
- Публикация — изменяющая операция: идемпотентность по ключу черновика,
  лимит частоты, лок (`15-engineering-standards.md` §4).
- Права разделены: геймдизайнер правит баланс и контент; цены — с
  подтверждением второго участника (§6); флаги и постепенный выкат — владелец.

## 9. Фазы внедрения

Не всё сразу, но и не «когда-нибудь». Привязка к роадмапу:

| Фаза | Когда | Что есть |
|---|---|---|
| **0** | этапы 1–2 | Контент в файлах `content/*`, golden-тесты в CI. Админки нет — она бессмысленна, пока нет игры |
| **1** | этап 4 | Конфигурация переезжает в БД, публикуется версионированным снапшотом. Интерфейс минимальный: редактор структурированных данных с валидацией, прогоном симуляции, публикацией и откатом. **Этого достаточно, чтобы этап 5 роадмапа стал выполнимым** |
| **2** | после публичного лонча | Формы под каждую сущность, наглядный дифф, постепенный выкат и A/B, загрузка ассетов из интерфейса |
| **3** | по потребности | Дашборд с метриками рядом с редактором: изменил баланс — видишь, что стало с retention и конверсией |

Фаза 1 намеренно скромная: ценность даёт не красота интерфейса, а связка
«валидация + симуляция + версия + откат». Красивые формы без этой связки —
опасный инструмент.

**Шаг 1 — песочница, где сделано.**

- **Сервер** — версии, черновики, правка по пути, разница и очередь проверки
  (§3, «Версии и черновики на сервере», `T-0303`).
- **Панель** — раздел «Баланс» (`T-0304`): таблицы восьми разделов, правка
  числа прямо в ячейке с прежним значением, ошибка сервера строкой под записью,
  лист «Правки» с «Вернуть». Устройство экрана — `29-admin-panel.md` §5.8.
- **Цены и награды** (`T-0309`, `T-0310`) — вкладка «Цены и награды»: цена товара
  и числа наград меняются только заявкой с подтверждением второго участника
  (§6). Устройство — `29-admin-panel.md` §5.8.
- **Прогон симуляции и коридоры** (`T-0305`) — «Проверить» и рельсы.

**Шаг 2 — публикация, где сделано** (`T-0306`).

- **Сервер** — «Команде» и «Всем» только по свежей зелёной проверке, откат,
  версия для клиента по его схеме, снимок по хэшу с вечным кешем, версии из
  кода при выкате (§3, «Публикация и выдача версии»).
- **Панель** — кнопки рядом с рельсами, окно «Всем» со списком правок,
  «История и откат», «Взять из кода» (`29-admin-panel.md` §5.8).
- **Дальше** — загрузка версии клиентом и известные хэши забегов (`T-0307`),
  PR со снимком (`T-0308`), доли выката и A/B — фаза 2.

## 10. Чего не делаем

- **Не даём править код через админку.** Ни выражений, ни формул, ни скриптов.
  Как только конфиг становится исполняемым, он перестаёт быть проверяемым, а
  админка превращается в способ выполнить произвольный код на клиентах.
- **Не редактируем живую конфигурацию без версии.** Только публикация нового
  снапшота.
- **Не даём править данные игроков** — балансы, прогресс, результаты забегов.
  Админка про правила игры, а не про её состояние. Ручные операции с
  игроками — отдельный инструмент с отдельными правами и отдельным аудитом.
- **Не выключаем прогон симуляции ради скорости.** Именно в тот раз, когда его
  выключат, и произойдёт поломка.
