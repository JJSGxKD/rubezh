# Масштабируемость: как проект держит рост нагрузки

Документ отвечает на вопрос «что мы сделаем, когда пользователей станет
кратно больше». Принцип — **не строить сейчас инфраструктуру под нагрузку,
которой нет**, но и не принимать решений, которые эту нагрузку потом не дадут
пережить без переписывания.

`09-ci-cd.md` §6 уже фиксирует: Kubernetes и подобное на текущем масштабе не
нужно. Этот документ не отменяет то решение, а достраивает его — показывает,
какой следующий шаг делается на каждом пороге и почему до порога его делать не
надо.

---

## 1. Профиль нагрузки: что именно нагружает систему

Начинать надо не с «сколько RPS выдержим», а с того, какой формы у нас трафик.
У bullet-heaven-игры в мессенджере он очень характерный.

| Что происходит | Частота | Стоимость для бэкенда |
|---|---|---|
| Загрузка билда игры (JS + ассеты) | 1 раз на сессию, ~несколько МБ | **Нулевая для API** — статика уходит с CDN |
| Сам геймплей (забег 3-10 минут) | постоянно | **Нулевая** — весь цикл в клиенте, сеть не трогаем (`01-tech-stack.md` §2) |
| Авторизация (`POST /auth/telegram`) | 1 раз на запуск приложения | средняя: валидация подписи + запись сессии |
| Отправка результата забега (`POST /runs`) | 1 раз на забег | **высокая**: запись в БД + антифрод + обновление лидерборда |
| Чтение лидерборда | несколько раз на сессию | низкая при Redis ZSET, высокая при чтении из Postgres |
| Показ/подтверждение рекламы | 1-3 раза на сессию | средняя: Redis-сессия показа + запись `AdsViews` |
| Покупка | редко | высокая, но объём мал |

**Главный вывод, определяющий всю архитектуру:** игровой цикл не создаёт
сетевой нагрузки. Мы не пишем шутер с 60 тиками в секунду на сервер — мы пишем
сервис, который принимает **один запрос на забег**. Это на порядки более
щадящий профиль, и вся стратегия масштабирования строится на нём: держать
«горячий» путь коротким и не пускать в него Postgres.

Второй вывод — про форму трафика. Рост в мессенджерах не линейный: удачный
пост в подборке или репост в крупном канале даёт **всплеск в десятки раз за
минуты**, а не плавную кривую. Поэтому важнее «выживать в пике без ручного
вмешательства», чем «держать высокий средний RPS».

Третий — про геометрию: аудитория RU-центричная (`01-tech-stack.md` §7,
`04-marketing-plan.md`), то есть суточный пик узкий (вечер по Москве), а не
размазан по часовым поясам. Планировать запас надо от пика, не от среднего.

## 2. Что уже сделано правильно (и это не случайность)

Несколько решений, уже записанных в документации, — это как раз решения про
масштабируемость, просто принятые заранее:

- **Статика на Bunny.net CDN** (`01-tech-stack.md` §10, `09-ci-cd.md` §5).
  Самый тяжёлый по байтам трафик вообще не доходит до нашего сервера. При
  вирусном всплеске первым падал бы именно раздатчик билда — у нас его нет.
- **Хэши Vite в именах файлов** — кеш на CDN бесконечный, инвалидация не нужна.
- **Игровой цикл без сети** — нет постоянных соединений, нет WebSocket-ов, нет
  состояния сессии на сервере во время игры. API остаётся stateless, значит
  масштабируется горизонтально копированием.
- **Redis ZSET для лидербордов** (`01-tech-stack.md` §3) — чтение топа это
  `ZREVRANGE`, а не `ORDER BY ... LIMIT` по растущей таблице.
- **BullMQ для вебхуков оплаты** — медленная и ненадёжная внешняя интеграция
  вынесена из HTTP-запроса в очередь.
- **Аккаунты не связываются между платформами** (`08-web-and-identity.md` §3) —
  побочный эффект: данные естественно шардируются по платформе, и при
  необходимости платформу можно разнести физически.

## 3. Этапы масштабирования и пороги перехода

Каждый этап — минимальное изменение, дающее следующий порядок запаса. Переход
делается **по сигналу метрики, а не по календарю**.

### Этап 0 — один VPS, Docker Compose (сейчас, до софт-лонча)

Один хост: API + Postgres + Redis + Caddy. Как в `01-tech-stack.md` §10 и как
в `vpnsibcom_api`. Этого достаточно на первые тысячи DAU.

**Что обязательно сделать уже на этом этапе** (дёшево сейчас, дорого потом):

1. **API — stateless.** Никакого состояния в памяти процесса: сессии в Redis,
   троттлинг в Redis (`RedisThrottlerStorage`, `13-reuse-from-vpnsibcom.md` §7),
   локи в Redis. Если это соблюдено, переход к этапу 1 — правка одной строки
   в compose. Если нет — переписывание.
2. **Все крон-задачи под распределённым локом** (`redis.withLock`). Иначе при
   первой же второй реплике каждая задача выполнится дважды: двойные начисления,
   двойные рассылки.
3. **Идемпотентность на записи.** `POST /runs` принимает клиентский `runId`
   (uuid, сгенерированный на старте забега) и обрабатывает повтор как no-op.
   Мобильная сеть теряет ответы регулярно; клиент будет ретраить.
4. **Индексы под реальные запросы** — по образцу `AdsViews` в источнике:
   составные `(userId, createdAt)`, а не только по одному полю.
5. **`Decimal` для любых балансов**, никогда `Float`. Постфактум мигрировать
   валютные поля — самая неприятная миграция из возможных.

**Порог перехода:** CPU API устойчиво > 60% в вечерний пик, или p95 времени
ответа выше ~300 мс.

### Этап 1 — несколько реплик API за Caddy

`deploy.replicas: N` в compose, Caddy балансирует. Postgres и Redis остаются
в одном экземпляре.

Работает без изменений в коде **при условии**, что пункты 1-2 этапа 0
соблюдены. Это самый дешёвый шаг: почти вся нагрузка на этом профиле — это
CPU на валидацию подписей и сериализацию, а он линейно делится между репликами.

**Порог перехода:** одного хоста перестаёт хватать по CPU/RAM целиком.

### Этап 2 — разделение ролей по хостам

Postgres на отдельный хост, Redis на отдельный, API — на третий (или
несколько). Это тот момент, когда БД перестаёт конкурировать за диск и память
с приложением. Обычно даёт больше, чем добавление ещё одной реплики API.

Одновременно: **вынести фоновую обработку в отдельный процесс-воркер**. Сейчас
BullMQ-воркеры живут внутри API-процесса; при росте их надо отделить, чтобы
всплеск вебхуков и рассылок не отъедал CPU у HTTP-хендлеров.

**Порог перехода:** Postgres — первое, что упирается (см. §4).

### Этап 3 — read-реплика Postgres и разделение путей чтения/записи

Аналитические выборки (когорты, воронка `Events`, отчёты по источникам из
`Acquisition`) уводятся на реплику. Горячий путь (`/runs`, `/auth`) остаётся на
мастере.

Это почти всегда следующий по эффективности шаг после этапа 2, потому что
аналитические запросы по природе тяжёлые и нерегулярные — именно они дают
неожиданные просадки в пике.

### Этап 4 — партиционирование горячих таблиц

`Run`, `Sessions`, `Events`, `AdsViews` растут линейно и вечно, и почти всегда
читаются за последний период. Партиционирование по месяцам (`PARTITION BY
RANGE (created_at)`) + автоматическое отцепление старых партиций в холодное
хранилище держит рабочий набор в памяти.

**Порог:** таблица перестаёт помещаться в page cache — видно по росту
disk read и деградации запросов, которые раньше были мгновенными.

### Этап 5 — то, что почти наверняка не понадобится

Kubernetes, шардирование Postgres, отдельный ClickHouse под аналитику, Redis
Cluster. Это не «когда-нибудь», это «при масштабе, на котором проект уже
окупает выделенного инженера по инфраструктуре». Записываем как известный
следующий шаг и не трогаем — преждевременный переход сюда убивает скорость
разработки, а скорость разработки для лайв-опс-игры важнее теоретического
запаса по нагрузке (`02-roadmap.md`, раздел про контент-дропы).

## 4. Узкие места по порядку, в котором они реально наступают

### 4.1 Первое: запись забегов в Postgres

Каждый забег = INSERT + чтение профиля + обновление лидерборда + антифрод. При
десятках тысяч забегов в вечерний пик это самая горячая точка.

Решения по возрастанию сложности:

1. **Не делать в HTTP-запросе ничего, что можно сделать после ответа.**
   Синхронно: валидация + антифрод-проверка на разумность + `ZADD` в Redis +
   ответ игроку. Асинхронно, через BullMQ: запись сырого забега в Postgres,
   пересчёт агрегатов, начисление наград, аналитические события. Игрок видит
   свой результат в лидерборде сразу, БД догоняет.
2. **Батчинг вставок.** Воркер пишет не по одной строке, а пачками
   (`createMany`) раз в N секунд. На порядок уменьшает количество транзакций.
3. **Партиционирование** (этап 4).

### 4.2 Второе: лидерборд

Redis ZSET решает чтение, но остаются два неочевидных момента.

- **«Лидерборд среди контактов»** (`01-tech-stack.md` §3, `03-notes-and-risks.md`
  про виральность) — это пересечение множества друзей с общим ZSET. Наивная
  реализация — `ZSCORE` по каждому контакту в цикле; при сотнях контактов это
  сотни round-trip к Redis на один запрос. Правильно: `ZMSCORE` одним вызовом
  или Lua-скрипт, сортировка на стороне приложения.
- **Сегментация ключей.** Один глобальный ZSET на всё — плохо: он растёт вечно
  и его нельзя обнулить без потери истории. Ключи вида
  `lb:{platform}:{season}:{mode}` дают естественную сегментацию, ограниченный
  размер каждого ключа и бесплатное «обнуление сезона» (`10-progression-and-ladder.md`).

### 4.3 Третье: Redis как единая точка отказа

К этапу 1 в Redis лежит всё: сессии, refresh-токены, троттлинг, локи, ZSET
лидербордов, рекламные сессии, BullMQ. Падение Redis = падение всего.

Что с этим делать:

- **Персистентность включена** (`appendonly yes`, `appendfsync everysec` — как
  в compose источника). Перезапуск не теряет сессии и лидерборды.
- **Лидерборды восстановимы из Postgres.** Сырые забеги — источник истины, ZSET
  — производный кеш. Нужна процедура перестроения ZSET из таблицы `Run`;
  написать её **до** того, как она понадобится в аварийном режиме.
- **Деградация вместо падения.** Недоступен Redis → лидерборд отдаёт «временно
  недоступен», но игра запускается и забег принимается. В источнике есть
  готовый паттерн: `ThrottlerModule` при недоступном Redis падает обратно на
  in-memory-режим вместо отказа старта.
- Redis Sentinel / managed Redis — этап 2+, не раньше.

### 4.4 Четвёртое: внешние интеграции

Telegram Bot API, рекламные сети, платёжные провайдеры — все имеют лимиты и
все иногда лежат. Правила, которые дёшево соблюдать сразу:

- всё, что можно, — **через BullMQ** с ретраями и экспоненциальным backoff
  (в источнике: 5 попыток, `removeOnComplete: 24h`, `removeOnFail: 7d`);
- **таймауты на все исходящие вызовы** — без них зависший провайдер выедает
  пул соединений и роняет весь API;
- **fallback-цепочка для рекламы** уже заложена (`priority` в `AdsNetworks`,
  `13-reuse-from-vpnsibcom.md` §3) — одна упавшая сеть не ломает монетизацию;
- **circuit breaker** на повторяющиеся отказы — не долбить провайдера, который
  уже отвечает ошибками, а быстро отдавать деградированный ответ.

### 4.5 Пятое: антифрод как источник нагрузки

Проверка забега на «разумность» — единственная сложная синхронная логика на
горячем пути. Держать её дешёвой: проверки на границы (счёт vs время vs
достигнутая волна, физически достижимый DPS) — это арифметика, она бесплатна.
Всё, что требует истории игрока или сравнения с популяцией, — **асинхронно**,
с отложенным аннулированием результата, а не в момент запроса.

Здесь же — ограничение частоты: троттлинг `POST /runs` по пользователю (забег
не может длиться 5 секунд) отсекает основную массу примитивной накрутки до
того, как она дойдёт до БД. Механика подписанной one-time-сессии из рекламного
модуля (`13-reuse-from-vpnsibcom.md` §3) — прямой образец: сессия забега тоже
может выдаваться подписанной на старте и предъявляться при сдаче результата.

## 5. Экономия на стороне клиента — самый дешёвый способ снизить нагрузку

Пункты ниже не про серверы, но по влиянию на пиковую нагрузку они сопоставимы
с целым этапом масштабирования:

- **Один запрос на старте вместо пяти.** Профиль + лидерборд + конфиг рекламных
  блоков + прайс-лист SKU одним `GET /bootstrap`. Это разница между 1 и 5 RPS
  на каждого заходящего игрока — ровно в тот момент, когда их приходит много
  сразу.
- **Конфиг игры — со статики, не с API.** Таблицы врагов/волн/апгрейдов
  (`01-tech-stack.md` §9) собираются в билд или лежат на CDN. Они одинаковы
  для всех, ходить за ними в API незачем.
- **Ретраи с джиттером.** Клиент, который ретраит ровно через 1 секунду,
  создаёт синхронизированную волну повторов после любого сбоя и добивает
  сервис, который только начал вставать. Экспоненциальный backoff + случайный
  разброс — обязательны.
- **Кеш лидерборда на клиенте на 30-60 секунд.** Игрок не заметит, нагрузка
  падает кратно.

## 6. Стоимость и запас: что мерить, чтобы решать вовремя

Ключевая метрика планирования — **стоимость инфраструктуры на 1000 DAU**. Она
считается с первого месяца, потому что определяет, окупает ли себя рост:
`11-revenue-split.md` делит доход **после расходов**, то есть неконтролируемая
инфраструктурная стоимость бьёт прямо по доле каждого участника.

Что должно быть на дашборде до софт-лонча (Grafana/Prometheus уже в стеке
источника, `13-reuse-from-vpnsibcom.md` §7):

| Метрика | Зачем |
|---|---|
| RPS и p50/p95/p99 по эндпоинтам | Отличить «медленно у всех» от «медленно у хвоста» |
| CPU/RAM по контейнерам | Порог этапов 0→1→2 |
| Postgres: активные соединения, самые медленные запросы, размер таблиц | Первое узкое место (§4.1) |
| Redis: память, hit rate, длина очередей BullMQ | Растущая очередь = воркеры не справляются, это ранний сигнал |
| Ошибки 5xx и 429 по эндпоинтам | 429 в норме означает работающий троттлинг; всплеск = либо атака, либо слишком жёсткий лимит |
| Доля неудачных показов рекламы по сетям | Деньги; заодно ранний признак, что сеть лежит |
| Время от конца забега до появления в лидерборде | Прямое измерение отставания асинхронного пути (§4.1) |

**Алерты — в Telegram-тред** через готовый `LoggerTelegramService`
(`13-reuse-from-vpnsibcom.md` §7). Команда из трёх человек без дежурств —
других каналов нет, и это нормально на данном масштабе.

## 7. Нагрузочное тестирование: когда и что

Не раньше недели 4-5 роадмапа (иначе тестируем несуществующий код), но
**обязательно до публичного лонча** и до посевов из `04-marketing-plan.md` —
именно они дают всплеск.

Сценарий один и он же самый важный: **волна одновременных стартов**.
Массовый `POST /auth/telegram` + `GET /bootstrap` + через несколько минут волна
`POST /runs`. Это буквально то, что происходит, когда пост выходит в крупном
канале.

Цель теста — не «найти максимальный RPS», а найти, **что ломается первым**, и
убедиться, что оно ломается мягко: 429 и очередь вместо 502 и потерянных
забегов. Порог, на котором нужно начинать этап 1, определяется по результатам
этого теста, а не по интуиции.

## 8. Резюме: что делаем сейчас, что откладываем

**Делаем сейчас (стоит часы, не дни):**

- API stateless, всё разделяемое состояние — в Redis
- Крон-задачи под распределённым локом
- Идемпотентный `POST /runs` по клиентскому `runId`
- Лидерборды — ZSET с ключами по платформе/сезону/режиму + процедура
  перестроения из Postgres
- Тяжёлая часть приёма забега — в BullMQ, ответ игроку не ждёт БД
- `Decimal` для балансов, составные индексы под реальные запросы
- Таймауты и ретраи с джиттером на всех внешних вызовах
- Метрики и алерты в Telegram — до софт-лонча, не после

**Откладываем осознанно:**

- Несколько реплик API — по порогу CPU, а не заранее
- Разнесение Postgres/Redis по хостам — по порогу этапа 1
- Read-реплика, партиционирование — по метрикам роста таблиц
- Kubernetes, шардирование, отдельное аналитическое хранилище — не в этом
  горизонте планирования (`09-ci-cd.md` §6)

Разница между двумя списками простая: первый — это решения, которые дёшевы
сегодня и дороги завтра; второй — решения, которые одинаково дороги в любой
момент, поэтому их надо принимать тогда, когда есть данные.
