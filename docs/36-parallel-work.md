# Параллельная работа двух ИИ-агентов

С 26 сентября 2026 этап 4 (`35-stage4-plan.md`) ведут два агента одновременно.
Этот документ — договор между ними: кто что делает, чьи это файлы и как
не сломать работу друг друга. Оба агента читают его **до начала задачи**, а
не после конфликта.

| | Кто | Где работает |
|---|---|---|
| **Локальный агент** | Claude Code на машине участника 1 | локальная копия, живые Postgres и Redis, Docker, будущий сервер |
| **Облачный агент** | Claude Code в облаке, модель Fable 5.1 | свежий клон с GitHub; своей базы и Redis нет — интеграционные тесты за него гоняет CI |

Правила репозитория (`CLAUDE.md`) действуют для обоих без исключений. Здесь —
только то, что добавляет параллельная работа.

## 2. Чьи это файлы

**Зона агента** — каталоги из таблиц выше: там он правит свободно. В чужой
зоне — только то, без чего задача не делается, **одной-двумя строками**, с
упоминанием в описании PR («тронул чужую зону: …»). Типичный случай —
экспорт сервиса из модуля: `exports: [WalletService]`.

Серверная часть панели **не правит** доменные модули, а зовёт их
экспортированные сервисы и репозитории из своих контроллеров. Если нужного
метода нет — он добавляется в сервис модуля отдельным маленьким коммитом с
тестом, а не пишется запросом Prisma в модуле панели.

### 2.1 Общие файлы — реестры

Их правят оба, и конфликты в них ожидаемы. Правило одно: **правка — добавление
в свой участок, конфликт решается сохранением обеих сторон**, чужие строки не
переписываются.

| Файл | Как добавлять |
|---|---|
| `backend/api/prisma/schema.prisma` | свои модели — блоком в конце файла с комментарием-заголовком пакета (`// Друзья (WP14)`); связь в `model Account` — одной строкой |
| `backend/api/prisma/migrations/` | миграция генерируется **после** перебазирования на свежий `dev`. Если пока PR ждал, в `dev` влилась более новая миграция соседа, — своя пересоздаётся с новой меткой времени: Prisma применяет их по порядку имени. Генерация — один раз (`--create-only` на отдельной базе), проверка — `ls prisma/migrations \| tail` |
| `backend/api/src/app.module.ts` | одна строка импорта и одна в `APP_MODULES` |
| `backend/api/src/modules/roles/permissions.ts` | новые права — своим блоком с комментарием; владельцу они достаются сами, роли — явным списком |
| `backend/api/src/config/app-config.ts`, `.env.example` | новая переменная — своим блоком по процедуре `20-env-and-ports.md` §7 |
| `apps/web-telegram/vite.config.ts` | префикс прокси — одна строка |
| `packages/app-shell/src/i18n/ru.json` | новые экраны **не добавляют** строки в основной словарь: у них свой ленивый словарь (`i18n/account.ts` — образец), это заодно бережёт первую загрузку |
| `docs/35-stage4-plan.md` | только «Как сделано» своих пакетов и свои строки решений |
| `docs/30-configuration-map.md` | строки своего пакета — в конец таблицы своей темы |
| `docs/21-diagrams.md` | сущности ER — в конец блока `erDiagram`, связи — в конец списка связей; узлы схемы модулей — рядом с соседями |
| `CLAUDE.md`, `README.md` | только строка в карте документации или разделе, который меняет задача |
| `pnpm-lock.yaml` | конфликт **не решается руками** — после перебазирования `pnpm install`, и в коммит идёт то, что он записал |

### 2.2 Общие ресурсы

- **Бюджет бандла** (`pnpm budget`). Первая загрузка и ленивые экраны
  `web-telegram` — общий кошелёк. Облачный агент в первую загрузку не
  добавляет ничего; ленивые экраны — только после Л1. Панель `apps/admin` в
  бюджет игры не входит: это другой бандл.
- **Словарь событий аналитики** (`22-analytics-and-metrics.md` §3.3) — новые
  события сначала в словарь и схему, одним коммитом, до кода.
- **Тестовые базы.** Облачному агенту своя база не нужна: интеграционные тесты
  без `TEST_DATABASE_URL` пропускаются локально и идут в CI.

## 3. Порядок работы

1. Перед задачей и перед PR — `git fetch` и перебазирование на `origin/dev`.
2. Ветка от `dev`: у локального агента — `feat/…`, `fix/…`, `docs/…`; у
   облачного — `cloud/…`. По префиксу видно, чья ветка, и никто не пушит в
   чужую.
3. PR маленький — один пакет или его часть — и проходит гейт `CLAUDE.md`
   локально; CI зелёный. Сводка для команды и метка релиза — как обычно.
4. Вливает автор PR, когда CI зелёный: merge-коммитом в `dev` (`CLAUDE.md`,
   «Ветки»). Перед вливанием — ещё раз перебазирование, если `dev` ушёл вперёд,
   и гейт.
5. `main`, релизы, настройки репозитория, секреты, сервер и всё, что уходит
   наружу (сообщения в Telegram, оплаты), — **только по команде участника 1**.
   Облачный агент сервер не трогает вовсе.
6. Нужна правка в чужой зоне больше пары строк — это задача соседа: запись в
   описании своего PR «нужно от локального/облачного агента: …» и строка в
   таблице §1 этого документа отдельным маленьким PR.

## 4. Как запустить облачного агента

Первое сообщение облачной сессии — примерно такое:

```text
Проект — «Рубеж», Telegram Mini App (pnpm-монорепо). Прочитай CLAUDE.md и
docs/36-parallel-work.md целиком: ты — облачный агент из §1.2, работаешь
параллельно с локальным агентом. Начни с задачи О1 (серверная часть
админ-панели, docs/35-stage4-plan.md WP17 и docs/29-admin-panel.md), в своей
зоне backend/api/src/modules/admin/. Ветки — cloud/…, PR — в dev, вливать
после зелёного CI, merge-коммитом. main, релизы, сервер, секреты и отправка
чего-либо наружу — только по моей команде. Своей базы у тебя нет —
интеграционные тесты проверит CI. Пиши по-русски, комментарии в коде — тоже.
```

Дальше — следующая задача из §1.2 тем же сообщением с другим номером.
