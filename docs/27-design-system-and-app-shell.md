# Дизайн-система и оболочка приложения

Как устроен интерфейс вне забега и вокруг него: чем рендерится, как делится
с движком, из каких токенов и компонентов собирается, как ведёт себя на
разных экранах и в fullscreen-режиме Telegram. План работ по этому
документу — `26-stage2-plan.md`, WP5.

Смежное: `16-tech-stack-decisions.md` §3 (библиотеки клиента),
`15-engineering-standards.md` §2 (границы слоёв), `21-diagrams.md` §2
(пакеты), `22-analytics-and-metrics.md` (события интерфейса).

---

## 1. Решение: React-оболочка, Phaser только в забеге

### 1.1 Что меняется

Раньше `16-tech-stack-decisions.md` §3.1 фиксировал: **интерфейс игры — в
Phaser, не DOM/React**, DOM-оверлей только для платформенных вещей. Решение
пересмотрено на старте этапа 2:

- **главное меню, разделы, настройки, экраны паузы, выбора апгрейда и
  смерти, HUD забега** — React-оболочка;
- **Phaser рисует только мир забега**: арену, врагов, снаряды, эффекты,
  виртуальный джойстик;
- Phaser не грузится, пока игрок в меню, — он приходит отдельным чанком.

### 1.2 Почему прежний аргумент не нарушается

Аргумент против React был производительностный: второй цикл отрисовки и
конкуренция за главный поток с игровым циклом при главном техническом риске
проекта. Он верен для **React внутри забега**, и эта часть решения остаётся:

- в забеге React не участвует в кадре. HUD получает снимок состояния не
  чаще 10 раз в секунду, остальное дерево не перерисовывается вовсе (§3.3);
- оверлеи паузы, выбора апгрейда и смерти показываются, когда симуляция
  **стоит** — за главный поток в этот момент соревноваться не с кем;
- вес React (~60 КБ gzip) меньше пятой части веса Phaser и при этом
  **ускоряет** старт: меню появляется до загрузки движка, а не после.

Что выигрываем: интерфейс на DOM отзывчивее и доступнее, чем на канве —
нативная прокрутка, выделение текста, системные шрифты с кириллицей без
мыла, отступы безопасной зоны через CSS, адаптивная вёрстка без ручного
пересчёта координат. Вёрстка экранов меню на канве Phaser — это
переизобретение браузера, и при двенадцати разделах оно обошлось бы дороже
всего остального этапа.

Проверка решения — прогон стенда испытаний **внутри оболочки** на точке M2
(`26-stage2-plan.md` §5): запас по нагрузке не должен просесть относительно
замеров этапа 1 больше, чем на погрешность.

### 1.3 Выбор фреймворка

| Кандидат | За | Против | Итог |
|---|---|---|---|
| **React 19** | Опыт команды в продакшене (`vpnsibcom_web` — React 19 + Zustand + Tailwind 4, `13-reuse-from-vpnsibcom.md` §11); наибольшая экосистема; ИИ-агенты всех троих участников пишут на нём увереннее всего | Самый тяжёлый из четырёх; виртуальный DOM | **Выбран** |
| Preact | ~5 КБ вместо ~60 при почти том же API | Слой совместимости с библиотеками экосистемы; выигрыш в весе на фоне Phaser несущественный | Отклонён: экономия ~55 КБ не стоит второго класса проблем совместимости |
| SolidJS | Быстрее всех, точечные обновления без виртуального DOM | Меньше опыта в команде и у агентов; меньше готовых решений | Отклонён: производительность оболочки не узкое место (§1.2) |
| Svelte 5 | Малый рантайм, компилятор | Отдельный язык шаблонов, опыта нет | Отклонён по той же причине |

Решающий аргумент — не скорость фреймворка, а то, что узкое место оболочки
не в нём: в забеге она почти не работает, а в меню нагрузка ничтожна. При
таком профиле выигрывает то, на чём команда быстрее и надёжнее пишет.

### 1.4 Сопутствующие решения

| Задача | Решение | Почему |
|---|---|---|
| Стили | **Tailwind CSS 4**, токены в `@theme` | Опыт команды; токены сразу становятся и CSS-переменными, и утилитами — один источник (§4.2) |
| Состояние меты | **Zustand** | Уже зафиксирован в `16-tech-stack-decisions.md` §3.1 |
| Навигация | **Свой стек экранов** в Zustand, без роутера и без URL | В Mini App нет адресной строки; кнопка «назад» — платформенная; глубокие ссылки приходят через `startParam`, а не путь (§7) |
| Компоненты | **Свои**, без UI-библиотеки | У игры своя айдентика. Библиотеки под нативный вид Telegram делают игру похожей на бота с настройками; универсальные библиотеки тянут вес под задачи, которых у нас нет |
| Анимации | **CSS-переходы**, без библиотеки анимаций | На MVP хватает `transform` и `opacity`; библиотека — отдельным решением, если понадобятся жесты с физикой |
| Иконки | Набор с импортом по одной иконке (например `lucide-react`) как временный; свой набор в стиле сеттинга — по готовности ассетов | В бандл попадают только использованные иконки |
| Шрифты | **Rubik** (акцидентная) и **Inter** (текстовая), вариативные `woff2` из пакетов `@fontsource-variable`, в бандле; подмножества — кириллица и латиница (§4.3) | Внешние шрифтовые CDN в WebView — лишний запрос, риск недоступности и адрес игрока у третьей стороны. Пакет даёт то же, что `next/font`: файлы из npm с точной версией, сборщик кладёт их рядом с бандлом |

## 2. Раскладка и границы

```
apps/web-telegram         точка входа: создаёт адаптер, монтирует оболочку
        │
        ├──► packages/adapter-telegram   SDK площадки
        │
        └──► packages/app-shell          React: дизайн-система, экраны,
                    │                    состояние меты, навигация
                    ▼
             packages/core-game          забег: симуляция + Phaser,
                    │                    публичный API — §3.1
                    ▼
             packages/shared-types       контракты
```

Правила (дополняют `15-engineering-standards.md` §2.2):

| Правило | Почему |
|---|---|
| `app-shell` **не** импортирует `adapter-*` | Адаптер приходит готовым объектом из `apps/web-*`. Иначе оболочка становится телеграм-оболочкой, и порт на MAX — это её переписывание |
| `app-shell` импортирует `core-game` **только через публичный API** (`index.ts`) | Внутренности забега — не контракт; оболочка не лезет в `game/sim/*` за числами для HUD |
| `core-game` **не** импортирует `app-shell` и React | Движок ничего не знает о том, кто и чем рисует меню |
| `app-shell` **не** импортирует Phaser | Phaser уходит отдельным чанком; прямой импорт в оболочке затянул бы его в основной бандл |

Дизайн-система живёт внутри `app-shell` (`src/design-system/*`), а не
отдельным пакетом: второго потребителя пока нет. Админка геймдизайнера
(`19-content-admin.md`) — десктопный инструмент с другими задачами; вынос в
пакет — когда появится реальное второе применение
(`15-engineering-standards.md` §1, принцип 5).

## 3. Контракт движок ↔ оболочка

### 3.1 Публичный API забега

Эскиз контракта — фиксирует границу, а не реализацию:

```ts
// packages/core-game — публичный API
export function loadRunEngine(): Promise<RunEngine>; // динамический импорт Phaser

export interface RunEngine {
  start(options: RunOptions): RunSession;
}

export interface RunOptions {
  container: HTMLElement;
  seed: number;
  mode: "endless";
  mapId: string;
  startingWeaponId: string;
  diagnostics: { recordRun: boolean; fpsOverlay: boolean };
}

export interface RunSession {
  on<E extends keyof RunEvents>(event: E, handler: (payload: RunEvents[E]) => void): () => void;
  chooseUpgrade(optionId: string): void;
  pause(reason: "manual" | "app_inactive"): void;
  resume(): void;
  abandon(): void;
  restart(seed: number): void;
  destroy(): void;
}

export interface RunEvents {
  hud: HudSnapshot;                  // не чаще 10 Гц
  segmentStarted: { index: number }; // отрезок таймлайна спавна, «волна» в аналитике
  levelUp: { level: number; options: UpgradeOption[]; queued: number };
  finished: RunResult;               // смерть
  abandoned: RunResult;
  diagnostics: RunDiagnostics; // сводка у всех, запись — только при recordRun
  error: { message: string };
}
```

Контракт реализован (WP5). Отличия готового кода от эскиза выше — уточнения, а
не другой замысел:

- добавлены события `waveReached`, `paused` и `resumed`: отрезок таймлайна
  уходит в аналитику как `wave_reached`, а пауза может прийти и от площадки
  (сворачивание приложения), не только от кнопки;
- технический итог — событие `diagnostics` сразу перед `finished`/`abandoned`
  в том же вызове: сводка производительности у всех игроков и полная запись
  забега при `recordRun` (`28-diagnostics.md` §3);
- у `RunOptions` есть `pixelRatio` и `renderCapFps` — их фиксирует стенд
  испытаний, чтобы прогоны на разных экранах были сравнимы.

Экранов на канве больше нет: пауза, выбор улучшения и смерть — React-оверлеи
над остановленной канвой, а в движке остались мир, камера и джойстик.

Три свойства контракта, ради которых он такой:

- **Команды и события, а не общее состояние.** Оболочка не читает мир
  напрямую и не держит на него ссылку — иначе React-компонент однажды
  подпишется на позицию врага и начнёт перерисовываться 60 раз в секунду.
- **Выбор улучшения — команда, которая пишется в лог ввода.** Движок
  применяет её на границе тика; забег остаётся воспроизводимым. `queued` —
  сколько ещё уровней ждёт выбора, если набрано несколько подряд
  (`26-stage2-plan.md`, WP2).
- **Движок не шлёт аналитику и отчёты сам.** Он отдаёт `RunResult` и
  `RunDiagnosticsReport`, отправкой занимается оболочка. Движок не знает о
  сети (`15-engineering-standards.md` §2.2).

### 3.2 Кто что рисует

| Элемент | Чем | Почему |
|---|---|---|
| Мир, враги, снаряды, кристаллы опыта, эффекты | Phaser | Сотни объектов в кадре |
| Динамическая камера: следование и масштаб от движения | Phaser | Только рендер, симуляция о камере не знает (`26-stage2-plan.md`, WP4.3) |
| Виртуальный джойстик | Phaser, ввод с канвы | Задержка ввода минимальна и не зависит от React; джойстик появляется там, где коснулся палец |
| Кристаллы и подборы (аптечка, магнит, динамит) с полётом от места смерти, волна динамита и кольцо магнита; телеграфы угроз (кольцо взрыва, полоса рывка); числа урона и вспышка гибели врага | Phaser: `render/pickups.ts`, `render/telegraphs.ts`, `render/combat-feedback.ts` | Живут в мире и масштабируются камерой; числа урона ограничены по количеству — текст на канве дорогой |
| HUD: HP, таймер, уровень и полоса опыта, слоты оружия и пассивок | React, слой с `pointer-events: none` | Отступы безопасной зоны и шрифты — через дизайн-систему; обновление 10 Гц |
| Радар: враги, элиты и подборы в пределах кольца спавна | React, маленькая канва 2D в HUD; точки — в снимке HUD (`radar`) | Экранный элемент с отступами безопасной зоны; перерисовка только с новым снимком, 10 Гц. Дальние угрозы прижаты к краю. Подборы — формой и цветом силуэта на земле: крест — аптечка, кольцо — магнит, ромб — динамит |
| Полоса здоровья босса: имя, остаток, деления фаз | React, из снимка HUD (`boss`) | Появляется только когда на поле босс, а не элита: элит за забег десятки, и полоса на каждую стала бы фоном. Деления — фазы боя: перейдённый порог меняет и полосу, и поведение босса |
| Кнопка паузы | React, единственный интерактивный элемент HUD | В зоне, недоступной джойстику |
| Пауза, выбор улучшения, смерть | React-оверлей над остановленной канвой | Симуляция стоит, конкуренции нет |
| Оверлей FPS диагностики | React, 2 Гц | Читается глазом, чаще не нужно |

### 3.3 Правила производительности оболочки во время забега

Нарушение любого из них — блокирующее замечание на ревью:

1. **Во время забега перерисовывается только HUD**, не чаще 10 раз в
   секунду. Компонент HUD изолирован и мемоизирован; остальное дерево
   не подписано на события забега.
2. **Анимируются только `transform` и `opacity`.** Изменение `width`,
   `top`, `box-shadow` в забеге вызывает перерасчёт раскладки на каждом
   кадре. Полоса HP — `scaleX`, а не ширина.
3. **Экраны меню размонтируются** на время забега, а не прячутся
   `display: none` — скрытое дерево продолжает реагировать на изменения
   стора.
4. **Никаких `backdrop-filter` и больших размытий** поверх живой канвы: на
   бюджетном Android это стоит дороже всего мира забега. Над остановленной
   канвой — допустимо.
5. **Стенд испытаний прогоняется внутри оболочки** при заметных изменениях
   HUD и оверлеев, а не только на голом движке.

### 3.4 Загрузка

```
index.html: критичный CSS + заставка в разметке (знак, имя, бегущая полоса)
  → бандл оболочки → заставка React с теми же знаком и полосой
      этапы: площадка готова → шрифты (не дольше 800 мс) → главная
  → в простое браузера из лобби: предзагрузка чанка движка
  → «В бой»: экран загрузки забега — чанк движка → мир → первый кадр
      с предзагруженным чанком первый этап проходит мгновенно
```

Этапы на полосах **настоящие**, а не ползущая сама по себе анимация: каждый
этап — момент в `mountAppShell` или в сторе забега. Заставка из `index.html`
повторяет раскладку заставки React, поэтому подмена разметки не видна глазом.

Шрифты ждутся с таймаутом (`FONT_WAIT_MS`): на медленной сети главная
откроется системным шрифтом, а свой подменит его по приходу
(`font-display: swap`). Ждать дольше — держать игрока на заставке ради шрифта.

Предзагрузка движка не запускается при экономии трафика (`saveData`) и без
сети: браузер может запомнить неудавшийся динамический импорт, и неудачная
предзагрузка сломала бы сам забег до перезапуска.

Бюджеты проверяются в CI командой `pnpm budget` после сборки
(`09-ci-cd.md` §2, шаг 7; пороги — в `scripts/bundle-budget.mjs`). JS и CSS
считаются в gzip, шрифты — как есть: `woff2` уже сжат.

| Часть | Бюджет | Замер |
|---|---|---|
| JS оболочки, первая загрузка | ≤ 150 КБ | 143 КБ |
| CSS | ≤ 30 КБ | 10 КБ |
| Экраны по требованию | ≤ 58 КБ | 56 КБ |
| Интерфейс забега: HUD, пауза, выбор улучшения, характеристики, их словарь | ≤ 12 КБ | 10,5 КБ |
| Инструменты команды: витрина, звуковая лаборатория, лист и панель разработчика | ≤ 14 КБ | 9 КБ |
| Движок, стенд и стресс-тест | ≤ 380 КБ | 341 КБ |
| Звук: движок, рецепты, музыка (`31-audio-and-haptics.md`) | ≤ 15 КБ | 9 КБ |
| Шрифты | ≤ 120 КБ | 115 КБ: Rubik 50 + Inter 65, кириллица и латиница |

Запас первой загрузки выстрадан: тексты режима разработчика, стресс-теста и
звуковой лаборатории лежат отдельным словарём (`i18n/ru-team.json`,
дополняется чанками их экранов), лист разработчика и техническая сводка —
отдельными чанками, разбор устройства грузится при отправке отчёта, сессия
игрока — тоже отдельным чанком после главной. Экран смерти — свой чанк
(`screens/run/death-overlay-lazy.tsx`), который подтягивается, как только
забег пошёл: смерть не ждёт сети, а первая загрузка за него не платит. Игроку
всё это в первую минуту не нужно.

**Инструменты команды — своей строкой** с этапа 3. Витрину, звуковую
лабораторию, лист и техническую панель разработчика игрок не качает вовсе:
доступ к ним решает сервер по ролям. Пока они жили в «экранах по
требованию», бюджет игровых экранов мерил не то, что едет к игроку, и рост
витрины съедал запас профиля. Порог игровых экранов снижен с 60 до 55 КБ на
их вес — запас остался прежним, а не вырос. Стресс-тест и диагностика
остались в игровых экранах: их видят тестировщики закрытого теста.

**Порог поднят со 150 до 152 КБ на этапе 3** — вместе с проверкой версии
клиента и экраном «обновите Telegram» (§5.2). Запас к тому моменту был уже
исчерпан: замер показывал 149,6 при пороге 150, и любая правка первой
загрузки упёрлась бы в него. Поднят ровно настолько, чтобы влезла эта
проверка, — запас снова почти нулевой, и это по замыслу. В первой загрузке
при этом лежит 4,6 КБ умолчаний паттернов врагов: они приходят транзитом
через `index.ts` пакета `core-game`, а нужны только гайдбуку. Это отдельная
задача — трогать здесь границу слоёв нельзя.

**Интерфейс забега вынесен из первой загрузки на этапе 4** (`35-stage4-plan.md`,
`36-parallel-work.md`, Л1). К тому моменту первая загрузка упёрлась в 152 из
152 КБ, и ни один новый экран оболочки в неё не помещался. Экран забега — HUD,
пауза, выбор улучшения, характеристики, радар, полоса босса — лежал в ней
целиком, хотя без чанка движка забег всё равно не начнётся. Теперь он —
ленивый экран (`app/lazy-screens.tsx`), который лобби подтягивает в простое
вместе с движком, а его строки — свой словарь (`i18n/ru-run.json`, дополняется
файлами экрана забега). Первая загрузка — 143 КБ, и порог вернулся к исходным
150 КБ. У интерфейса забега своя строка: иначе он съел бы запас экранов меню,
которые игрок открывает руками. Порог экранов меню поднят с 55 до 58 КБ: к ним
перешли общие с первой загрузкой мелочи — иконки и формат карточки улучшения,
около 1 КБ, — и нужен запас под экраны друзей и шеринга. Итог по всем строкам
меньше прежнего, а быстрее стала именно главная.

Осталось в первой загрузке и ждёт своей очереди: контент движка и
разбор его типов — общим чанком, который нужен выбору оружия (около 5 КБ), и
Zod (`zod/mini`) — его читает разбор сохранённого на устройстве.

**Первая загрузка** — то, на что ссылается `index.html` (скрипт и
`modulepreload`), и всё, что эти чанки статически импортируют. Считается по
ссылкам, а не по именам файлов: сборщик вправе выделить общий модуль в чанк с
любым именем, и такой чанк молча выпал бы из бюджета — ровно это случилось при
переходе на Vite 8 (`16-tech-stack-decisions.md` §9.2). Всё остальное, кроме
движка и стенда, — экраны по требованию.

**Раскладка чанков зависит от машины — мерить надо в CI.** Rolldown по
умолчанию сливает общий чанк с одним из «входных», и входными для него
считаются в том числе чанки динамического импорта. На Windows общие
runtime-хелперы оставались отдельным чанком, а в CI на Linux та же сборка
положила их в чанк движка: первая загрузка стала статически импортировать
Phaser — 453 КБ вместо 123, хотя локально бюджет проходил. Слияние общих
чанков выключено (`scripts/vite/chunking.ts`), а `pnpm budget` отдельно падает,
если чанк движка оказался в первой загрузке. Прочие различия остаются: на Linux
сборщик объединяет Phaser, забег и стенд в один чанк, на Windows — нет, поэтому
цифры бюджета в CI и локально расходятся на несколько килобайт.

**Ленивые экраны.** В первую загрузку входит только путь до «Играть»:
заставки, лобби, выбор режима и оружия. Сам забег — ленивым чанком из лобби
вместе с движком (см. выше). Настройки, диагностика, витрина,
разделы-заглушки и мета — задания, награда дня, колесо — грузятся по
требованию (`app/lazy-screens.tsx`) и
подтягиваются заранее из лобби вместе с движком. Не пришёл чанк — экран
показывает ошибку с повтором, а не роняет приложение. Новый раздел, который
игроку не нужен в первую минуту, добавляется туда же.

Словарь `ru.json` пока целиком едет в первой загрузке, вместе с текстами
ленивых разделов: тексты одних только заглушек меты весят около 1 КБ gzip.
Когда разделы станут рабочими и текстов прибавится, словари разделов
переезжают в их чанки.

**Бюджет 150 КБ — исходный, и он верен.** Прежние замеры 174–183 КБ и
вывод, что React 19 не помещается в 150 КБ, были ошибкой измерения: корневой
`.env` содержит `NODE_ENV="development"` для бэкенда, Vite читал его из того же
файла и собирал клиент **в режиме development** — с отладочными React и JSX.
Production-сборка той же оболочки — 119 КБ, React с `react-dom` около 60 КБ,
как и оценивалось в §1.3. Вопрос о возврате к Preact снят вместе с ошибкой.
Сборка клиента теперь не берёт `NODE_ENV` из `.env`
(`scripts/vite/production-node-env.ts`), а `pnpm budget` падает, если в бандле
есть отладочный JSX.

Время до интерактивной главной и до первого кадра забега пишется событием
`load_time` — бюджет проверяется и на реальных устройствах тестеров, а не
только размером файлов. Фазы: `shell_ready` (с признаком `fontsLoaded` —
успели ли шрифты к главной) и `run_first_frame` — от «В бой» до первого
снимка HUD (`22-analytics-and-metrics.md` §3.3).

### 3.5 Ассеты: паки и загрузка по требованию

Сейчас в игре нет ни одного файла-ассета: мир рисуется текстурами, которые
движок строит сам при старте сцены (`core-game/src/game/render/textures.ts`), и
весь вес забега — это чанк движка. Со спрайтами и звуковыми файлами вес вырастет
в разы, поэтому порядок загрузки фиксируется до первых ассетов, а не после
жалоб на первый запуск.

| Пак | Что внутри | Когда грузится |
|---|---|---|
| `core` | персонаж, враги первых минут, кристаллы, подборы, вспышки попаданий | этап «Мир» экрана загрузки забега; из лобби — в простое, вместе с чанком движка |
| `late` | элиты и враги поздних отрезков таймлайна | в фоне после первого кадра забега |
| `audio` | звуки | после первого кадра и только при включённом звуке |
| облики, карты | скины, будущие карты | когда игрок открывает раздел или выбирает карту |

Правила:

- **Манифест собирается сборкой**: пак → файлы с хэшем в имени и размером в
  байтах. Хэш даёт вечный кеш CDN и браузера, размер — полосу загрузки в
  байтах, а не в штуках файлов: один атлас весит как сто звуков.
- **Один атлас на пак** (`16-tech-stack-decisions.md` §3.2); имена файлов —
  строчными (`CLAUDE.md`, «Окружение команды»).
- **Забег не ждёт необязательного.** Старт — с одним `core`; до прихода
  остальных паков движок рисует нынешнюю процедурную замену того же размера и
  цвета. Игрок на медленной сети играет сразу, а не смотрит на полосу, и
  недошедший атлас не роняет забег.
- **При экономии трафика** (`saveData`) фоновые паки не грузятся до явной
  нужды — как и предзагрузка движка (§3.4).
- **Бюджет `core`** объявляется вместе с первыми ассетами и встаёт в
  `pnpm budget` отдельной строкой. Ориентир — не тяжелее чанка движка.

## 4. Дизайн-система

### 4.1 Принципы

- **Своя айдентика, не вид Telegram.** Цвета темы Telegram (`themeParams`)
  для интерфейса не используются: игра выглядит одинаково у всех. Цвета
  шапки, фона и нижней панели Telegram выставляются **из наших токенов** —
  чтобы при открытии не мигал чужой цвет.
- **Одна тёмная тема на MVP.** Светлая — не раньше, чем появится запрос:
  игровой мир тёмный, и светлое меню вокруг него — два разных продукта.
- **Токены — единственный источник визуальных значений.** Цвет, отступ или
  радиус числом в компоненте — замечание на ревью. Иначе смена визуального
  направления превращается в поиск по всем файлам.
- **Тёмная тема высокой контрастности с «игровой» энергией** — решение
  команды на этапе 2. Ориентир — мобильные игры жанра вроде Survivor.io, но
  без их яркой мультяшной палитры и без веса их графики: почти чёрный
  холодный фон, один тёплый акцент (янтарь) на главном действии, объём у
  кнопок и карточек (блик сверху, кромка снизу), крупная акцидентная
  типографика, свечение за главным. Всё — CSS из токенов, ни одной картинки.
- **Сеттинг задаёт стиль, система — структуру.** Направление (фольклор,
  постсоветская эстетика — `05-game-design.md` §2) решает участник 3,
  воплощает участник 2. Значения этапа 2 — предложение до этого решения:
  смена направления — правка токенов, а не экранов.

### 4.2 Токены и их единственный источник

**Базовые токены** — палитра, гарнитуры, шкала текста, радиусы, тени, кривые и
длительности движения — в пакете `packages/design-tokens`: `src/tokens.css`
(блок `@theme` Tailwind 4) и `src/index.ts` (те же значения числами). Пакет
общий для игры и панели управления (`29-admin-panel.md` §4): второе
применение палитры запретило держать её копией
(`15-engineering-standards.md` §1, принцип 5). Файл пакета — не вход
Tailwind: его импортирует вход приложения сразу после `@import "tailwindcss"`,
и `@theme` из него становится утилитами (`bg-surface`, `rounded-lg`).

**Токены игры** — поверхности и кнопки (`@utility`), анимации и гайдбук, слои,
отступы площадки, высота вьюпорта — в `packages/app-shell/src/design-system/tokens.css`,
цвета площадки числами — в `tokens.ts` рядом. Своих цветов мимо пакета там
нет — это проверяет тест оболочки.

Phaser цвета из CSS не читает. Для канвы — `COLORS` пакета с той же палитрой
числами, и **тест, который разбирает `tokens.css` пакета и сверяет значения**
(`packages/design-tokens/test/tokens.test.ts`).
Две копии без проверки разойдутся на первой правке палитры — так же, как
тип и валидация до Zod (`16-tech-stack-decisions.md` §6).

Оговорка по факту реализации: `tokens.ts` покрывает то, что рисует **оболочка**
(HUD, полосы, слоты) и цвета площадки. Палитра самого мира забега — враги,
снаряды, эффекты — осталась в `core-game`: движок не импортирует оболочку, это
запрещено направлением зависимостей (§2). Сводить обе палитры имеет смысл
вместе с ассетами, когда появится настоящий визуальный стиль.

### 4.3 Типографика

- Не больше **двух гарнитур**: акцидентная для заголовков и крупных цифр
  HUD, текстовая для остального. Обе — с полноценной кириллицей.
- Гарнитуры: **Rubik** — акцидентная (заголовки, кнопки, цифры: округлые
  формы, плотная жирная начертка, читается «игрой»), **Inter** — текстовая
  (описания, списки: крупный x-height, чётко на мелких кеглях и плохих
  экранах). Обе вариативные — одна пара файлов на все начертания — и с
  кириллицей, латиницей и расширениями под будущие языки, которые
  добавляются подмножеством в `fonts.css`, а не сменой шрифта. Лицензия —
  SIL Open Font License 1.1.
- Файлы — из `@fontsource-variable/*` точной версией, подключаются
  `@font-face` в `design-system/fonts.css`; сборщик кладёт их рядом с
  бандлом. Имена гарнитур дублируются в `tokens.ts` (`FONT_FAMILY`) для
  ожидания при запуске — совпадение проверяет `tokens.test.ts`.
- Шкала: 12 / 14 / 16 / 20 / 24 / 32 / 40 / 48 CSS px. Минимальный размер
  текста — 12, основной — 14–16; 48 — только имя игры.
- **Цифры, которые меняются** (таймер, счётчик, HP), — `tabular-nums`: иначе
  строка дёргается при каждой смене цифры.
- Длинные слова: русские заголовки длиннее английских в полтора раза,
  карточки проверяются на самом длинном тексте, а не на «Лорем».

### 4.4 Цвет и контраст

- Текст к фону — контраст не ниже **4.5:1**, крупный текст и иконки — **3:1**.
- Состояние не передаётся только цветом: у низкого HP — ещё и пульсация
  или значок; у недоступной кнопки — ещё и подпись.
- Цвета врагов и эффектов на канве отличаются формой и силуэтом, а не
  только оттенком — часть игроков различает цвета хуже.
- **Персонаж не делит цвет ни с кольцами вокруг себя, ни с врагами.** Тело
  светлое и нейтральное, в тёмном канте, чтобы читаться и на светлом рое, и на
  тёмной земле; цвет несут кольца: здоровье зелёное → жёлтое → красное, опыт
  синий (`render/looks.ts`). Раньше персонаж и полное кольцо здоровья были
  почти одним зелёным и сливались в пятно.
- **Низкое здоровье видно движением, а не только цветом**: кольцо здоровья
  пульсирует, когда его осталось меньше трети, — цвет в бою игрок может и не
  заметить.

### 4.5 Движение

- Анимируются только `transform` и `opacity` (§3.3). Там, где нужно
  «дышащее» свечение, анимируется прозрачность отдельного слоя с градиентом,
  а не тень.
- Смена экрана — 200 мс, оверлей — 300 мс, отклик на нажатие — 120 мс.
- При `prefers-reduced-motion` — только проявление, без перемещений;
  бесконечные анимации останавливаются на первом кадре.
- Отклик на нажатие — ещё и тактильный, где платформа его даёт: щелчок у
  обычных кнопок, удар средней силы у крупных, щелчок выбора у вкладок и
  переключателей. Компоненты зовут `uiFeedback` (`state/ui-feedback.ts`), а
  не адаптер: туда же приходит звук интерфейса.
- **Вибрация забега** — одна точка `state/haptics.ts` и один переключатель в
  настройках. У каждого события свой минимальный интервал, между любыми
  двумя вибрациями — не меньше 35 мс, а из пачки сигналов забега (`RunCues`,
  до 30 раз в секунду) выбирается одна, самая важная: динамит, взрыв рядом,
  появление элиты, попадание, убийство элиты, подбор. Отдельно — уровень,
  выбор улучшения, спуск здоровья ниже 30 %, смерть и рекорд. Вне Telegram —
  `navigator.vibrate` короткими шаблонами (адаптер).

Набор анимаций (`animate-*` в `tokens.css`):

| Анимация | Что | Где |
|---|---|---|
| `screen-in` | проявление со сдвигом на 8 px | смена экрана — ключом экрана в `ScreenTransition`, без таймеров |
| `fade-in` | проявление | затемнение под модалкой, HUD при старте забега |
| `pop-in` | проявление с пружиной от 92% | модалка по центру, отметка выбора, плашка рекорда |
| `sheet-in` | подъём снизу | лист подтверждения |
| `rise-in` | подъём на 12 px лесенкой (`staggerStyle`) | карточки улучшений и оружия, строки итогов |
| `glow` | «дыхание» прозрачности ореола | главное действие экрана, знак игры, значки модалок |
| `float` | покачивание знака | заставки и лобби |
| `ping-dot` | расходящееся кольцо | точка на вкладке |
| `shimmer` | бегущий блик | полоса загрузки |
| `pulse-soft` | мигание прозрачности | низкое здоровье, текущий этап загрузки |

Во время забега поверх живой канвы работает только `pulse-soft` у сердца
низкого здоровья; остальное — над остановленной симуляцией или вне забега.

### 4.6 Компоненты

Базовый набор этапа 2 — ровно то, что нужно экранам из §6:

| Компонент | Варианты | Где |
|---|---|---|
| `Button` | primary, secondary, ghost, danger; размеры m, l; состояние загрузки; ореол `glow` — у одного действия на экране | везде |
| `IconButton` | с подписью для скринридера | верхняя панель, HUD |
| `Emblem`, `Wordmark` | знак игры разметкой SVG и имя акцидентным шрифтом | заставки, лобби |
| `IconEmblem` | значок в светящемся круге, тона accent / info / muted | модалки забега, заглушки, экраны запуска |
| `TopBar` | заголовок, действия слева и справа | разделы |
| `TabBar` | 6 разделов; подпись у активного, у всех — от ширины панели 560 px (container query); активный — приподнятая плитка; бейдж-число или точка `dot` | нижняя навигация |
| `ScreenTransition` | появление экрана при смене | корень оболочки |

## 5. Адаптивность и fullscreen Telegram

### 5.1 Отступы безопасной зоны — платформенно-нейтральные

Оболочка знает только четыре переменные: `--app-inset-top`, `-right`,
`-bottom`, `-left`. Кто и как их заполняет — забота адаптера:

- **Telegram:** сумма системной безопасной зоны (вырез камеры, полоса
  жестов) и безопасной зоны контента (кнопки Telegram поверх приложения в
  fullscreen), с подпиской на изменения обеих;
- **браузер** (открыто вне мессенджера, dev): `env(safe-area-inset-*)`;
- **MAX и VK** — своими средствами при портировании.

Складывать ли две зоны Telegram или брать большую — **проверяется на
устройствах** в QA этапа 2 (Android с вырезом, iPhone с Dynamic Island).
Документация описывает их раздельно, а поведение клиентов разных версий
расходится; решение фиксируется здесь по факту проверки, а не по памяти.

Реализовано **сложение** — консервативный выбор: ничего не окажется ни под
вырезом, ни под кнопками Telegram. Живёт в одной функции `sumInsets`
(`adapter-telegram/src/insets.ts`) и покрыто тестом, так что решение по итогам
QA меняется в одном месте.

Высота экрана — от стабильной высоты вьюпорта, которую сообщает платформа,
а не `100vh`: во WebView iOS `100vh` включает зону под панелями, и нижняя
кнопка уезжает за край.

### 5.2 Fullscreen-режим: что учитываем

Возможности Telegram Mini Apps, на которые опирается оболочка (версия Bot
API, в которой появились):

| Возможность | Bot API | Как используем |
|---|---|---|
| Режим запуска fullscreen — в настройках Main Mini App у BotFather или параметром `mode=fullscreen` в прямой ссылке | 8.0 | Бот закрытого теста настроен на fullscreen; ссылки приглашений — с параметром |
| `requestFullscreen` / `exitFullscreen`, `isFullscreen`, события `fullscreenChanged`, `fullscreenFailed` | 8.0 | **Выбор режима экрана в настройках** (§5.2.1); при отказе клиента — обычный режим на всю высоту |
| `safeAreaInset`, `contentSafeAreaInset` и события их изменения | 8.0 | §5.1 |
| `lockOrientation` / `unlockOrientation` | 8.0 | **Не используем**: ориентация любая (Р5, `26-stage2-plan.md` §2) |
| `isActive`, события `activated` / `deactivated` | 8.0 | Автопауза забега, остановка отправки телеметрии по таймеру |
| `disableVerticalSwipes` | 7.7 | **Обязательно** на время забега: иначе движение пальцем вниз по джойстику сворачивает приложение |
| Подтверждение закрытия | 6.2 | Включено во время забега, выключено в меню |
| `BackButton` | 6.1 | Связан со стеком экранов (§7); в корне стека скрыт |
| `SettingsButton` | 7.0 | Открывает экран настроек |
| `setHeaderColor`, `setBackgroundColor` | 6.1 | Из токенов (§4.1) |
| `setBottomBarColor` | 7.10 | Из токенов — иначе на Android полоса навигации чужого цвета |
| `HapticFeedback` | 6.1 | Отклик на нажатия и попадания |
| `DeviceStorage` | 9.0 | Кандидат вместо `localStorage`, §7 |

Всё это работает через `@tma.js/sdk` внутри `adapter-telegram` и выходит
наружу методами `PlatformAdapter` (`26-stage2-plan.md`, WP5). Перед вызовом
проверяется поддержка версией клиента: у тестеров будут и старые клиенты.

**Минимальная версия Bot API — 7.7** (`34-stage3-plan.md`, Р11). Ниже неё
приложение показывает экран «обновите Telegram» и в игру не пускает. Граница
проведена по `disableVerticalSwipes`: всё, что появилось позже, лишь обедняет
игру и заменяется запасным вариантом, а без отключения свайпов движение
пальцем закрывает приложение посреди забега — это не «беднее», это сломано.
Число задаёт сборка (`apps/web-telegram/src/main.tsx`), сравнение — в
`app-shell/src/state/platform-version.ts`; неизвестная версия не блокирует,
иначе браузерная сборка для разработки заперлась бы сама.

#### 5.2.0 Компактное окно

Пока приложение занимает часть экрана, играть нельзя: джойстик и мир не
помещаются. Оболочка показывает плашку «разверните» — **поверх приложения, а
не вместо него**, и ставит забег на паузу.

Это не косметика. Плашка, подменявшая всё дерево, размонтировала экран забега
вместе с движком; экран монтировался заново, когда окно разворачивали, и
начинал **новый** забег поверх сохранения. Игрок терял четырнадцать минут,
ничего для этого не сделав. Отсюда два правила, которые нельзя нарушать:

- ни одно состояние площадки не подменяет дерево приложения, если под ним
  идёт забег, — только слой поверх;
- забег начинается **по намерению игрока** («Играть» или «Продолжить»), а не
  потому, что экран смонтировался. Экран без намерения продолжает сохранение,
  а не занимает его место (§7).

«Развёрнуто ли окно» считается по двум признакам: `isExpanded` и
`isFullscreen`. Полноэкранный режим — развёрнутый по определению, а отдельный
флаг шторки у части клиентов остаётся ложным, и игрок видел просьбу
развернуть уже развёрнутое окно.

#### 5.2.1 Выбор режима экрана

Игрок сам решает, в каком режиме играть: **Настройки → Экран →
«Полноэкранный режим»**.

- Настройка хранится на устройстве и применяется при каждом запуске: бот
  может быть настроен на запуск в fullscreen, а игрок его выключил — тогда
  приложение сразу выходит из fullscreen, и наоборот.
- Переключение действует сразу, без перезапуска: раскладка перестраивается по
  событию смены режима и новым отступам безопасной зоны, забег при этом не
  прерывается (переключить можно и из паузы).
- Там, где клиент fullscreen не поддерживает (старые версии, часть
  десктопных и веб-клиентов), переключатель неактивен с пояснением, а не
  молча не работает.
- Выход из fullscreen жестом или кнопкой Telegram — тоже смена режима:
  настройка синхронизируется с фактическим состоянием, иначе переключатель
  врёт.
- Умолчание — **полноэкранный на телефонах и планшетах, обычный в Telegram
  Desktop** (Р15 `26-stage2-plan.md` §2).
- Смена пишется `settings_changed`; режим на старте забега — в
  `run_started.payload` (`22-analytics-and-metrics.md` §3.3).

Что в fullscreen отличается по существу:

- **Шапки Telegram нет, но кнопки Telegram остаются** поверх приложения в
  верхней части. Верхняя панель оболочки начинается ниже
  `--app-inset-top`, а в зоне кнопок Telegram не должно быть ничего
  интерактивного — нажатие уйдёт в Telegram.
- **Строка состояния системы — поверх приложения.** Фон под ней — наш,
  контраст значков часов и батареи проверяется на устройствах.
- **Telegram Desktop и веб-клиенты** ведут себя как окно: fullscreen может
  быть недоступен или означать полноэкранное окно. Раскладка обязана
  работать и в обычном окне изменяемого размера.
- **Компактный режим** (`mode=compact`, неполная высота) для забега
  непригоден: вместо забега — экран с просьбой развернуть приложение и
  кнопкой, которая это делает.

### 5.3 Раскладка по размерам

Классы по ширине (CSS px):

| Класс | Ширина | Раскладка |
|---|---|---|
| compact | < 360 | Уменьшенные отступы, карточки апгрейдов — столбцом |
| regular | 360–599 | Базовая раскладка под телефон |
| expanded | ≥ 600 | Колонка контента до 480 px по центру, нижняя панель — внутри колонки; фон вокруг — декоративный |

По высоте: при высоте меньше 640 — плотный вертикальный ритм и
прокручиваемые экраны; кнопка основного действия всегда видна без
прокрутки.

Модалки забега уплотняются раньше — при высоте меньше 760 (вариант `short`
в `tokens.css`): значок над заголовком прячется, заголовок и поля меньше.
Выбор улучшения на таком экране теряет ещё и подсказку «Выбери улучшение»;
значок, название и метка карточки идут одной строкой с переносом, счётчик
ожидающих выборов — плашкой в ряду слотов, в ландшафте описание обрезается
до двух строк. Проверено без прокрутки: 360×640, 375×667, 390×844, 640×360,
844×390. На 320×568 три карточки с длинными текстами всё ещё прокручиваются —
класс compact, прокрутка там допустима.

**Ориентация — любая** (Р5), и ландшафт на телефоне — отдельный случай, а не
«широкий портрет»: высота около 360–430 CSS px, а в fullscreen из неё ещё
вычитаются отступы. Правила:

| Ситуация | Раскладка |
|---|---|
| Ландшафт, высота < 500 | Нижняя панель разделов становится **боковой колонкой** слева; верхняя панель — компактная; контент — справа |
| Ландшафт, выбор улучшения | Три карточки **в ряд**, а не столбцом |
| Ландшафт, экран смерти | Итоги слева, оружие и кнопки справа — без прокрутки к кнопке «Ещё раз» |
| Ландшафт, HUD | HP и уровень — левый верхний угол, таймер — центр сверху, слоты — нижний край; всё с учётом боковых отступов выреза камеры |
| Поворот во время забега | Без паузы и без перезапуска сцены: канва меняет размер, видимая область мира пересчитывается движком |
| Поворот на экране выбора улучшения | Раскладка карточек меняется, задержка от случайного тапа (`26-stage2-plan.md`, WP2) отсчитывается заново |

В ландшафте вырез камеры и полоса жестов оказываются **сбоку**: левые и
правые отступы безопасной зоны перестают быть нулевыми и обязательны для
боковой колонки и HUD.

Канва забега занимает весь экран в любом классе и ориентации; видимая
область мира нормализуется движком и одинакова по объёму в портрете и
ландшафте (`26-stage2-plan.md`, WP4.3, Р14), HUD — по отступам безопасной
зоны.

## 6. Карта экранов

**Рабочий** — экран с настоящей логикой. **Заглушка** — экран, который
открывается, выглядит как будущий раздел и явно помечен «в разработке». Ни
одна кнопка не должна молча ничего не делать: для тестера это баг, а не
заглушка.

| Раздел | Экран | Статус | Содержимое |
|---|---|---|---|
| Запуск | Заставка и загрузка | рабочий | Знак и имя игры, полоса по этапам запуска, подпись этапа, версия мелко; та же раскладка статичной разметкой в `index.html` (§3.4) |
| Запуск | Открыто вне Telegram | рабочий | Объяснение и ссылка на бота |
| Запуск | Разверните приложение | рабочий | Для компактного режима, §5.2 |
| Запуск | Первый запуск | рабочий | Короткое предупреждение о закрытом тесте и сборе технических данных, одна кнопка |
| **Главная** | Лобби | рабочий | Кнопка «Играть», рекорд на выбранной сложности — лучший из поставленных на этом устройстве и на других (приходит с сервера плейтеста при запуске и после каждого отправленного забега, записывается и в хранилище устройства), плитки «Награда дня» и «Колесо удачи», карточка гайдбука; валюта — в шапке, с сервера. При сохранённом забеге — его карточка, «Продолжить» и «Новый забег» с подтверждением (§7) |
| Главная | Награда дня | заглушка | Календарь из семи дней, седьмой крупнее; подсвечен сегодняшний, «Забрать» недоступна (`05-game-design.md` §3) |
| Главная | Колесо удачи | заглушка | Демо-крутка: колесо крутится до выпавшего сектора, награда не начисляется; крутка за рекламу недоступна; таблица шансов (`07-monetization-and-ads.md` §7) |
| Главная | Выбор режима | рабочий | «Бесконечный» — рабочий; «Забег разработчика» — администраторам (`ADMIN_TELEGRAM_IDS`, в dev-сервере всем); «Стресс-тест» — тем, кому открыт (`28-diagnostics.md` §2.3); «Кампания» — заглушка |
| Главная | Забег разработчика | рабочий | Тот же выбор сложности и оружия, сверху — карточка «Настроить режим разработчика» с пометкой, пойдёт ли забег в рейтинг. Лист режима — наборы «Чистый», «Телеграфы», «Весь арсенал», «Поздняя игра» и четыре вкладки: **Вид** — техническая сводка, хитбоксы, радиусы оружия и подбора, кольца спавна и удержания, границы, сетка столкновений, выключатели телеграфов, чисел урона и эффектов; **Время** — скорость ×0.25–×4, остановка спавна, заморозка врагов, в забеге — шаг на паузе и переход к минуте; **Читы** — бессмертие, убийство с одного удара, урон и скорость бега множителем, улучшения без выбора, «Учитывать в рейтинге»; **Мир** — на старте: всё оружие и навыки на максимуме, начать с минуты; в забеге: уровень, лечение, убить всех, кристаллы и подбор рядом, враги рядом кольцом, выдать оружие или навык на первом или последнем уровне. Настройки запоминаются на устройстве (`state/dev-mode.ts`) |
| Главная | Стресс-тест | рабочий | Памятка: что делает тест, сколько длится, не сворачивать, нагрев, что уходит команде. На прогоне канва без своего интерфейса, поверх — объекты крупно, враги, снаряды и кристаллы, время, FPS, плашка просадки, полоса предела по времени, «Остановить». Итог модалкой: предел найден, не найден или тест остановлен, пик объектов, сколько врагов держит плавно, средний FPS, кадр 95%, частота экрана, длительность, статус отправки с повтором, «Ещё раз» и «Готово». Уход с экрана уничтожает движок |
| Главная | Перед забегом | рабочий | Сложность переключателем с описанием и три карточки оружий с описанием атаки; последний выбор того и другого запомнен (Р12, Р18 `26-stage2-plan.md` §2) |

## 7. Навигация, состояние, хранение

**Стек экранов.** Навигация — стек в Zustand: `push`, `pop`, `replace`,
`resetTo`. Нижняя панель переключает корень стека. Кнопка «назад» Telegram
видна, когда в стеке больше одного экрана, и вызывает `pop`. Во время
забега «назад» ставит паузу, а не выходит из забега.

URL-роутер не используется: адресной строки нет, история браузера в
WebView ведёт себя непредсказуемо, а глубокие ссылки (этап 4) приходят
через `startParam` и разбираются в экран на старте.

Экран поверх забега — например, настройки с паузы — **не размонтирует
забег**: он остаётся под новым экраном скрытым и на паузе. Размонтированный
экран забега уничтожил бы движок, и возврат из настроек начинал бы забег
заново.

**Сохранение прерванного забега.** Забег, прерванный сворачиванием, вылетом
или закрытием приложения, продолжается с того же места. Движок отдаёт снимок
состояния мира (`RunSession.snapshot()`, `core-game/src/game/run/snapshot.ts`),
оболочка кладёт его на устройство: на каждой паузе, на выборе улучшения, при
уходе с экрана и раз в `AUTOSAVE_SEC` секунд забега. В лобби сохранённый
забег показывается карточкой, а «Играть» становится «Продолжить»; новый забег
при сохранённом — с подтверждением. Продолженный забег стартует на паузе
(«Забег сохранён») или на том же выборе улучшения.

**Забег начинается по намерению игрока, а не по монтированию экрана.** «Играть»
и «Продолжить» кладут намерение в стор, экран забега его читает. Экран
монтируется и сам — после сворачивания, смены раскладки, любого состояния
площадки, — и тогда намерения нет: такой вход **продолжает** сохранение, а не
занимает его место. Правило появилось после того, как тестер потерял
четырнадцать минут: экран пересобрался и начал новый забег поверх
сохранённого (§5.2.0).

Вместе с миром снимок помнит **режим забега** — читы и режим разработчика.
Признак хранится в самом снимке, а не во взведённом флаге стора: флаг живёт до
перезапуска приложения, а продолжают забег и через сутки. Без этого
продолженный забег разработчика тихо превращался в обычный, и панель
исчезала.

Снимок, а не повтор по логу ввода: повтор даёт тот же забег, но десять
минут симуляции на бюджетном телефоне пересчитываются секундами, а снимок
восстанавливается сразу. Продолженный забег идёт бит в бит как непрерванный —
это проверяет `core-game/test/run-snapshot.test.ts`. Снимок годится только для
той версии контента и формата, на которой снят: после обновления игры
сохранение удаляется, а не продолжается с чужими числами.

**Хранилища:**

| Стор | Что | Хранится на устройстве |
|---|---|---|
| `settings` | режим экрана, громкость звука, вибрация | да |
| `diagnostics` | режим диагностики, запись забегов, оверлей FPS | да |
| `meta` | локальный рекорд времени выживания, число забегов, последнее стартовое оружие | да |
| `install` | `installId` | да, создаётся один раз |
| `navigation` | стек экранов | нет |
| `run` | состояние текущего забега для оверлеев | нет |
| `run-save` | снимок прерванного забега | да, один; удаляется, когда забег кончился |

Хранение на устройстве — через интерфейс хранилища ключ-значение от
адаптера, а не прямым `localStorage` из оболочки. На этапе 2 все адаптеры
реализуют его поверх `localStorage` с обработкой исключений (в приватных
режимах и при переполнении он бросает). Если тест покажет потерю данных на
iOS — Telegram-адаптер переходит на `DeviceStorage` без правки оболочки.

Данные из хранилища — **граница системы**: читаются Zod-схемой с версией,
битое значение сбрасывается к умолчанию с событием `client_error`, а не
роняет запуск. Исключение — одиночные скаляры вроде локального рекорда: у них
версия в имени ключа, а проверка — `Number.isFinite` и границы правдоподобия;
схема появляется вместе с первым объектом в хранилище
(`15-engineering-standards.md` §5).

На этапе 2 порт называется `KeyValueStorage` (`shared-types`) и приходит от
адаптера площадки: до появления оболочки его читает движок — там же живёт
локальный рекорд (`26-stage2-plan.md`, WP3).

## 7.1 Настройки игрока

Настройки — часть игры, а не свалка переключателей: каждый отвечает на
вопрос «мне это мешает», и у каждого есть умолчание, которое считается
правильным.

| Раздел | Что внутри | Умолчание |
|---|---|---|
| Экран | полноэкранный режим | как отдаёт площадка |
| Звук | общая громкость, бой, интерфейс, музыка, вибрация | музыка выключена (`31-audio-and-haptics.md` §6), интерфейс громче эффектов |
| Графика | телеграфы угроз, эффекты оружия, числа урона | включено всё |
| Подсказки | сбросить подсказки первого забега | — |
| Для тестировщиков | режим диагностики, запись забегов, оверлей FPS | по сборке (`28-diagnostics.md` §2.1) |

**Графика** (`state/graphics.ts`, `bh.graphics.v1`) уходит в забег
`RunOptions.graphics` и доходит до `WorldRenderer`; режим разработчика
перебивает её своими выключателями. Экран предупреждает прямо: телеграфы и
эффекты — способ прочитать бой, и без них ощущение от игры другое. Поэтому
выключатели даны ровно там, где эффект дорогой или мешает лично игроку, а не
на каждый эффект подряд.

Без выключателя — то, без чего бой не прочитать. Так решён пульс
неуязвимости после второго шанса (`core-game/src/game/render/invulnerable.ts`):
без него непонятно, почему враги не ранят и когда начнут. Пульс мягкий —
прозрачность, а не вспышка, — и не чаще трёх раз в секунду.

**Правило: настройки не отстают от игры.** Появилась заметная анимация,
эффект или звук — в том же PR решается, попадает ли он под существующий
переключатель, нужен ли новый или он обязателен для чтения боя. Умолчания
пересматриваются так же: звук, который надоедает к третьему забегу,
выключается по умолчанию, а не «остаётся, раз уже написан». Иначе экран
настроек через полгода описывает прошлую игру, и игрок выключает не то, что
ему мешает. Проверка — в `pre-pr` и в Definition of Done
(`15-engineering-standards.md` §11).

- Тексты ошибок и сообщений для игрока — на русском, без технических
  подробностей; технические подробности — в `client_error`.
- Тон — от геймдизайнера; до его решения — нейтральный, без канцелярита.

## 9. Тестирование и витрина компонентов

Автоматически **не** тестируются вёрстка и внешний вид
(`17-testing-strategy.md` §1). Тестируется логика — всё перечисленное ниже
реализовано в WP5:

- стек экранов и связь с кнопкой «назад» — `app-shell/test/navigation.test.ts`;
- расчёт отступов безопасной зоны из платформенных значений —
  `adapter-telegram/test/insets.test.ts`;
- синхронизация `tokens.css` и `index.ts` пакета токенов (§4.2) —
  `design-tokens/test/tokens.test.ts`, он разбирает сам CSS, а не сверяется со
  списком: список стал бы третьей копией; подключение пакета, шрифты и отступы
  площадки — `app-shell/test/tokens.test.ts`;
- чтение хранилища: битые данные, старая версия схемы, отсутствие хранилища —
  `app-shell/test/persisted.test.ts`;
- множественное число и подстановки в текстах — `app-shell/test/i18n.test.ts`;
- правила импортов §2 — тестом по исходникам,
  `scripts/test/layer-boundaries.test.ts`;
- контрактные тесты новых методов `PlatformAdapter` — одинаково для всех
  адаптеров, включая no-op заглушки MAX и VK (`17-testing-strategy.md` §5):
  `shared-types/test/platform-ui.test.ts` проверяет эталонную пустую
  реализацию, которую эти заглушки и используют.

**Витрина компонентов** — экран внутри приложения, доступный в режиме
диагностики: все компоненты во всех состояниях. Вместо Storybook, и это
лучше него для нашей задачи: компоненты видны в настоящем WebView Telegram
на настоящем устройстве, с настоящими отступами безопасной зоны, а не в
десктопном браузере.

Экраны забега и запуска открываются в витрине **на тестовых данных**:
заставка, загрузка забега, выбор улучшения (обычный и с самыми длинными
текстами словаря), пауза, смерть в режиме диагностики и с новым рекордом.
Иначе, чтобы проверить экран смерти в ландшафте 568×320, пришлось бы в этом
ландшафте умереть.
