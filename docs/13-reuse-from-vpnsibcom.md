# Перенос наработок из vpnsibcom_api / vpnsibcom_web

Источники:

- [`Kennix88/vpnsibcom_api`](https://github.com/Kennix88/vpnsibcom_api) — NestJS 11
  (Fastify) + Prisma 7 + PostgreSQL + Redis (ioredis) + BullMQ + Telegraf,
  версия 1.11.0
- [`Kennix88/vpnsibcom_web`](https://github.com/Kennix88/vpnsibcom_web) — Next.js 15
  + React 19 + `@tma.js/sdk-react` + Zustand + Tailwind 4, версия 1.11.0

Оба репозитория — работающий продакшен-продукт в Telegram Mini Apps. Это
основная причина, по которой первой платформой выбран Telegram
(`02-roadmap.md` §«Приоритет платформ»): у нас есть проверенные боем решения
доменных задач — валидация `initData`, верификация рекламных наград, атрибуция
трафика, рефералка.

**Но это документ не про копирование.** Ниже — §1 задаёт обязательную политику
переноса, §2 показывает на конкретных примерах, почему копирование как есть
недопустимо, §3-§11 разбирают блоки по существу.

---

## 1. Политика переноса — обязательная

Правила ниже имеют силу требования, а не рекомендации. Их нарушение — основание
не принять PR (`06-team-and-workflow.md`, гейт ревью).

### 1.1 Пять правил

**Правило 1. Перенос — это адаптация, а не копирование.**
Каждый перенесённый фрагмент проходит переработку под доменную модель игры,
под нашу архитектуру слоёв (`15-engineering-standards.md` §2) и под наш стек
(`16-tech-stack-decisions.md`). Дословно скопированный файл, отличающийся от
оригинала только импортами, — дефект ревью, а не выполненная задача.

**Правило 2. Источник — точка вдохновения, а не эталон.**
Если решение в источнике не является хорошей реализацией — пишем свою,
лучшую. Источник в этом случае ценен как **спецификация требований и краевых
случаев**: он показывает, какие ситуации реально возникают в бою (ушедший
клиент, дубль запроса, replay рекламной награды, старый аккаунт по чужой
рефералке), а не как их следует обрабатывать в коде.

**Правило 3. Код осовременивается.**
Перенесённый код приводится к актуальным версиям библиотек и текущим языковым
возможностям, а не тащит за собой старые API и обходные пути. Конкретно:
валидация на Zod вместо `class-validator`, композиция вместо наследования от
клиентов библиотек, `node:`-префиксы для встроенных модулей, отсутствие
`any`/`@ts-ignore`/`// eslint-disable` без письменного обоснования в коде.
Целевые версии и обоснование выбора — `16-tech-stack-decisions.md`.

**Правило 4. Каждый перенесённый блок проходит проверку безопасности и
устойчивости к нагрузке.**
Это не «посмотреть глазами». Это два формальных чек-листа из
`15-engineering-standards.md` (§7 безопасность, §8 нагрузка), пройденные
построчно, с отметкой в описании PR. Перенос без пройденных чек-листов не
мержится. Причина — в §2: в источнике есть ошибки, которые проявляются именно
под нагрузкой и именно в атаке, то есть ровно тогда, когда цена ошибки
максимальна.

**Правило 5. Перенос без тестов не считается переносом.**
На перенесённую логику пишутся тесты **до** мержа, минимум — на краевые
случаи, ради которых блок и переносится (`17-testing-strategy.md`). В
источнике настроен jest и **ноль тестов** — повторять это мы не будем.

### 1.2 Как классифицируем блоки

| Вердикт | Что означает |
|---|---|
| **Опора** | Решение в источнике по существу верное. Берём как основу: переписываем под нашу доменную модель, обновляем API и зависимости, декомпозируем, покрываем тестами |
| **Переработка** | Задача поставлена верно, реализация слабая. Пишем свою реализацию; источник читаем ради списка краевых случаев |
| **Только идея** | Берём подход, структуру данных или последовательность шагов. К коду не обращаемся |
| **Не берём** | Не применимо к игре или противоречит нашим решениям |

Вердикта «копируем как есть» в этой таблице нет намеренно.

### 1.3 Процедура переноса одного блока

1. Прочитать оригинал целиком и **выписать список краевых случаев**, которые
   он обрабатывает. Это главная извлекаемая ценность — она добыта в
   продакшене и стоит дороже самого кода.
2. Спроектировать свою реализацию под нашу модель слоёв. Если получается
   проще — значит, часть сложности источника была наносной, это нормальный
   результат.
3. Прогнать чек-листы безопасности и нагрузки (`15-engineering-standards.md`
   §7-§8).
4. Написать тесты на выписанные в п. 1 краевые случаи.
5. В PR — раздел «Перенос»: что взято, что переделано и **почему**, какие
   находки из §2 закрыты.

## 2. Аудит источника: почему копирование недопустимо

Раздел разбирает конкретные места. Он не про качество работы авторов —
продукт работает и приносит деньги — а про то, что при переносе эти места
воспроизводить нельзя. Многие из них авторы уже осознают: в коде есть
комментарии `ИСПРАВЛЕНО:` и `[БАГ #N]` с разбором прошлых ошибок.

### 2.1 Безопасность

**(A) Обход rate-limit и сканера через подделку `X-Forwarded-For` — критично.**
В `src/main.ts` и allow-list `@fastify/rate-limit`, и хук-сканер берут IP так:

```ts
const ip = (req.headers['x-forwarded-for'] as string)?.split(',')[0]?.trim() || req.ip || ''
return isInternalIp(ip)   // → true = лимиты не применяются
```

Первый элемент `X-Forwarded-For` полностью контролируется клиентом. Запрос с
заголовком `X-Forwarded-For: 10.0.0.1` считается внутренним — и rate-limit
отключается. При этом `trustProxy` уже включён, то есть у Fastify есть
корректно вычисленный `req.ip`, но его игнорируют в пользу сырого заголовка.

*Наше решение*: доверять только `req.ip` при настроенном `trustProxy` и явном
списке доверенных прокси; внутренние вызовы аутентифицировать отдельным
секретом, а не по форме IP-адреса.

**(B) Сканер пропускает любой запрос с заголовком `Authorization`.**
Там же: `if (request.headers.authorization || request.headers['x-api-key']) return` —
проверка на подозрительные пути и ботовые UA не выполняется. Заголовок может
быть любым мусором, его никто на этом этапе не валидирует.

*Наше решение*: фильтрация мусорного трафика — задача периметра (Caddy/CDN), а
не хука приложения. В приложении остаётся аутентификация, а не эвристики по
User-Agent. Заодно уходит хрупкий блок-лист, который в источнике режет
`postman`, `java/`, `go-http-client` — то есть и легитимные интеграции тоже.

**(C) Тихий небезопасный дефолт секрета.**
`PreventDuplicateInterceptor`: `this.HMAC_SECRET = process.env.HMAC_SECRET || 'default-secret'`.
Если переменная не задана, приложение стартует с публично известным секретом и
никак об этом не сообщает.

*Наше решение*: **валидация всей конфигурации при старте** (Zod-схема env,
`16-tech-stack-decisions.md` §6). Нет секрета — процесс не поднимается.
Дефолтов у секретов не бывает.

**(D) Кеш ответа с деградацией личности до IP.**
Тот же интерцептор кеширует **тело ответа** в Redis по хэшу от
(метод + путь + тело + query + личность), где личность при отсутствии JWT —
это IP. За общим NAT/CGNAT два разных пользователя дают один ключ и второй
получает ответ первого.

*Наше решение*: идемпотентность только по явному клиентскому ключу
(`Idempotency-Key` / `runId`), только на изменяющих запросах, только для
аутентифицированного пользователя, с ключом, включающим `userId`.

**(E) Блэклист токенов по полному JWT в ключе.**
`blacklist:${token}` — весь JWT становится частью ключа Redis, попадает в
`MONITOR`, slowlog и дампы памяти.

*Наше решение*: блэклист по `jti` с TTL до `exp`.

**(F) Валидация `initData` без явного окна свежести.**
`isValid(initData, botToken)` вызывается без параметра `expiresIn` — значение
берётся из умолчания библиотеки, то есть окно повторного использования
`initData` фактически не контролируется нами.

*Наше решение*: `expiresIn` задаётся явно и коротко, значение вынесено в
конфигурацию, покрыто тестом на просроченный `initData`.

**(G) Прод-compose публикует Postgres и Redis на хост.**
`ports: '5432:5432'` и `'6379:6379'` в боевом `docker-compose.yml`. Пароль
Redis при этом собирается shell-скриптом через `echo` в конфиг.

*Наше решение*: только `expose`, без публикации портов; доступ к БД — через
SSH-туннель. Конфиг Redis — файлом, пароль — через secrets, не через
интерполяцию в командной строке.

**(H) Заголовки безопасности отключены.**
На бэке `helmet` подключён с `contentSecurityPolicy: false`; на фронте весь
блок `headers()` с CSP, HSTS, `X-Frame-Options` закомментирован.

*Наше решение*: CSP настраивается сразу и с учётом того, что Mini App
загружается во фрейме мессенджера — то есть `frame-ancestors` описывает
разрешённые платформы, а не запрещает фреймы полностью. Это не «сделаем
потом»: подключение рекламных SDK (`§5`) без заданной CSP превращает третью
сторону в неограниченного исполнителя кода на нашей странице.

### 2.2 Корректность и поведение под нагрузкой

**(I) Счётчик rate-limit неатомарен.**
`RedisThrottlerStorage.increment()` делает read-modify-write: `getRecord()` →
мутация в памяти процесса → `setRecord()`. Два параллельных запроса читают
одно значение и оба пишут `n+1` вместо `n+2`. То есть лимит перестаёт работать
именно при высокой конкурентности — ровно в сценарии, ради которого он нужен.

*Наше решение*: атомарный Lua-скрипт (или `INCR` + `EXPIRE` в одном
`pipeline`), плюс тест на конкурентный инкремент.

**(J) Гонка при регистрации refresh-токена.**
`registerRefreshToken()`: внутри `multi()` — `set` + `sadd`, а следом
**вне** транзакции `ttl()` и условный `expire()`. Между чтением и записью TTL
влезает параллельный вход с другого устройства.

*Наше решение*: одна атомарная операция (Lua), либо схема, где TTL сета не
требует чтения.

**(K) Интерцептор блокирует запрос до 3 секунд.**
При занятом локе `handleConcurrentRequest` опрашивает Redis 10 раз по 300 мс.
Под нагрузкой это удерживает соединения и выедает пул именно тогда, когда
дублей больше всего.

*Наше решение*: дубль получает немедленный `409`/`425` с `Retry-After`, а не
удерживаемое соединение.

**(L) Усиление логов.**
Тот же интерцептор шлёт в Telegram-очередь событие на **каждое** попадание в
кеш и на каждый взятый лок. При всплеске трафика очередь логов становится
узким местом и глушит настоящие ошибки.

*Наше решение*: в Telegram — только `warn`/`error` с дедупликацией и
rate-limit на сам алерт; остальное — в pino и метрики
(`14-scalability.md` §6).

**(M) Ошибки Redis схлопываются в `null`.**
`getObject()` возвращает `null` и при отсутствии ключа, и при битом JSON, и
при недоступности Redis. Авторы отметили это комментарием и оставили как есть.

*Наше решение*: разделить «нет значения» и «хранилище недоступно». Для кеша
допустима мягкая деградация, но вызывающий код должен иметь возможность её
отличить — иначе сбой Redis выглядит как «данных нет» и приводит к неверным
решениям (например, к повторной выдаче награды).

### 2.3 Сопровождаемость

**(N) Линт-гейт формальный.** В `eslint.config.mts` источника выключены
`@typescript-eslint/no-explicit-any`, `no-unused-vars` и `ban-ts-comment`. То
есть основные правила, ради которых линт и нужен в TS-проекте, отключены.
*У нас*: см. `15-engineering-standards.md` §5 — эти правила включены как
`error`, `@ts-ignore` требует `@ts-expect-error` с описанием причины.

**(O) Тестов нет.** jest сконфигурирован, спеков — ноль.
*У нас*: `17-testing-strategy.md`, гейт покрытия в CI.

**(P) God-сервисы.** `users.service.ts` — 1054 строки, `ads.service.ts` — 862,
`new-era.service.ts` — около 1400.
*У нас*: границы модулей и лимиты сложности — `15-engineering-standards.md` §2, §5.

**(Q) Сгенерированный Prisma-клиент закоммичен** в `src/core/prisma/generated`
(десятки файлов в диффах, конфликты при мерже).
*У нас*: генерация в `postinstall` и в CI, каталог в `.gitignore`.

**(R) Дублирование утилит.** `token.service.ts` содержит собственный
`parseExpiryToSeconds()` при существующем `shared/utils/ms.util.ts` в том же
репозитории.

**(S) Дублирующиеся зависимости.** Одновременно `@nestjs/platform-express` и
`@nestjs/platform-fastify`, `express-session` и `@fastify/session`,
`cookie-parser` и `@fastify/cookie`, `redis` и `ioredis` и `keyv` и
`cache-manager`. Это лишняя поверхность атаки в supply chain и источник
путаницы.
*У нас*: одна библиотека на задачу, `16-tech-stack-decisions.md` §9.

**(T) Комментарии-чейнджлоги.** `// ИСПРАВЛЕНО: раньше…`, `// [БАГ #5]…` —
история изменений внутри кода.
*У нас*: «почему» — в комментарии, «что было раньше» — в git и описании PR
(`CLAUDE.md`, раздел про комментарии).

**(U) Бизнес-конфиг как одна строка на ~50 колонок.** Таблица `Settings` с
единственной записью: новая ручка = миграция схемы, нет валидации значений,
нет истории изменений.
*У нас*: типизированный конфиг с Zod-валидацией и версионированием,
`16-tech-stack-decisions.md` §6.

**(V) Несогласованные денежные типы.** `AdsViews.rewardStars` — `Float`, тогда
как остальные балансы — `Decimal(18,6)`.
*У нас*: `Decimal` для всего, что имеет денежный или наградной смысл, без
исключений (`14-scalability.md` §3).

**(W) `@ts-ignore` вместо типизации.** `ad-session.guard.ts` читает
`req.body.verifyKey` через два `@ts-ignore` подряд.
*У нас*: типизированное тело запроса через Zod-схему, `@ts-ignore` запрещён.

## 3. Каркас бэкенда

**Что есть в источнике.** Bootstrap на `FastifyAdapter` с `trustProxy`,
compression, cookie, helmet, JWT, сессии в Redis, rate-limit, CORS по списку
origin, `ValidationPipe`, pino, глобальный exception-фильтр. Плюс `RedisService`
с распределёнными локами, `PrismaService` на `@prisma/adapter-pg`, прод-Dockerfile
(трёхстадийный, `dumb-init`, непривилегированный пользователь, healthcheck).

**Вердикт: опора, с переработкой bootstrap и `RedisService`.**

Берём: набор плагинов и порядок их регистрации, `retryStrategy` и
`reconnectOnError` на `READONLY` (нужен при Sentinel-failover), graceful
shutdown, форму Dockerfile и `entrypoint.sh` с `prisma migrate deploy`.

Переделываем:

| Что | Как у нас |
|---|---|
| `main.ts` на ~250 строк с инлайновым сканером и WAF-регулярками | Тонкий `bootstrap()`; фильтрация мусора — на периметре (§2.1 B); конфигурация плагинов — отдельными модулями |
| `RedisService extends Redis` | Композиция: `RedisConnection` (соединение) + `CacheService` + `LockService`. Наследование от клиента библиотеки экспортирует наружу весь её API и делает подмену в тестах невозможной |
| Логика локов внутри того же класса, что и соединение | Отдельный `LockService` с явным контрактом и тестами на истечение/чужой токен/автопродление |
| Конфигурация через `getOrThrow` в момент использования | Zod-схема env, валидация при старте — падаем сразу, а не при первом обращении |

Особая ценность источника — **`withLock` с автопродлением**: лок берётся с
TTL, а фоновый интервал продлевает его, пока задача выполняется, со сверкой
токена через Lua. Это закрывает три наши задачи сразу — идемпотентность
вебхуков, защита от гонок при начислении наград, «одна крон-задача на все
реплики» (`14-scalability.md` §3). Реализацию берём за основу, но выносим в
отдельный сервис и добавляем то, чего в источнике нет: тест на потерю лока
между продлениями (`fn()` должна уметь об этом узнать, а не продолжать
выполняться, думая, что владеет локом).

## 4. Авторизация: Telegram initData + JWT

**Что есть.** Полный цикл: `initData` → валидация через
`@tma.js/init-data-node` → поиск/создание пользователя → пара
access/refresh → refresh в Redis с ротацией и блэклистом. Мультидевайс через
`SET` на пользователя. Гвард умеет брать токен и из cookie, и из
`Authorization`. Троттлинг 5/мин на `/auth/telegram` и `/auth/refresh`.

**Где.** `src/core/auth/**` (guards, services, decorators, controller).

**Вердикт: опора — самый ценный блок для этапа 3.**

Краевые случаи, добытые в бою, — берём все:

- **клиент ушёл до ответа**: `req.raw.on('close')` и молчаливый выход, иначе
  Fastify пишет в закрытый поток;
- **компенсирующий откат**: если выпуск новой пары упал уже после блэклиста
  старого refresh — блэклист снимается, иначе пользователь заперт;
- **TTL сета токенов продлевается только вверх** — иначе новый вход с одного
  устройства срезает живые сессии остальных;
- **блэклист только при положительном TTL** — истёкший токен блэклистить
  бессмысленно.

Переделываем:

1. **Идентичность.** В источнике `JwtPayload` — `{ sub, telegramId, role }`.
   У нас аккаунты не связываются между платформами (`08-web-and-identity.md` §3),
   значит payload — `{ sub, platform, platformUserId, role, jti }`, а
   `telegramId` не является ключом идентичности **нигде**. Это правка,
   которую нужно сделать в момент переноса: иначе Telegram-специфика
   расползётся по коду и разрушит платформенную границу (`01-tech-stack.md` §1).
2. **Блэклист по `jti`**, не по телу токена (§2.1 E).
3. **Явный короткий `expiresIn`** при валидации `initData` (§2.1 F).
4. **Атомарная регистрация refresh-токена** (§2.2 J).
5. **Типизированные ошибки** вместо `return false` в гварде: сейчас все
   причины отказа схлопываются в один 403 без диагностики.
6. **DTO на Zod** вместо `class-validator`.

**Про MAX и VK.** Каркас (`TokenService`, гварды, декораторы, контроллер)
платформонезависим — меняется только стратегия валидации. `MaxAuthGuard` и
`VkAuthGuard` встают рядом с `TelegramAuthGuard`, `AuthService` получает
единую точку входа. Это ровно архитектура из `01-tech-stack.md` §4 — перенос
её реализует, а не подменяет.

## 5. Рекламный модуль: цепочка провайдеров с верификацией награды

**Что есть.** Не «вставить SDK», а подсистема:

- **`AdsBlocks`** — рекламные места в БД (`TASK`, `REWARD_TASK`, `BANNER`,
  `FULLSCREEN`, `MESSAGE`, `FEED`) с флагами показа по платформам
  (`showAndroid`/`showIos`/`showDesktop`/`showBot`/`showWeb`), длительностью,
  лимитом;
- **`AdsNetworks`** — сети (`ADSGRAM`, `TADDY`, `RICHADS`, `MONETAG`, …) с
  `isActive` и `priority` — отсюда fallback-цепочка;
- **подписанная одноразовая сессия показа**: `POST /ads/get/:place/:type`
  кладёт мету в Redis (`ad:session:meta:<sid>`) и возвращает JWT `verifyKey` на
  отдельном секрете; после показа `POST /ads/confirm` проверяет подпись,
  мету, совпадение `userId` и что сессия ещё не использована;
- **`AdsViews`** — журнал с `claimedAt`, IP/UA, наградой и индексами
  `(userId, createdAt)`, `(userId, claimedAt)`;
- **кулдауны** `nextAdsRewardAt` / `nextAdsgramTaskAt` на пользователе.

**Вердикт: опора для механики сессии, переработка реализации.**

Механика «подписанная одноразовая сессия показа» — правильная и обязательная:
без неё кнопка «награда за просмотр» превращается в бесплатный кран валюты.
Берём принцип целиком.

Переделываем:

- **`verifyKey` не должен быть JWT в колонке `String @unique`.** Индекс по
  длинной строке, токен в БД. У нас — короткий непредсказуемый идентификатор
  сессии, подпись проверяется отдельно.
- **Проверка «использована ли сессия» — атомарная.** В источнике это
  `get` → сравнение → дальнейшая работа: два параллельных `confirm` могут оба
  пройти проверку. Награда обязана начисляться в одной атомарной операции
  (`SET NX` на `used`-ключ + начисление в транзакции), иначе двойное
  начисление воспроизводится тривиально.
- **`rewardStars` → `Decimal`** (§2.3 V).
- **Декомпозиция** `ads.service.ts` (862 строки) на: выбор блока/сети,
  жизненный цикл сессии, начисление награды, интеграции провайдеров за общим
  интерфейсом.

Связь с нашими документами: `07-monetization-and-ads.md` §3 требует логики
«кнопка награды доступна/недоступна в зависимости от платформы и
антирекламного пакета» — таблица `AdsBlocks` с флагами `show*` реализует это
данными, без ветвлений по платформе в коде, что совпадает с принципом «контент
как данные» (`01-tech-stack.md` §9).

**Фронт.** `adDisplayLock.ts` (два рекламных виджета не показываются
одновременно) — идея обязательная: fullscreen поверх активного забега = плохой
отзыв. Реализацию пишем свою, с учётом того, что у нас есть игровой цикл, из
которого нужно корректно выйти (пауза, приглушение звука, возврат фокуса).

**Не берём:** `graspil.service.ts` (аналитика стороннего сервиса),
`ads-sender.service.ts` (рассылка рекламных сообщений в бот).

## 6. Атрибуция трафика: startParam, Sessions, Acquisition, Events

**Что есть.**

- `parseStartParamUtil` — парсер `startParam` формата
  `r-<ref>_source-<src>_compaing-<id>_record-<id>` плюс ветка `_tgr_<id>`;
- `Sessions` — запись каждого входа: place, IP, UA, разобранные
  `browser`/`device`/`os` через `ua-parser-js`, страна, источник/кампания,
  платформа Telegram; **окно дедупликации 30 секунд** — без него один запуск
  Mini App пишет несколько сессий;
- `Acquisition` — first-touch и last-touch атрибуция на пользователя;
- `Events` — воронка (`REGISTRATION`, `ACTIVATION`, `FIRST_PAYMENT`, …).

**Вердикт: опора по модели данных, переработка реализации записи.**

Модель (сессия / первое касание / последнее касание / событие) — правильная,
берём. `EventTypeEnum` меняем под игровую воронку: `FIRST_RUN`,
`RUN_COMPLETED`, `FIRST_PURCHASE`, `AD_REWARD_CLAIMED`, `D1_RETURN`.

Переделываем: в источнике `createSession` выполняет `SELECT … FOR UPDATE` по
строке пользователя и пишет сессию **синхронно, в транзакции, на горячем пути
авторизации**. Это блокировка строки пользователя на каждый вход — под
всплеском трафика (а всплеск в мессенджере — это норма, `14-scalability.md` §1)
такая схема создаёт очередь на самой популярной строке. У нас запись сессии
уходит в очередь (BullMQ) и не задерживает ответ игроку; дедупликация делается
Redis-ключом с TTL, а не блокировкой в БД.

`detect-platform.util.ts` (UA → `DESKTOP`/`IOS`/`ANDROID`/`WEB`/`BOT` + ОС) —
**переработка**: цепочка `includes()` по строке UA хрупкая, но сама
классификация нужна и рекламному таргетингу, и разрезу FPS/крэшей по
платформам (`01-tech-stack.md` §8 — производительность WebView названа главным
техническим риском, и мерить его нужно именно в этом разрезе).

**Когда переносить:** на этапе 3, вместе с авторизацией. Сессии, не
записанные в первые недели, задним числом не восстановятся, а этап 5
роадмапа требует мерить retention D1/D3/D7 и эффективность посевов
(`04-marketing-plan.md`).

## 7. Реферальная программа

**Что есть.** Трёхуровневая система: `Referrals` с уникальным индексом по
тройке `(inviterId, referralId, level)`, проценты по уровням в `Settings`,
начисление комиссий внутри транзакции платежа, статистика через `groupBy` на
стороне БД (а не выгрузкой строк в память — это правильно, берём).

Ценная часть — **антифрод привязки** в `auth.service.ts`: реферал
привязывается, только если у аккаунта нет уже привязанного пригласившего **и**
аккаунт моложе 3 суток. Иначе старый игрок, кликнувший чужую ссылку,
бесплатно засчитывался бы как приведённый.

**Вердикт: опора по антифроду, переработка экономики.**

Три уровня с денежными процентами — модель подписочного VPN-сервиса. В игре
берём каркас и антифрод, экономику упрощаем: один уровень, награда в
мета-валюте за игрока, который **дошёл до определённой волны**, а не просто
открыл приложение. Порог активации — параметр баланса, зона геймдизайнера
(`CLAUDE.md`, зоны ответственности).

Связь: `03-notes-and-risks.md` фиксирует, что виральность не встроена в жанр и
её надо достраивать. Рефералка + шеринг результата забега (этап 4) — этот
слой, и хорошо, что его не надо изобретать.

## 9. Наблюдаемость и эксплуатация

**Что есть.**

- **Логи в Telegram через BullMQ**: `LoggerTelegramService` кладёт в очередь,
  `TelegramLogWorker` разбирает и шлёт в разные треды супергруппы по уровню и
  теме, с дедупликацией через Redis и 5 попытками с экспоненциальным backoff;
- **`RedisThrottlerStorage`** — троттлинг через общий Redis;
- **`pg-backup`** — дамп Postgres каждые 6 часов с отправкой в Telegram-тред;
- **Caddy** с автоматическим TLS, Grafana + Prometheus в compose.

**Вердикт: опора по идее, переработка двух мест.**

Логи в Telegram — правильный выбор для команды из трёх человек без дежурств
(`06-team-and-workflow.md` не предполагает другого канала алертов). Но:

- **уровни и объём** — только `warn`/`error` с дедупликацией и лимитом частоты
  самих алертов (§2.2 L);
- **`RedisThrottlerStorage` переписывается на атомарный счётчик** (§2.2 I) —
  и переносится вместе с каркасом, не «потом»: переход на несколько реплик
  API описан как первый шаг масштабирования (`14-scalability.md` §3), а
  in-memory-троттлинг молча умножает реальный лимит на число реплик.

`PreventDuplicateInterceptor` — **не берём** в текущем виде (§2.1 C, D; §2.2 K,
L). Задача идемпотентности решается явным ключом на изменяющих запросах, см.
`15-engineering-standards.md` §4.

`pg-backup`, Caddy, Prometheus/Grafana — опора, с проверкой восстановления:
бэкап, из которого ни разу не восстанавливались, бэкапом не является. Учебное
восстановление — пункт чек-листа софт-лонча.

## 13. Два решения, которые нужно принять до первого переноса

**Лицензии.** `vpnsibcom_*` — CC BY-NC-SA 4.0, этот репозиторий — PolyForm
Noncommercial 1.0.0. Оба автора в команде, внутреннее соглашение описано в
`12-ip-and-licensing.md`. Перенос между своими проектами допустим, но
формулировки нужно сверить **до** первого коммита с перенесённым кодом, а не
после.

**Приватность бэкенда. Решено на этапе 3: репозиторий остаётся публичным**
(`34-stage3-plan.md`, Р7). Изначально здесь стояло «перенос антифрод-логики —
тот самый момент, когда бэкенд нужно вынести в приватный репозиторий»
(`12-ip-and-licensing.md` §4). Пересмотрено: секрет — не структура проверки, а
её числа. Окно привязки реферала, правила верификации рекламной сессии и
пороги проверки забегов теряют смысл опубликованными, но сам код проверки —
нет. Поэтому в репозитории живёт структура, а значения — в конфигурации, и с
появлением редактора конфигурации (`19-content-admin.md` §9) переезжают в БД
вместе с остальным балансом. Разрезать монорепо ради этого пришлось бы по
живому: pnpm workspace, `shared-types`, общий CI и единая версия.
