# Админ-панель: роли, аналитика, бухгалтерия, рассылки

Единая рабочая среда команды: здесь меняют баланс, смотрят аналитику, ведут
учёт денег проекта, работают с игроками, делают рассылки в бота и посты в
каналы. Документ задаёт рамку — состав модулей, модель ролей, принципы
аналитики и учёта, порядок внедрения. Детальные спецификации модулей пишутся
перед реализацией соответствующего этапа.

Смежное: `19-content-admin.md` (модуль контента и баланса — часть этой
панели), `22-analytics-and-metrics.md` (события и витрины, на которых стоит
аналитика), `23-referral-and-partner-program.md` §4.4 (кабинет партнёра),
`11-revenue-split.md` (модель, которую реализует бухгалтерия),
`24-attribution-and-sharing.md` (отслеживаемые ссылки в рассылках).

---

## 1. Зачем своя панель, а не Grafana и таблицы

Раньше продуктовая аналитика планировалась в Grafana
(`22-analytics-and-metrics.md` §6), учёт дохода — в общей таблице
(`11-revenue-split.md` §5), редактор баланса — отдельным приложением
(`19-content-admin.md`). Решение пересмотрено: **одна своя панель**, Grafana
остаётся только для технической аналитики.

Почему:

- **Геймдизайнер и маркетинг не должны жить в Grafana.** Это инструмент
  инженера: язык запросов, панели, источники данных. Человек, который
  принимает решения по балансу, должен выбирать метрику и разрез, а не
  писать запрос.
- **Права по ролям.** Выручку, персональные данные игроков и учёт денег
  видят не все. В Grafana разграничение доступа к отдельным метрикам и
  строкам данных — борьба с инструментом; в своей панели — обычная проверка
  прав на сервере.
- **Партнёрам нужны дашборды** со строго своими данными
  (`23-referral-and-partner-program.md` §4.4). Тот же слой аналитики с
  принудительным фильтром — вместо второй системы.
- **Учёт денег требует фиксации.** Закрытый месяц не должен меняться задним
  числом, распределение дохода должно считаться по формуле, а не руками в
  таблице. Таблица это не гарантирует.
- **Своя среда надёжнее**: одна авторизация, один аудит действий, данные не
  расползаются по сторонним сервисам.

Что остаётся в **Grafana**: метрики Prometheus — задержки и ошибки API,
очереди, Postgres, Redis, хост, алерты. Быстрые технические графики для
участника 1, не продуктовые решения.

## 3. Роли и права

### 3.1 Роли

| Роль | Кто | Коротко |
|---|---|---|
| `owner` — владелец | участник 1 | Всё, включая назначение ролей, закрытие финансового периода и выплаты |
| `admin` — администратор | участник 2 | Операционка: игроки, реклама, флаги, одобрение рассылок, диагностика. Без бухгалтерии и ролей |
| `game_designer` — геймдизайнер | участник 3 | Контент и баланс, аналитика геймплея и экономики, симуляции |
| `moderator` — модератор | по мере роста | Игроки без платёжных данных, жалобы, блокировки, очередь антифрода |
| `marketer` — маркетолог | участник 2, позже отдельный человек | Рассылки, посты в каналы, атрибуция, аналитика привлечения, управление партнёрами без выплат |
| `finance` — финансы | владелец, позже бухгалтер | Ввод операций, подготовка выплат партнёрам; закрытие периода — только владелец |
| `analyst` — аналитик | по потребности | Только чтение дашбордов, без персональных данных |
| `stakeholder` — участник проекта | участники 1–3 | Свой расчёт распределения дохода и сводный финансовый отчёт (`11-revenue-split.md` §5) |

У пользователя может быть **несколько ролей**: участник 2 — `admin` +
`marketer` + `stakeholder`, участник 3 — `game_designer` + `analyst` +
`stakeholder`.

`partner` — не роль панели: партнёр работает в своём кабинете и в панель не
входит вообще.

### 3.2 Права — код, назначение ролей — данные

- **Право** — конкретное действие: `content.publish`, `analytics.revenue.view`,
  `players.pii.view`, `players.ban`, `broadcast.send`, `broadcast.approve`,
  `finance.entry.create`, `finance.period.close`, `data.export`,
  `roles.assign`. Список
  прав — перечисление в `shared-types`, меняется через PR.
- **Роль → права** — тоже в коде: состав роли меняется ревью, а не кликом.
  Иначе однажды «модератору временно дали посмотреть выручку» и забыли.
- **Пользователь → роли** — данные в БД, назначает владелец, каждое
  назначение в аудите.
- Произвольные роли из интерфейса — не на MVP; появятся, если набора выше
  перестанет хватать.

### 3.4 Правила

- **Закрыто по умолчанию.** Каждый эндпоинт панели объявляет требуемое право;
  эндпоинт без объявления — тест, который падает (`17-testing-strategy.md`
  §4.3). Интерфейс скрывает недоступное, но решает всегда сервер.
- **Аудит всех изменений** и чувствительного чтения (просмотр персональных
  данных, выгрузки): кто, когда, что, было → стало. Журнал не редактируется
  из панели (`19-content-admin.md` §8).
- **Правило двух ключей** для действий с прямым денежным или репутационным
  эффектом — инициирует один, подтверждает другой:
  - изменение цены (`19-content-admin.md` §6);
  - рассылка на аудиторию больше порога и любая рекламная рассылка;
  - выплата партнёру;
  - закрытие финансового периода — владелец закрывает, участники
    подтверждают отчёт до выплаты (`11-revenue-split.md` §4);
  - выдача ролей `owner` и `admin`.
- **Повторная авторизация** перед чувствительным действием: сессия панели
  может быть открыта часами, а закрытие периода — это не то, что должно
  случиться с забытого ноутбука.

## 4. Устройство

- **`apps/admin`** — отдельное приложение на отдельном поддомене: React 19 +
  Vite + Tailwind CSS 4 + Zustand, тот же стек, что оболочка игры
  (`27-design-system-and-app-shell.md` §1), но десктоп в первую очередь и
  плотные таблицы. Ни строчки админского кода в игровом бандле
  (`19-content-admin.md` §8).
- Базовые токены дизайна общие с игрой — выносятся в отдельный пакет
  токенов, когда появится панель: это второе применение, и дублировать
  палитру больше нельзя (`15-engineering-standards.md` §1, принцип 5).
  Компоненты — свои: таблица с фильтрами и форма операции не похожи на
  карточку апгрейда.
- **Бэкенд — модули в том же монолите** под `/api/v1/admin/*`, со своей
  стратегией сессии и гвардом прав. Отдельный сервис не нужен
  (`16-tech-stack-decisions.md` §10, микросервисы). Сделано на этапе 4 —
  `backend/api/src/modules/admin/` (`35-stage4-plan.md`, WP17, «Как
  сделано»): cookie `HttpOnly; SameSite=Strict` только на маршруты панели,
  хэш токена в Redis, заголовок панели на изменяющих запросах, права — тем
  же гвардом, что у игры.
- **Вход через Telegram**, два рубежа: список допущенных Telegram ID в
  окружении и роли в БД (`19-content-admin.md` §8).
- Порт dev — `ADMIN_PORT` (`20-env-and-ports.md` §2), кабинет партнёра —
  `PARTNER_CABINET_PORT`.

## 5. Аналитика в панели

### 5.1 Семантический слой вместо произвольных запросов

Метрики и разрезы **описаны в коде**: имя, определение поверх витрин,
допустимые разрезы, формат, свежесть, требуемое право, признак персональных
данных. Пользователь панели выбирает, а не пишет запрос:

- **метрику** — DAU, забеги, медиана длительности, частота выбора апгрейда,
  выручка, ARPPU, K-фактор…;
- **разрез** — платформа, источник, кампания, версия конфигурации, версия
  клиента, модель устройства, персонаж, оружие…;
- **период и шаг** — час, сутки, неделя; сравнение с прошлым периодом;
- **фильтры**;
- **вид** — линия, столбцы, воронка, когорты тепловой картой,
  распределение, таблица, одно число с изменением.

Произвольный SQL из панели — **нет**, и это не ограничение ради
ограничения:

- у каждого своё «DAU» — отчёты перестают сходиться
  (`22-analytics-and-metrics.md` §3.3, та же проблема, что со словарём
  событий);
- произвольный запрос обходит права на метрики и персональные данные;
- тяжёлый запрос кладёт реплику, с которой читают все.

Новая метрика — это PR с определением, как новое событие в словаре.

### 5.2 Дашборды

- **Готовые дашборды по ролям** — то, что было расписано для Grafana
  (`22-analytics-and-metrics.md` §6): Live, Геймплей и баланс, Монетизация,
  Привлечение, Реклама, Рефералы. Появляются первыми.
- **Конструктор**: свой график из метрики, разреза и вида; сохранение в
  личный или общий по роли дашборд. Появляется после готовых.
- Правила оформления из `22-analytics-and-metrics.md` §6 переходят сюда:
  у каждого графика подписаны период и свежесть, деньги всегда с разбивкой
  по платформе, сравнение с прошлым периодом там, где абсолютное число
  ничего не говорит.
- Выгрузка данных графика в CSV — с правом и записью в аудит.

### 5.3 Производительность

- Запросы — **только к витринам на реплике**, не к горячим таблицам
  (`22-analytics-and-metrics.md` §1).
- У каждого запроса таймаут и лимит строк; результат кешируется в Redis по
  ключу «запрос + окно свежести».
- Когорты и retention — предпосчитанные витрины, не расчёт на лету.
- Живые счётчики панели Live — из Redis через API, опрос раз в 10–15
  секунд. Prometheus для них не нужен.
- Если витрин на Postgres перестанет хватать — отдельное аналитическое
  хранилище по порогам из `14-scalability.md`, не раньше.

### 5.4 Кабинет партнёра на том же слое

- Тот же семантический слой, но **фильтр по партнёру навязывается сервером**
  и не приходит от клиента.
- Только агрегаты, без персональных данных приведённых игроков
  (`23-referral-and-partner-program.md` §4.4).
- **Порог размера группы**: разрез, в котором меньше N игроков, не
  показывается. Иначе агрегат по одной кампании с тремя игроками — это уже
  данные конкретных людей.

### 5.5 Библиотека графиков

Выбирается при реализации по критериям `16-tech-stack-decisions.md` §0.
Кандидаты: Apache ECharts (широкий набор, включая воронки и тепловые карты),
Recharts (простой React-API, беднее виды), uPlot (очень быстрые временные
ряды, мало видов). Панель десктопная, вес библиотеки здесь вторичен по
сравнению с игрой.

### 5.6 До появления панели

На этапе 2 аналитика — **выгрузка данных и разбор ИИ-агентом**
(`26-stage2-plan.md`, WP8), без дашбордов вообще. Вопросы, на которые
выгрузка должна отвечать, — `26-stage2-plan.md` §7; удачные разборы
становятся первыми кандидатами в готовые дашборды.

## 5.7 Обратная связь от игроков

Панели ещё нет, а спрашивать игроков надо уже сейчас: закрытый тест затем и
нужен. Форма живёт в клиенте, карточка зовёт с главной.

**Что собирается.** Три быстрых вопроса кнопками — сложность, что понравилось,
будет ли играть дальше — и свободное поле для пожеланий. Вопросы кнопками, а
не полями ввода: на телефоне в игре набирают текст единицы, а нажать три раза
готов почти каждый. Свободное поле остаётся для тех, кому есть что сказать, и
именно оно ценнее всего.

**Куда уходит.** Отзыв ложится в таблицу `feedback` **и** уходит сообщением в
чат администраторов (`ADMIN_CHAT_FEEDBACK`, по умолчанию общий адрес). База —
чтобы собрать сводку за неделю и не потерять отзыв, когда Telegram недоступен;
чат — чтобы прочитать сегодня. Неудачная отправка в чат не роняет запрос:
запись уже есть, в логе останется причина.

**Как забрать себе.** Команда бота `/feedback` в личном чате присылает
администратору CSV с последними отзывами — как `/export` с данными теста, но
без очереди и блокировок: отзывов десятки, а не гигабайты.

**Когда спрашиваем.** Карточка появляется после первого забега и дальше раз в
десяток забегов; отправленный отзыв помнится на устройстве. Спрашивать в
каждый запуск — верный способ, чтобы форму перестали замечать.

**Что в аналитике.** Событие `feedback_sent` — только факт и разрез: сколько
вопросов отвечено, был ли текст, сколько забегов сыграно
(`22-analytics-and-metrics.md` §3.3). Сам отзыв в события не попадает: у него
своя таблица и свой чат.

**Состав опроса задаёт клиент** (`shared-types`, `FEEDBACK_QUESTIONS`), сервер
проверяет форму, а не смысл: ключ и вариант — короткие слаги, пар немного. Так
вопрос добавляется без выката бэкенда, а в базу не попадёт ни длинная строка,
ни сотня полей. Подписи для чата — на сервере; неизвестный ключ показывается
как есть, и в чате сразу видно, что вопрос добавили, а подпись — нет.

## 6. Бухгалтерия

### 6.1 Что это и чем не является

Это **управленческий учёт проекта**: быстро внести факты о деньгах,
посчитать доходность, распределить доход по `11-revenue-split.md` и
зафиксировать всё это для последующего анализа.

Это **не** налоговый учёт и не замена бухгалтеру. Налоговая база и
декларации считаются по официальным источникам (банк, «Мой налог», учётная
система ИП). Расхождение между панелью и официальным учётом — повод найти
ошибку, а не выбрать удобную цифру (`11-revenue-split.md`, оговорка в
начале).

### 6.2 Модель

| Сущность | Что хранит |
|---|---|
| **Операция** | Тип (доход, расход, заём, погашение займа, налог, выплата участнику, выплата партнёру), категория, платформа, источник (сеть рекламы, Stars, эквайринг), сумма в исходной валюте, курс к рублю **на дату операции**, сумма в рублях, дата (UTC), период, вложения (чек, выписка), комментарий, автор |
| **Шаблон** | Повторяющаяся операция: VPS, CDN, домены — создаётся в месяц одним действием |
| **Период** | Календарный месяц: открыт → на сверке → закрыт |
| **Параметры периода** | Режим и ставка налога, ставка погашения займа, доли участников — **копируются в период при закрытии**, чтобы смена процентов в будущем не переписывала прошлые расчёты |
| **Расчёт распределения** | Результат водопада `11-revenue-split.md` §3 по закрытому периоду: выручка по источникам и платформам, расходы, налог, транш займа, прибыль к разделу, суммы участникам |
| **Заём** | Тело, премия, остаток — убывает траншами из расчётов периодов |

### 6.3 Правила

- **Суммы — `Decimal`**, никогда `Float` (`15-engineering-standards.md` §7).
- **Валюта исходная плюс курс на дату.** Stars, USDT и рубли не
  складываются напрямую; курс вносится фактический (по которому реально
  вывели или конвертировали), а не «примерно по рынку».
- **Закрытый период неизменяем.** Ошибка, найденная после закрытия,
  исправляется **корректирующей операцией** в открытом периоде со ссылкой на
  исходную. Правка закрытого месяца переписала бы уже выплаченное и уже
  разосланный отчёт (`11-revenue-split.md` §4).
- **Отчёт участникам формируется из закрытого периода** по составу
  `11-revenue-split.md` §5 и доступен им в панели до выплаты — прозрачность
  как обязательство, а не жест.
- **Партнёрские выплаты — расход** до раздела прибыли
  (`23-referral-and-partner-program.md` §4.6); панель берёт их из модуля
  партнёров, а не из ручного ввода.

### 6.4 Доходность

Потому учёт и живёт рядом с аналитикой, а не в таблице: деньги из учёта
соединяются с продуктовыми данными.

- маржа по платформам — экономика считается раздельно
  (`03-notes-and-risks.md`);
- стоимость привлечения по источнику: расходы на закупку трафика из учёта ÷
  активированные игроки из атрибуции;
- окупаемость канала: LTV когорты источника против стоимости её привлечения;
- доля выплат по программам привлечения от дохода — экономический
  предохранитель `23-referral-and-partner-program.md` §6;
- расходы на инфраструктуру на активного игрока — вход для
  `14-scalability.md`.

### 6.5 Ввод данных

- Первая фаза — **ручной ввод**, но быстрый: форма операции с клавиатуры,
  шаблоны повторяющихся расходов, загрузка вложения перетаскиванием.
- Импорт — CSV-выгрузки рекламных сетей и платёжных провайдеров, по одному
  формату за раз, по мере появления реальных выгрузок.
- Автоимпорт через API провайдеров — только там, где он окупится, и после
  того, как ручной процесс устоялся.

## 7. Рассылки в бота и постинг в каналы

### 7.1 Аудитория

Конструктор сегмента по фильтрам с оценкой размера аудитории до отправки:

- платформа и язык;
- источник: органика, реферал, партнёр, кампания, UTM (`24-attribution-and-sharing.md`);
- давность: дата регистрации, последний заход, число дней активности;
- прогресс: число забегов, лучшее время, достигнутый уровень;
- место в топе и лиге — когда появятся (`10-progression-and-ladder.md` §4);
- деньги: платящий или нет, сумма, давность последней покупки;
- исключения: получал рассылку за последние N дней, отписался, заблокировал
  бота.

Сегменты сохраняются и переиспользуются.

**Кому вообще можно писать.** Бот может написать только тому, кто начал с
ним диалог или разрешил боту писать из Mini App (запрос доступа на запись,
`requestWriteAccess`). Игрок, который только открыл Mini App, в аудиторию
рассылок не попадает, пока не дал разрешения. Запрос разрешения — отдельный
продуманный момент в игре, а не всплывающее окно на первом экране.

### 7.2 Сообщение

| Тип | Пример | Особенность |
|---|---|---|
| Сервисное | «Твой реферал активирован, награда начислена» | По событию, без ручного запуска; отключается только вместе со всеми уведомлениями |
| Информационное | Обновление, новый контент, итоги сезона | Лимит частоты на игрока |
| Удерживающее | «Ты не заходил 3 дня, новый враг ждёт» | Строгий лимит частоты, тихие часы |
| Рекламное | Промо партнёра, акция | **Маркировка рекламы** по закону о рекламе, если применимо (`07-monetization-and-ads.md` §2); всегда правило двух ключей |

Содержимое: текст с форматированием, медиа, кнопки — открыть Mini App с
параметром запуска, внешняя ссылка. **Каждая ссылка отслеживаемая** — свой код
на кампанию (`24-attribution-and-sharing.md` §3), иначе эффект рассылки не
отделить от органики.

Перед отправкой: предпросмотр, тестовая отправка себе, отправка на тестовый
сегмент.

### 7.3 Доставка

- Очередь BullMQ, отправка с ограничителем скорости под лимиты Bot API: для
  массовых рассылок Telegram ориентирует порядка 30 сообщений в секунду;
  платные рассылки (`allow_paid_broadcast`) дают больше за Stars. Точные
  лимиты сверяются с документацией при реализации.
- Ответ `429` — ожидание указанного `retry_after`, а не повтор сразу.
- Ответ `403` (бот заблокирован) — отметка у игрока, дальше он из аудиторий
  исключается.
- **Идемпотентность по паре (кампания, игрок)** — уникальный индекс: ретрай
  очереди или повторный запуск не шлёт сообщение дважды
  (`15-engineering-standards.md` §4.1).
- Отложенный запуск, пауза, отмена; прогресс в панели.
- Содержимое кампании после старта неизменяемо — иначе половина аудитории
  получила бы другой текст, чем видно в отчёте.
- Лимит частоты на игрока и тихие часы — параметры конфигурации.
- Отписка: настройка в игре и команда в боте; сервисные и рекламные
  сообщения — раздельные согласия.

### 7.4 Посты в каналы

- Бот — администратор канала с правом публикации.
- Черновики, расписание, закрепление, правка и удаление опубликованного.
- Шаблоны: список изменений из GitHub Release версии (`09-ci-cd.md` §8.1) —
  черновик поста о патче одним действием.
- Те же отслеживаемые ссылки и те же правила маркировки рекламы.

### 7.5 Аналитика рассылок

Отправлено, ошибки, заблокировали бота после рассылки, переходы по ссылкам,
запуски, забеги и покупки в окне после перехода. События рассылок
добавляются в словарь (`22-analytics-and-metrics.md` §3.3) при реализации
модуля — до кода, по общему правилу.

## 8. Безопасность панели

Помимо чек-листа `15-engineering-standards.md` §7:

- отдельный поддомен, отдельная cookie-сессия с коротким сроком жизни,
  `SameSite=Strict`;
- CSP без сторонних скриптов, кроме виджета входа Telegram;
- лимит частоты на вход и на чувствительные действия;
- выгрузки и просмотр персональных данных — в аудите;
- отзыв всех сессий пользователя при снятии роли — сразу, а не по истечении
  срока жизни;
- ни одного секрета окружения в интерфейсе панели: ключи сетей и токены ботов
  остаются в окружении сервера (`20-env-and-ports.md` §1).
