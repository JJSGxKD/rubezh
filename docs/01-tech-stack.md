# Технологический стек и архитектура

## 1. Общая архитектура

```
/packages
  /core-game          <- весь игровой движок, платформонезависимый
  /adapter-telegram    <- тонкий слой под Telegram WebApp SDK
  /adapter-max         <- тонкий слой под MAX Bridge / Web Apps SDK
  /adapter-vk          <- тонкий слой под VK Bridge (опционально, фаза 2)
  /adapter-web         <- браузерная версия, несколько auth-провайдеров внутри одного адаптера (см. 08)
  /shared-types        <- общие TS-интерфейсы (PlatformAdapter, User, PurchaseResult)
/apps
  /web-telegram        <- сборка под Telegram (env=telegram)
  /web-max             <- сборка под MAX (env=max)
  /web-vk              <- сборка под VK (env=vk, опционально)
  /web-browser         <- отдельная браузерная сборка (env=web, фаза 2)
/backend
  /api                 <- NestJS, единая точка входа для всех платформ
```

Принцип: **core-game ничего не знает о платформе**. Всё общение с внешним миром
идёт через интерфейс `PlatformAdapter`, три реализации которого различаются только
деталями авторизации, оплаты, шеринга и (опционально) рекламы.

```ts
interface PlatformAdapter {
  init(): Promise<UserContext>;          // id, имя, аватар
  purchase(itemId: string): Promise<PurchaseResult>;
  share(payload: SharePayload): void;    // шеринг результата забега
  haptic(type: HapticType): void;
  showAd?(): Promise<AdResult>;          // опционально, не везде доступно
}
```

Платформа определяется на этапе сборки (переменная окружения), а не в рантайме —
это отдельные регистрации мини-аппа на каждой площадке, рантайм-детект не нужен
и добавляет только точки отказа.

## 2. Фронтенд (игра)

| Компонент | Технология | Причина |
|---|---|---|
| Игровой движок | **Phaser 3** | Зрелый, много готовых примеров именно под arcade/roguelite, встроенная физика/коллизии, легко укладывается в canvas WebView |
| Сборка | **Vite** | Быстрый dev-сервер, легко параметризовать под 3 разные сборки через `--mode` |
| Язык | TypeScript | Общий стиль с остальным стеком |
| State/сохранения забега | локальный in-memory + синк на бэкенд по окончании забега | не гонять сеть во время самого геймплея |
| Ассеты | пиксель-арт / готовые ассет-паки (itch.io, Kenney.nl — многие под CC0) | не тратить время/бюджет на художника на старте |

## 3. Бэкенд

Выбранный стек — на основе стека, с которым команда уже имеет продакшен-опыт
(не изобретаем новый ради нового проекта). Конкретно: это стек `vpnsibcom_api`,
из которого переносится каркас и готовые модули — подробная инвентаризация в
`13-reuse-from-vpnsibcom.md`.

- **NestJS** — единая точка API для всех платформ
- **PostgreSQL + Prisma** — пользователи, забеги, покупки, лидерборды
- **Redis** — кэш лидербордов (сортированные множества, ZSET, отдаются мгновенно)
- **BullMQ** — асинхронная обработка вебхуков оплаты (идемпотентность, ретраи)
- **Docker Compose** — деплой по образцу текущей инфры

### Модули бэкенда

- `auth` — три отдельных стратегии валидации initData (Telegram HMAC, MAX Bridge подпись, VK `sign`), на выходе единый `AuthenticatedUser`
- `runs` — приём результатов забега, антифрод-проверка на разумность (защита от читерских забегов на клиенте)
- `leaderboard` — Redis ZSET, глобальный + "среди контактов/групп" (см. заметки о вирусности), кросс-платформенный агрегированный лидерборд и рейтинговые лиги — модель данных и обоснование в `08-web-and-identity.md`
- `payments` — три вебхук-хендлера → единое внутреннее событие `purchase.completed`
- `economy` — таблица цен **отдельно на каждую платформу** (Stars vs ₽), см. раздел 5

## 4. Авторизация по платформам

| Платформа | Механизм | Валидация на бэке |
|---|---|---|
| Telegram | `window.Telegram.WebApp.initData` | HMAC-SHA256 подписи токеном бота |
| MAX | MAX Bridge init-данные | подпись по документации MAX Bridge (уточнить актуальную схему на момент разработки — платформа меняет API довольно часто) |
| VK | VK Bridge (`vk-bridge` npm), `VKWebAppInit` | проверка `sign` секретом приложения |
| Web | несколько OAuth-провайдеров на выбор пользователя | стандартный OAuth2, отдельная стратегия на провайдера — детали и разделение RU/международных провайдеров в `08-web-and-identity.md` |

Полная схема веб-версии (набор провайдеров по региону, почему аккаунты не
связываются между платформами, что происходит с данными пользователя) —
в `08-web-and-identity.md`, здесь только точка входа в общую таблицу
`AuthenticatedUser`, куда сходятся все пять источников (Telegram, MAX, VK,
плюс провайдеры веб-версии).

## 5. Монетизация и платежи по платформам

| Платформа | Способ оплаты | Особенность |
|---|---|---|
| Telegram | **Telegram Stars** (обязательно для цифровых товаров внутри Mini App) | нельзя обойти внешним эквайрингом для виртуальных предметов — так требует сама платформа |
| MAX | СБП / VK Pay через нативный платёжный API MAX | прямые рубли, без обязательной внутренней валюты |
| VK | VK Pay / VK ID | прямые рубли |
| Web (международные пользователи) | **Xsolla** + опционально TON/Gram/USDT | подробности крипто-опции и её ограничений — `08-web-and-identity.md` §6 |
| Web (RU-пользователи) | **не Xsolla** — нужен отдельный, российский рельс оплаты | Xsolla с 2022 года не принимает платежи с карт российских банков — санкционные ограничения блокируют их на уровне биллинга/3D Secure, это стабильно воспроизводится и в 2026 году, а не разовый сбой<sup>[1]</sup>. Для RU-сегмента браузерной версии нужен тот же принцип, что уже используется на MAX — прямой рублёвый эквайринг/СБП, не единая интеграция на весь мир |

<sup>[1]</sup> Подтверждено несколькими независимыми источниками 2026 года
(vc.ru, DTF) — российские карты Visa/Mastercard/МИР отклоняются по бину или
геопризнаку, это не проблема аккаунта или способа оплаты конкретного игрока.

**Важно**: цены задаются отдельной таблицей на платформу (не автоконвертацией по курсу) —
юнит-экономика по Stars и по прямым рублям считается независимо. Веб-версия
добавляет ещё два прайс-листа (Xsolla-валюта для интернационального
сегмента, рубли для RU-сегмента) — не пять разных случайных цифр, а те же
принципы, что уже заложены для трёх мини-апп платформ.

**Принципиально исключено**: любые randomized-purchases (лутбоксы, гача-паки) —
только фиксированная цена за конкретный предмет/эффект. Причина — см. `03-notes-and-risks.md`.

## 6. Реклама — асимметрия по платформам

| Платформа | Нативная реклама в mini-app |
|---|---|
| MAX | **Нет** на момент разработки (только реклама на уровне каналов через РСЯ, не внутри мини-аппа) |
| Telegram | Нет "из коробки", но есть сторонние сети (несколько провайдеров, есть готовый опыт интеграции) |
| VK | **Есть**: rewarded video, interstitial, баннеры — нативно в VK Mini Apps |
| Web (RU) | Яндекс Директ/РСЯ-рекламные SDK для игр | |
| Web (международный) | отдельная сеть под несовместимый с RU-рынком регион (уточняется при реализации фазы 2) | |

Модуль `showAd()` в адаптере — опциональный, не-op на MAX, реализован через
рекламных провайдеров на Telegram, через нативный VK Ads SDK на VK, через
Яндекс/международную сеть на вебе. Полная логика антирекламного пакета,
кнопки "награда за рекламу" и различий поведения между платформами — в
`07-monetization-and-ads.md`.

## 7. Локализация — не везде одинаковая

- **MAX и VK — только русская локализация.** Обе площадки — RU-рынок, добавлять
  переключатель языка, который никто не будет использовать, — лишняя
  поверхность для багов и лишний вес бандла
- **Telegram и веб-версия — мультиязычность.** У обеих реальная международная
  аудитория (см. `08-web-and-identity.md` про разделение RU/international
  на вебе)
- Разграничивается на этапе сборки, тем же механизмом, что и остальная
  платформенная специфика (`--mode`): для сборок `max`/`vk` строка локали
  жёстко зашита в `ru`, UI-переключателя языка нет даже в разметке (не
  просто скрыт — физически не собирается в бандл); для `telegram`/`web`
  подключается полный набор locale-файлов и переключатель
- Практическое следствие: тексты (описания апгрейдов, названия врагов,
  UI-строки) с самого начала держать в i18n-формате (ключ → строка), даже
  для MAX/VK версии, которая физически покажет только `ru` — переносить
  захардкоженные строки в i18n постфактum дороже, чем сразу писать через
  ключи

## 8. Производительность (WebView constraint)

Постоянный game loop (60 FPS, десятки объектов на экране) внутри WebView мессенджера —
не то же самое, что нативное приложение. Проверить в первую неделю разработки:

- FPS на 2-3 бюджетных Android-устройствах внутри реального клиента MAX и Telegram
- Поведение при сворачивании/разворачивании мини-аппа (что происходит с game loop)
- Память при длинных забегах (утечки от неубираемых спрайтов/партиклов)

## 9. Контент как данные, а не как код

> Развитие этого принципа до рантайма — `19-content-admin.md`: числа и
> композиция меняются через админку без пересборки клиента и без модерации
> площадки, новые понятия по-прежнему требуют кода и релиза.

Начиная с недели 2 у проекта команда из трёх человек с разным бэкграундом
(см. `06-team-and-workflow.md`) — один пишет TS/Phaser, второй приходит из
Unity/Gmod/Яндекс Игр, третий — геймдизайнер, который в принципе может не
писать код вообще. Чтобы и второй, и третий человек могли полноценно
влиять на геймплей, не залезая в внутренности движка, весь контент, который
часто меняется в процессе баланса, должен жить в виде данных, а не быть
зашито в код:

```ts
// content/enemies.ts — правит любой участник команды, без знания Phaser
export const ENEMIES: EnemyDef[] = [
  { id: "swarm_rat", hp: 5, speed: 90, damage: 3, pattern: "swarm" },
  { id: "tank_ghoul", hp: 60, speed: 30, damage: 8, pattern: "chase" },
  { id: "shooter_wisp", hp: 12, speed: 40, damage: 5, pattern: "kite_and_shoot" },
];

// content/waves.ts
export const WAVES: WaveDef[] = [
  { second: 0,  spawns: [{ enemy: "swarm_rat", count: 10 }] },
  { second: 60, spawns: [{ enemy: "swarm_rat", count: 15 }, { enemy: "shooter_wisp", count: 3 }] },
];

// content/upgrades.ts, content/economy.ts — аналогично
```

`core-game` читает эти таблицы и интерпретирует `pattern` через уже
реализованное поведение — новый паттерн движения/атаки добавляет
программист, а новые враги/волны/цифры баланса на основе существующих
паттернов правит геймдизайнер (или напарник по части ассетов) через PR,
даже не разбираясь в Phaser. Для геймдизайнера, который может не писать код
вообще, это работает даже без ручного редактирования файлов — см.
`06-team-and-workflow.md` §1 про правки через описание задачи ИИ-агенту.

## 10. Инфраструктура

- **Сервер — Ubuntu Server LTS** (24.04 или актуальная LTS на момент аренды),
  x86-64. Разработка ведётся на Windows, прод — Linux; список расхождений,
  которые из-за этого надо держать в голове, — `20-env-and-ports.md` §5.1
- Время на сервере — **UTC**. Все метки времени в БД и логах хранятся в UTC,
  локальное время — только на отображении
- VPS/Docker Compose подход, уже проверенный командой на предыдущих проектах
- Bunny.net CDN — раздача статики игры (ассеты, спрайты) с малой задержкой
- Отдельная БД/схема Prisma — это самостоятельный проект, домены с другими продуктами не смешиваем

Как эта схема развивается при росте числа игроков — этапы, пороги перехода и
узкие места в порядке их наступления — в `14-scalability.md`. Там же список
решений, которые дёшевы сейчас и дороги потом (stateless API, идемпотентность
приёма забегов, локи на кронах) — их нужно соблюдать с первого дня, даже пока
нагрузки нет.
