# T-0031. API панели отвечает только на домене панели

[![статус](https://img.shields.io/endpoint?url=https://raw.githubusercontent.com/JJSGxKD/rubezh/task-board/status/T-0031.json)](README.md#значки-статуса)

## Зачем

Маршруты панели (`/api/v1/admin/*`) должны быть доступны только с домена
панели — у неё своя cookie-сессия. Домен клиента Telegram их уже закрывает,
а домен API (`api.<домен>`) пропускает к серверу всё подряд, в том числе
префикс панели. Это лишняя открытая дверь: вход в панель и её маршруты
доступны не с того домена. Пункт аудита «закрыть `/api/v1/admin` на `api.`».

## Решения

- **На домене API префикс панели отвечает 404** — так же, как на домене
  клиента (`tg.<домен>`). Остальное на домене API работает как раньше:
  вебхук бота, адрес награды сети, ссылки.
- **Правило держит тест по тексту Caddyfile.** У каждого блока домена, кроме
  `admin.<домен>`, который проксирует `/api/`, префикс `/api/v1/admin/*`
  закрыт раньше прокси.
- Выкат: `deploy.yml` уже копирует Caddyfile на сервер, а `deploy.sh`
  перезагружает Caddy (`caddy reload`). Ничего отдельно делать не нужно.

## Как сейчас

`infra/prod/Caddyfile`:

- `tg.{$DOMAIN}` (строки 65–85) — порядок обработчиков:
  - `handle /api/v1/admin/* { respond 404 }`;
  - `handle /api/* { reverse_proxy api:4000 }`;
  - `handle /r/* …`;
  - `handle { import spa web-telegram }`.
- `admin.{$DOMAIN}` (строки 88–100) — `/api/v1/admin/*` проксируется, прочее
  `/api/*` — 404.
- `api.{$DOMAIN}` (строки 105–108):

  ```
  api.{$DOMAIN} {
  	import edge
  	reverse_proxy api:4000
  }
  ```

  Обработчиков нет, проксируется всё.
- `{$DOMAIN}` (лендинг) проксирует только `/r/*`. Вывод панели там некуда:
  префикса `/api/` нет.

## Шаги по порядку

1. Тест первым коммитом (раздел «Тесты»).
2. **`infra/prod/Caddyfile`**, блок `api.{$DOMAIN}`:

   ```
   # API снаружи — вебхук бота и то, что ходит не со страниц клиента.
   # Префикс панели сюда не пускается — у неё свой домен и cookie-сессия.
   api.{$DOMAIN} {
   	import edge
   	handle /api/v1/admin/* {
   		respond 404
   	}
   	handle {
   		reverse_proxy api:4000
   	}
   }
   ```

   Отступы — табуляцией, как во всём файле.
3. **`docs/20-env-and-ports.md`**, раздел о доменах прода — строка: «Префикс
   панели `/api/v1/admin/*` проксируется только на `admin.<домен>`; на
   доменах клиента и API он отвечает 404».

## Чего не трогаем

- Остальные блоки Caddyfile.
- `compose.yml`, `deploy.sh`, `deploy.yml`.
- Сервер API: проверки прав остаются в коде, Caddy — дополнительный слой.

## Тесты

Первым коммитом, новый `scripts/test/caddyfile.test.ts`. Файл читается
текстом (`node:fs`), переводы строк приводятся к LF. Путь — от корня через
`fileURLToPath(new URL("../..", import.meta.url))`, как в
`scripts/test/action-pins.test.ts`.

Разбор: блок домена — строка, которая начинается с имени без отступа и
кончается `{`, до парной `}` на нулевом отступе. Сниппеты в скобках `(spa)`,
`(edge)` и т. п. не считаются блоками доменов.

- «на домене API префикс панели закрыт»: в блоке `api.{$DOMAIN}` есть
  `handle /api/v1/admin/* {` с `respond 404` внутри, и эта строка стоит раньше
  `reverse_proxy`;
- «на домене клиента префикс панели закрыт»: то же для `tg.{$DOMAIN}`;
- «панель проксирует свой префикс»: в блоке `admin.{$DOMAIN}` у
  `handle /api/v1/admin/*` — `reverse_proxy api:4000`;
- «новый домен с API не забудет закрыть префикс»: каждый блок домена, в
  котором встречается `handle /api/*` или `reverse_proxy api:4000` на уровне
  самого блока (с отступом в одну табуляцию), кроме `admin.{$DOMAIN}`,
  содержит `handle /api/v1/admin/* {`. Сейчас под это правило попадают
  `tg.{$DOMAIN}` и `api.{$DOMAIN}`; лендинг проксирует API только внутри
  `handle /r/*`, и правило его не задевает.
