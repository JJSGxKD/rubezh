# T-0085. Первый выкат на чистый сервер проходит без --no-backup

[![статус](https://img.shields.io/endpoint?url=https://raw.githubusercontent.com/JJSGxKD/rubezh/task-board/status/T-0085.json)](README.md#значки-статуса)

## Зачем

На чистом сервере (новый VPS, новая среда) первый выкат останавливается ещё до
запуска API: `deploy.sh` берёт дамп базы, а Postgres там не работает — compose
поднимает его только вместе с API, который идёт позже. Обойти можно только
`--no-backup`, то есть отключив страховку именно в тот выкат, где её роль
минимальна, но привычка обходить остаётся. Находка приёмки PR #247, 11.10.
После задачи Postgres поднимается до дампа, и первый выкат идёт тем же путём,
что остальные.

## Решения

- **Поднимаем Postgres до дампа** (первый из двух вариантов во входящих), а не
  дописываем в инструкцию «первый раз — с `--no-backup`»: обход не должен быть
  штатным шагом.
- **Дамп на чистом сервере не пропускаем.** Он берёт пустую базу за секунды, и
  у выката остаётся один путь без ветвления «есть ли что защищать».
- **`--no-backup` остаётся аварийным флагом** (`docs/09-ci-cd.md` §10), его
  смысл не меняется.
- **`--no-recreate`:** на живом сервере подъём ничего не пересоздаёт, конфигурацию
  приводит к новой версии привычный подъём API ниже по скрипту.
- **Образ API тянется под тегом новой версии** (см. «Как сейчас»): иначе на
  чистом сервере, где тег в `.env` пуст, уже `docker compose pull` падает.

  `ensure_space` → дамп (строки 155-160) → `ensure_space` →

  после дампа: порядок «дамп раньше смены тега» держит тест

- Откат (строки 172-184) возвращает `previous` в `.env`; он работает, пока тег
  версии не попал в окружение самого скрипта.

## Шаги по порядку

1. **Тесты первым коммитом** (раздел «Тесты»), красные до кода.
2. **`infra/prod/deploy.sh`, строка 147:** тянуть образ под тегом версии.

   ```bash
   # Тег — перед командой, а не в .env: в .env он меняется только после дампа
   # (дамп не сделался — файл не тронут), а на чистом сервере там пусто.
   API_TAG="$VERSION" docker compose pull --quiet api
   ```

3. **`infra/prod/deploy.sh`, сразу после второго `ensure_space` (строка 149) и до
   комментария про дамп (строка 150):** вставить блок. Флаги — ровно в этом
   порядке: существующий тест ищет первую подстроку `docker compose up -d --wait`
   как подъём API.

   ```bash
   # Дамп берётся из работающего Postgres. На чистом сервере его ещё нет: compose
   # поднимает базу вместе с API, а дамп идёт раньше. `--no-recreate` на живом
   # сервере ничего не трогает — к новой конфигурации приведёт подъём API ниже.
   if ! API_TAG="$VERSION" docker compose up -d --no-recreate --wait --wait-timeout 120 postgres; then
     log "Postgres не поднялся — выкат остановлен до дампа и миграций, API остаётся на ${previous:-прежней версии}"
     docker compose logs --tail 40 postgres || true
     exit 1
   fi
   ```

4. **Шапка `deploy.sh` (строки 1-10):** после строки с `--no-backup` дописать
   комментарий: «Первый выкат на чистый сервер идёт без `--no-backup`: базу для
   дампа выкат поднимает сам.»
5. **`docs/09-ci-cd.md`, §10, пункт про бэкап перед миграцией** (ищется по
   «Аварийный обход — `./deploy.sh <версия>`»): после «API остаётся на прежней
   версии.» добавить: «Базу для дампа выкат поднимает сам, поэтому первый выкат на
   чистый сервер флага не требует.»
6. **`docs/20-env-and-ports.md`, абзац «Сверх двух — **дамп перед выкатом**»**:
   в конец абзаца (после «Не сделался — выкат останавливается.») добавить:
   «На чистом сервере Postgres до первого выката не работает: `deploy.sh` поднимает
   его сам (`docker compose up -d --no-recreate --wait postgres`) и берёт дамп
   пустой базы. `--no-backup` для первого выката не нужен.»

## Чего не трогаем

- **Не экспортируем `API_TAG` в окружение скрипта** (`export API_TAG=…` или
  строка `API_TAG=… ` отдельной командой). Окружение сильнее `.env`: откат на
  строках 179-182 записал бы прежний тег в `.env`, а `docker compose up` взял бы
  из окружения новый и снова поднял неудавшуюся версию. Тег — только префиксом
  к одной команде.
- Порядок «дамп раньше `set_env_value API_TAG`» и «дамп раньше подъёма API».
- `backup.sh`, `compose.yml`, `.github/workflows/deploy.yml`: правки не нужны,
  workflow флаг `--no-backup` по-прежнему не передаёт.
- Redis на чистом сервере: дампу он не нужен, его поднимет подъём API.
- `provision.sh`, `infra/server/bootstrap.sh` и первичная настройка ключей
  бэкапа — другая тема.

## Сценарий и интерфейс

Игрок и панель не затронуты. Оператор на чистом сервере видит в логе выката:
подъём Postgres, строку бэкапа перед выкатом, дальше обычный подъём API. Если
база не поднялась — строку «Postgres не поднялся — выкат остановлен до дампа и
миграций…» и 40 последних строк логов Postgres.

## Тесты

Первым коммитом, `scripts/test/deploy-script.test.ts`, в существующее
описание `describe("deploy.sh: бэкап перед выкатом", …)` (там уже есть `callAt`):

- «Postgres поднимается раньше дампа, без пересоздания» — индекс
  `deploy.search(/API_TAG="\$VERSION" docker compose up -d --no-recreate --wait [^\n]*postgres/)`
  больше -1 и меньше `callAt`;
- «не поднявшаяся база останавливает выкат до дампа» —
  `deploy.slice(индекс_подъёма_postgres, callAt)` содержит `exit 1` и текст
  «Postgres не поднялся»;
- «образ тянется под тегом версии до дампа» — в тексте есть
  `API_TAG="$VERSION" docker compose pull`, и его индекс меньше `callAt`;
- «тег версии не уходит в окружение скрипта» —
  `expect(deploy).not.toMatch(/^\s*export\s+API_TAG/m)` и
  `expect(deploy).not.toMatch(/^\s*API_TAG=\S*\s*$/m)` (второй шаблон ловит
  строку, где присваивание стоит само по себе; присваивание-префикс перед
  `docker compose` в такую строку не попадает: после значения идёт команда);
- существующие кейсы файла (включая «дамп делается раньше смены тега API и
  подъёма контейнера») остаются зелёными без правок.

Первые три красные до кода, четвёртый зелёный и играет роль страховки.
`bash -n` по скрипту уже есть в этом файле (на Windows пропускается).
