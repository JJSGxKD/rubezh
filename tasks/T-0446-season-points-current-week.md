# T-0446. Недельный сезон по очкам с идущей недели — панель пускает, таблица пересобирается сама

[![статус](https://img.shields.io/endpoint?url=https://raw.githubusercontent.com/JJSGxKD/rubezh/task-board/status/T-0446.json)](README.md#значки-статуса)

## Зачем

Владелец видит, что недельный рейтинг считает по времени, а общий — по
очкам. Так задумано правилом T-0294: идущая в момент выката неделя
дотягивается по времени, а v0.13.0 (11.11.2026) поставила переход на
понедельник 16.11. Решение владельца — **по очкам и идущую неделю**. Сейчас
панель не даёт поставить идущую неделю, а после смены ключа таблица недели
пустая, пока кто-то не запустит `seasons:rebuild`. После задачи владелец
ставит дату в панели — и таблица недели уже по очкам.

## Решения

- `docs/35-stage4-plan.md`, **Р212**, п. 1–3:
  - проверка сохранения `rating.points-from` пускает понедельник **идущей**
    недели; прошлые недели — нет (их итоги в архиве);
  - смена ключа, которая переводит идущий сезон на очки, сама пересобирает
    таблицу недели из базы (`SeasonsProjection.rebuild`) под замком Redis — у
    API несколько реплик, пересобирает одна;
  - награды сезона не меняются: лестница мест `PLACE_LADDER`, порог участника
    `rating.season-threshold-points`; закрытие уже считает сезон по очкам по
    `points` (`seasons-close.repository.ts`).
- Архив закрытых сезонов не пересчитывается (T-0294, `rating-switch.ts`).

## Как сейчас

- `backend/api/src/modules/settings/setting-catalog.ts`, `ratingPointsFrom`
  (строки ~600–628): `saveCheck` отказывает, если
  `from.getTime() <= seasonOf(now).startsAt.getTime()` — то есть и идущей
  неделе. Подсказка (`hint`) и текст отказа говорят «следующей недели».
- `backend/api/src/modules/seasons/seasons-schedule.ts`: `scoringOf(season)`,
  `boardSeason(season)` (ключ `pts:<понедельник>` у сезона по очкам) — читают
  настройку на каждый вызов: после смены ключа API сразу читает доску
  `pts:…`, а она пуста.
- `backend/api/src/modules/seasons/seasons-projection.ts`: `rebuild(at)`
  (строки ~105–126) собирает обе доски (`full`, `common`) текущей недели
  по режиму сезона; зовётся только командой `cli/seasons-rebuild.ts`.
- `settings.service.ts`: `SettingsReader.onChange(listener)` — слушатель
  получает ключи, у которых поменялось действующее значение (на каждой
  реплике — по сообщению Redis).
- Образец замка: `runs/leaderboard-warmup.ts` (`LOCK_KEY`, `SET NX PX`,
  снятие по токену), `reminders/reminders.store.ts`.
- Очки забегов, сыгранных до v0.13.0, досчитал прогрев на старте API
  (`runs/leaderboard-warmup.ts`); забег без очков на доске по очкам не стоит.

## Шаги по порядку

1. `setting-catalog.ts`, `ratingPointsFrom.saveCheck`: отказ, только если
   `from < seasonOf(now).startsAt` (строго раньше идущей недели); текст
   отказа — «Сезоны по очкам не могут начаться с прошлой недели — укажите
   понедельник идущей недели или позже». `hint` — дописать: «Понедельник
   идущей недели переводит её на очки сразу: таблица недели пересоберётся
   из базы». Комментарий над ключом — поправить под новое правило.
2. `seasons-schedule.ts`: метод `onScoringSettingChange(listener: () => void): void` —
   подписка на `settings.onChange`, зовёт `listener`, если среди ключей есть
   `rating.points-from`.
3. `seasons-projection.ts`:
   - в `onModuleInit` — подписка шага 2 на `this.switchBoard()` (без
     `await`, ошибки — в лог `season_board_switch_failed`, не наружу);
   - `switchBoard(at = new Date())`: сезон идёт и `scoringOf(season) === "points"`,
     а ключ `boardSeason(season).key` отличается от последнего, для которого
     доска собрана этой репликой (поле класса; на старте — `null`), — взять
     замок `seasons:board-switch:lock` (`SET NX PX 120000` с токеном,
     таймаут команды 2 с), `rebuild(at)`, снять замок по токену. Замок занят
     — ничего не делать (пересобирает другая реплика). Сезон по времени —
     ничего не делать: его доска и так полна.
   - лог `season_board_switched` с ключом и числами `rebuild` (без
     идентификаторов игроков).
4. `cli/seasons-rebuild.ts` собирает `SeasonsProjection` руками — передать
   новые зависимости, если конструктор поменялся.
5. `docs/10-progression-and-ladder.md` §4.1 (пункт «Недельные сезоны
   переходят…») — правило: дата может быть понедельником идущей недели,
   тогда неделя переходит сразу, таблица пересобирается сама. `docs/30` —
   строка ключа `rating.points-from`.

## Чего не трогаем

- `rating-switch.ts` (`scoringOfSeason`, `boardKeyOf`, `scoreOf`) — правило
  «сезон по очкам, если начался не раньше даты» прежнее.
- Закрытие сезона, награды, порог участника, дивизионы.
- Общую доску всех времён и её прогрев.
- Ленту главной и карточку бота — это T-0447.

## Сценарий и интерфейс

Панель → «Настройки» → «Рейтинг» → «Сезоны по очкам с понедельника»:
владелец вводит `20261109` в четверг 12.11 — сохранение проходит. В течение
минуты (пересборка) «Рейтинг» → «Неделя» в игре показывает места по очкам
эффективности, у строк — очки и время подписью. Ввод `20261102` — отказ с
текстом шага 1.

  `null`.
- `backend/api/test/seasons-switch.test.ts` (заглушки настроек, хранилища и
  репозитория, как в `seasons.test.ts`):
  - смена `rating.points-from` на понедельник идущей недели → `rebuild` один
    раз, доска пишется под ключ `pts:<понедельник>`;
  - смена на следующий понедельник (идущий сезон остаётся по времени) →
    `rebuild` не зовётся;
  - смена другого ключа → не зовётся;
  - замок занят → не зовётся; повторное событие с тем же ключом доски на той
    же реплике → не зовётся второй раз;
  - `rebuild` бросил ошибку → замок снят, исключение не ушло из слушателя.

## Аналитика

Нет новых событий: смена ключа пишется в журнал действий панели (как любая
настройка), пересборка — в лог API. Метрик с идентификаторами нет.

## Настройки и окружение

Ключ `rating.points-from` — меняется проверка сохранения и подсказка, не
значение по умолчанию. Новых ключей и переменных нет.
