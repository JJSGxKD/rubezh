# T-0169. Порядок заданий у игрока — по состоянию, внутри по порядку из панели

[![статус](https://img.shields.io/endpoint?url=https://raw.githubusercontent.com/JJSGxKD/rubezh/task-board/status/T-0169.json)](README.md#значки-статуса) [![T-0167](https://img.shields.io/endpoint?url=https://raw.githubusercontent.com/JJSGxKD/rubezh/task-board/status/T-0167.json&label=T-0167)](archive/T-0167-admin-sortable-list-tasks-order.md)

## Зачем

Геймдизайнер расставляет задания перетаскиванием (T-0167), но игрок порядка
не видит: клиент сортирует задания ещё и по виду цели и по её величине, и
порядок из панели доходит только как «последний довод». После этой задачи
порядок из панели решает всё, кроме состояния: сверху то, что можно забрать,
дальше то, что в работе, внизу полученное.

## Решения

Р118 (`docs/35-stage4-plan.md`, последняя фраза): у игрока задания
сортируются сначала по состоянию (можно забрать, в работе, получено), внутри —
по порядку из панели.

Следствия, без которых «внутри — по порядку из панели» не складывается
(исполнитель их не пересматривает):

- **Вид и величина цели в сортировку не входят.** Прежнее правило «похожие цели
  рядом и по величине» (`KIND_ORDER`, сравнение `target`) снимается: порядок
  похожих целей теперь выбирает геймдизайнер.
- **Порядок отдаёт сервер.** Клиент `sort` не получает (`TaskView` не
  меняется), а использует порядок ответа. Сейчас ответ идёт в порядке каталога
  `ORDER BY period, sort, task_id`, и во вкладке «Партнёры» — где ежедневные
  подписки и достижения лежат вместе — срок оказался бы старше порядка из
  панели. Поэтому `viewOf` на сервере отдаёт задания по `sort`, при равном —
  по `taskId`; клиент затем только разводит их по состоянию.
- Порядок ответа сервера при равных состояниях клиент не перемешивает
  (устойчивая сортировка, как сейчас — по индексу).

## Шаги по порядку

1. **Тесты первым коммитом** (раздел «Тесты»).
2. `backend/api/src/modules/tasks/tasks.service.ts`, `viewOf`: перед `flatMap`
   упорядочить копию `defs` по `sort`, при равном — по `taskId` (сравнение
   строк через `<`/`>`, не `localeCompare`: порядок не должен зависеть от
   локали сервера). Исходный массив не менять. Комментарий — почему: порядок
   задаёт панель, а каталог отдаёт его вперемешку по срокам (Р118).
3. `packages/app-shell/src/state/tasks-api.ts`:
   - убрать `KIND_ORDER` и его комментарий;
   - `sortTasks<T extends Pick<TaskItem, "done" | "claimed">>(tasks)` — ключ
     только `stage`, затем индекс (устойчивость). Описание функции переписать:
     сверху — что можно забрать, дальше — в работе, внизу — полученное; внутри
     — порядок сервера, то есть порядок из панели.
4. Проверить, что вызовов `KIND_ORDER` и `sortTasks` с полями `kind` и `target`
   больше нет (`rg "KIND_ORDER|sortTasks"`), `pnpm typecheck` из корня зелёный.
5. `docs/35-stage4-plan.md`: в абзаце «Порядок на экране» части 5 WP13 (строка
   «Порядок на экране: вкладка «Партнёрские» первая…») заменить «похожие цели
   рядом и по величине» на «внутри состояния — порядок, заданный в панели
   (Р118)».

## Чего не трогаем

- Панель (`apps/admin/**`), запрос порядка и колонку `sort` — это T-0167.
- `TaskView` и ответ `GET /api/v1/tasks`: поле `sort` игроку не отдаём.
- Порядок каталога панели: `ORDER BY` в `tasks.repository.ts`, `groupByPeriod`.
- Задания рекламных сетей на вкладке «Партнёры»: их место (сразу за тем, что
  можно забрать) задаёт `tasks.tsx`, оно не меняется.
- Ротацию пула (`task-pool.ts`): выбор заданий дня и недели не затрагивается.

- Исходный массив не изменился; пустой список даёт пустой.
- `isClaimable` — три существующих утверждения остаются.

`backend/api/test/tasks.test.ts`:

- `viewOf` на трёх заданиях, поданных как `weekly_a` (`weekly`, sort 0),
  `daily_b` (`daily`, sort 20), `daily_c` (`daily`, sort 10), отдаёт
  `weekly_a`, `daily_c`, `daily_b`: порядок по `sort`, а не по сроку.

  (ежедневная подписка, sort 0) → `viewOf` отдаёт сначала ежедневную.

- Существующие кейсы `viewOf` (лимит, видимость) проходят без правок, кроме тех,
  что полагались на порядок по сроку: их ожидание поправить и назвать в PR.
