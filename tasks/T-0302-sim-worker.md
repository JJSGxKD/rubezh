# T-0302. sim-worker — отдельный процесс со своей сборкой движка: очередь проверки и симуляции черновика контента, отчёт против текущей версии

[![статус](https://img.shields.io/endpoint?url=https://raw.githubusercontent.com/JJSGxKD/rubezh/task-board/status/T-0302.json)](README.md#значки-статуса) [![T-0301](https://img.shields.io/endpoint?url=https://raw.githubusercontent.com/JJSGxKD/rubezh/task-board/status/T-0301.json&label=T-0301)](archive/T-0301-content-snapshot.md)

## Зачем

Сервер не импортирует пакеты игры (Р6, Р15), а редактору баланса нужно
прогнать черновик контента ботом калибровки до того, как его увидят
игроки (`docs/19` §4.3). После задачи есть `sim-worker` — свой процесс со
своей сборкой движка. Он берёт задание из очереди и проверяет снимок
контента:
- схемой;
- проверками контента;
- симуляцией сценариев против текущей версии.

Отчёт возвращается в ту же очередь. Позже в нём же будет перепроверка
забегов (WP5).

## Решения

Решения владельца — `docs/35-stage4-plan.md`:
- Р15 — отдельный процесс-воркер со своей сборкой движка; пользуются
  перепроверка забегов (WP5) и прогон баланса перед публикацией (WP17);
- 25.10.2026 — редактор баланса, шаг 1 — песочница с симуляцией.

Решения `claude-lead-1` от 25.10.2026:

- **Пакет** `apps/sim-worker` — Node LTS:
  - импортирует `@bh/core-game` (без Phaser: только `game/sim`,
    `game/balance`, `content`);
  - сборка — один файл (`esbuild`, точная версия);
  - в границах слоёв: воркер не импортирует `backend/api` и `adapter-*`.
- **Очередь** BullMQ `content-check` в том же Redis:
  - задание `{ checkId, snapshot, baseSnapshot, scenarios }`;
  - результат — `{ checkId, schemaProblems, contentProblems, report }`;
  - сервер читает результат событием завершения задания (T-0303).

  Конкурентность — 1: прогон занимает процессор целиком.
- **Сценарии** — те же, что у `balance:sim`:
  - боты калибровки (уклоняющийся, неидеальный) × 20 зёрен × профили силы
    (T-0196), если они есть, иначе без набора;
  - каждый — на черновике и на базе.

  Отчёт по сценарию — медианы:
  - времени жизни;
  - первого сундука;
  - убийств;
  - уровня;
  - секунд до первой смерти.

  Плюс сравнение с коридорами `balance-targets` снимка: в коридоре / ниже /
  выше.
- **Пределы:**
  - снимок до 2 МБ JSON;
  - прогон — не дольше 120 с, дольше — `timeout` в отчёте;
  - очередь — не больше 5 ждущих: шестое задание отклоняется с причиной
    «Проверка уже идёт, дождитесь».
- **Детерминизм** — те же зёрна и тот же код, что у `balance:sim`: отчёт по
  снимку-умолчанию совпадает с выводом `pnpm balance:sim` по тем же
  сценариям (тест).
- **Метрики** — Prometheus на `SIM_WORKER_METRICS_PORT`:
  - `sim_jobs_total{queue,outcome}`;
  - `sim_job_seconds{queue}`.

  Порт — новая строка карты `docs/20` §2:
  - dev `4010`;
  - staging `127.0.0.1:4110`;
  - production — не публикуется.

  По процедуре §7: `.env.example`, Zod-схема конфигурации воркера.
- **Контейнер** — сервис `sim-worker` в `docker-compose.yml` и в
  развёртывании (`infra/`), тот же образ Node, что у API, точной версией.

## Шаги по порядку

1. **Тесты первым коммитом** — `apps/sim-worker/test/`:
   - задание с испорченным снимком → проблемы схемы, симуляции нет;
   - снимок-умолчание против себя → нулевые дельты;
   - отчёт по умолчанию совпадает с `balance:sim` (2 зерна);
   - шестое задание в очереди → отказ;
   - прогон дольше предела → `timeout`.
2. **Пакет** — `package.json`, сборка, `src/main.ts` (подключение к Redis,
   воркер очереди), `src/check.ts` (проверка и симуляция — чистая часть).
3. **Метрики и конфигурация** — порт по карте, Zod-схема.
4. **Контейнер** — `docker-compose.yml`, `infra/`, шаг сборки в CI.
5. **Граница** — строка воркера в `layer-boundaries.test.ts`.
6. **Документы:**
   - `docs/01` — процесс в схеме системы;
   - `docs/20` — порт;
   - `docs/21` — схема связей.
