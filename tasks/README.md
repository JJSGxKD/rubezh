# Реестр задач

[![можно брать](https://img.shields.io/endpoint?url=https://raw.githubusercontent.com/JJSGxKD/rubezh/task-board/status/free.json)](https://github.com/JJSGxKD/rubezh/blob/task-board/README.md) — [доска задач](https://github.com/JJSGxKD/rubezh/blob/task-board/README.md): что можно брать прямо сейчас, кто что делает, вклад

Отсюда берут работу все исполнители: сессии ИИ на разных аккаунтах, локальные и
облачные, и люди. Порядок один для всех. Правила репозитория (`CLAUDE.md`)
действуют без исключений, здесь — только то, что добавляет работа по задачам.

**Кто что делает** (подробно — «Роли и кодовые имена»):

- **Тимлиды** (основной чат с участником 1) решают, пишут спецификации и макеты,
  принимают работу и вливают PR в `dev`. Код сами не пишут.
- **Тимлид второго уровня, ревьюер и дизайнер** — запасные руки тимлидов, когда
  у основного чата кончаются лимиты: задачи по принятым решениям, проверка PR,
  макеты.
- **Исполнитель** — поток: сессия, которая сама берёт задачи своей модели и
  уровня, открывает PR и, не дожидаясь ответа, берёт следующую (раздел
  «Автопоток»). Сам PR не вливает, на прод не выкатывает, задачи не заводит.

Задача — это спецификация, по которой работу можно сделать **без домыслов**.
Если что-то пришлось бы додумать, задача не готова: это вопрос тимлидам, а не
повод решить самому.

## Роли и кодовые имена

Решение пользователя от 12.10.2026. У каждой роли — кодовое имя
`claude-<роль>-N`, где `N` — номер аккаунта Claude, как у потоков
исполнителей. Им подписываются комментарии и ревью в PR
(`**claude-lead-1:** …`), ответы в задачах («Ответ claude-lead-1,
12.10.2026: …») и поле `author` у задач, которые роль завела.

| Роль | Кодовое имя | Что делает | Чего не делает |
|---|---|---|---|
| Тимлид | `claude-lead-N` (основной чат — `claude-lead-1`) | решения с пользователем, спецификации, макеты, приёмка и мердж в `dev`, релизы в `main`, прод, локальный аудит и секреты | код задач исполнителей |
| Тимлид второго уровня | `claude-lead2-N` | спецификации и нарезка задач **по решениям, уже записанным в `docs/`**, ответы на `## Вопросы` по ним же, приёмка и мердж в `dev` | новых решений не принимает — вопрос пользователю или основному тимлиду; без прода, `main`, секретов и локального аудита (`docs/audit/` у него нет), задач по безопасности и антифроду не пишет |
| Ревьюер | `claude-review-N` | приёмка PR по чек-листу раздела «Приёмка»: «Approve» или «Request changes» с меткой «доработка» | не вливает, не правит PR сам, задач не заводит |
| Дизайнер | `claude-design-N` | макеты в `design/` от нынешнего кода (`design/README.md`), токены облика по направлению «Сумеречный рубеж», PR с макетом под задачу | решений по продукту не принимает, код экранов не пишет, сам не вливает |
| Исполнитель | поток `claude-N / <модель> / <уровень>` | задачи своей модели и уровня (раздел «Автопоток») | всё, что вне спецификации и зон |

Кодовое имя ставит человек, который запускает сессию, первой строкой промта:
«Ты — claude-review-2, ревьюер проекта «Рубеж»…». Скиллы ролей:
`task-spec` — тимлидам обоих уровней, `review-pr` — ревьюеру и тимлидам,
`take-task` — исполнителю.

## Файлы

| Файл | Что это | Кто правит |
|---|---|---|
| [`epics.md`](epics.md) | Эпики, их порядок и приоритет | тимлиды |
| `T-NNNN-<slug>.md` | Одна задача — один файл | тимлиды обоих уровней пишут; исполнитель меняет только поля `status` и `owner` |
| [`_template.md`](_template.md) | Шаблон спецификации | тимлиды |
| [`inbox.md`](inbox.md) | Входящие: замечания и идеи, у которых ещё нет спецификации. Исполнители отсюда не берут | тимлиды |

Номера задач выдают тимлиды по порядку, `slug` — латиницей через дефис.

## Поля задачи

Шапка файла — блок YAML между строками `---`. Формат держится строго: проверка
реестра и захват задачи читают его скриптом.

| Поле | Значения | Смысл |
|---|---|---|
| `id` | `T-0001` | совпадает с началом имени файла |
| `title` | строка | заголовок задачи, он же основа заголовка PR |
| `epic` | `E1` | эпик из `epics.md` |
| `priority` | `P0` блокер · `P1` сейчас · `P2` следом · `P3` потом | внутри пачки (`batch`) из свободных задач берут по приоритету, при равном — по порядку в `epics.md` |
| `status` | `draft` · `ready` · `in-progress` · `done` · `cancelled` | брать можно только `ready` |
| `owner` | строка или пусто | поток, который ведёт задачу: `аккаунт / модель / уровень`, например `claude-3 / sonnet-5.5 / medium`. У задач, взятых до 12.10.2026, — без уровня |
| `author` | кодовое имя, необязательно | кто написал задачу: `claude-lead-1`, `claude-lead2-2` (раздел «Роли и кодовые имена»). У задач до 12.10.2026 поля нет |
| `size` | `S` до полудня · `M` 1–2 дня | `L` не бывает: такую задачу тимлиды дробят |
| `depends_on` | список `id` | задачу нельзя брать, пока все они не `done` |
| `zones` | список путей и шаблонов | файлы, которые задача меняет. **Пересечение зон с задачей в работе блокирует** |
| `shared` | список путей | общие файлы-реестры, куда задача дописывает свои строки (раздел «Общие файлы»). Не блокируют |
| `runner` | `any` · `local` · `human` | `any` — хватит клона и CI; `local` — нужны живые Postgres и Redis, Docker или устройство; `human` — нужен человек, исполнителю-ИИ не брать |
| `executor` | `sonnet-5.5` · `haiku-5.5` | какой исполнитель-ИИ допущен к задаче. Список и выбор — раздел «Исполнители и effort» |
| `effort` | `low` · `medium` · `high` · `extra` | уровень рассуждения, который ставит в сессии тот, кто её запускает |
| `release` | `none` · `patch` · `minor` | метка релиза PR |
| `design` | путь к макету или `null` | макет экрана в `design/` |
| `batch` | целое число от 1, необязательно | номер пачки очереди: пачка уходит в `main` одним релизным PR (раздел «Пачки очереди», `docs/38-release-plan.md`). Потоки берут задачи ближней пачки первыми, задача без пачки — последней. Прежнее поле `version` не допускается |

Шаблоны путей: `*` — любые символы в имени, `**` — любые вложенные каталоги.

## Пачки очереди

Выпуск в `main` идёт пачками, а не по календарю (`docs/38-release-plan.md`,
Р103). Пачка — номер очереди: 1, 2, 3 и так далее; поле `batch` говорит, в
какой пачке задача уйдёт игрокам.

- **Порядок выдачи.** `pnpm task next` и колонки `pnpm task board` сортируют
  так: пачка (меньше — раньше), приоритет, эпик по порядку в `epics.md`, `id`.
  Задача без `batch` идёт после всех задач с пачкой. В строке задачи
  печатается «пачка N» или «—».
- **Зависимости.** `pnpm task check` не пропустит задачу, которая зависит от
  задачи более поздней пачки, и задачу с пачкой, которая зависит от задачи
  без пачки. Сделанные и отменённые зависимости не в счёт. Ошибка называет обе
  задачи и обе пачки.
- **Перенос в следующую пачку.** Задача не влита к выпуску пачки — тимлид
  правит в её шапке одну строку: `batch: 2` вместо `batch: 1`. Зависящие от
  неё задачи переносятся вместе с ней. Исполнитель пачку не меняет: это
  решение тимлида, и задача `done` в чужой пачке ни на что не влияет.
- **Номера абсолютные.** Выпущенная пачка больше не используется, новая
  задача получает номер ещё не выпущенной пачки.
- **У сделанных и отменённых** поле `batch` можно оставить или убрать: оно у
  них ни на что не влияет.

## Исполнители и effort

**Какие ИИ участвуют в разработке, решают тимлиды.** Задача рассчитана на
конкретного исполнителя и конкретный уровень: от них зависят качество кода и
то, сколько спецификации нужно разжёвывать. Поэтому отклоняться нельзя:
- другая модель задачу не берёт, даже если «тоже справится»;
- уровень `effort` в сессии ставится ровно тот, что в файле задачи.

Нужен другой исполнитель или уровень — это решение тимлидов правкой файла, а
не исполнителя.

Допущены два исполнителя:

| `executor` | Кто | Где | Каким задачам |
|---|---|---|---|
| `sonnet-5.5` | Claude Sonnet 5.5 | сессии Claude Code на аккаунтах команды | любым |
| `haiku-5.5` | Claude Haiku 5.5 | там же | расписанным до строки и с малой ценой ошибки: тексты и словари, данные контента, документы, тесты по точному списку, правка экрана по макету в одном файле |

**Haiku не получает** задачи про деньги и платежи, миграции и схему БД,
конкурентность и очереди, авторизацию, права и антифрод, детерминизм движка
— на любом уровне `effort`. Это задачи `sonnet-5.5`. Haiku допущен с
12.10.2026 и только к новым задачам: у заведённых раньше `executor` не
меняется.

Новый исполнитель появляется строкой в этой таблице и новым значением поля
(`EXECUTORS` в `scripts/tasks/task-file.mjs`). У задачи, которую могут делать
двое, тимлиды перечисляют их явно.

**Как тимлиды выбирают `effort`:**

| Уровень | Когда |
|---|---|
| `low` | механическая правка по точному списку: тексты, ключи словаря, переименование |
| `medium` | маленькая задача (`S`) с понятной проверкой: ошибка в одном экране, правка правила |
| `high` | задача `M` или `S` с тонким местом: несколько слоёв сразу, детерминизм, доступ, своя логика разбора |
| `extra` | деньги, конкурентность, миграции, то, где ошибка дорога и не видна в тестах сразу |

Имена — как в выборе уровня Claude Code: `extra` идёт между `high` и `max`
(раньше этот уровень назывался `xhigh`).

`max` и Ultracode исполнителям не ставятся: они рассчитаны на широкий перебор
и веера субагентов, а детальной спецификации с готовыми тестами это не нужно —
на аккаунтах Pro лимит кончится раньше задачи.

**Кто ставит.**
- Модель и уровень выставляет человек, который запускает сессию, — по полям
  задачи.
- Исполнитель-ИИ первым делом сверяет, что он та модель, что в `executor`. Если
  нет — задачу не берёт и говорит об этом человеку.
- В `owner` при захвате пишется поток: `claude-3 / sonnet-5.5 / medium`.
  `pnpm task claim` и `pnpm task resume` сверяют с задачей и модель, и
  уровень: поток уровня `medium` задачу уровня `high` не возьмёт.

## Состояния

```
draft ──▶ ready ──▶ in-progress ──▶ PR на ревью ──▶ done
  (пишут тимлиды)   (ветка task/T-NNNN)  (открыт PR)   (влит в dev)
                         │                   │  ▲
                         │        метка «доработка»  │ поток доработал
                         │                   ▼  │
                         │               доработка (любой поток той же модели и уровня)
                         └──────── cancelled (тимлиды)
```

«Доработка» — не статус в файле, а метка PR: ответ на вопросы дан или
ревьюер попросил правок (раздел «Доработка»).

На `dev` у файла статус `draft`, `ready`, `done` или `cancelled`. Статус
`in-progress` живёт только в ветке задачи. Взята ли задача, видно по ветке
`task/T-NNNN` на GitHub: ветка есть — задача занята.

## Значки статуса

Под заголовком каждой задачи — строка значков: статус самой задачи и статус
каждой её зависимости. Значки живые: картинка читает статус из ветки
`task-board` (`status/T-NNNN.json`), а не из файла задачи. Поэтому файл не
нужно править на каждый захват, а связанные задачи меняют значок сами, когда
соседнюю берут или вливают.

| Значок | Цвет | Что значит |
|---|---|---|
| ![](https://img.shields.io/badge/статус-можно_брать-brightgreen) | `brightgreen` | все зависимости сделаны, зоны свободны — брать можно |
| ![](https://img.shields.io/badge/статус-в_работе_·_claude--2-orange) | `orange` | есть ветка `task/T-NNNN`, рядом — аккаунт того, кто взял (без модели) |
| ![](https://img.shields.io/badge/статус-на_ревью_·_%23214-blue) | `blue` | открыт PR, рядом — его номер |
| ![](https://img.shields.io/badge/статус-доработка_·_%23214-yellow) | `yellow` | у PR метка «доработка»: ответ дан, его заканчивает любой поток той же модели и уровня |
| ![](https://img.shields.io/badge/статус-ждёт_T--0003-red) | `red` | не сделана зависимость — **не брать**. Названо до двух номеров, дальше `+N` |
| ![](https://img.shields.io/badge/статус-зона_занята_T--0005-red) | `red` | зоны пересекаются с задачей в работе или на ревью — **не брать** |
| ![](https://img.shields.io/badge/статус-готово-6e40c9) | `6e40c9` | влита в `dev` |
| ![](https://img.shields.io/badge/статус-черновик-lightgrey) | `lightgrey` | спецификация не готова — не брать |
| ![](https://img.shields.io/badge/статус-отменено-inactive) | `inactive` | задачу отменили тимлиды |

Сообщения и цвета заданы одной таблицей в коде — `statusBadge` в
`scripts/tasks/board.mjs`; эта таблица должна совпадать с ней.

**Как значки обновляются.** Workflow `task-board.yml` пересчитывает файлы
`status/T-NNNN.json` в ветке `task-board` тем же кодом, что `pnpm task board`
(второй копии логики нет):
- когда в ветку `task/*` пушат (захват — первый такой push) и когда её создают или удаляют;
- когда PR такой ветки открывают, закрывают, переводят в черновик или обратно,
  ставят или снимают метку;
- когда что-то вливают в `dev`;
- раз в час — на случай, если событие потерялось.

Пока workflow не попал в `main` (ветка по умолчанию), `create`, `delete`, час и
ручной запуск не работают — GitHub берёт для них файл из `main`. Захват и мердж
это не задевает: для `push` и `pull_request` берётся файл из самой ветки. Не
обновится только отдача задачи без PR (`pnpm task release`) — до следующего
`push` в `dev`.

Ветка `task-board` без общей истории: каждый пересчёт заменяет её одним
коммитом. Руками её не правят.

**Строка значков в файле задачи статична.** Её ставит `pnpm task fix`: значок
самой задачи и по значку на каждую зависимость, в порядке `depends_on`.
Меняется картинка, а не файл: коммиты в `dev` на каждый захват не нужны. Формат —
`badgeLine` в `scripts/tasks/task-file.mjs`; `pnpm task check` сверяет строку с
`depends_on`, называет ожидаемую и подсказывает `pnpm task fix`.

**В эпиках.** Ячейка «Задачи» в `epics.md` — те же живые значки, что под
заголовками задач: «готово», «можно брать», «ждёт…». Её тоже ставит
`pnpm task fix`, а `pnpm task check` сверяет с реестром: номера руками отстали
бы от доски в первый же день.

**Доска.** Страница [`README.md` ветки `task-board`](https://github.com/JJSGxKD/rubezh/blob/task-board/README.md) — её пересчитывает
тот же `pnpm task status-json`, что и значки:
- колонки «Доработка», «Можно брать», «В работе», «На ревью», «Ждут» и «Готово»;
- значок `status/free.json` («можно брать · 3 задачи») — в начале этого файла и
  `epics.md`, он ведёт на страницу;
- раздел «Вклад»: сделанные задачи и очки по автору влитого PR задачи на
  GitHub, внутри аккаунта — по полю `owner` («аккаунт / модель / уровень»),
  так потоки под одним аккаунтом различаются. Очки — сумма размеров: `S` — 1, `M` — 2.
  Это наглядность, а не формула выплат: доли участников задаёт
  [`docs/11-revenue-split.md`](../docs/11-revenue-split.md). На странице — только
  логины GitHub, они и так видны у PR.

**Значок — сигнал для людей, а не защита.** shields.io и GitHub кэшируют
картинку, и она может отставать на 5–10 минут. Защищают захват три вещи:
- атомарный push ветки;
- проверки `pnpm task claim`: зависимости, зоны, исполнитель;
- проверки зон и захвата в CI PR: `diff-check` и `claim-check`.

Сомневаешься — верь `pnpm task board`, а не картинке.

## Как взять задачу

1. **Выбрать задачу.** Свободные — на [доске задач](https://github.com/JJSGxKD/rubezh/blob/task-board/README.md) или `pnpm task next`.
   Брать можно только ту, у которой значок «можно брать» (раздел «Значки
   статуса»), и только командой `pnpm task claim` — вручную ветку не заводят: PR,
   взятый в обход, не пройдёт `claim-check` в CI.

   ```bash
   pnpm task next --executor sonnet-5.5 --effort medium
   ```

   Команда читает реестр из `origin/dev` и ветки `task/*` на `origin`, поэтому
   показывает одно и то же на любой ветке. Сначала — PR на доработке твоей
   модели и уровня (их берут `pnpm task resume`, раздел «Доработка»), потом
   свободные задачи. Первая свободная — лучшая:
   `status: ready`, все `depends_on` — `done`, зоны не пересекаются с задачами в
   работе и на ревью, ближняя пачка (`batch`), в ней — старший `priority`, при
   равном — эпик раньше в `epics.md`. Весь реестр по колонкам — `pnpm task board`. `--runner local` —
   только если у тебя есть то, что нужно; `runner: human` исполнитель-ИИ не
   берёт, команда его не показывает. Бери только задачу, где `executor` — твоя
   модель (раздел «Исполнители и effort»).

2. **Захватить.** Захват атомарный: ветку `task/T-NNNN` создаёт тот, чей push
   прошёл первым.

   ```bash
   pnpm task claim T-NNNN --owner "claude-3 / sonnet-5.5 / medium"
   ```

   Команда отказывает, если рабочая копия не чистая, задача не свободна или
   модель и уровень в `--owner` не совпадают с `executor` и `effort`. Иначе создаёт ветку от
   `origin/dev`, ставит `status: in-progress` и `owner`, коммитит и пушит без
   `--force`. Push отклонён — задачу уже взяли: команда сама убирает локальную
   ветку, выбери другую задачу.

3. **Если команды нет** (старая ветка, нет Node), то же руками:

   ```bash
   git fetch origin --prune
   git ls-remote --heads origin "task/*"   # ветка есть — задача занята
   git switch -c task/T-NNNN origin/dev
   # в файле задачи: status: in-progress, owner: <аккаунт / модель / уровень>
   git commit -am "chore(tasks): Взять T-NNNN в работу"
   git push origin HEAD:refs/heads/task/T-NNNN
   ```

   Зависимости и зоны при этом сверяешь сам: `depends_on` — `done`, `zones` не
   пересекаются с задачами в работе (открой их спецификации). Коммит захвата
   обязан что-то менять: без него ветка совпала бы с `dev`, и второй push тоже
   «прошёл» бы. **Никогда не пушь в чужую `task/*` и не пушь с `--force`.**
   Единственное исключение — PR с меткой «доработка», взятый командой
   `pnpm task resume` (раздел «Доработка»): после неё ветка твоя.

4. **Прочитать спецификацию целиком** и всё, на что она ссылается. Если неясно —
   раздел «Если что-то неясно», не угадывать.

5. **Сначала тесты.** Тест-кейсы из раздела «Тесты» пишутся первым коммитом
   (`test(scope): …`). Они падают — так и должно быть. Тест — договор: менять его
   под код нельзя, только по ответу тимлидов.

6. **Код — по «Шагам по порядку».** Коммиты дробные, по правилам `CLAUDE.md`.

7. **Трогать только свои файлы:** `zones`, строки в `shared` и сам файл задачи.
   Понадобился файл вне зон — это вопрос тимлидам. «Заодно поправил рядом» —
   причина вернуть PR.

8. **Гейт** — пять команд из `CLAUDE.md` и `pnpm docs:check`. Для экранов ещё
   снимки на 320, 390, 768 и 1440 px против макета. Без зелёного гейта задача не
   сделана.

   Облачному исполнителю без Postgres и Redis интеграционные тесты прогонит CI
   его PR: локально они пропускаются, но в PR обязаны быть зелёными.

9. **Закрыть задачу в том же PR:** в файле задачи поставить `status: done`.

10. **Открыть PR в `dev`:**
    - заголовок — из раздела «PR» спецификации;
    - метка — из поля `release`;
    - описание — по скиллу `pre-pr`; раздел «Сводка для команды» — готовый блок
      из спецификации, с номером PR в заголовке;
    - первой строкой — `Задача: tasks/T-NNNN-<slug>.md`, дальше чек-лист критериев приёмки с отметками;
    - последней строкой перед подписью агента — поток: `Поток: claude-3 / sonnet-5.5 / medium`.

    **Не вливать самому:** вливают тимлиды. Ответа не ждать: PR открыт —
    сразу следующая задача (раздел «Автопоток»).

**Бросить задачу** (не успел, задача оказалась не той): удали ветку
`git push origin --delete task/T-NNNN` и закрой PR, если он был, с причиной в
комментарии. Задача снова свободна.

## Если что-то неясно

Не додумывать. Если спецификация допускает два прочтения, конфликтует с кодом или
документом или требует файла вне зон:

1. **Сначала перечитай спецификацию целиком**, от шапки до раздела «PR»:
   ответ часто стоит в другом шаге. Сверяй её саму, а не её пересказ в
   README.
2. Открой черновик PR (`--draft`) с разделом `## Вопросы`. В каждом вопросе:
   - **цитата строки спецификации** с номером, на которую ты опираешься, и
     почему она допускает два прочтения;
   - варианты ответа;
   - что ты нашёл в коде (пути и строки).
3. Не делай то, что зависит от ответа, а **независимые шаги продолжай**:
   ожидание ответа не должно останавливать всю задачу. Сделал всё, что можно
   без ответа, — запушь и бери следующую задачу: ждать ответа в сессии не
   нужно.
4. Тимлиды ответят комментарием в PR или правкой спецификации в `dev` и
   поставят PR метку «доработка». Заканчивать будет тот поток, что первым
   возьмёт её, — не обязательно ты (раздел «Доработка»).

## Доработка

PR, который ждёт исполнителя, а не тимлида, помечается меткой
**«доработка»**. Её ставит тот, кто ответил:

- **тимлид** — ответил на `## Вопросы` комментарием или правкой
  спецификации в `dev`;
- **ревьюер или тимлид** — по приёмке нужны правки: замечания — ревью
  «Request changes» или комментарием со списком.

Заканчивает PR **любой поток** с теми же `executor` и `effort`, что у задачи:
на любом аккаунте Claude и под любым аккаунтом GitHub — у всех исполнителей
есть право push в ветки `task/*`. Тот, кто PR открыл, ничем не выделен.

1. `pnpm task next --executor <модель> --effort <уровень>` — доработка
   показывается первой.
2. Взять:

   ```bash
   pnpm task resume T-NNNN --owner "claude-1 / sonnet-5.5 / medium"
   ```

   Команда берёт ветку `task/T-NNNN` с origin, пишет в `owner` твой поток,
   коммитит и пушит без `--force`, потом снимает с PR метку. Push — замок:
   двое продолжили одновременно — коммит первого лёг, второй получил отказ и
   берёт другую задачу. Снять метку не вышло — команда скажет, сними руками
   (`gh pr edit <номер> --remove-label доработка`), иначе задачу возьмёт ещё
   один поток.
3. Прочитай PR целиком: описание, `## Вопросы`, ответы, ревью и
   комментарии, затем спецификацию в `dev` — она могла измениться.
4. `dev` ушёл вперёд или в PR конфликт — влей его в ветку
   (`git merge origin/dev`), а не перебазируй: в ветке уже чужие коммиты, и
   переписывать их историю нельзя, `--force` под запретом. Конфликт в общем
   файле — по таблице «Общие файлы».
5. Сделай то, что ответили, по тем же правилам: тесты, зоны, гейт. Ответ
   спорит со спецификацией — снова `## Вопросы` в PR, метку не ставь: её
   ставят тимлиды.
6. Готово — в PR комментарий «Доработано: …» с подписью потока, черновик
   переведи в «Ready for review» (`gh pr ready`). Дальше — следующая задача.

## Автопоток

Поток — сессия, которая работает без остановки: берёт задачу своей модели и
уровня, открывает PR и, не дожидаясь ответа, берёт следующую. На каждом
аккаунте Claude — по потоку на каждую пару «модель + уровень»:

| Сессия | Поток в `owner` |
|---|---|
| Sonnet — Low — Claude-N | `claude-N / sonnet-5.5 / low` |
| Sonnet — Medium — Claude-N | `claude-N / sonnet-5.5 / medium` |
| Sonnet — High — Claude-N | `claude-N / sonnet-5.5 / high` |
| Sonnet — Extra — Claude-N | `claude-N / sonnet-5.5 / extra` |
| Haiku — Low — Claude-N | `claude-N / haiku-5.5 / low` |
| Haiku — Medium — Claude-N | `claude-N / haiku-5.5 / medium` |
| Haiku — High — Claude-N | `claude-N / haiku-5.5 / high` |
| Haiku — Extra — Claude-N | `claude-N / haiku-5.5 / extra` |

`N` — номер аккаунта Claude: по нему видно, чьи лимиты кончились и чьи задачи
встали. Модель и уровень в настройках сессии ставит тот, кто её запускает, —
те же, что в имени.

**У каждого потока — своя рабочая копия.** Потоки одного аккаунта на одной
машине в общем клоне переключали бы друг другу ветки посреди работы. Своя
копия — облачная сессия, сессия Claude Code с изоляцией в worktree или
`git worktree add ../rubezh-sonnet-medium origin/dev`.

**Цикл потока:**

0. **Свежий `dev` и нужный Node.** `git fetch origin`, затем `git switch --detach
   origin/dev` — реестр и задачи живут только в `dev`; копия, не обновлённая
   с прошлого дня, видит старый реестр и «задач нет». Node — ровно из `.nvmrc`
   (`node -v`; другой — `nvm install` и `nvm use` этой версии), потом
   `pnpm install`. Исполнитель и уровень пишутся строчными: `haiku-5.5`, `low`.
1. `pnpm task next --executor <модель> --effort <уровень>`.
2. Есть доработка — `pnpm task resume` (раздел «Доработка»). Нет — первая
   свободная задача, `pnpm task claim`. Отказ «уже взяли» — следующая из
   списка.
3. Работа по разделу «Как взять задачу»: тесты первыми, зоны, гейт, PR.
   Неясно — `## Вопросы` в черновике PR, независимые шаги — до конца.
4. PR открыт или запушен черновик с вопросами — `git switch --detach
   origin/dev` и снова шаг 1. Ответа не ждать.
5. Задач нет — отчёт: какие PR открыты, какие ждут ответа, почему остальное
   недоступно (зависимости, зоны, другая модель или уровень). Сессию после
   этого человек перезапускает позже.

**Промт потока** — подставить номер аккаунта, модель и уровень:

```
Ты — исполнитель проекта «Рубеж», поток claude-N / sonnet-5.5 / medium.
Сначала git fetch origin и git switch --detach origin/dev, Node — из .nvmrc,
pnpm install; так же — перед каждой новой задачей. Прочитай AGENTS.md и tasks/README.md, разделы «Автопоток» и «Доработка»,
и работай по скиллу take-task в режиме автопотока: бери задачи только
своей модели и уровня — pnpm task next --executor sonnet-5.5 --effort medium,
доработку первой (pnpm task resume), иначе pnpm task claim T-NNNN
--owner "claude-N / sonnet-5.5 / medium". Делай строго по спецификации,
только в ветке task/T-NNNN, в dev и main не пушь, PR не вливай — вливают
тимлиды. Неясно — черновик PR с разделом «Вопросы» и цитатой строки
спецификации, независимые шаги продолжай. PR открыт — сразу следующая
задача, ответа не жди: закончит PR тот поток, что первым возьмёт его на
доработку. Задач не осталось — отчёт и стоп.
```

## Приёмка (ревьюер и тимлиды)

Проверяет ревьюер или тимлид, вливает тимлид или тимлид второго уровня —
сессией, которая сама PR не писала. Исход ревью — один из двух:

- **принято** — ревью «Approve» с отмеченным чек-листом ниже; дальше мердж;
- **нужны правки** — «Request changes» со списком замечаний и метка
  «доработка» (раздел «Доработка»).

Ревью и комментарии начинаются с кодового имени: `**claude-review-2:** …`.

PR принимается, если выполнено всё:

- [ ] тесты из спецификации есть и зелёные, CI зелёный;
- [ ] дифф только в `zones`, своих строках `shared` и файле задачи — зоны проверяет CI (`pnpm task diff-check`, шаг в `pr-checks.yml`), красный шаг значит возврат PR;
- [ ] задача взята по порядку — `claim-check` в CI зелёный (`pnpm task claim-check`: на базе `ready`, зависимости сделаны, зоны не заняты чужой задачей), красный шаг значит возврат PR;
- [ ] ничего лишнего: попутных рефакторингов, переименований, «улучшений» нет;
- [ ] все критерии приёмки выполнены и отмечены в описании;
- [ ] документы, названные в спецификации, обновлены;
- [ ] коммиты дробные, по правилам `CLAUDE.md`, заголовок и метка — из спецификации.

Вливается merge-коммитом, строго по одному. Отстал от `dev` или конфликт —
метка «доработка» с комментарием «влить dev»: в ветке исполнителя `dev`
вливают, а не перебазируют.

## Общие файлы

Эти файлы правят почти все задачи, и конфликты в них ожидаемы. Правило одно:
**правка — добавление в свой участок, конфликт решается сохранением обеих
сторон**, чужие строки не переписываются.

| Файл | Как добавлять |
|---|---|
| `backend/api/prisma/schema.prisma` | свои модели — блоком в конце файла с комментарием-заголовком; связь в `model Account` — одной строкой |
| `backend/api/prisma/migrations/` | миграция генерируется **после** перебазирования на свежий `dev`, один раз, командой `prisma migrate dev --create-only` на отдельной базе. Если пока PR ждал, в `dev` влилась более новая миграция, своя пересоздаётся с новой меткой времени: Prisma применяет их по порядку имени. Проверка — `ls backend/api/prisma/migrations \| tail` |
| `backend/api/src/app.module.ts` | одна строка импорта и одна в `APP_MODULES` |
| `backend/api/src/modules/roles/permissions.ts` | новые права — своим блоком с комментарием |
| `backend/api/src/modules/events/event-dictionary.ts` | новое событие — сначала в словарь `docs/22-analytics-and-metrics.md` §3.3, потом сюда |
| `backend/api/src/config/app-config.ts`, `.env.example` | новая переменная — своим блоком по процедуре `docs/20-env-and-ports.md` §7 |
| `backend/api/src/modules/settings/setting-catalog.ts` | новый ключ — строкой в своей группе |
| `apps/web-telegram/vite.config.ts` | префикс прокси — одна строка |
| `packages/app-shell/src/i18n/ru.json` | новые экраны строк сюда **не добавляют**: у экрана свой ленивый словарь (`i18n/account.ts` — образец) |
| `scripts/bundle-budget.mjs` | порог поднимают только тимлиды, и только если спецификация это разрешает |
| `docs/30-configuration-map.md`, `docs/21-diagrams.md` | строки своей задачи — в конец таблицы своей темы; сущности ER — в конец блока `erDiagram` |

## Окружение исполнителя

- **Ключи.** Корневой `.env` с настоящими ключами исполнителю не нужен и не
  копируется. Запуску API хватает `.env.example` с тестовыми базами.
- **Бот.** Бота с боевым токеном исполнитель не запускает:
  `TELEGRAM_BOT_UPDATES=off`.
- **Опасные команды запрещены.** Нельзя `prisma migrate reset`, `docker compose
  down -v`, удалять чужие ветки, пушить в `dev` и `main`, вливать PR, менять
  настройки репозитория, секреты и переменные Actions.
- **Прод.** Сервер исполнителю недоступен и не нужен. Выкат — только релизом
  тимлидов.
- **Версия Node** — из `.nvmrc`. Если в окружении другая и `pnpm build` или
  `pnpm budget` не запускаются (`engine-strict`), проверку не обходить: отметь в
  PR, какие команды не прошли и почему. Их подтвердит CI PR.
