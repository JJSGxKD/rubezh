# Реестр задач

[![можно брать](https://img.shields.io/endpoint?url=https://raw.githubusercontent.com/JJSGxKD/rubezh/task-board/status/free.json)](https://github.com/JJSGxKD/rubezh/blob/task-board/README.md) — [доска задач](https://github.com/JJSGxKD/rubezh/blob/task-board/README.md): что можно брать прямо сейчас, кто что делает, вклад

Отсюда берут работу все исполнители: сессии ИИ на разных аккаунтах, локальные и
облачные, и люди. Порядок один для всех. Правила репозитория (`CLAUDE.md`)
действуют без исключений, здесь — только то, что добавляет работа по задачам.

**Кто что делает** (подробно — «Роли и кодовые имена»):

- **Тимлиды** (основной чат с владельцем) решают, пишут спецификации и макеты,
  принимают работу и вливают PR в `dev`. Код сами не пишут.
- **Тимлид второго уровня, ревьюер и дизайнер** — запасные руки тимлидов, когда
  у основного чата кончаются лимиты: задачи по принятым решениям, проверка PR,
  макеты.
- **Исполнитель** — поток: сессия, которая сама берёт задачи своей модели и
  уровня, открывает PR и, не дожидаясь ответа, берёт следующую (раздел
  «Автопоток»). Сам PR не вливает, на прод не выкатывает, задачи не заводит.

Задача — это спецификация, по которой работу можно сделать **без домыслов**.
Если что-то пришлось бы додумать, задача не готова: это вопрос тимлидам, а не
повод решить самому. Что исполнитель всё же решает сам, с записью в PR, —
раздел «Что исполнитель решает сам» (Р176).

## Роли и кодовые имена

Решение пользователя от 12.10.2026. У каждой роли — кодовое имя
`claude-<роль>-N`, где `N` — номер аккаунта Claude, как у потоков
исполнителей. Им подписываются комментарии и ревью в PR
(`**claude-lead-1:** …`), ответы в задачах («Ответ claude-lead-1,
12.10.2026: …») и поле `author` у задач, которые роль завела.

| Роль | Кодовое имя | Что делает | Чего не делает |
|---|---|---|---|
| Тимлид | `claude-lead-N` (основной чат — `claude-lead-1`) | решения с пользователем, спецификации, макеты, приёмка и мердж в `dev`, релизы в `main`, прод, локальный аудит и секреты | код задач исполнителей |
| Тимлид второго уровня | `claude-lead2-N` | спецификации и нарезка задач **по решениям, уже записанным в `docs/`**, ответы на `## Вопросы` по ним же, приёмка и мердж в `dev` | новых решений не принимает — вопрос пользователю или основному тимлиду; без прода, `main`, секретов и локального аудита (`docs/audit/` у него нет), задач по безопасности и антифроду не пишет |
| Ревьюер | `claude-review-N` | приёмка PR по чек-листу раздела «Приёмка»: «Approve» или «Request changes» с меткой «доработка» | не вливает, не правит PR сам, задач не заводит |
| Дизайнер | `claude-design-N` | макеты в `design/` от нынешнего кода (`design/README.md`), токены облика по направлению «Сумеречный рубеж», PR с макетом под задачу | решений по продукту не принимает, код экранов не пишет, сам не вливает |
| Исполнитель | поток `claude-N / <модель> / <уровень>` | задачи своей модели и уровня (раздел «Автопоток») | всё, что вне спецификации и зон |

Кодовое имя ставит человек, который запускает сессию, первой строкой промта:
«Ты — claude-review-2, ревьюер проекта «Рубеж»…». Скиллы ролей:
`task-spec` — тимлидам обоих уровней, `review-pr` — ревьюеру и тимлидам,
`take-task` — исполнителю, `ui-design`, `game-art` и `game-sound` — дизайнеру
и исполнителю задачи с обликом и звуком, `game-design` — тимлидам до
спецификации, `growth` — текстам продвижения и монетизации.

Модель и уровень усилий ролей. Рекомендация `claude-lead-1` от 15.10.2026,
под лимиты Pro:

- **тимлид второго уровня** — Opus 5.5, high. Ошибка в спецификации
  размножается на всех исполнителей, а работа — прочитать документы и код
  целиком;
- **ревьюер** — Sonnet 5.5, high. PR задач с `effort: extra` (деньги,
  конкурентность, миграции, авторизация) — Opus 5.5, high. Haiku на ревью не
  ставим: гонки и обходы проверок он пропускает;
- **дизайнер** — Opus 5.5, medium; новый экран или правка направления облика —
  high.

Субагенты, которых роль запускает сама, — по правилу «Субагенты и workflow —
экономно» из `CLAUDE.md`. Ревью PR и черновики спецификаций — Sonnet,
medium; механика — Haiku. Черновик субагента основной тимлид читает сам
до вливания.

## Файлы

| Файл | Что это | Кто правит |
|---|---|---|
| [`epics.md`](epics.md) | Эпики, их порядок и приоритет | тимлиды |
| `T-NNNN-<slug>.md` | Одна открытая задача (`draft`, `ready`, `in-progress`) — один файл | тимлиды обоих уровней пишут; исполнитель меняет только поля `status` и `owner` |
| `archive/T-NNNN-<slug>.md` | Готовые и отменённые задачи (`done`, `cancelled`); переносит `pnpm task archive` — уборка тимлида (раздел «Уборка архива») | скрипт по команде тимлида; руками не переносят |
| [`_template.md`](_template.md) | Шаблон спецификации | тимлиды |
| [`inbox.md`](inbox.md) | Входящие: замечания и идеи, у которых ещё нет спецификации. Исполнители отсюда не берут | тимлиды |

Номера задач выдают тимлиды по порядку, `slug` — латиницей через дефис.

## Поля задачи

Шапка файла — блок YAML между строками `---`. Формат держится строго: проверка
реестра и захват задачи читают его скриптом.

| Поле | Значения | Смысл |
|---|---|---|
| `id` | `T-0001` | совпадает с началом имени файла |
| `title` | строка | заголовок задачи, он же основа заголовка PR |
| `epic` | `E1` | эпик из `epics.md` |
| `priority` | `P0` блокер · `P1` сейчас · `P2` следом · `P3` потом | внутри пачки (`batch`) из свободных задач берут по приоритету, при равном — по порядку в `epics.md` |
| `status` | `draft` · `ready` · `in-progress` · `done` · `cancelled` | брать можно только `ready` |
| `owner` | строка или пусто | поток, который ведёт задачу: `аккаунт / модель / уровень`, например `claude-3 / sonnet-5.5 / medium`. У задач, взятых до 12.10.2026, — без уровня |
| `author` | кодовое имя, необязательно | кто написал задачу: `claude-lead-1`, `claude-lead2-2` (раздел «Роли и кодовые имена»). У задач до 12.10.2026 поля нет |
| `size` | `S` до полудня · `M` 1–2 дня | `L` не бывает: такую задачу тимлиды дробят |
| `depends_on` | список `id` | задачу нельзя брать, пока все они не `done` |
| `zones` | список путей и шаблонов | файлы, которые задача меняет. **Пересечение зон с задачей в работе блокирует** |
| `shared` | список путей | общие файлы-реестры, куда задача дописывает свои строки (раздел «Общие файлы»). Не блокируют |
| `runner` | `any` · `local` · `owner` · `human` | `any` — хватит клона и CI; `local` — нужно **запущенное приложение** на машине: dev-сервер, браузер (Playwright), сборка образа Docker (Р177). Живые Postgres и Redis — не причина: интеграционные тесты на них прогоняет `gate` в CI, а миграцию поток собирает без базы (раздел «Общие файлы», строка миграций); `owner` — только машина владельца: прод, настоящие секреты, телефон, бот в Telegram; `human` — нужен человек, исполнителю-ИИ не брать |
| `executor` | `sonnet-5.5` · `haiku-5.5` | какой исполнитель-ИИ допущен к задаче. Список и выбор — раздел «Исполнители и effort» |
| `effort` | `low` · `medium` · `high` · `extra` | уровень рассуждения, который ставит в сессии тот, кто её запускает |
| `release` | `none` · `patch` · `minor` | метка релиза PR |
| `merge` | `self` · `lead`, необязательно | кто вливает PR: `lead` (по умолчанию, у старых задач поля нет) — тимлид; `self` — сам поток после самопроверки (раздел «Самостоятельный мердж», Р176). Ставит тимлид в спецификации. Проверка реестра допускает `self` только по белому списку путей (раздел «Самостоятельный мердж») и не допускает при `effort: extra`, `runner: owner` и `human` |
| `design` | путь к макету или `null` | макет экрана в `design/` |
| `batch` | целое число от 1, необязательно | номер пачки очереди: пачка уходит в `main` одним релизным PR (раздел «Пачки очереди», `docs/38-release-plan.md`). Потоки берут задачи ближней пачки первыми, задача без пачки — последней. Прежнее поле `version` не допускается |

Шаблоны путей: `*` — любые символы в имени, `**` — любые вложенные каталоги.

## Пачки очереди

Выпуск в `main` идёт пачками, а не по календарю (`docs/38-release-plan.md`,
Р103). Пачка — номер очереди: 1, 2, 3 и так далее; поле `batch` говорит, в
какой пачке задача уйдёт игрокам.

- **Порядок выдачи.** `pnpm task next` и колонки `pnpm task board` сортируют
  так: пачка (меньше — раньше), приоритет, эпик по порядку в `epics.md`, `id`.
  Задача без `batch` идёт после всех задач с пачкой. В строке задачи
  печатается «пачка N» или «—».
- **Зависимости.** `pnpm task check` не пропустит задачу, которая зависит от
  задачи более поздней пачки, и задачу с пачкой, которая зависит от задачи
  без пачки. Сделанные и отменённые зависимости не в счёт. Ошибка называет обе
  задачи и обе пачки.
- **Раздел «PR».** У задач `ready` и `in-progress` метка и заголовок из раздела
  «PR» сходятся с полем `release`: метка равна шапке, а поле `release` не ниже,
  чем требует тип заголовка. Ошибка называет оба значения.
- **Перенос в следующую пачку.** Задача не влита к выпуску пачки — тимлид
  правит в её шапке одну строку: `batch: 2` вместо `batch: 1`. Зависящие от
  неё задачи переносятся вместе с ней. Исполнитель пачку не меняет: это
  решение тимлида, и задача `done` в чужой пачке ни на что не влияет.
- **Номера абсолютные.** Выпущенная пачка больше не используется, новая
  задача получает номер ещё не выпущенной пачки.
- **У сделанных и отменённых** поле `batch` можно оставить или убрать: оно у
  них ни на что не влияет.

## Исполнители и effort

**Какие ИИ участвуют в разработке, решают тимлиды.** Задача рассчитана на
конкретного исполнителя и конкретный уровень: от них зависят качество кода и
то, сколько спецификации нужно разжёвывать. Поэтому отклоняться нельзя:
- другая модель задачу не берёт, даже если «тоже справится»;
- уровень `effort` в сессии ставится ровно тот, что в файле задачи.

Нужен другой исполнитель или уровень — это решение тимлидов правкой файла, а
не исполнителя.

Допущены два исполнителя:

| `executor` | Кто | Где | Каким задачам |
|---|---|---|---|
| `sonnet-5.5` | Claude Sonnet 5.5 | сессии Claude Code на аккаунтах команды | любым |
| `haiku-5.5` | Claude Haiku 5.5 | там же | расписанным до строки и с малой ценой ошибки: тексты и словари, данные контента, документы, тесты по точному списку, правка экрана по макету в одном файле |

**Haiku не получает** задачи про деньги и платежи, миграции и схему БД,
конкурентность и очереди, авторизацию, права и антифрод, детерминизм движка
— на любом уровне `effort`. Это задачи `sonnet-5.5`. Haiku допущен с
12.10.2026 и только к новым задачам: у заведённых раньше `executor` не
меняется.

Новый исполнитель появляется строкой в этой таблице и новым значением поля
(`EXECUTORS` в `scripts/tasks/task-file.mjs`). У задачи, которую могут делать
двое, тимлиды перечисляют их явно.

**Как тимлиды выбирают `effort`:**

| Уровень | Когда |
|---|---|
| `low` | механическая правка по точному списку: тексты, ключи словаря, переименование |
| `medium` | маленькая задача (`S`) с понятной проверкой: ошибка в одном экране, правка правила |
| `high` | задача `M` или `S` с тонким местом: несколько слоёв сразу, детерминизм, доступ, своя логика разбора |
| `extra` | деньги, конкурентность, миграции, то, где ошибка дорога и не видна в тестах сразу |

Имена — как в выборе уровня Claude Code: `extra` идёт между `high` и `max`
(раньше этот уровень назывался `xhigh`).

`max` и Ultracode исполнителям не ставятся: они рассчитаны на широкий перебор
и веера субагентов, а детальной спецификации с готовыми тестами это не нужно —
на аккаунтах Pro лимит кончится раньше задачи.

**Кто ставит.**
- Модель и уровень выставляет человек, который запускает сессию, — по полям
  задачи.
- Исполнитель-ИИ первым делом сверяет, что он та модель, что в `executor`. Если
  нет — задачу не берёт и говорит об этом человеку.
- В `owner` при захвате пишется поток: `claude-3 / sonnet-5.5 / medium`.
  `pnpm task claim` и `pnpm task resume` сверяют с задачей и модель, и
  уровень: поток уровня `medium` задачу уровня `high` не возьмёт.

## Состояния

```
draft ──▶ ready ──▶ in-progress ──▶ PR на ревью ──▶ done
  (пишут тимлиды)   (ветка task/T-NNNN)  (открыт PR)   (влит в dev)
                         │                   │  ▲
                         │        метка «доработка»  │ поток доработал
                         │                   ▼  │
                         │               доработка (любой поток той же модели и уровня)
                         └──────── cancelled (тимлиды)
```

«Доработка» — не статус в файле, а метка PR: ответ на вопросы дан или
ревьюер попросил правок (раздел «Доработка»). «Задел» — тоже метка PR: задачу
начали поверх веток зависимостей, пока те ждут ревью (раздел «Задел»). Все
состояния PR — метками (раздел «Метки статуса»).

На `dev` у файла статус `draft`, `ready`, `done` или `cancelled`. Статус
`in-progress` живёт только в ветке задачи. Взята ли задача, видно по ветке
`task/T-NNNN` на GitHub: ветка есть — задача занята.

## Метки статуса

У каждого PR ветки `task/T-NNNN` **ровно одна метка статуса** (Р172,
`docs/35-stage4-plan.md`). Доска, значки и захват читают метку, а не
черновик: черновик с вопросами тимлиду — это «на ревью», а не «в работе».
Без метки поток, отправивший PR, висел бы «в работе», задачи стояли бы, а
зоны были бы заняты, хотя код никто не пишет. Метка видна и на самом PR —
статус задачи читается прямо в списке PR на GitHub.

| Метка | Кто ставит | Что значит | Зоны |
|---|---|---|---|
| `в работе` | исполнитель, пока пишет код в PR; `pnpm task resume` при продолжении доработки | код ещё пишут, поток задачу не бросал | держит |
| `на ревью` | исполнитель, отправляя работу — **в том числе черновик с `## Вопросы`**; бот на новом PR без метки и при выходе из черновика | отправлено тимлиду, поток уже взял следующую задачу | не держит |
| `доработка` | ревьюер или тимлид, вернув PR; бот на ревью «Request changes» | PR ждёт исполнителя: ответ дан или нужны правки | держит |
| `ждёт владельца` | тимлид | нужно решение или действие владельца (раздел «Приёмка») | не держит |
| `задел` | исполнитель, открывая черновик PR после `pnpm task claim --ahead` (Р178) | задачу начали поверх веток зависимостей, которые ждут ревью; PR — всегда черновик и до мерджа зависимостей не вливается | не держит |

Правила жёсткие, без исключений:

- **Отправил — «на ревью».** Готовый PR, PR после доработки, черновик с
  вопросами, черновик «посмотрите, что получилось» — любая отправка на проверку
  ставит `на ревью` и снимает `в работе`: при открытии
  `gh pr create --label "на ревью" …`, потом
  `gh pr edit <номер> --add-label "на ревью" --remove-label "в работе"`.
- **Продолжил — «в работе».** `pnpm task resume` сам меняет `доработка` (у
  созревшего задела — `задел`) на `в работе`. Закончил доработку — снова
  `на ревью`.
- **Задел — только черновик.** Пока у задачи есть невлитые зависимости, её PR —
  черновик с меткой `задел`; «на ревью» поставит поток после доводки (раздел
  «Задел»).
- **Вернул — «доработка».** Ревьюер и тимлид, возвращая PR (в том числе
  ответом на вопросы), ставят `доработка` и снимают `на ревью` (или
  `ждёт владельца`) — старый статус не оставляют.
- **Одна метка.** Две и ни одной — красный шаг `pr-check`
  (`статус: нет метки статуса…` и `статус: меток статуса несколько…`).

**Страховка** (`scripts/release/pr-status-label.mjs`, шаг перед `pr-check` в
`pr-checks.yml` и `pr-status-label.yml`; только ветки `task/T-NNNN` этого
же репозитория): на новом или заново открытом PR без метки бот ставит `на
ревью`; при выходе из черновика ставит `на ревью` и снимает `в работе`;
если меток стало две, оставляет поставленную последней; ревью «Request
changes» ставит `доработка` и снимает остальные статусы. Метку `задел` бот не
заменяет ни на новом PR, ни при выходе из черновика: снятие черновика у задела
с невлитыми зависимостями делает красным `claim-check`, а не бот. Страховка
ловит забытое, но не заменяет правило: исполнитель ставит метку сам.

Для PR, открытых до правила, запасной путь доски: без метки черновик считается
«в работе», остальное — «на ревью» (`prStatus` в `scripts/tasks/board.mjs`).
Несколько меток читаются по старшинству: доработка, ждёт владельца, в работе,
на ревью, задел. «Задел» младшая: рядом с «в работе» значит, что его только
что взяли доводить, рядом с «на ревью» — что довели.

**Разделы доски.** Страница доски показывает: строку счётчиков (свободно, в
работе, на ревью, на доработке, ждут тимлида, ждут владельца, влито сегодня —
сутки по Москве, — ближайшая пачка и сколько в ней осталось) и разделы «Ждут
владельца», «Ждут тимлида», «Потоки сейчас», «Доработка», «Можно брать» (тремя
таблицами: облако, машина с Docker, машина владельца), «Можно заделом»,
«В работе», «На ревью», «Задел», «Ждут», «Готово», «Вклад». Время на странице — МСК. Кого ждёт PR, решает
`waitingOn` в `scripts/tasks/board.mjs`: метка «ждёт владельца» — владельца,
«доработка» и красный CI — исполнителя, черновик с разделом `## Вопросы` и
открытый PR без замечаний — тимлида. В какую колонку попал PR, решает метка
статуса (раздел «Метки статуса»): «в работе» — «В работе», «доработка» —
«Доработка», «на ревью» и «ждёт владельца» — «На ревью», «задел» — «Задел»
(зависимость закрыли без мерджа — задел уходит в «Ждут» с причиной).

Раздел «Вклад» считает по каждому потоку или роли («кодовое имя · человек», человек — из
строки `Запустил:` описания PR) пять видов работы: задачи и очки (`S` — 1, `M` — 2; влитые
PR веток `task/`), круги доработки (коммиты «Продолжить T-NNNN после ответа»), ревью и ответы
(комментарии и ревью влитых PR, начинающиеся с `**claude-…:**`), спецификации (файлы задач,
добавленные в `dev`; поле `author`) и PR тимлидов (влитые PR не из `task/` с такой же подписью
в первой строке). Периоды — сегодня, вчера, неделя (с понедельника), месяц и всё время, по
Москве. Это наглядность, а не формула выплат. Один вызов `gh` на все влитые PR; без него
остаются только спецификации.

В разделах «В работе», «На ревью» и «Доработка» столбцы одни: поток, кто его
запустил (строка `Запустил:` из описания PR), сколько суток висит, сколько
кругов доработки прошёл PR и кого он ждёт. Висящее от трёх суток помечено «⚠️».

Сообщения и цвета заданы одной таблицей в коде — `statusBadge` в
`scripts/tasks/board.mjs`; эта таблица должна совпадать с ней.

**Как значки обновляются.** Workflow `task-board.yml` пересчитывает файлы
`status/T-NNNN.json` в ветке `task-board` тем же кодом, что `pnpm task board`
(второй копии логики нет):
- когда в ветку `task/*` пушат (захват — первый такой push) и когда её создают или удаляют;
- когда PR такой ветки открывают, закрывают, переводят в черновик или обратно,
  ставят или снимают метку;
- когда что-то вливают в `dev`;
- раз в час — на случай, если событие потерялось.

Пока workflow не попал в `main` (ветка по умолчанию), `create`, `delete`, час и
ручной запуск не работают — GitHub берёт для них файл из `main`. Захват и мердж
это не задевает: для `push` и `pull_request` берётся файл из самой ветки. Не
обновится только отдача задачи без PR (`pnpm task release`) — до следующего
`push` в `dev`.

Ветка `task-board` без общей истории: каждый пересчёт заменяет её одним
коммитом. Руками её не правят.

**Строка значков в файле задачи статична.** Её ставит `pnpm task fix`: значок
самой задачи и по значку на каждую зависимость, в порядке `depends_on`.
Меняется картинка, а не файл: коммиты в `dev` на каждый захват не нужны. Формат —
`badgeLine` в `scripts/tasks/task-file.mjs`; `pnpm task check` сверяет строку с
`depends_on`, называет ожидаемую и подсказывает `pnpm task fix`.

**В эпиках.** Ячейка «Задачи» в `epics.md` — те же живые значки, что под
заголовками задач: «готово», «можно брать», «ждёт…». Её тоже ставит
`pnpm task fix`, а `pnpm task check` сверяет с реестром: номера руками отстали
бы от доски в первый же день. Под таблицей — раздел «Потоки по эпикам»: по
строке на эпик, его тоже ставит `pnpm task fix` между метками, а в ячейке
таблицы широкий значок нечитаем. Значок — `status/epic-E10.json`: «сейчас: sonnet·high 2, haiku·low 1» (до трёх пар
«модель·уровень» и число свободных задач и доработки, остаток — `+N`; `local`
помечен) зелёным или «нет свободных · в очереди N» светло-серым. Он ведёт на
раздел «Потоки сейчас» доски. Эпик без задач в раздел не попадает.

**Доска.** Страница [`README.md` ветки `task-board`](https://github.com/JJSGxKD/rubezh/blob/task-board/README.md) — её пересчитывает
тот же `pnpm task status-json`, что и значки:
- колонки «Доработка», «Можно брать», «Можно заделом», «В работе», «На ревью», «Задел», «Ждут» и «Готово»;
- раздел «Потоки сейчас» в начале страницы — какие потоки запускать (то же, что
  печатает `pnpm task streams`, раздел «Автопоток»);
- значок `status/free.json` («можно брать · 3 задачи») — в начале этого файла и
  `epics.md`, он ведёт на страницу;
- раздел «Вклад»: сделанные задачи и очки по автору влитого PR задачи на
  GitHub, внутри аккаунта — по полю `owner` («аккаунт / модель / уровень»),
  так потоки под одним аккаунтом различаются. Очки — сумма размеров: `S` — 1, `M` — 2.
  Это наглядность, а не формула выплат: доли участников задаёт
  [`docs/11-revenue-split.md`](../docs/11-revenue-split.md). На странице — только
  логины GitHub, они и так видны у PR.

**Значок — сигнал для людей, а не защита.** shields.io и GitHub кэшируют
картинку, и она может отставать на 5–10 минут. Защищают захват три вещи:
- атомарный push ветки;
- проверки `pnpm task claim`: зависимости, зоны, исполнитель;
- проверки зон и захвата в CI PR: `diff-check` и `claim-check`.

Сомневаешься — верь `pnpm task board`, а не картинке.

## Как взять задачу

1. **Выбрать задачу.** Свободные — на [доске задач](https://github.com/JJSGxKD/rubezh/blob/task-board/README.md) или `pnpm task next`.
   Брать можно только ту, у которой значок «можно брать» (раздел «Значки
   статуса»), и только командой `pnpm task claim` — вручную ветку не заводят: PR,
   взятый в обход, не пройдёт `claim-check` в CI.

   ```bash
   pnpm task next --executor sonnet-5.5 --effort medium
   ```

   Команда читает реестр из `origin/dev` и ветки `task/*` на `origin`, поэтому
   показывает одно и то же на любой ветке. Сначала — PR на доработке твоей
   модели и уровня (их берут `pnpm task resume`, раздел «Доработка»), затем
   созревший задел (зависимости влиты, его доводит `pnpm task resume`, раздел
   «Задел»), потом свободные задачи и в самом конце — «можно заделом»
   (`pnpm task claim --ahead`). Первая свободная — лучшая:
   `status: ready`, все `depends_on` — `done`, зоны не пересекаются с задачами,
   где ещё пишут код (в работе, доработка), ближняя пачка (`batch`), в ней — старший `priority`, при
   равном — эпик раньше в `epics.md`. Весь реестр по колонкам — `pnpm task board`. `--runner local` —
   только если на машине можно запустить приложение (dev-сервер, браузер, Docker), `--runner owner` (показывает `any`, `local` и
   `owner`) — только поток на машине владельца; `runner: human` исполнитель-ИИ не
   берёт, команда его не показывает. Бери только задачу, где `executor` — твоя
   модель (раздел «Исполнители и effort»).

2. **Захватить.** Захват атомарный: ветку `task/T-NNNN` создаёт тот, чей push
   прошёл первым.

   ```bash
   pnpm task claim T-NNNN --owner "claude-3 / sonnet-5.5 / medium"
   ```

   Команда отказывает, если рабочая копия не чистая, задача не свободна или
   модель и уровень в `--owner` не совпадают с `executor` и `effort`. Иначе создаёт ветку от
   `origin/dev`, ставит `status: in-progress` и `owner`, коммитит и пушит без
   `--force`. Push отклонён — задачу уже взяли: команда сама убирает локальную
   ветку, выбери другую задачу. Зависимости ещё не влиты, но их PR на ревью —
   `pnpm task claim T-NNNN --ahead --owner "…"` (раздел «Задел»).

3. **Если команды нет** (старая ветка, нет Node), то же руками:

   ```bash
   git fetch origin --prune
   git ls-remote --heads origin "task/*"   # ветка есть — задача занята
   git switch -c task/T-NNNN origin/dev
   # в файле задачи: status: in-progress, owner: <аккаунт / модель / уровень>
   git commit -am "chore(tasks): Взять T-NNNN в работу"
   git push origin HEAD:refs/heads/task/T-NNNN
   ```

   Зависимости и зоны при этом сверяешь сам: `depends_on` — `done`, `zones` не
   пересекаются с задачами в работе (открой их спецификации). Коммит захвата
   обязан что-то менять: без него ветка совпала бы с `dev`, и второй push тоже
   «прошёл» бы. **Никогда не пушь в чужую `task/*` и не пушь с `--force`.**
   Единственное исключение — PR с меткой «доработка», взятый командой
   `pnpm task resume` (раздел «Доработка»): после неё ветка твоя.

4. **Прочитать спецификацию целиком** и всё, на что она ссылается. Если неясно —
   раздел «Если что-то неясно», не угадывать.

5. **Сначала тесты.** Тест-кейсы из раздела «Тесты» пишутся первым коммитом
   (`test(scope): …`). Они падают — так и должно быть. Тест — договор: менять его
   под код нельзя, только по ответу тимлидов.

6. **Код — по «Шагам по порядку».** Коммиты дробные, по правилам `CLAUDE.md`.

7. **Трогать только свои файлы:** `zones`, строки в `shared` и сам файл задачи
   (он остаётся в `tasks/`: `tasks/archive/`, `tasks/epics.md` и чужие файлы
   задач PR задачи не меняет — их правит уборка тимлида). Понадобился файл вне зон — это вопрос тимлидам, кроме вынужденных следствий (раздел «Что исполнитель решает сам»). «Заодно поправил рядом» —
   причина вернуть PR.

8. **Гейт** — пять команд из `CLAUDE.md` и `pnpm docs:check`. Для экранов ещё
   снимки на 320, 390, 768 и 1440 px и в ландшафте 667×375 и 640×360 против
   макета и блока «Интерфейс» из «Приёмки»: `pnpm screens` (нужен `pnpm dev`)
   снимает их сам; PNG посмотреть самому, в PR перечислить сценарии, размеры и
   замеченное. Без зелёного гейта задача не
   сделана.

   Облачному исполнителю без Postgres и Redis интеграционные тесты прогонит CI
   его PR: локально они пропускаются, но в PR обязаны быть зелёными.

9. **Закрыть задачу в том же PR:** в файле задачи поставить `status: done`. Файл
   остаётся в `tasks/`: в архив его вместе со ссылками перенесёт уборка тимлида
   (раздел «Уборка архива»), `pnpm task fix` для этого не нужен.

10. **Открыть PR в `dev`:**
    - заголовок — из раздела «PR» спецификации;
    - метка — из поля `release`;
    - описание — по скиллу `pre-pr`; раздел «Сводка для команды» — готовый блок
      из спецификации, с номером PR в заголовке;
    - первой строкой — `Задача: tasks/T-NNNN-<slug>.md` (файл задачи остаётся в `tasks/`), дальше чек-лист критериев приёмки с отметками;
    - предпоследней и последней строками перед подписью агента — `Поток: claude-3 / sonnet-5.5 / medium` и `Запустил: владелец` (или `Запустил: помощник <ник>`); без них `pr-check` красный;
    - **метка статуса «на ревью»** (раздел «Метки статуса»): `gh pr create --label "на ревью"`. Без метки статуса или с двумя `pr-check` красный, а задача висит «в работе» и держит зоны.

    **Не вливать самому:** вливают тимлиды — кроме задач с `merge: self` в
    `dev`: их поток вливает командой `pnpm task merge` после самопроверки
    (раздел «Самостоятельный мердж»). Ответа не ждать: PR открыт — сразу
    следующая задача (раздел «Автопоток»).

**Бросить задачу** (не успел, задача оказалась не той): удали ветку
`git push origin --delete task/T-NNNN` и закрой PR, если он был, с причиной в
комментарии. Задача снова свободна.

## Что исполнитель решает сам

Решение владельца Р176 (`docs/35-stage4-plan.md`). Спецификация не может
предусмотреть всё, и круг «вопрос — ответ» ради одной строки стоит дороже самой
строки. Поэтому четыре вида решений исполнитель принимает сам — и **каждое
записывает в описании PR, в разделе «Отступления»**, с причиной: ревьюер
проверяет и их.

1. **Технические детали внутри зон**, где спецификация молчит: имена,
   разбиение на файлы, внутренние типы, вспомогательные функции.
2. **Вынужденные следствия вне зон** — правка, без которой не сходится гейт
   или которой требует общий реестр: фикстура под новый тип, строка в реестре
   (`apps/admin/src/screens/sections.tsx`, `routes.ts`, `ui/help.ts` и другие
   из раздела «Общие файлы»), ожидание в соседнем тесте, ключ словаря. По
   смыслу — одна-две строки на файл, и только если:
   - файл не держит задача «в работе» или «доработка» — это говорит команда
     `pnpm task holds <путь>` (файл или каталог): она печатает такие задачи с
     номером PR, а пусто — «Файл не держит ни одна задача в работе»;
   - путь дописан в `shared` файла своей задачи — тогда `diff-check` зелёный;
   - правка не меняет поведение чужого кода.
   Больше этого — вопрос тимлидам.
3. **Текст игроку под правила.** Текст из спецификации нарушает правила
   текстов (на «ты», без рода, Р163; тесты `i18n-address`, `player-address`) —
   перепиши его с тем же смыслом.
4. **Следствия своей правки в эталонах и документах**: golden-эталоны баланса
   (с дельтой длины забега в описании), схемы `docs/21`, карта настроек
   `docs/30`, словарь событий `docs/22`, гайдбук — даже если файл не назван в
   спецификации (путь — в `shared`).

**Всегда вопрос, а не решение:** продукт, экономика, баланс, коридоры, цены,
награды и смысл текстов; новые события, настройки, ключи, переменные
окружения, зависимости и миграции, которых нет в спецификации; деньги, права,
безопасность и антифрод; ломающие изменения контракта API; ослабление теста;
правка чужой задачи.

## Самостоятельный мердж

Решение владельца Р176 (`docs/35-stage4-plan.md`). Очередь приёмки — узкое
место, и простые задачи (документы, данные контента, рефакторинг без смены
поведения) ждут той же проверки, что деньги и миграции. Поэтому задачу, которую
тимлид пометил `merge: self`, поток вливает сам — после самопроверки, зелёного
CI и команды, которая проверяет всё это за него. Остальные задачи вливает
тимлид, как раньше.

**Когда.** Только если в **`origin/dev`** (не в ветке PR!) в шапке задачи стоит
`merge: self`. Пометку ставит тимлид в спецификации (скилл `task-spec`); потоку
выдать её себе нельзя: поменял поток в своей ветке `zones`, `runner`, `effort`
или `merge` — команда отказывает.

**Белый список путей** (поправка `claude-lead-1` от 28.10.2026 к Р176). `self`
допустим, только если **каждый** путь в `zones` и `shared` задачи и **каждый
реально изменённый файл PR** лежит в белом списке и не лежит в чёрном:

| Белый список (`SELF_MERGE_ALLOWED`) | Чёрный, он сильнее (`SELF_MERGE_FORBIDDEN`) |
|---|---|
| `docs/**`, `design/**` | `docs/35-stage4-plan.md` |
| `packages/core-game/src/content/**`, `packages/core-game/src/game/**`, `packages/core-game/test/**` | любые `package.json` |
| `packages/app-shell/src/i18n/**` | `tsconfig*.json` |
| `apps/admin/src/**`, `apps/admin/test/**` | `vitest.config.*`, `eslint.config.*` |
| файл самой задачи `tasks/<её файл>` | |

Остальное закрыто тем, что его в списке нет: бэкенд, экраны игрока, `scripts/**`,
`.github/**`, `.claude/**`, `CLAUDE.md`, `AGENTS.md`, `tasks/README.md`,
`pnpm-*`, `infra/**`, адаптеры, `apps/web-*`. Шаблон в `shared`, шире белого
(`backend/**`, `packages/**`, `**` + `/*.ts`), — причина отказа. Не подходит и
задача с `effort: extra`, `runner: owner` или `human`. `pnpm task check` ловит
это по `zones` и `shared`, `pnpm task merge` — ещё и по настоящему диффу PR.
Это страховка, а не замена суждения тимлида: тимлид не ставит `self`, если
сомневается.

**Порядок потока** (шаги 1–10 «Цикла потока» не меняются):

1. Гейт, PR в `dev` с меткой «на ревью» и закрытая в PR задача
   (`status: done`) — как всегда.
2. Дождаться зелёных `check` и `gate` (красный `board` не помеха).
3. **Самопроверка по скиллу `review-pr`**: поток проверяет свой PR по чек-листу
   «Приёмки» ниже как чужой — построчно, с гейтом на чистой голове — и пишет
   комментарий в PR:

   ```
   **claude-3:** самопроверка по review-pr
   head: <полный SHA головы PR, 40 знаков>

   - [x] <пункт «Приёмки»>
   - [x] …
   ```

   Подпись — аккаунт из `owner` файла задачи, `head:` — голова PR сейчас
   (`git rev-parse HEAD` после пуша), отмечены **все** пункты «Приёмки» (их не
   меньше семи) и нет ни одной `- [ ]`. Пункт, который не выполнен, — не
   галочка, а доработка: поток правит PR и пишет самопроверку заново — после
   каждого нового коммита `head:` устаревает. Комментарий пишет тот же
   аккаунт GitHub, что открыл PR, и **после** последнего коммита: отредактированный
   старый комментарий с новым `head:` не принимается.
4. `pnpm task merge T-NNNN` — из рабочей копии, где `scripts/tasks` такие же,
   как в `origin/dev`. Команда сама сходит в `origin/dev` и в GitHub и
   вольёт PR **только если сходится всё**: пометка `merge: self` в `dev`;
   в ветке PR файл задачи — `status: done`, а `zones`, `runner`, `effort` и
   `merge` те же, что в `dev` (в `shared` допустимы дописанные вынужденные файлы,
   но внутри белого списка); **каждый изменённый файл PR** (по
   `git diff --numstat origin/dev...голова`) в белом списке и не в чёрном, а
   файлы вне `zones` и `shared` из `dev` (кроме файла самой задачи) — не больше
   5 изменённых строк в каждом и 20 всего, двоичный вне зон — отказ («правки
   вне зон больше предела — нужна приёмка тимлида»); ветка не отстала от `dev`
   (`origin/dev` — предок головы: иначе «влей свежий dev и дождись CI»);
   PR открыт, не черновик, метка статуса ровно «на ревью»;
   все проверки, кроме `board`, зелёные, а `check` и `gate` есть
   (в расчёт идёт последний прогон каждой проверки); GitHub отвечает
   `MERGEABLE`; самопроверка есть, на текущей голове, от автора PR, после
   коммита головы, подписана потоком задачи и
   отмечена целиком. Иначе — код 1 и список причин, ничего не влито. Вливает
   она merge-коммитом и `--match-head-commit`: пуш между проверкой и мерджем
   мердж отменяет. После — печатает раздел «Сводка для команды» из описания PR;
   поток отдаёт его в чат, как и тимлид.
5. Следующая задача — без ожидания.

Вручную `gh pr merge` потоку нельзя ни для задач с `merge: self`, ни для
остальных: обход команды — это обход проверок.

**Что делает тимлид.** Каждый заход выборочно читает PR, влитые самими потоками
(их отличает комментарий самопроверки), и при дефекте откатывает его revert-PR
или заводит задачу. Если самопроверки потока оказываются поверхностными, тимлид
перестаёт ставить `merge: self` таким задачам: пометка — его решение, а не право
потока.

## Если что-то неясно

Не додумывать. Если спецификация допускает два прочтения, конфликтует с кодом или
документом или требует файла вне зон сверх вынужденных следствий (раздел «Что
исполнитель решает сам»):

1. **Сначала перечитай спецификацию целиком**, от шапки до раздела «PR»:
   ответ часто стоит в другом шаге. Сверяй её саму, а не её пересказ в
   README.
2. Открой черновик PR (`--draft`) с разделом `## Вопросы` и меткой
   **«на ревью»** — это отправка тимлиду, без метки задача остаётся «в
   работе» и держит зоны (раздел «Метки статуса»). В каждом вопросе:
   - **цитата строки спецификации** с номером, на которую ты опираешься, и
     почему она допускает два прочтения;
   - варианты ответа;
   - что ты нашёл в коде (пути и строки).
3. Не делай то, что зависит от ответа, а **независимые шаги продолжай**:
   ожидание ответа не должно останавливать всю задачу. Сделал всё, что можно
   без ответа, — запушь и бери следующую задачу: ждать ответа в сессии не
   нужно.
4. Тимлиды ответят комментарием в PR или правкой спецификации в `dev` и
   переведут PR в «доработка» (снимут «на ревью»). Заканчивать будет тот поток, что первым
   возьмёт её, — не обязательно ты (раздел «Доработка»).

## Доработка

PR, который ждёт исполнителя, а не тимлида, помечается меткой
**«доработка»** вместо «на ревью» (раздел «Метки статуса»). Её ставит тот,
кто ответил:

- **тимлид** — ответил на `## Вопросы` комментарием или правкой
  спецификации в `dev`;
- **ревьюер или тимлид** — по приёмке нужны правки: замечания — ревью
  «Request changes» или комментарием со списком.

Заканчивает PR **любой поток** с теми же `executor` и `effort`, что у задачи:
на любом аккаунте Claude и под любым аккаунтом GitHub — у всех исполнителей
есть право push в ветки `task/*`. Тот, кто PR открыл, ничем не выделен.

1. `pnpm task next --executor <модель> --effort <уровень>` — доработка
   показывается первой.
2. Взять:

   ```bash
   pnpm task resume T-NNNN --owner "claude-1 / sonnet-5.5 / medium"
   ```

   Команда берёт ветку `task/T-NNNN` с origin, пишет в `owner` твой поток,
   коммитит и пушит без `--force`, потом меняет на PR метку «доработка» на
   «в работе»: зоны снова заняты, задача уходит из «Доработки». Push — замок:
   двое продолжили одновременно — коммит первого лёг, второй получил отказ и
   берёт другую задачу. Поменять метку не вышло — команда скажет, сделай
   руками (`gh pr edit <номер> --add-label "в работе" --remove-label
   доработка`), иначе задачу возьмёт ещё один поток.
3. Прочитай PR целиком: описание, `## Вопросы`, ответы, ревью и
   комментарии, затем спецификацию в `dev` — она могла измениться.
4. `dev` ушёл вперёд или в PR конфликт — влей его в ветку
   (`git merge origin/dev`), а не перебазируй: в ветке уже чужие коммиты, и
   переписывать их историю нельзя, `--force` под запретом. Конфликт в общем
   файле — по таблице «Общие файлы».
5. Сделай то, что ответили, по тем же правилам: тесты, зоны, гейт. Ответ
   спорит со спецификацией — снова `## Вопросы` в PR и метка «на ревью»
   (вместо «в работе»): дальше ответ дают тимлиды.
6. Готово — в описании PR замени строки `Поток:` и `Запустил:` своими. В PR
   комментарий «Доработано: …» с подписью потока, черновик переведи в
   «Ready for review» (`gh pr ready`). **Метка:** сними «в работе», поставь
   «на ревью» (`gh pr edit <номер> --remove-label "в работе" --add-label "на
   ревью"`) — иначе задача висит «в работе». Дальше — следующая задача.

## Задел

Задачу можно взять, только когда все её зависимости `done` в `dev`, то есть
влиты. Пока зависимость ждёт ревью, задачи за ней стоят, а потоки простаивают.
**Задел** (Р178, `docs/35-stage4-plan.md`) — начать следующую задачу поверх
веток зависимостей и довести, когда они влиты.

**Когда можно.** Задача `ready`, зоны свободны (Р171, как у обычного захвата), и
у каждой её незакрытой зависимости (`status` не `done`) открыт PR со статусом
«на ревью», «ждёт владельца» или «доработка», а сама зависимость **не задел**:
поверх задела брать нельзя, ступень одна. Такие задачи `pnpm task next` показывает
последними («Можно начать заделом»), на доске они в колонке «Можно заделом».

**Как взять.**

```bash
pnpm task claim T-NNNN --ahead --owner "claude-3 / sonnet-5.5 / medium"
```

Команда строит ветку `task/T-NNNN` от `origin/dev` и вливает в неё ветки
незакрытых зависимостей `origin/task/T-XXXX` по порядку `depends_on`
(`git merge --no-edit`), потом коммит-замок и push без `--force` — как у обычного
захвата. Ветки зависимостей конфликтуют друг с другом — захват отменён
(«возьми другую задачу»). Печатает команду для **черновика PR с меткой «задел»**:
`gh pr create --draft --label "задел" …`. Метка — статус задачи (раздел «Метки
статуса»), «на ревью» ставить нельзя.

**Что значит «задел».**

- PR задела — всегда черновик с меткой «задел»; **зон задача не держит**, как «на
  ревью»: кто вливается вторым, перебазируется (Р171).
- В диффе PR лежат и коммиты зависимостей. `diff-check` вычитает из диффа файлы,
  которые меняют PR незакрытых зависимостей (`git diff --name-only
  origin/dev...origin/task/T-XXXX`): зоны проверяет PR самой зависимости, а своё
  в диффе остаётся под проверкой зон.
- Брать заделом можно, пока PR зависимости «на ревью», «ждёт владельца» или
  «доработка»; вернули её в «в работе» после захвата — задел не краснеет
  (`claim-check` требует лишь, чтобы PR зависимости был открыт и сам не был
  заделом).
- Зависимость закрыли без мерджа (PR закрыт, задача `cancelled` или ветку отдали) —
  задел на доске в «Ждут» с причиной «зависимость T-XXXX закрыта без мерджа»;
  решает тимлид.
- Ревьюер задел не проверяет, пока он не созрел (скилл `review-pr`).

**Влить задел до его зависимостей нельзя.** `claim-check` в CI красный, если у PR
есть незакрытые зависимости, а он не черновик или без метки «задел»;
`pnpm task merge` отказывает, если хоть одна зависимость в `dev` не `done`, и
всегда — на метке «задел».

**Доводка.** Когда все зависимости задела влиты в `dev`, значок задачи
«задел готов · #N», а в `pnpm task next` он идёт сразу после доработки, раньше
свободных. Берёт его любой поток той же модели и уровня:

```bash
pnpm task resume T-NNNN --owner "claude-1 / sonnet-5.5 / medium"
```

Команда пишет `owner`, коммитит и пушит (замок, как при доработке), меняет метку
«задел» на «в работе» и вливает `origin/dev` в ветку (`git merge`, не rebase).
Конфликт — команда останавливается и печатает файлы, решает поток: поправить,
`git add`, `git commit`, `git push`. Не созревший задел `resume` не берёт.
Дальше — доделать, пройти гейт, снять черновик (`gh pr ready`) и заменить
«в работе» на «на ревью»: с этого момента PR — обычный, и его принимают как
обычный.

## Автопоток

Поток — сессия, которая работает без остановки: берёт задачу своей модели и
уровня, открывает PR и, не дожидаясь ответа, берёт следующую. На каждом
аккаунте Claude — по потоку на каждую пару «модель + уровень»:

| Сессия | Поток в `owner` |
|---|---|
| Sonnet — Low — Claude-N | `claude-N / sonnet-5.5 / low` |
| Sonnet — Medium — Claude-N | `claude-N / sonnet-5.5 / medium` |
| Sonnet — High — Claude-N | `claude-N / sonnet-5.5 / high` |
| Sonnet — Extra — Claude-N | `claude-N / sonnet-5.5 / extra` |
| Haiku — Low — Claude-N | `claude-N / haiku-5.5 / low` |
| Haiku — Medium — Claude-N | `claude-N / haiku-5.5 / medium` |
| Haiku — High — Claude-N | `claude-N / haiku-5.5 / high` |
| Haiku — Extra — Claude-N | `claude-N / haiku-5.5 / extra` |

`N` — номер аккаунта Claude: по нему видно, чьи лимиты кончились и чьи задачи
встали. Модель и уровень в настройках сессии ставит тот, кто её запускает, —
те же, что в имени.

**Какие потоки запускать.** Тому, кто запускает потоки, не нужно листать
доску: `pnpm task streams` (из `origin/dev`, как `pnpm task next`) печатает
«Запускать сейчас» — по каждой паре «модель + уровень» сколько задач свободно и
на доработке и первые пять номеров с пачкой — и «На очереди»: сколько ждут
зависимостей или занятых зон и какая пачка ближайшая. Созревший задел
считается свободной работой («Запускать сейчас»), «можно заделом» — очередью. Строки `local` и
`owner` — отдельно: такие задачи берут только потоки на машине с Docker
(`--runner local`) и на машине владельца (`--runner owner`). Пара без задач не печатается; запускать стоит потоки из
первой таблицы. `pnpm task streams --epic E10` — только один эпик. То же —
раздел «Потоки сейчас» в начале [доски](https://github.com/JJSGxKD/rubezh/blob/task-board/README.md#потоки-сейчас)
и раздел «Потоки по эпикам» в `epics.md`.

**У каждого потока — своя рабочая копия.** Потоки одного аккаунта на одной
машине в общем клоне переключали бы друг другу ветки посреди работы. Своя
копия — облачная сессия, сессия Claude Code с изоляцией в worktree или
`git worktree add ../rubezh-sonnet-medium origin/dev`.

**Цикл потока:**

0. **Свежий `dev` и нужный Node.** `git fetch origin`, затем `git switch --detach
   origin/dev` — реестр и задачи живут только в `dev`; копия, не обновлённая
   с прошлого дня, видит старый реестр и «задач нет». Node — ровно из `.nvmrc`
   (`node -v`; другой — `nvm install` и `nvm use` этой версии), потом
   `pnpm install`. Исполнитель и уровень пишутся строчными: `haiku-5.5`, `low`.
1. `pnpm task next --executor <модель> --effort <уровень>`: по порядку —
   доработка, созревший задел, свободные задачи, «можно заделом».
2. Есть доработка — `pnpm task resume` (раздел «Доработка»). Следом созревший
   задел — тоже `pnpm task resume` (раздел «Задел»). Нет — первая свободная
   задача, `pnpm task claim`; свободных нет, а в списке есть «можно заделом» —
   `pnpm task claim --ahead` (раздел «Задел»). Отказ «уже взяли» — следующая из
   списка.
3. Работа по разделу «Как взять задачу»: тесты первыми, зоны, гейт, PR.
   Неясно — `## Вопросы` в черновике PR, независимые шаги — до конца.
4. PR открыт или запушен черновик с вопросами — на PR метка «на ревью»
   (раздел «Метки статуса»; у задела — черновик с меткой «задел»), потом
   `git switch --detach origin/dev` и снова шаг 1. Ответа не ждать.
5. Задач нет — отчёт: какие PR открыты, какие ждут ответа, почему остальное
   недоступно (зависимости, зоны, другая модель или уровень). Сессию после
   этого человек перезапускает позже.

Готовый промт с номером своего аккаунта — `pnpm task streams --account claude-N`
или подраздел «Запуск по аккаунтам» на доске: там только потоки, которые на
этом аккаунте сейчас не работают и которым есть что делать. Строку «запустил:
владелец» помощник меняет на «запустил: помощник <ник>» сам.

**Промт потока** — подставить номер аккаунта, модель и уровень:

```
Ты — исполнитель проекта «Рубеж», поток claude-N / sonnet-5.5 / medium, запустил: владелец.
Сначала git fetch origin и git switch --detach origin/dev, Node — из .nvmrc,
pnpm install; так же — перед каждой новой задачей. Прочитай AGENTS.md и tasks/README.md, разделы «Автопоток» и «Доработка»,
и работай по скиллу take-task в режиме автопотока: бери задачи только
своей модели и уровня — pnpm task next --executor sonnet-5.5 --effort medium,
доработку первой (pnpm task resume), иначе pnpm task claim T-NNNN
--owner "claude-N / sonnet-5.5 / medium". Делай строго по спецификации,
только в ветке task/T-NNNN, в описании PR — строки Поток и Запустил, в dev и main не пушь, PR не вливай — вливают
тимлиды. Неясно — черновик PR с разделом «Вопросы» и цитатой строки
спецификации, независимые шаги продолжай. PR открыт — сразу следующая
задача, ответа не жди: закончит PR тот поток, что первым возьмёт его на
доработку. Задач не осталось — отчёт и стоп.
```

## Второй аккаунт на этой машине

Второй аккаунт Claude нужен, когда у основного кончился лимит. Он продолжает
по записанным решениям, берёт локальные задачи (`runner: local`) и приёмку.

**Где запускать.** Приложение Claude держит один аккаунт: входа во второй
рядом с первым в нём нет, а два экземпляра приложения документация Claude
Code не поддерживает. Поэтому второй аккаунт — одним из трёх способов:

| Способ | Что даёт | Ограничение |
|---|---|---|
| CLI `claude` в терминале — Windows Terminal или вкладка терминала в самом приложении Claude | всё, что умеет основной чат, на нашем Postgres и Redis | интерфейс терминала |
| Расширение Claude Code в VS Code, настройка расширения `environmentVariables` с `CLAUDE_CONFIG_DIR` | окно с чатом и диффами | путь — только абсолютный, `~` не раскрывается; удобно в отдельном профиле VS Code |
| claude.ai/code в другом профиле браузера | ничего ставить не нужно | облачная машина без нашего Postgres и Redis: только задачи `runner: any` |

Аккаунты разводит переменная `CLAUDE_CONFIG_DIR`: у каждой папки настроек —
свой вход, история сессий и память
([документация](https://code.claude.com/docs/en/authentication.md)).

**Настройка один раз** (PowerShell):

1. CLI — родным установщиком. `npm install -g` для CLI не нужен:
   ```powershell
   irm https://claude.ai/install.ps1 | iex
   ```
2. Команда `claude2` — в профиль PowerShell (`notepad $PROFILE`):
   ```powershell
   function claude2 {
     $old = $env:CLAUDE_CONFIG_DIR
     $env:CLAUDE_CONFIG_DIR = "$HOME\.claude-acc2"
     try { claude @args } finally { $env:CLAUDE_CONFIG_DIR = $old }
   }
   ```
3. **Общая память — до первого запуска.** Память Claude о проекте
   (`MEMORY.md`, решения и запреты, которых нет в репозитории) лежит в папке
   настроек. Чтобы второй аккаунт помнил то же, что основной, его папку
   памяти делают ссылкой на основную. Имя папки проекта — путь клона с
   дефисами: `F:\projects\rubezh` → `F--projects-rubezh`.
   ```powershell
   $project = "F--projects-rubezh"
   New-Item -ItemType Directory -Force "$HOME\.claude-acc2\projects\$project" | Out-Null
   New-Item -ItemType Junction -Path "$HOME\.claude-acc2\projects\$project\memory" -Target "$HOME\.claude\projects\$project\memory"
   ```
4. Пользовательские настройки (`settings.json`: режим разрешений, workflow) —
   копией, без файла входа:
   ```powershell
   Copy-Item "$HOME\.claude\settings.json" "$HOME\.claude-acc2\settings.json"
   ```
5. Вход: `claude2`, затем `/login` вторым аккаунтом.

**Своя рабочая копия.** Второй аккаунт не работает в основном клоне: сессии
переключали бы друг другу ветки. Рабочая копия:
`git worktree add --detach ..\rubezh-acc2 origin/dev`, в ней `pnpm install`.
Запуск — `cd ..\rubezh-acc2; claude2`. Файл `.env` — по разделу «Окружение
исполнителя».

**Тимлид на втором аккаунте** — кодовое имя `claude-lead-2`, первой строкой
промта: «Ты — claude-lead-2, тимлид проекта «Рубеж»…». Вливает PR в каждый
момент один тимлид. Пока основной аккаунт в лимите, вливает
`claude-lead-2`; вернувшись, основной сначала читает
`git log --first-parent origin/dev` и комментарии тимлидов в открытых PR.
Переписки сессий не видно друг другу: всё, что должен знать другой тимлид,
пишется в задачу, PR, `tasks/inbox.md` или память.

**Потоки на втором аккаунте** — номер аккаунта `2` в имени потока:
`claude-2 / sonnet-5.5 / medium`. Промт — «Промт потока» из раздела
«Автопоток»; для локальных задач — `pnpm task next --runner local …`. У
каждого потока — своя рабочая копия (`git worktree add --detach ..\rubezh-acc2-sonnet-medium origin/dev`).
Чтобы интеграционные тесты потоков не мешали друг другу:
- база — своя схема в `TEST_DATABASE_URL` (`?schema=t<номер задачи>`,
  `docs/17-testing-strategy.md` §4.2);
- Redis — своя база: у потоков второго аккаунта
  `PLAYTEST_TEST_REDIS_URL=redis://localhost:6379/12`. База 13 — у потоков
  основного, 14 — у dev-API.

**Чего второй аккаунт не делает без отдельного разрешения пользователя в его
собственном чате** — того же, что основной: выкат в `main`, прод, секреты,
настройки репозитория. Разрешение, данное в чате одного аккаунта, на другой
не переходит.

## Приёмка (ревьюер и тимлиды)

Проверяет ревьюер или тимлид, вливает тимлид или тимлид второго уровня —
сессией, которая сама PR не писала; задачу с `merge: self` вливает сам поток
по разделу «Самостоятельный мердж», а чек-лист ниже он проходит как
самопроверка. Исход ревью — один из двух:

- **принято** — ревью «Approve» с отмеченным чек-листом ниже; дальше мердж;
- **нужны правки** — «Request changes» со списком замечаний; PR переходит в
  «доработка» с снятием «на ревью» (раздел «Метки статуса»; бот делает это на
  «Request changes» сам, но проверь).

Ревью и комментарии начинаются с кодового имени: `**claude-review-2:** …`.

PR принимается, если выполнено всё:

- [ ] тесты из спецификации есть и зелёные, CI зелёный;
- [ ] дифф только в `zones`, своих строках `shared` и файле задачи — зоны проверяет CI (`pnpm task diff-check`, шаг в `pr-checks.yml`), красный шаг значит возврат PR;
- [ ] задача взята по порядку — `claim-check` в CI зелёный (`pnpm task claim-check`: на базе `ready`, зависимости сделаны, зоны не заняты чужой задачей), красный шаг значит возврат PR;
- [ ] ничего лишнего: попутных рефакторингов, переименований, «улучшений» нет;
- [ ] все критерии приёмки выполнены и отмечены в описании;
- [ ] документы, названные в спецификации, обновлены;
- [ ] коммиты дробные, по правилам `CLAUDE.md`, заголовок и метка — из спецификации.

**Интерфейс** — если PR меняет то, что видит игрок или команда в панели
(решение владельца от 24.10.2026). Тимлид смотрит экран сам и отвечает не
только за букву спецификации: недостающее состояние, кривой перенос или
невнятную подпись он додумывает, а не пропускает.

- [ ] **ширины и ландшафт:** 320, 390, 768 и 1440 px и ландшафт 667×375 и
  640×360 — ничего не вылезает и не обрезается, не уходит под вырез камеры
  и кнопки Telegram (`--app-inset-*`), горизонтальной прокрутки нет;
- [ ] **тексты и числа:** переносы и обрезание, длинные имена и большие
  числа (`1 234 567`), падежи и множественное число, нигде не торчит ключ
  i18n вместо текста;
- [ ] **состояния и контраст:** есть «пусто», «загрузка», «ошибка»,
  «нажато», «недоступно»; контраст текста не ниже 4,5:1, зона нажатия не
  меньше 44 px;
- [ ] **подача:** с первого взгляда понятно, зачем экран и что нажать;
  награда и цена видны сразу, главная кнопка одна, текст цепляет, а не
  звучит канцеляритом.

Снимки до T-0145 тимлид делает сам — Playwright в облаке, после неё
`pnpm screens`. Владельцу их показывают приватной страницей-галереей
(артефакт claude.ai, сетка «размер × экран») со ссылкой в чате; в git снимки
не кладутся.

**Мелочь правит тимлид сам.** Мелкий дефект в зонах задачи — обрезанный
текст, перенос, отступ, подпись, примерно до 20 строк — тимлид исправляет
коммитом в ветку PR, подписывает в комментарии кодовым именем и вливает: так
быстрее, чем круг через поток. Всё, что крупнее, — «Request changes» и метка
«доработка» со снимком и описанием, что не так.

**Нужен владелец.** Если PR нужно решение или действие владельца (секрет,
прод, проверка на телефоне, вопрос продукта), тимлид ставит метку «ждёт
владельца» вместо «на ревью»; PR попадает в раздел «Ждут владельца» на доске. После ответа владельца тимлид переводит PR в «на
ревью» или «доработка». Метку на GitHub заводят руками при первой
надобности, скрипт её не создаёт.

Вливается merge-коммитом, строго по одному. Отстал от `dev` или конфликт —
метка «доработка» с комментарием «влить dev»: в ветке исполнителя `dev`
вливают, а не перебазируют. Конфликт в общих файлах или с соседней задачей,
взятой параллельно, тимлид при вливании решает сам — сохраняя обе стороны.

**Пересечение с PR на ревью не держит захват** (Р171, `docs/35-stage4-plan.md`).
Зоны держат только задачи, где ещё пишут код: ветка без PR, PR с меткой «в
работе», доработка (Р172: решает метка, а не черновик — черновик с меткой «на
ревью» зоны не держит). Пока PR ждёт ревью, соседнюю задачу с теми же файлами можно брать;
кто вливается вторым, вливает `dev` в свою ветку. Из двух задач в работе
держит та, что взята раньше (`claim-check` сверяет время коммита захвата).
Смысловая зависимость — по-прежнему `depends_on`.

**Ревью — пакетом каждый заход тимлида** (Р171). Все PR из колонки «На ревью»
проверяют разом агенты Sonnet по скиллу `review-pr` (деньги и движок — с
усилием high). Мелочь до ~20 строк тимлид правит сам коммитом в ветку и
вливает; остальное — «доработка» с точным списком замечаний.

## Уборка архива

Закрытая задача (`done`, `cancelled`) остаётся в `tasks/`, пока её не перенесёт
уборка. Раньше файл переезжал в `tasks/archive/` в самом PR задачи, а с ним
менялись ячейка эпика в `epics.md`, строки значков зависимых задач и ссылки в
текстах других спецификаций: любые два PR задач одного эпика конфликтовали, а
закрытие задачи с зависимыми выходило за её зоны. Теперь PR задачи меняет из
`tasks/` только шапку своего файла, и PR задач друг с другом не конфликтуют.

- `pnpm task check` пишет «ждут уборки N»; закрытая задача наверху не ошибка.
  Открытая задача в архиве — ошибка, её вернёт наверх `pnpm task archive`.
- **Когда:** не реже раза в пачку, перед релизным PR (`docs/38-release-plan.md`
  §2, шаг 1), и когда закрытых наверху набралось много.
- **Порядок** (тимлид):
  1. ветка от свежего `dev`, не `task/*`;
  2. `pnpm task archive`, затем `pnpm task check`;
  3. PR `chore(tasks): Перенести закрытые задачи в архив` с меткой
     `release: none`, мердж после зелёного CI.
- В PR спецификации `pnpm task archive` не запускают: два PR, перенёсшие разные
  наборы задач, спорили бы за те же строки `epics.md`.
- PR спецификаций, задевшие те же строки `epics.md`, после уборки вливают `dev`:
  `git checkout --theirs tasks/epics.md`, затем `pnpm task fix`. PR задач
  уборка не задевает.
- `pnpm task fix` ставит строки значков, ссылки и ячейки эпиков по тому, где
  файлы лежат сейчас, и ничего не переносит.

## Общие файлы

Эти файлы правят почти все задачи, и конфликты в них ожидаемы. В шапке задачи они
идут в `shared`, а не в `zones`: файлы из `zones` блокируют захват соседних задач,
из `shared` — нет. Правило одно:
**правка — добавление в свой участок, конфликт решается сохранением обеих
сторон**, чужие строки не переписываются.

| Файл | Как добавлять |
|---|---|
| `backend/api/prisma/schema.prisma` | свои модели — блоком в конце файла с комментарием-заголовком; связь в `model Account` — одной строкой |
| `backend/api/prisma/migrations/` | миграция собирается **после** влития свежего `dev`, один раз и **без базы** (Р177): `git show origin/dev:backend/api/prisma/schema.prisma > <временная папка>/before.prisma`, затем из `backend/api` — `pnpm exec prisma migrate diff --from-schema <временная папка>/before.prisma --to-schema prisma/schema.prisma --script > prisma/migrations/<ГГГГММДДччммсс по UTC>_<имя>/migration.sql`. ## Окружение исполнителя

- **Ключи.** Корневой `.env` с настоящими ключами исполнителю не нужен и не
  копируется. Запуску API хватает `.env.example` с тестовыми базами.
- **Бот.** Бота с боевым токеном исполнитель не запускает:
  `TELEGRAM_BOT_UPDATES=off`.
- **Опасные команды запрещены.** Нельзя `prisma migrate reset`, `docker compose
  down -v`, удалять чужие ветки, пушить в `dev` и `main`, вливать PR, менять
  настройки репозитория, секреты и переменные Actions.
- **Прод.** Сервер исполнителю недоступен и не нужен. Выкат — только релизом
  тимлидов.
- **Версия Node** — из `.nvmrc`. Если в окружении другая и `pnpm build` или
  `pnpm budget` не запускаются (`engine-strict`), проверку не обходить: отметь в
  PR, какие команды не прошли и почему. Их подтвердит CI PR.
