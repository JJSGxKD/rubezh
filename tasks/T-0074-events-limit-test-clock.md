# T-0074. Тест лимита приёмника событий не зависит от границы минуты

[![статус](https://img.shields.io/endpoint?url=https://raw.githubusercontent.com/JJSGxKD/rubezh/task-board/status/T-0074.json)](README.md#значки-статуса)

## Зачем

Кейс «считает лимит установки в событиях» в `backend/api/test/events.test.ts`
иногда падает: ответ 202 вместо 429 (CI PR #267, 12.10). Красный CI без причины
в коде приучает не верить тестам и задерживает мердж. После задачи кейс идёт
всегда одинаково, а причина сбоя закреплена вторым кейсом.

## Решения

- **Поведение прода не меняется.** Лимитёр (`rate-limiter.ts`) и приёмник событий
  не трогаем: окно лимита — календарная минута, это задумано
  (`docs/28-diagnostics.md` §5.3).
- **Часы подаём подменой `Date` в самом тесте**, а не новым параметром в
  лимитёр. Метод `consume(rule, key, cost, nowMs = Date.now())` уже принимает
  время, но зовут его гард приёмника и сервис событий без четвёртого
  аргумента; тянуть часы через них — правка прод-кода ради теста. Приём
  `vi.useFakeTimers({ toFake: ["Date"] })` уже стоит в
  `backend/api/test/media.test.ts:333` по той же причине (окно лимита — минута).
  Таймеры остаются настоящими, чтобы Fastify отвечал как обычно.

## Как сейчас

- `backend/api/src/modules/ingest/rate-limiter.ts:48-50`:
  - `consume` берёт время `nowMs = Date.now()`;
  - ключ счётчика включает номер окна:
    `windowIndex = Math.floor(nowMs / 1000 / rule.windowSec)`.

  Redis в тесте нет (`unavailableRedis`, `events.test.ts:38`), лимитёр уходит в
  память (`consumeInMemory`, строка 60) с тем же ключом. Минута сменилась
  посреди серии — ключ другой, счёт начался заново.
- `backend/api/src/modules/ingest/ingest-limits.ts:29-31` — события: на IP,
  установку и Telegram ID по `limit: 600` за `windowSec: 60`.
- `backend/api/src/modules/events/events.service.ts:88` — лимит установки
  списывает по числу событий в пачке; `ingest.guard.ts:66` — лимит IP по
  запросу. Оба зовут `consume` без времени.
- `backend/api/test/events.test.ts:147-154` — кейс:

  ```ts
  it("считает лимит установки в событиях: пачки по сто быстро упираются в него", async () => {
    const target = await start();
    const batch = (): unknown => ({ events: Array.from({ length: 100 }, () => event()) });
    const statuses: number[] = [];
    for (let i = 0; i < 7; i++) statuses.push((await post(target, batch())).statusCode);
    expect(statuses.slice(0, 6)).toEqual([202, 202, 202, 202, 202, 202]);
    expect(statuses[6]).toBe(429);
  });
  ```

  Шесть пачек по 100 — ровно 600; седьмая обязана получить 429. Если между
  первой и седьмой пачкой пришла граница минуты, седьмая — снова первая в
  окне, и ответ 202 (строка 153).
- `backend/api/test/events.test.ts:3` — импорт `afterEach, describe, expect, it`
  из `vitest`, без `vi`. `afterEach` (строка 89) закрывает приложение.

## Шаги по порядку

1. **Файл `backend/api/test/events.test.ts`, импорт:** добавить `vi` в
   `import { afterEach, describe, expect, it } from "vitest";`.
2. **`afterEach` (строка 89):** первой строкой внутри вернуть настоящие часы —
   `vi.useRealTimers();` — и только потом `await app?.close();`.
3. **Общая пачка.** Перед первым `it` внутри `describe("приёмник событий")`
   вынести помощник (он нужен двум кейсам):

   ```ts
   /** Пачка из ста событий — столько стоит в лимите установки. */
   const hundredEvents = (): unknown => ({ events: Array.from({ length: 100 }, () => event()) });
   ```
4. **Кейс из строки 147 — часы закреплены.** Заголовок и ожидания не меняются.
   Первой строкой в теле, до `await start()`:

   ```ts
   // Окно лимита — календарная минута: серия запросов на её границе начала бы
   // счёт заново. Часы стоят в середине минуты, таймеры — настоящие.
   vi.useFakeTimers({ toFake: ["Date"] });
   vi.setSystemTime(Date.UTC(2026, 9, 13, 10, 0, 30));
   ```

   Локальный `const batch = …` заменить на `hundredEvents`.
5. **Новый кейс сразу после него — причина сбоя.** Заголовок дословно:
   «на границе минуты счёт лимита начинается заново — поэтому кейс выше закрепляет часы».

   ```ts
   vi.useFakeTimers({ toFake: ["Date"] });
   vi.setSystemTime(Date.UTC(2026, 9, 13, 10, 0, 59));
   const target = await start();
   for (let i = 0; i < 6; i++) expect((await post(target, hundredEvents())).statusCode).toBe(202);
   expect((await post(target, hundredEvents())).statusCode).toBe(429);
   // Наступила следующая минута — окно другое, счёт с нуля.
   vi.setSystemTime(Date.UTC(2026, 9, 13, 10, 1, 0));
   expect((await post(target, hundredEvents())).statusCode).toBe(202);
   ```
6. Прогнать файл несколько раз подряд:
   `pnpm vitest run backend/api/test/events.test.ts` — зелёный каждый раз.
   Дальше — гейт.

## Чего не трогаем

- `rate-limiter.ts`, `ingest.guard.ts`, `events.service.ts`, `ingest-limits.ts` —
  прод-код и числа лимитов.
- Остальные кейсы файла: им часы не нужны, подмена `Date` — только в двух
  кейсах выше (иначе «берёт Telegram ID только из проверенной подписи» получит
  подпись запуска с чужой датой).
- Другие тесты с лимитом на границе минуты (`readiness.test.ts`,
  `promo-codes.test.ts`, `ads.test.ts`): если они тоже мигают, это отдельная
  задача. Нашёл признак — напиши строкой в описании PR, файлы не правь.

## Тесты

Задача целиком состоит из правки теста, поэтому «тесты до кода» здесь —
единственный коммит `test(api): …` с обоими кейсами.

- `backend/api/test/events.test.ts`:
  - «считает лимит установки в событиях…» — шесть пачек по 100 событий → 202
    каждая, седьмая → 429, при закреплённых часах на 10:00:30 UTC;
  - «на границе минуты счёт лимита начинается заново…» — шесть пачек → 202,
    седьмая → 429 в 10:00:59 UTC, после перевода часов на 10:01:00 UTC
    следующая пачка → 202.
