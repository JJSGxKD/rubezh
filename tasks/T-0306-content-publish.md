# T-0306. Публикация контента — версия сначала команде, потом всем, только после зелёной проверки; откат кнопкой; версия для клиента по его схеме

[![статус](https://img.shields.io/endpoint?url=https://raw.githubusercontent.com/JJSGxKD/rubezh/task-board/status/T-0306.json)](README.md#значки-статуса) [![T-0305](https://img.shields.io/endpoint?url=https://raw.githubusercontent.com/JJSGxKD/rubezh/task-board/status/T-0305.json&label=T-0305)](T-0305-balance-editor-check.md)

## Зачем

Шаг 2 редактора баланса (решение 25.10.2026). Песочница (T-0303–T-0305) даёт
черновик с проверкой. После задачи черновик становится версией игры:
1. сначала её получают только аккаунты команды — посмотреть глазами;
2. потом все.

Публикация возможна, только если проверка зелёная и свежая. Откат —
кнопкой, за секунды. Клиент получает последнюю версию, которую понимает.
Загрузку версии клиентом делает T-0307.

## Решения

Решения владельца — `docs/35-stage4-plan.md`:
- Р16 — опубликованный снимок хранится в базе по хэшу;
- 25.10.2026 — фаза 1 `docs/19`, шаг 2 — публикация.

Правила — `docs/19` §4–§5.

Решения `claude-lead-1` от 25.10.2026:

- **Staging — это «команде».** `docs/19` §4.4 просит посмотреть версию в
  настоящем клиенте до игроков. Отдельная база staging этого не даёт:
  черновик живёт в базе прода. Поэтому:
  - **«Команде»** — версия становится текущей для аккаунтов с ролью
    (`account_role`);
  - **«Всем»** — для всех.

  Это первая ступень постепенного выката. Доли 10 % → 50 % — фаза 2 `docs/19`.
- **Указатель** `content_current (audience: "team" | "all", version_no,
  set_by, set_at)`. Публикация «Всем» ставит оба указателя.
- **Условия публикации** — право `content.publish` и:
  - последний отчёт проверки по **тому же** `snapshot_hash` — `done`;
  - нет проблем схемы и контента;
  - все метрики сценариев в коридорах.

  Иначе 409 `content_check_required` с причиной. Обойти можно только ключом
  панели `content.publish-require-check` = `false` (владелец, в аудите;
  умолчание — `true`).
- **Публикация:**
  - снимок черновика → новая `content_version` (`source: panel`,
    `published_at`) → указатель;
  - лок Redis на публикацию;
  - идемпотентность по `draft_id`.
- **Откат** — «Откатить на v{N}»: указатель на прошлую опубликованную версию
  той же аудитории. Новой версии не создаёт; в аудите.
- **Версия для клиента** — `GET /api/v1/content/current?schema=<n>&team=<0|1>`:
  - отдаёт `{ versionNo, hash, url }` последней версии, совместимой со схемой
    клиента (`schema_version ≤ n`);
  - аудиторию «команда» сервер берёт из сессии, а не из параметра:
    параметра `team` нет.
- **Снимок по адресу** — `GET /api/v1/content/v/<hash>.json`:
  - вечный кеш (адрес по хэшу);
  - сжатие;
  - CDN — как у остальной статики API.
- **Новые версии из репозитория при выкате** — шаг деплоя
  `content:import` (T-0303) в `deploy.yml` после миграций.
  - Версия `repo` становится текущей, только если текущая тоже `repo` (до
    первой публикации из панели).
  - Иначе ставится рядом и показывается в «Истории» с меткой «из кода —
    новое понятие». Её поля сливает в черновик кнопка «Взять из кода»:
    новые id и поля добавляются, значения существующих не меняются.
- **Панель:**
  - кнопки «Команде» и «Всем» с рельсами T-0305;
  - «История и откат» — список версий с автором, датой, аудиторией и
    «Откатить»;
  - подтверждение «Всем» — диалогом со списком правок.

## Тесты

Первым коммитом.

- `content-publish.integration.test.ts`:
  - публикация без свежей проверки → 409 с причиной;
  - проверка по другому хэшу → 409;
  - «Команде» — версия у аккаунта с ролью, у игрока — прежняя;
  - «Всем» — у всех;
  - откат возвращает прошлую, новой версии нет;
  - две публикации разом — одна версия;
  - клиент со схемой 1 при версии со схемой 2 получает последнюю со схемой 1;
  - снимок по хэшу — вечный кеш;
  - импорт из кода при текущей `panel` — версия рядом, указатель не тронут.
- `balance-publish.test.ts` — кнопки живут только при зелёных рельсах.
